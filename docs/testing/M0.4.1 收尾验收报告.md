## 2. 端到端验收场景

验收测试在真实 LangGraph 编排下构建最小可执行回路：

```text
parse_script
  -> continuity_check（发现 style_inconsistent，来源阶段 convert_prompt）
  -> convert_prompt（消费修复参数并重新生成）
  -> continuity_check（复查通过）
  -> generate_output（生成报告快照并清理当前问题）
```

断言结果：

- 修复阶段被实际触发 1 次，说明修复参数驱动了来源阶段重跑。
- 轮次记录为 `needs_repair -> passed`，共 2 轮。
- 报告 `final_status = passed_after_repair`。
- 修复前后对比：初始 1 个问题，最终 0 个，解决 1 个。
- `repair_history.json` 记录 `convert_prompt` 修复动作及建议。

## 3. 报告落盘产物

端到端场景实际生成以下文件：

| 文件 | 验收要点 |
|---|---|
| `continuity_report.json` | 轮次、修复动作、修复前后对比、最终状态、契约违规 |
| `repair_history.json` | 按阶段聚合修复动作、轮次与最新修复参数 |
| `execution_summary.json` | 任务执行摘要 |
| `stage_statistics.json` | 阶段统计 |
| `issues_report.json` | 各阶段问题汇总（当前展示最终状态） |
| `quality_report.json` | 质量审查报告（本场景无审查数据） |
| `memory_report.json` | 记忆统计 |

`continuity_report.json` 关键字段：

- `rounds`：每轮问题、严重程度、来源阶段、修复阶段与建议。
- `comparison`：`initial_issue_count` / `final_issue_count` / `resolved_issue_count` / 趋势。
- `detected_issue_count`、`detected_issues_by_type`：累计检测问题（含已修复项）。
- `remaining_issues_by_type`：最终残留问题。
- `final_status`：`passed` / `passed_after_repair` / `needs_human_review` 等。

## 4. 验收期间修复的问题

1. **报告异步落盘无法等待**
   - 现象：`WorkflowOutputWriter.save_all_reports` 仅提交后台任务，调用方无法确认报告是否写完，验收测试存在竞态。
   - 修复：返回后台保存任务的 `Future`，调用方可按需等待落盘完成；生产流程行为不变。

2. **报告缺少“累计检测问题”视角**
   - 现象：修复通过后顶层 `issues_by_type` 为空，只能从 `comparison` 推断历史问题。
   - 修复：新增 `detected_issue_count`、`detected_issues_by_type`、`detected_issues_by_severity`，并保留 `remaining_issues_by_type/severity`，兼顾历史回溯与最终状态。
