PenShot（story-shot-agent）是基于 LangGraph 的剧本分镜工作流：接入层接收剧本，任务层排队调度，八个业务节点顺序生成分镜提示词、资产计划与模型路由结果，四个控制节点负责循环计数、错误回退、人工干预与结果收口。当前版本 v0.4.4。

分层架构

系统按接入、任务、工作流、智能体、记忆五层划分，各层可独立降级；输出端由 WorkflowOutputFixer 修复片段序列后以 JSON 返回。

技术栈

组件 实现
智能体框架 LangGraph StateGraph + 条件边、LangChain
LLM OpenAI、Ollama、通义千问、DeepSeek，按 base_url 路由；默认 gpt-4o，timeout=300
任务队列 AsyncTaskProcessor 进程内优先级队列

检查点 LangGraph SqliteSaver（data/checkpoints/），降级内存

资产与路由 Pydantic 契约模型 + 静态能力注册表 + settings.yaml 路由规则

各层独立降级：Redis 不可用时任务记录落进程内存，SQLite 不可写时检查点转内存模式，LLM 不可用时智能体退回规则引擎。单点故障不会直接中断工作流，但降级后的任务记录与检查点无法跨进程恢复。

video_model（runway_gen2 / sora / veo / pika 等）只影响提示词风格适配。PenShot 不调用视频模型，也不包含 FFmpeg 合成环节；v0.4.3 起可选的图生视频路由只生成首帧指令与适配包，不执行真实视频生成。

调用方可选四种入口，但四者最终都收敛到 TaskFactory：Python API 适合脚本内嵌，REST API 适合服务化，MCP Server 面向智能体工具调用，CLI 用于本地调试。入口层不保存状态，任务进度统一由任务层回写。

LangGraph 共注册 12 个节点：上述八个业务节点加四个控制节点；END 是终止标记，不计入注册节点。拆分、分段、转换、路由成功后先经过 LOOP_CHECK；它承担全局计数与阶段推进，节点级上限由各阶段决策函数维护。质量审计与连续性守护不经过 LOOP_CHECK。详细规则见工作流节点。

阶段 主产物 关键内容

GENERATE_ASSETS asset_plan / asset_manifest 资产规格、使用范围、回填绑定
SEGMENT_SHOT ShotSequence 镜头起止时间、景别、时长、主角色

节点间共享一个 PipelineState 状态对象：task_id、script_id 标识任务，domain 存放各阶段产物（parsed_script、asset_plan、asset_manifest、shot_sequence、fragment_sequence、instructions、audit_report、continuity_issues、repair_params），execution 存放循环计数器与阶段状态。条件边读取 execution、domain 与顶层字段，路由函数显式处理各层字段。

路由产物怎么消费见模型路由；资产计划与下游回填见资产计划与交接；首帧与图生视频的两段式规则见首帧与图生视频。

状态 含义 后续动作
SUCCESS 完全成功 进入下一节点
VALID 有轻微问题 放行
NEEDS_RETRY 需要重试 重跑当前节点
NEEDS_REPAIR 需要修复 带修复参数重跑
NEEDS_HUMAN 需要人工干预 转人工节点
NEEDS_ASSET_EDIT 需要人工编辑资产提示词 回到资产计划节点
FAILED 一般失败 转错误处理
ABORT 中止流程 结束

SUCCESS 与 VALID 都表示放行，区别在语义：SUCCESS 视为完全合格，VALID 表示存在可接受的轻微问题，带病继续但不携带修复参数。只有 NEEDS_REPAIR 才会把修复参数交给下一轮生成；NEEDS_RETRY 只重置当前节点，不修改输入。NEEDS_ASSET_EDIT 由人工干预触发，只允许修改资产提示词，不改变角色身份等锁定字段。

质量审查失败不重跑审查，而是回 CONVERT_PROMPT 重新生成。连续性检查则按问题来源动态路由：角色或场景问题回到解析或拆分，片段时长问题回到分段，提示词问题回到转换；无法定位来源或修复轮次耗尽时才转人工。修复目标写在 domain.repair_params，由对应节点读取。

GENERATE_OUTPUT 汇总各阶段产物后，由 WorkflowOutputFixer 对片段序列做结构修复，再序列化为 JSON 返回调用方。该层只做结构修复，不重新调用模型。

三级循环防护

三个独立计数器分别约束节点自旋、阶段重试与全局预算，任一触顶即熔断。

节点级 node_current_loops node_max_loops（2~5） 各阶段决策函数每次进入当前节点 拆分 / 分段 / 路由转人工，其余 FAILED
阶段级 stage_current_retries stage_max_retries（2~3） 质量不达标、需带修复参数重来 转人工或修复
全局级 global_current_loops max_total_loops × 2（默认 40） 每次经过 LOOP_CHECK 直接 FAILED

node_max_loops 防止节点在图内打转；stage_max_retries 只在该阶段质量不达标、需要携带修复参数重来时才递增。另有 max_continuity_retries=3 控制连续性修复循环。全局计数达到上限 80% 时输出 Warning 日志；触顶后不再重试。

任务队列与持久化

任务按 CRITICAL > HIGH > NORMAL > LOW 入队，AsyncTaskProcessor 按优先级拉取，并受并发信号量约束。默认 max_concurrent=10、queue_size=1000；队列为普通 list，入队时有序插入，cancel_task 按 task_id 遍历删除。

任务记录以 task_id 为主键，保存状态、当前阶段、进度、结果元信息与时间戳。状态从 PENDING 进入 PROCESSING，执行结束后写入结果；recover_task(task_id) 可将单个任务软重置为 PENDING、阶段置为 recovered、进度归零，用于人工重新投递。

get_queue_status() 返回 queue_length、queue_waiting、active_tasks、max_concurrent、queue_max_size、queue_usage_percent 六个字段。

存储 实现 内容 降级
任务记录 TaskRepository：penshot:tasks:data:{task_id} + 索引集合 penshot:tasks:ids，TTL 86400 秒 状态、阶段、进度、结果元信息 Redis 不可用→进程内存
工作流检查点 WorkflowCheckpointer：data/checkpoints/{script_id}/task_{task_id}.db 图执行位置与各阶段中间状态 目录不可写或依赖缺失→内存模式

任务记录与工作流检查点相互独立：前者服务任务查询与恢复筛选，后者保存图执行位置与中间状态，二者不共享存储。

启动时 recover_pending_tasks(max_age_hours=2) 筛选 PENDING / PROCESSING 且 2 小时内的任务，重建为 NORMAL 优先级并追加到队尾。恢复按任务起点重跑，不接检查点续跑；超窗任务不标记、不删除，等待 TTL 过期。检查点细节见检查点与恢复。

质量修复闭环

质量保障采用“轻前置检测 + 重最终检测”：节点内处理格式、时长、空值等本地问题，AUDIT_QUALITY 集中做规则与 LLM 深度审查，并将问题转换为修复参数。

前置检测与最终审查分工明确：节点内检测只处理本节点能修复的格式、时长与空值问题，避免明显不合格的产物进入下游；AUDIT_QUALITY 读取完整提示词包与路由结果，规则检查与 LLM 深度审查合并后形成报告。修复成本高于一次生成，因此只有达到修复档位才回炉，轻微问题直接放行。

检测 时机 内容 修复
节点内基础检测 每个业务节点执行期间 格式、时长、空值 节点产出问题列表
统一深度检测 ROUTE_MODEL 之后 11 项规则 + LLM 连贯性/一致性/语义审查 生成修复参数，回 CONVERT_PROMPT
跨片段一致性 CONTINUITY_CHECK 角色、道具、场景、动作、风格、时间 按来源阶段与严重度处理

11 项规则检查覆盖：片段时长、提示词内容、提示词长度、片段数量、模型支持、外观锚点污染、契约违规、景别与提示词一致性、镜头运动与提示词一致性、风格光照冲突、资产使用。规则报告与 LLM 报告合并后计算加权分数。

修复参数按 PipelineNode 写入 state.domain.repair_params，节点只读取自己的键；应用成功后清理实例状态。修复重试同时计入阶段级与全局级计数器，不会无限回炉。评分分档：≥90 PASSED、≥75 MINOR_ISSUES、≥60 MODERATE_ISSUES、≥40 MAJOR_ISSUES、≥20 CRITICAL_ISSUES，其余 FAILED；MINOR 且违规不超过 3 个时放行，FAILED 但分数 ≥80 同样放行；存在 critical 或 major 超过 2 条时置 needs_human_review。

错误处理

ERROR_HANDLER 定义七类错误（NETWORK / TIMEOUT / RATE_LIMIT / VALIDATION / CONFIG / BUSINESS / UNKNOWN）、四级严重度（LOW~CRITICAL）与六种动作（RETRY / DELAY_RETRY / REPAIR / HUMAN / ABORT / IGNORE）。回退目标按错误来源映射：审查或连续性失败→CONVERT_PROMPT；循环检查失败或未知来源→PARSE_SCRIPT。资产与路由来源未列入映射表，默认回退到 PARSE_SCRIPT。

恢复策略由错误来源决定回退目标，由严重度决定是否需要人工；ABORT 不进入错误处理，直接结束图执行。错误处理节点自身也有循环上限，避免在回退与再失败之间反复。

当前限制

限制 表现
超时保护不完整 asyncio.wait_for 包裹的是同步 workflow.invoke()，会阻塞事件循环，超时可能不触发；实际兜底为 LLM timeout 与循环上限，生产环境宜加进程级看门狗
检查点不参与恢复 检查点会随图编译写入，但恢复流程仍从任务起点重跑，没有按 thread_id 续跑的接口
恢复语义有限 超过 2 小时的任务静默跳过；恢复后优先级统一为 NORMAL 并追加队尾
循环告警口径不一 节点级与全局级 80% 预警共用 loop_warning_issued，仅先触发者报警；节点超限判定使用 >=
全局上限推导偏差 global_max_loops 实为 max_total_loops × 2（默认 40），与“各节点上限之和”的注释不一致
资产失败不阻断 资产生成未启用或全部失败时继续主流程，只保留提示词并由首帧指令兜底；不会因资产缺失中止任务
