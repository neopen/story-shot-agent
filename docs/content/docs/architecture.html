PenShot 是基于 LangGraph 的剧本分镜工作流：接入层接收剧本，任务层排队调度，六个业务节点顺序生成分镜提示词，四个控制节点负责循环计数、错误回退、人工干预与结果收口。

分层架构

系统按接入、任务、工作流、智能体、记忆五层划分，各层可独立降级；输出端由 WorkflowOutputFixer 修复片段序列后以 JSON 返回。

技术栈

组件 实现
智能体框架 LangGraph StateGraph + 条件边、LangChain
LLM OpenAI、Ollama、通义千问、DeepSeek，按 base_url 路由
任务队列 AsyncTaskProcessor 进程内优先级队列
任务存储 Redis，降级进程内存
检查点 LangGraph SqliteSaver（data/checkpoints/），降级内存
记忆 ScriptMemory 三层：Redis / 磁盘 / Chroma

各层独立降级：Redis 不可用时任务记录落进程内存，SQLite 不可写时检查点转内存模式，LLM 不可用时智能体退回规则引擎。单点故障不会直接中断工作流，但降级后的任务记录与检查点无法跨进程恢复。

video_model（runway_gen2 / sora / veo / pika 等）只影响提示词风格适配。PenShot 不调用视频模型，也不包含 FFmpeg 合成环节。

调用方可选四种入口，但四者最终都收敛到 TaskFactory：Python API 适合脚本内嵌，REST API 适合服务化，MCP Server 面向智能体工具调用，CLI 用于本地调试。入口层不保存状态，任务进度统一由任务层回写。

节点构成

业务节点 职责 输出
PARSE_SCRIPT 统一剧本格式，提取场景、角色、动作、对话 ParsedScript
SEGMENT_SHOT 划分镜头单元，估算时长 ShotSequence
SPLIT_VIDEO 按 5 秒上限切分，写入连续性注释 FragmentSequence
CONVERT_PROMPT 生成视频与音频提示词 AIVideoInstructions
AUDIT_QUALITY 五项规则检查与加权评分 QualityAuditReport
CONTINUITY_CHECK 六维连续性检查 ContinuityCheckResult
控制节点 职责
LOOP_CHECK 计数器递增、上限检查、阶段推进
ERROR_HANDLER 错误分类，选择回退节点
HUMAN_INTERVENTION 接收人工决策
GENERATE_OUTPUT 组装最终结果

拆分、分段、转换成功后不直接进入下一节点，而是先经过 LOOP_CHECK；它同时承担计数、超限判定与阶段推进。详细规则见工作流节点。

LOOP_CHECK 读取刚完成的节点标识，分别递增节点计数器与全局计数器，达到阈值即转人工或失败；未超限时按当前阶段把流程推进到下一业务节点。质量审查与连续性守护不经过 LOOP_CHECK。

阶段 主产物 关键内容
PARSE_SCRIPT ParsedScript 场景、角色、元素序列、global_metadata
SEGMENT_SHOT ShotSequence 镜头起止时间、景别、时长、主角色
SPLIT_VIDEO FragmentSequence 单段不超过 5 秒的片段与连续性注释
CONVERT_PROMPT AIVideoInstructions 双语提示词、负面词、音频、模型标记
AUDIT_QUALITY QualityAuditReport 分数、状态、违规列表、修复建议
CONTINUITY_CHECK ContinuityCheckResult 按严重度分级的问题与来源阶段

节点间共享一个 PipelineState 状态对象：task_id、script_id 标识任务，domain 存放各阶段产物（parsed_script、shot_sequence、fragment_sequence、instructions、audit_report、continuity_issues），repair_params 与循环计数器也挂在 domain 下。条件边只读取顶层字段，这一约定是后文连续性路由缺口的成因。

工作流与决策路由

每个业务节点执行后由 PipelineDecision 收敛为七种状态，再由 LangGraph 条件边路由。

flowchart TD
    Start([开始/剧本输入]) --> Parse[剧本解析节点]

    Parse --> Decision1{解析结果判断}
    Decision1 -->|成功| Split[镜头拆分节点]
    Decision1 -->|需要重试| Parse
    Decision1 -->|严重失败| Error[错误处理节点]
    Decision1 -->|需要人工干预| Human[人工干预节点]

    Split --> Decision2{拆分结果判断}
    Decision2 -->|成功| Loop{循环检查节点<br/>LOOP_CHECK}
    Decision2 -->|需要重试/修复| Split
    Decision2 -->|严重失败/超限| Error

    Loop -->|阶段推进| Fragment[视频分段节点]

    Fragment --> Decision3{分段结果判断}
    Decision3 -->|成功| Loop
    Decision3 -->|需要重试/修复| Fragment
    Decision3 -->|严重失败/超限| Error

    Loop -->|阶段推进| Prompt[提示词生成节点]

    Prompt --> DecisionP{生成结果判断}
    DecisionP -->|通过| Loop
    DecisionP -->|需要重试/修复| Prompt
    DecisionP -->|严重失败| Error

    Loop -->|阶段推进| Audit[质量审查节点]

    Audit --> Decision4{审查结果判断}
    Decision4 -->|通过/轻微问题| Continuity[连续性守护节点]
    Decision4 -->|需要重试/修复| Prompt
    Decision4 -->|需要人工干预| Human
    Decision4 -->|失败/中止| Error

    Continuity --> Decision5{连续性判断}
    Decision5 -->|通过| Output[生成输出节点]
    Decision5 -->|需要修复| Prompt
    Decision5 -->|需要人工干预| Human
    Decision5 -->|严重失败| Error

    Output --> End([工作流完成])

    Error --> DecisionE{错误处理判断}
    DecisionE -->|按错误来源回退| Node[对应阶段节点<br/>解析/拆分/分段/转换]
    DecisionE -->|需要人工干预| Human
    DecisionE -->|中止流程| End

    Human --> DecisionH{人工决策判断}
    DecisionH -->|继续流程| Output
    DecisionH -->|重新开始| Parse
    DecisionH -->|调整提示词| Prompt
    DecisionH -->|重试失败| Error
    DecisionH -->|中止流程| End
状态 含义 后续动作
SUCCESS 完全成功 进入下一节点
VALID 有轻微问题 放行
NEEDS_RETRY 需要重试 重跑当前节点
NEEDS_REPAIR 需要修复 带修复参数重跑
NEEDS_HUMAN 需要人工干预 转人工节点
FAILED 一般失败 转错误处理
ABORT 中止流程 结束

SUCCESS 与 VALID 都表示放行，区别在语义：SUCCESS 视为完全合格，VALID 表示存在可接受的轻微问题，带病继续但不携带修复参数。只有 NEEDS_REPAIR 才会把修复参数交给下一轮生成；NEEDS_RETRY 只重置当前节点，不修改输入。

决策路由表

节点 通过 修复 人工 / 失败
PARSE_SCRIPT SEGMENT_SHOT 自身（RETRY） HUMAN / ERROR
SEGMENT_SHOT LOOP_CHECK 自身（RETRY / REPAIR） HUMAN / ERROR
SPLIT_VIDEO LOOP_CHECK 自身（RETRY / REPAIR） HUMAN / ERROR
CONVERT_PROMPT LOOP_CHECK 自身（RETRY / REPAIR） HUMAN / ERROR
LOOP_CHECK 按阶段推进 - HUMAN / ERROR
AUDIT_QUALITY CONTINUITY_CHECK CONVERT_PROMPT HUMAN / ERROR；ABORT→END
CONTINUITY_CHECK GENERATE_OUTPUT CONVERT_PROMPT（REPAIR） HUMAN / ERROR
HUMAN_INTERVENTION GENERATE_OUTPUT RETRY→PARSE；REPAIR→CONVERT 自身等待；ABORT→END
ERROR_HANDLER 按错误来源回退 - HUMAN；ABORT→END

质量审查失败不重跑审查，而是回 CONVERT_PROMPT 重新生成；连续性检查的修复目标同样收敛到 CONVERT_PROMPT。两处都遵循“问题出在被审查的提示词上”的约定。

GENERATE_OUTPUT 汇总各阶段产物后，由 WorkflowOutputFixer 对片段序列做结构修复，再序列化为 JSON 返回调用方。该层只做结构修复，不重新调用模型。

三级循环防护

三个独立计数器分别约束节点自旋、阶段重试与全局预算，任一触顶即熔断。

层级 计数器 上限 递增时机 触顶后果
节点级 node_current_loops node_max_loops（3~5） LOOP_CHECK 每次经过当前节点 拆分 / 分段转人工，其余 FAILED
阶段级 stage_current_retries stage_max_retries（2~3） 质量不达标、需带修复参数重来 转人工或修复
全局级 global_current_loops max_total_loops × 2（默认 40） 每次经过 LOOP_CHECK 直接 FAILED
节点 node_max_loops stage_max_retries 节点超限后果
PARSE_SCRIPT 3 3 FAILED
SEGMENT_SHOT 5 3 转人工
SPLIT_VIDEO 5 3 转人工
CONVERT_PROMPT 5 3 FAILED
AUDIT_QUALITY 3 2 FAILED
CONTINUITY_CHECK 5 2 FAILED
ERROR_HANDLER 5 - 转人工
HUMAN_INTERVENTION 1 - 不参与循环计数

node_max_loops 由 LOOP_CHECK 每次经过时递增，防止节点在图内打转；stage_max_retries 只在该阶段质量不达标、需要携带修复参数重来时才递增。另有 max_continuity_retries=3 控制连续性修复循环。任一计数器达到上限 80% 时输出 Warning 日志；触顶后不再重试。

        System->>System: 决策:拆分结果判断

            System->>Fragmenter: 开始视频分段
        else 需要重试/修复
            System->>Splitter: 应用修复参数后重试
        else 严重失败
            System->>Error: 进入错误处理
        end
    end

    %% 视频分段 + 重试循环
    loop 最多5次循环（质量重试上限3）
        Fragmenter->>Fragmenter: 5秒智能分段
        Fragmenter-->>System: 返回片段序列
        System->>System: 决策:分段结果判断
        
        alt 分段成功
            System->>Converter: 生成AI指令
        else 需要修复(时长问题)
            System->>Fragmenter: 应用修复参数后重试
        else 严重失败
            System->>Error: 进入错误处理
        end
    end

    %% 指令转换 + 重试循环
    loop 最多5次循环（质量重试上限3）
        Converter->>Converter: 生成提示词
        Converter-->>System: 返回Prompt序列
        System->>System: 决策:生成结果判断
        
        alt 生成通过
            System->>Auditor: 开始质量审查
        else 需要重试/修复
            System->>Converter: 应用修复参数后重试
        else 严重失败
            System->>Error: 进入错误处理
        end
    end

    %% 质量审查 + 修复决策
    Auditor->>Auditor: 规则审查
    Auditor->>Auditor: LLM深度审查
    Auditor->>Auditor: 问题分类+生成修复参数
    Auditor-->>System: 返回审查报告
    System->>System: 决策:审查结果判断

    alt 审查通过
        System->>Guardian: 开始连续性检查
        
    else 轻微问题(≤3个)
        System->>System: 视为有效，直接放行
        System->>Guardian: 继续连续性检查
        
    else 中等问题
        System->>System: 标记需要修复
        System-->>Converter: 返回到指令转换修复
        
    else 严重问题
        System->>Error: 进入错误处理
        
    else 需要人工干预
        System->>Human: 请求人工决策
        Human-->>System: 返回人工决策
    end

    %% 连续性检查 + 修复循环
    loop 最多3次连续性修复
        Guardian->>Guardian: 角色连续性检查
        Guardian->>Guardian: 场景连续性检查
        Guardian->>Guardian: 动作连续性检查
        Guardian->>Guardian: 风格连续性检查
        Guardian->>Guardian: 时间连续性检查
        Guardian->>Guardian: 道具连续性检查
        Guardian-->>System: 返回连续性问题列表
        System->>System: 决策:连续性判断(严重/中等/轻微)

        alt 检查通过(无问题)
            System->>User: 返回完整AI指令
            
        else 轻微问题
            System->>User: 返回AI指令(VALID 放行)
            
        else 严重/中等且可重试
            System->>Converter: 返回指令转换阶段重生成提示词
            
        else 严重问题且不可重试
            System->>Human: 请求人工干预
            Human-->>System: 返回人工决策
            
            alt 人工确认继续
                System->>User: 返回AI指令(带警告)
            else 人工要求中止
                System->>User: 返回失败信息
            end
        end
    end

    %% 错误处理流程
    System->>Error: 进入错误处理
    Error->>Error: 错误分类(NETWORK/TIMEOUT/RATE_LIMIT/VALIDATION/CONFIG/BUSINESS/UNKNOWN)
    Error->>Error: 按错误来源节点制定恢复策略

    alt 可恢复错误
        Error->>Error: 按 last_node 映射回退目标
        Note over Error,Parser: 审查/连续性失败→指令转换；循环检查失败/未知→剧本解析
        Error-->>Parser: 回退到映射出的节点重试
        
    else 需要人工干预
        Error->>Human: 请求人工干预
        Human-->>Error: 返回人工决策
        
        alt 人工继续
            Error-->>System: 继续执行
        else 人工中止
            Error->>User: 返回失败信息
        end
        
    else 不可恢复错误
        Error->>User: 返回失败信息(ABORT)
    end

任务队列与持久化

任务按 CRITICAL > HIGH > NORMAL > LOW 入队，AsyncTaskProcessor 按优先级拉取，并受并发信号量约束。默认 max_concurrent=10、queue_size=1000；队列为普通 list，入队时有序插入，cancel_task 按 task_id 遍历删除。

任务记录以 task_id 为主键，保存状态、当前阶段、进度、结果元信息与时间戳。状态从 PENDING 进入 PROCESSING，执行结束后写入结果；recover_task(task_id) 可将单个任务软重置为 PENDING、阶段置为 recovered、进度归零，用于人工重新投递。

get_queue_status() 返回 queue_length、queue_waiting、active_tasks、max_concurrent、queue_max_size、queue_usage_percent 六个字段。

存储 实现 内容 降级
任务记录 TaskRepository：penshot:tasks:data:{task_id} + 索引集合 penshot:tasks:ids，TTL 86400 秒 状态、阶段、进度、结果元信息 Redis 不可用→进程内存
工作流检查点 WorkflowCheckpointer：data/checkpoints/{script_id}/task_{task_id}.db 图执行位置与各阶段中间状态 目录不可写或依赖缺失→内存模式

任务记录与工作流检查点相互独立：前者服务任务查询与恢复筛选，后者保存图执行位置与中间状态，二者不共享存储。

启动时 recover_pending_tasks(max_age_hours=2) 筛选 PENDING / PROCESSING 且 2 小时内的任务，重建为 NORMAL 优先级并追加到队尾。恢复按任务起点重跑，不接检查点续跑；超窗任务不标记、不删除，等待 TTL 过期。检查点细节见检查点与恢复。

质量修复闭环

质量保障采用“轻前置检测 + 重最终检测”：节点内处理格式、时长、空值等本地问题，AUDIT_QUALITY 集中做规则与 LLM 深度审查，并将问题转换为修复参数。

前置检测与最终审查分工明确：节点内检测只处理本节点能修复的格式、时长与空值问题，避免明显不合格的产物进入下游；AUDIT_QUALITY 读取完整提示词包，规则检查与 LLM 深度审查并行后合并报告。修复成本高于一次生成，因此只有达到修复档位才回炉，轻微问题直接放行。

检测 时机 内容 修复
节点内基础检测 每个业务节点执行期间 格式、时长、空值 节点产出问题列表
统一深度检测 CONVERT_PROMPT 之后 连贯性、一致性、语义（规则 + LLM） 生成修复参数，回 CONVERT_PROMPT
跨片段一致性 CONTINUITY_CHECK 角色、道具、场景、时间等 按严重度分类处理

    A[剧本输入] --> B[剧本解析]
    B --> C[节点内基础检测]
    C --发现问题--> B

    C --> D[镜头拆分]
    D --> E[节点内基础检测]
    E --发现问题--> D

    E --> F[视频分段]

修复参数按 PipelineNode 写入 state.domain.repair_params，节点只读取自己的键；应用成功后调用 clear_repair_params() 与 clear_historical_context() 清理实例状态，历史记录保留到任务结束。修复重试同时计入阶段级与全局级计数器，不会无限回炉。评分分档：≥90 PASSED、≥75 MINOR_ISSUES、≥60 MODERATE_ISSUES、≥40 MAJOR_ISSUES、≥20 CRITICAL_ISSUES，其余 FAILED；MINOR 且违规不超过 3 个时放行，FAILED 但分数 ≥80 同样放行。

错误处理

ERROR_HANDLER 定义七类错误（NETWORK / TIMEOUT / RATE_LIMIT / VALIDATION / CONFIG / BUSINESS / UNKNOWN）、四级严重度（LOW~CRITICAL）与六种动作（RETRY / DELAY_RETRY / REPAIR / HUMAN / ABORT / IGNORE）。回退目标按错误来源映射：审查或连续性失败→CONVERT_PROMPT；循环检查失败或未知来源→PARSE_SCRIPT。

恢复策略由错误来源决定回退目标，由严重度决定是否需要人工；ABORT 不进入错误处理，直接结束图执行。错误处理节点自身也有循环上限，避免在回退与再失败之间反复。

        Error-->>Node: 26. 返回ABORT

当前限制

限制 表现
超时保护不完整 asyncio.wait_for 包裹的是同步 workflow.invoke()，会阻塞事件循环，超时可能不触发；实际兜底为 LLM timeout=60 与循环上限，生产环境宜加进程级看门狗
连续性路由缺口 decide_after_continuity 读取顶层 state.continuity_issues，实际字段位于 state.domain.continuity_issues，决策恒为 SUCCESS；修复参数生成后不会回流。即使修正读取路径，其返回的 NEEDS_RETRY 也不在条件边键集合中
恢复语义有限 超过 2 小时的任务静默跳过；恢复后优先级统一为 NORMAL 并追加队尾；任务从起点重跑，检查点不参与恢复
循环告警口径不一 节点级与全局级 80% 预警共用 loop_warning_issued，仅先触发者报警；节点超限判定同时存在 > 与 >=
全局上限推导偏差 global_max_loops 实为 max_total_loops × 2（默认 40），与“各节点上限之和”的注释不一致；八个节点上限之和为 32
队列不跨进程 AsyncTaskProcessor 为进程内优先级队列，多副本部署时各进程独立调度，队列不共享，跨进程扩展能力有限
