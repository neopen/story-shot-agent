PenShot 的记忆系统按短期、中期、长期三层保存任务上下文与历史经验：MemoryManager 按剧本路由到 ScriptMemory，后者统一负责写入分发、召回组装与提示词格式化。

适用范围：实现位于 knowledge/memory/，配置由 MemoryConfig 注入，已接入工作流四个处理阶段。中期摘要重启后无法读回、长期库为空时检索返回空结果、Redis 运行期中断会丢失当次交互，均属于已知边界。

架构与隔离

MemoryManager 是多剧本容器，内部持有 Dict[str, ScriptMemory]；ScriptMemory 才真正持有三层记忆。MemoryManager 的职责是按 script_id 路由，并统一做序列化与反序列化。

同一进程内不同剧本的记忆互不可见：Redis key 带 session_id，Chroma collection 与文件路径都带 script_id。重启后短期记忆能否恢复，取决于是否配置了持久化目录以及 Redis 是否可用。

层级 类 存储介质 隔离键

短期记忆

短期记忆是“Redis 优先、内存降级”的双轨结构：进程内用 deque(maxlen=20) 维护滑动窗口，Redis 侧用 RedisChatMessageHistory 保存会话，ttl=3600 秒。窗口是 FIFO，不是 LRU；窗口满时从队首挤出最旧条目。

    subgraph 输入流
        I1[交互1] --> I2[交互2] --> I3[...] --> I4[交互19] --> I5[交互20] --> I6[交互21]
    end

    subgraph 滑动窗口[deque maxlen 20]
        W1[交互19] --> W2[交互20] --> W3[交互21]
    end

    I1 -.->|超出自动丢弃| W1
    I4 & I5 & I6 --> W1 & W2 & W3
    W1 & W2 & W3 --> O[get_recent 当前上下文]

初始化时执行一次 Redis 探活（3 秒连接超时 + ping()）。失败则打 warning，整体切到“内存 + 文件”模式；若配置了 term_persist_path，每次 add() 同步写 short_term.json，重启后由 _load_from_file() 恢复窗口。

降级决策只发生在实例构造时。运行中途 Redis 才失效时，add() 的缓冲区追加与 Redis 写入在同一个 try 块内，本次交互既写不进 Redis，也不会进入内存窗口；后续写入持续失败，直到 Redis 恢复。当前没有重连探活或补偿队列。

短期记忆也没有“任务完成即清空”的钩子。退场只靠两个机制：deque 的 20 条上限与 Redis 的 1 小时 TTL。内存模式没有自动过期。

中期记忆

中期记忆用 LLM 做滚动摘要：每次写入把“已有摘要 + 新内容”交给模型融合，生成新的摘要文本。medium_term_max_tokens=500 是名义上限，实际以字符截断兜底：输入不超过 500*4=2000 字符，输出不超过 500*2=1000 字符，超出部分静默截断。

flowchart TB
    subgraph Trigger["触发判断（每次写入时）"]
        NEW[新增对话] --> CHK{积压字符数超过<br/>max_token_limit × 4 ?}
        CHK -->|否| WAIT[继续积压]
        CHK -->|是| LLM[调用 LLM 生成摘要]
    end

    subgraph Persist["持久化（按小时分文件）"]
        LLM --> CAP{摘要超长?<br/>超过 max_token_limit × 2}
        CAP -->|是| TRUNC[截断至 1000 字符]
        CAP -->|否| KEEP[原样保留]
        TRUNC --> FILE[(JSON 快照文件<br/>medium_summary 按小时命名)]
        KEEP --> FILE
    end

持久化路径存在一处读写不一致：_persist_to_file 写入 medium_summary_{YYYYMMDDHH}.json，_load_from_file 与 clear 操作固定名 medium_summary.json。结果是摘要快照持续产生，但进程重启后加载不回来，历史摘要留在磁盘上不参与后续上下文。

工作流还会写另一类中期数据：每个阶段完成后，WorkflowMemory.after_stage_completion() 提取场景数、角色数、问题数、修复参数等统计，生成带时间戳的阶段摘要；数值字段计算 avg / min / max / count，并对 completeness_score 做 improving / declining / stable 趋势判定。写入时统计摘要最多保留 20 条。

字符与 token 的换算按“4 字符 ≈ 1 token”处理，对中文会系统性低估 token 数。功能上仍会压缩，但配置中“500 tokens”的语义在中文场景下并不精确。

长期记忆

长期记忆使用 Chroma，collection 为 script_{script_id}_memory，持久化目录为 data/memory/{script_id}/。写入时把 tags / category 拼进正文再入库，让元数据参与语义召回；检索用 similarity_search_with_score 取前 k=3 条，并按 score >= 0.7 过滤。

    subgraph 存储
        T[记忆条目 + tags/category] --> E[共享 Embedding 模型<br/>默认 OpenAI 1536 维]
        E --> V[(Chroma 向量库<br/>每剧本一个 collection)]
    end

    subgraph 检索
        Q[查询: 林小雨的服装] --> E2[Embedding 模型]
        E2 --> S[similarity_search_with_score<br/>k=3]
        V --> S
        S --> R[按 score_threshold 0.7 过滤]
    end

长期层是“成功样本驱动”的冷启动系统。工作流阶段完成后，_is_successful_case 先判定是否达标（例如 parse_script 要求 completeness_score >= 0.8），通过才生成条目：格式为阶段名 + 统计 + 场景/角色/镜头摘要，单条限 2000 字符，成功模式保留最近 30 条。未达标就跳过写入。

因此空库不是异常：集合文档数为 0 时，检索安静返回零条结果，依赖历史经验增强的逻辑静默退化为“没有经验可用”。长期库也没有自动过期，只能显式清理。

两个必须核对的约束：查询与写入必须使用同一套嵌入模型与维度，换模型等于换度量尺；similarity_search_with_score 在 Chroma 默认 L2 度量下返回距离（越小越相似），而过滤条件是 score >= threshold，方向与“保留更相似结果”相反，使用前应打印分数分布确认。

写入分发

ScriptMemory.add(input_text, output_text, level, metadata) 的语义是一对交互，而不是键值写入。所有条目先写短期，再按级别或重要性分流：

  • level=MEDIUM_TERM：同时写入中期摘要链。
  • level=LONG_TERM 且长期层可用：拼接为“问题 + 回答”写入 Chroma。
  • 未指定级别：metadata.important 为真时提升到中期；短期用量达到容量 80% 时，取最近 5 条打成摘要写入中期。

    subgraph Write[写入链路]
        I[add input/output] --> ST[短期记忆<br/>deque + Redis]
        ST -->|metadata.important| MT[中期记忆<br/>LLM 摘要融合]
        ST -->|窗口用量≥ 80%<br/>最近 5 条打成摘要| MT
        I -->|level=LONG_TERM| LT[长期记忆<br/>Chroma]

        Q[recall query, level, k] --> R1[get_recent k]

没有“中期 → 长期”的自动晋升，也没有基于重要度评分的自动分层；进入长期必须由调用方显式传入 level=LONG_TERM。WorkflowMemory.after_stage_completion() 也不是逐层升华，而是在同一次事件里把不同粒度的结果分别写入三层。

80% 水位判断没有“已压缩”标记：窗口达到 16 条后，每次 add() 都会再触发一次摘要 LLM 调用，且近满载时每次取到的最近 5 条高度重叠。这是当前实现的额外调用开销。

召回组装

recall(query, level=None, k=3) 按层查询后原样组装为 MemoryContext：短期是最近 k 条列表，中期是摘要字符串，长期是相关条目列表。level 为 None 时查三层；指定某一层时只查该层。

sequenceDiagram
    participant A as 智能体
    participant M as MemoryManager
    participant S as ScriptMemory
    participant C as MemoryContext

    A->>M: recall(query, level, k, script_id)
    M->>S: 按 script_id 路由
    S->>S: 短期 get_recent / 中期 get_summary / 长期 search
    S->>C: 组装三层字段
    C-->>A: to_prompt(max_tokens=2000)
    Note over C: 无加权融合，按层拼接

to_prompt(max_tokens=2000) 依次拼接“最近对话 / 历史摘要 / 相关经验”。短期最多取 10 条、单条超过 500 字符截断；长期最多取 5 条、单条超过 800 字符截断。整体按 1 token ≈ 2 字符估算，超出预算时回退到最近句号或换行，并追加 [上下文已截断]。

这里没有 0.6 / 0.3 / 0.1 之类的加权融合，也不存在 MemoryFusion 类。三层的取舍只发生在两处：to_prompt() 的格式化上限，以及调用方传入的 level。便捷接口 get(key, ...) 同样走 recall()：按 key 匹配最近一条，短期返回该条的 output，长期返回该条的 content。

降级与限制

场景 行为 影响
Redis 初始化失败 warning 后切内存；配置了路径则写 short_term.json 跨进程可见性丢失；重启可经文件恢复
Redis 运行期中断 add() 整体失败，不落内存也不落 Redis 故障期间的交互丢失，无自动重连
Chroma 未启用或不可用 long_term 为 None，写入与召回跳过该层 长期能力整体缺失，短期与中期继续工作，无替代向量库
长期库为空 检索返回零条，不报错 历史经验增强静默失效，需要监控集合文档数
嵌入模型或维度不一致 相似度分数失去意义 召回结果不可用，且不会抛错
中期摘要重启 按小时文件名与固定读取名不一致 历史摘要加载不回来
  • EPHEMERAL 仅存在于枚举，没有实现。
  • 没有中期到长期的自动晋升，也没有重要度评分分层。
  • 没有加权融合或跨层重排；MemoryContext 只做按层拼接与截断。
  • long_term_enabled=False 时仍会探测已有数据，发现历史条目会自动启用并回写配置，避免配置错误导致旧记忆静默失效。
  • 记忆按 script_id 隔离；跨剧本迁移与共享不在当前能力内。
