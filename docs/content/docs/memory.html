PenShot 的记忆系统按短期、中期、长期三层保存任务上下文与历史经验：MemoryManager 按剧本路由到 ScriptMemory，后者统一负责写入分发、召回组装与提示词格式化。三层都继承 BaseMemoryLayer，共享按 key 的 KV 存取、持久化与统计骨架。

适用范围：本页对应 v0.4.9 源码。实现位于 knowledge/memory/，配置由 MemoryConfig 注入，已接入工作流多个处理阶段。0.4.8 起三层统一到 BaseMemoryLayer：按 key 的读写、摘要快照持久化、长期记忆容量清理与 key 精确命中均已接通；EPHEMERAL 仍只是枚举预留，没有对应实现。

架构与隔离

MemoryManager 是多剧本容器，内部持有 Dict[str, ScriptMemory]；ScriptMemory 才真正持有三层记忆。MemoryManager 的职责是按 script_id 路由，并统一做序列化与反序列化。

同一进程内不同剧本的记忆互不可见：Redis key 带 session_id，Chroma collection 与文件路径都带 script_id。重启后短期记忆能否恢复，取决于是否配置了持久化目录以及 Redis 是否可用。

短期记忆

短期记忆是“Redis 优先、内存降级”的双轨结构：进程内用 deque(maxlen=20) 维护滑动窗口，Redis 侧用 RedisChatMessageHistory 保存会话，ttl=3600 秒。窗口是 FIFO，不是 LRU；窗口满时从队首挤出最旧条目。

session_id 由 script_id 稳定派生（short_term_{script_id[2:]}），不再掺入时间戳，重启后能命中同一会话；完整 Redis key 为 message_store: 前缀加该 session_id。

初始化时执行一次 Redis 探活（3 秒连接超时 + ping()）。失败则打 warning，整体切到“内存 + 文件”模式；若配置了 term_persist_path，每次 add() 同步写 short_term.json，重启后由 _load_from_file() 恢复窗口，并按 key 从 short_term_kv.json 恢复 KV 侧车。

无论 Redis 是否可用，add() 都会先以 input_text 为 key 写入 KV，保证 MemoryManager.get() 能按 key 命中；消息窗口与 Redis 会话历史的写入包在同一个 try 块内，失败仅记 error 不抛错。

降级决策只发生在实例构造时。运行中途 Redis 才失效时，当次交互写入 KV 仍在进程内可见，但消息窗口与 Redis 会话历史不会落库；后续写入持续失败，直到 Redis 恢复。当前没有重连探活或补偿队列。

短期记忆也没有“任务完成即清空”的钩子。退场只靠两个机制：deque 的 20 条上限与 Redis 的 1 小时 TTL。内存模式没有自动过期。

中期记忆

中期记忆用 LLM 做滚动摘要：每次写入把“已有摘要 + 新内容”交给模型融合，生成新的摘要文本。medium_term_max_tokens=500 是名义上限，实际以字符截断兜底：输入不超过 500*4=2000 字符，输出不超过 500*2=1000 字符，超出部分静默截断。

        CUR --> LLM[LLM 融合生成新摘要]
        LLM --> CAP{摘要超长?<br/>超过 max_token_limit × 2}
        CAP -->|是| TRUNC[截断至 1000 字符]
        CAP -->|否| KEEP[原样保留]

        TRUNC --> FILE[(medium_summary.json<br/>summary + stage_summaries + key_values)]
        KEEP --> FILE

0.4.8 修复了此前读写文件名不一致的问题：持久化与加载统一使用 medium_summary.json，写入内容包括整体摘要、阶段摘要、KV 侧车与更新时间。进程重启后，_load_from_file() 恢复阶段摘要与 KV；在会话历史尚为空时，get_summary() 回退到磁盘恢复的 _restored_summary，历史摘要不再丢失。

工作流还会写另一类中期数据：每个阶段完成后，WorkflowMemory.after_stage_completion() 提取场景数、角色数、问题数、修复参数等统计，生成带时间戳的阶段摘要；数值字段计算 avg / min / max / count，并对 completeness_score 做 improving / declining / stable 趋势判定。写入时统计摘要最多保留 20 条。

字符与 token 的换算按“4 字符 ≈ 1 token”处理，对中文会系统性低估 token 数。功能上仍会压缩，但配置中“500 tokens”的语义在中文场景下并不精确。

长期记忆

长期记忆使用 Chroma，collection 为 script_{script_id}_memory，持久化目录为 data/memory/{script_id}/。写入时把 tags / category 拼进正文再入库，让元数据参与语义召回；检索用 similarity_search_with_score 取前 k=3 条。

向量库在后台线程池异步初始化，业务请求先到时由 _ensure_vectorstore() 等待初始化完成，避免构造阶段阻塞。除向量检索外，长期层还维护 long_term_kv.json 侧车：写入时先按 key 存 KV，再写向量库，向量库失败也不影响按 key 精确命中。

相关度换算已修正：Chroma 默认 L2 度量返回距离，_relevance_from_distance() 用 1 - distance/2 把单位化向量的平方欧氏距离换算为余弦相似度，再按 relevance >= long_term_score_threshold（默认 0.7）过滤，方向与“保留更相似结果”一致。

向量库只增不删会持续膨胀，因此每次写入后调用 prune_old()：long_term_max_documents（默认 500）为保留上限，超出时按 timestamp 元数据删除最旧记录。clear() 则删除并重建整个 collection。

长期层是“成功样本驱动”的冷启动系统。工作流阶段完成后，_is_successful_case 先判定是否达标（例如 parse_script 要求 completeness_score >= 0.8），通过才生成条目：格式为阶段名 + 统计 + 场景/角色/镜头摘要，单条限 2000 字符，成功模式保留最近 30 条。未达标就跳过写入。

因此空向量库不是异常：集合文档数为 0 时，语义检索安静返回零条结果，但已有 KV 侧车仍可按 key 命中；仅依赖历史经验增强的逻辑会静默退化为“没有经验可用”。

另有一类由模板管理器写入的长期条目：质量审计通过的提示词以 successful_prompt_patterns 为键、按哈希去重后序列化保存，保留最近 200 条。它们只供提示词转换节点作为历史参考，history_hint 截取首条前 100 个字符；这些条目不会回填模板向量索引，模板召回仍以模板库为准。

两个必须核对的约束：查询与写入必须使用同一套嵌入模型与维度，换模型等于换度量尺；MemoryConfig.embeddings 未显式提供时会复用统一嵌入工厂，避免再初始化一套无关模型。

写入分发

ScriptMemory.add(input_text, output_text, level, metadata) 的语义是一对交互，而不是键值写入。所有条目先写短期，再按级别或重要性分流：

  • level=MEDIUM_TERM：同时写入中期摘要链。
  • level=LONG_TERM 且长期层可用：先按 key 写 KV，再以“问题 + 回答”写入 Chroma。
  • 未指定级别：metadata.important 为真时提升到中期；短期用量达到容量 80% 时，取最近 5 条打成摘要写入中期。

    subgraph Read[召回链路]

add_stage() 走另一条路径：阶段内容写入中期；metadata.important 为真且长期层可用时，同样先写长期 KV 再写向量库。没有“中期 → 长期”的自动晋升，进入长期必须由调用方显式传入 level=LONG_TERM 或经 add_stage 标记。

80% 水位判断没有“已压缩”标记：窗口达到 16 条后，每次 add() 都会再触发一次摘要 LLM 调用，且近满载时每次取到的最近 5 条高度重叠。这是当前实现的额外调用开销。

召回组装

recall(query, level=None, k=3) 返回 MemoryContext，三层都先尝试 key 精确命中，再退回语义或窗口结果：

  • 短期：先取最近 k 条，query 命中内容、输出或元数据 key 时优先返回匹配条目。
  • 中期：has_value(query) 为真时返回该 key 的原文，否则返回整体摘要。
  • 长期：KV 命中项以 score=1.0 置顶，再补充向量检索结果并去重，整体截取前 k 条。
sequenceDiagram
    participant A as 智能体
    participant M as MemoryManager
    participant S as ScriptMemory
    participant C as MemoryContext

    A->>M: recall(query, level, k, script_id)
    M->>S: 按 script_id 路由
    S->>S: 短期 get_recent / 中期 key+摘要 / 长期 key+search
    S->>C: 组装三层字段
    C-->>A: to_prompt(max_tokens=2000)
    Note over C: 无加权融合，按层拼接

to_prompt(max_tokens=2000) 依次拼接“最近对话 / 历史摘要 / 相关经验”。短期最多取 10 条、单条超过 500 字符截断；长期最多取 5 条、单条超过 800 字符截断。整体按 1 token ≈ 2 字符估算，超出预算时回退到最近句号或换行，并追加 [上下文已截断]。

这里没有 0.6 / 0.3 / 0.1 之类的加权融合，也不存在 MemoryFusion 类。三层的取舍只发生在两处：to_prompt() 的格式化上限，以及调用方传入的 level。MemoryManager.get() 不走 recall()，而是按 level 直接读对应层的 KV：命中返回已反序列化的值，未命中返回默认值；get_list / count / exists 同源。

降级与限制

场景 行为 影响
Redis 初始化失败 warning 后切内存；配置了路径则写 short_term.json 与 KV 侧车 跨进程可见性丢失；重启可经文件恢复
Redis 运行期中断 当次消息窗口与会话历史不落库，KV 仍在进程内可见 故障期间的近期列表缺失，无自动重连
Chroma 未启用或不可用 long_term 为 None，写入与召回跳过向量能力 长期语义检索缺失，短期与中期继续工作，无替代向量库

嵌入模型或维度不一致 相似度分数失去意义 召回结果不可用，且不会抛错
向量库持续写入 写入后按 long_term_max_documents 清理最旧记录 默认保留 500 条，可通过配置调整或关闭（<=0）
  • EPHEMERAL 仅存在于枚举，没有实现。
  • 没有中期到长期的自动晋升，也没有重要度评分分层。
  • 没有加权融合或跨层重排；MemoryContext 只做按层拼接与截断。
  • long_term_enabled=False 时仍会探测已有数据，发现历史条目会自动启用并回写配置，避免配置错误导致旧记忆静默失效。
  • 记忆按 script_id 隔离；跨剧本迁移与共享不在当前能力内。
