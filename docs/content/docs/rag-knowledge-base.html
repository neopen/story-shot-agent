PenShot 的知识库与检索层把剧本解析结果、成功提示词模板与历史经验写入向量索引，并在工作流节点需要时按语义相似度取回，注入提示词或连续性修复流程。

知识库挂在提示词模板管理器 PromptTemplateManager（prompts/prompt_template_manager.py）之下，由它同时持有按剧本隔离的模板索引与剧本内容索引。工作流节点只与这个中枢交互，不直接访问向量存储。下表列出各能力的实现位置与当前状态。

知识库架构

索引层由两套相互独立的 LlamaIndex 向量索引组成，均以 SimpleVectorStore 为存储后端，并用 script_id 作为隔离键。模板索引保存质量审计通过的成功提示词；剧本内容索引由内嵌的 ScriptKnowledgeBase（knowledge/llamaIndex/llama_index_knowledge.py）承载，保存场景与角色文档。两者各有判分口径与过滤规则，不能视为同一个检索入口。

ScriptKnowledgeBase 的构造参数为 (embeddings, script_id, storage_dir=None, chunk_size=512, chunk_overlap=20)，第二个参数必需；内部用 _indices、_vector_stores、_storage_contexts、_retrievers 四组字典按剧本 ID 隔离数据。模板管理器同样按 script_id 维护索引与缓存，因此模板库不是全局共享的：真正跨剧本可见的只有长期记忆。

索引与分块

“分块”在代码里有两个互不相关的层次：入库时的文本切分，以及尚未接线的超长剧本分块。前者决定检索粒度，后者决定单次任务处理多少场景，两者的参数与调用方都不同。

入库切分

调用 add_parsed_script(parsed_script, script_id) 时，剧本先被转成两类文档：每个场景一个 type=scene 文档，元数据含 scene_id、location、time_of_day、element_count；每个角色一个 type=character 文档，元数据含 character_name、gender、role。文档总数等于场景数加角色数，script_id 由入库方法逐文档注入。

节点解析器的选择是一个条件分支：chunk_size > 1000 时使用 SentenceWindowNodeParser（窗口 3），否则使用 SentenceSplitter。默认 512/20，因此默认路径是 SentenceSplitter；调大分块参数会连带切换解析器，这是调整分块参数时需要留意的一点。切分后的节点经嵌入模型向量化写入 SimpleVectorStore，并立即由 _save_storage 落盘，同时校验向量文件与 docstore 是否写盘成功。

flowchart TD
    A[ParsedScript 场景与角色] --> B[create_documents]
    B --> C{chunk_size > 1000}
    C -->|是| D[SentenceWindowNodeParser window_size=3]
    C -->|否| E[SentenceSplitter 512/20]
    D --> F[嵌入模型向量化]
    E --> F
    F --> G[SimpleVectorStore 按 script_id 隔离]
    G --> H[_save_storage]
    H --> I[default__vector_store.json docstore.json index_store.json]

长剧本分块：LongScriptChunker

LongScriptChunker（continuity_guardian/long_script_chunker.py）处理的是另一件事：把解析后的场景序列切成块，供逐块执行。参数为每块最多 30 个场景、单块预估时长上限 180 秒、块间重叠 3 个场景。

切分使用“或”条件，任一条件满足即封块；判断发生在场景入块之前，因此场景不会被从中间切开，单个超长场景会成为新块的起点。封块后保留上一块末尾 3 个场景作为新块开端，并重算时长预算。场景时长按 max(10.0, 元素数 × 4.0) 估算：不调用模型，带 10 秒下限，精度有限。

实现的策略只有“按场景切分”一种，代码中没有角色弧、情绪曲线或平衡分块的对应实现。全仓库没有生产调用方，ScriptChunk 的 entry_character_states、exit_character_states、continuity_anchors 三个字段只在数据类中声明、构建块时从不赋值，跨块状态传递尚未落地。超长剧本当前可用的做法是按叙事段落分段输入，逐段调用工作流。

flowchart TD
    A[遍历场景序列] --> B{场景数达 30 或 时长将超 180 秒}
    B -->|否| C[场景入块 累加预估时长]
    B -->|是| D[结算当前块]
    D --> E[保留末尾 3 个场景]
    E --> C
    C --> F[遍历结束 结算末块]

检索

生产链路上有两条规则不同的检索路径，分别服务模板增强与场景检索。

剧本内容检索：手动余弦

ScriptKnowledgeBase.query() 不走 LlamaIndex 检索器。它用 embeddings.embed_query 编码查询，遍历向量存储的 embedding_dict，逐个计算余弦相似度，按分数降序截断 top_k（默认 5），再从 docstore 取回文本与元数据。复杂度为 O(N)，没有近似索引，单剧本几十到几百个节点时开销可以接受，规模上万后查询延迟会随文档数线性上升。

这条路径不做任何分数过滤，低分结果同样会占满名额。签名中的 search_type、use_rerank、rerank_model 三个参数从未被读取；search_similar_scene 内部传了 use_rerank=True，同样不产生重排序行为。函数对缺参和缺索引做早退：未指定 script_id 时返回带 error 字段的空结果，索引或向量存储未就绪时同样返回结构化错误，不会跨剧本检索；模长为零时相似度按 0 处理。

模板检索：检索器加后置过滤

PromptTemplateManager.search_similar 走 LlamaIndex 的 as_retriever，取回候选后做两道后置过滤：分数低于 min_similarity_score 的丢弃，metadata.type 不是 prompt_template 的丢弃。top_k 默认 3；min_similarity_score 类默认 0.5，WorkflowNodes 注入 0.7。相似度阈值属于应用层，检索器本身没有默认阈值。参数 include_global 未被使用，检索只在本剧本索引内进行。

两条路径的评分与过滤规则不同：模板路径先取检索器候选再按阈值与类型筛选，内容路径是无阈值的全量余弦排序，两者的分数不宜直接横向比较。

flowchart LR
    subgraph Content[剧本内容检索 query]
        Q1[查询文本] --> Q2[embed_query]
        Q2 --> Q3[遍历 embedding_dict 计算余弦]
        Q3 --> Q4[降序截断 top_k 默认 5]
        Q4 --> Q5[无阈值过滤]
    end
    subgraph Template[模板检索 search_similar]
        T1[查询文本] --> T2[as_retriever 相似度检索]
        T2 --> T3[后置过滤 min_similarity_score]
        T3 --> T4[仅保留 prompt_template 类型]
    end

空结果与索引自愈

检索返回空通常不是阈值问题，而是索引恢复或数据本身的问题。常见原因与处理方式如下。

原因 现象 处理
索引恢复不完整 retrieve() 返回 0 条；from_vector_store 报 Cannot initialize from a vector store that does not store text 用 StorageContext.from_defaults(persist_dir=...) 加载，再以 VectorStoreIndex(nodes=[], storage_context=...) 构造
docstore 文本缺失 有向量但取不到文本 向量、docstore、索引三件套一起恢复，不单独加载向量文件
未传 script_id 返回带 error 的空结果或空列表 调用方检查返回值并补齐剧本 ID
嵌入模型或维度不一致 不报错，分数失真 更换模型后重建索引
库中无数据 结果为空但无异常 确认剧本已入库；长期记忆需先积累达标样本
阈值过高 模板检索无命中 调整 min_similarity_score，或用内容检索查看原始分数

向量文件损坏时，_recreate_vector_store 会把损坏文件备份为 *_corrupted_{时间戳}，清理 docstore.json 与 index_store.json，再重建空存储。损坏前的数据保留在备份文件中，恢复后需要重新入库。

重排序

重排序的实现只有一处：create_retriever_for_script。它支持 similarity 与 mmr 两种检索模式（mmr_threshold=0.6），在触发条件下装配 SentenceTransformerRerank：模型选择链为本地路径、配置名、BAAI/bge-reranker-large，top_n 取 3 与 similarity_top_k 的较小值，以节点后处理器方式挂到检索器上。启用重排序时会用 as_retriever 重建检索器且不携带查询模式，因此 mmr 会被覆盖，两者不能叠加。

状态是“已装配，未生效”：触发条件为 use_rerank or retriever_config.rerank_enabled，而 rerank_enabled 默认为 false；唯一会装配它的 KnowledgeRouter 本身没有生产调用方；生产路径上的 query() 又不读取 use_rerank。仓库内的重排序对照测试脚本传入的同一参数同样不生效，其结果只能反映无重排序的基线。上述三点同时成立才会真正执行重排序。

配置项 默认值 说明
PENSHOT_RETRIEVER__RERANK_ENABLED false 重排序总开关
PENSHOT_RETRIEVER__RERANK_MODEL_NAME BAAI/bge-reranker-large 本地路径不可用时的回退名
PENSHOT_RETRIEVER__RERANK_MODEL_LOCAL_PATH data/models 默认指向父目录；应指向含模型文件的目录
PENSHOT_RETRIEVER__SEARCH_TYPE similarity 检索模式
PENSHOT_RETRIEVER__SIMILARITY_TOP_K 5 初筛候选数

默认路径 data/models 只通过存在性检查，模型文件位于其子目录，加载失败时异常被捕获并降级为无重排序。要让重排序真正生效，需要同时满足：开关打开、本地路径指向模型目录、调用走检索器装配路径而非 query()。交叉编码器输出的是相关性分数，与余弦分数不同口径；接线后若沿用现有阈值，需要重新校准。

提示词增强与工作流集成

增强流程

enhance_prompt(original_prompt, script_id, enhancement_mode) 先处理 none 模式短路，再调用 get_best_match（即 search_similar 取 top_k=1）。命中后按模式拼接：append 为原始提示词在前、追加参考优秀模板段；replace 与 hybrid 走同一个 _merge_prompts，模板在前、原始提示词置后并标注“根据当前片段调整”。两种模式都只是字符串拼接，没有额外融合算法，消化模板的是下游 LLM。未命中时原样返回。

flowchart TD
    A[原始提示词] --> B{enhancement_mode}
    B -->|none| Z[原样返回]
    B -->|其他模式| C[get_best_match top_k=1]
    C --> D{分数达标且类型为 prompt_template}
    D -->|否| Z
    D -->|是| E{拼接模式}
    E -->|append| F[原始在前 追加参考模板]
    E -->|replace 或 hybrid| G[模板在前 原始置后]
    F --> H[增强后提示词]
    G --> H

模板沉淀

质量审计状态为 PASSED 时，节点逐片段调用 save_successful_prompt(fragment_id, prompt_text, quality_score, script_id, additional_metadata)，元数据标记 source=quality_audit_passed。写入经 add_template：超过 2000 字符的模板截断为 1997 字符加省略号，入库前做哈希与全文双重去重，并由 _processing_stack 防止递归重入；模板写入本剧本索引与 templates_cache.json，默认同时写入长期记忆的 successful_prompt_patterns。长期记忆方向只写不读，不会回流模板索引；审计失败不产生任何知识沉淀。

工作流调用点

四个调用点均在 workflow_nodes.py：剧本解析节点入库（add_parsed_script），提示词转换节点增强（enhance_prompt，append 模式），质量审计节点通过后沉淀（save_successful_prompt），连续性守护节点为每个问题检索相似场景（search_similar_scene，top_k=2），命中结果写入问题对象的 historical_solutions，且受 hasattr 守卫。属性名 self.knowledge_manager 的类型就是 PromptTemplateManager，属于历史命名。节点的完整职责见工作流节点，连续性问题的判定逻辑见一致性策略。

持久化与恢复

剧本索引持久化为 default__vector_store.json（兼容读取旧名 vector_store.json）、docstore.json 与 index_store.json；解析结果单独存放在 parsed_results/{script_id}.json；模板库存放在 prompt_templates/{script_id}/ 下的 templates_cache.json 与 index_store/。目录中的 graph_store.json 与 image__vector_store.json 是 LlamaIndex 持久化的空占位，不承载数据。

加载是分层的：构造 ScriptKnowledgeBase 时只扫描剧本目录、把解析结果 JSON 读入内存，向量索引延迟到首次访问时由 _ensure_script_index 从 persist_dir 恢复；模板索引与缓存同样在首次访问该剧本时加载。进程重启后三类文件各自恢复，互不依赖；长期记忆中的模板不会回填模板索引。
