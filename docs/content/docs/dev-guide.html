面向需要修改 PenShot 源码的开发者，覆盖本地环境、项目结构、两级状态机、启动路径，以及新增智能体与提示词模板的扩展方法。

首次安装与运行见 快速开始；SDK、REST 与 MCP 的调用方式见 集成指南。

本地开发环境

PenShot 需要 Python 3.10 及以上版本和可用的 OpenAI 兼容 LLM 密钥。Redis 不是本地开发的硬依赖，只在多进程部署时用于共享任务记录。

git clone https://github.com/neopen/story-shot-agent.git
cd story-shot-agent
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
cp .env.example .env
python -m pytest tests/ -x -q

依赖由 pyproject.toml 管理，仓库没有 requirements.txt。[dev] 附加组包含 pytest、ruff、mypy 等工具；只运行服务时 pip install -e . 即可。配置从 .env 自动加载，最少需要填写 PENSHOT_LLM__DEFAULT__BASE_URL、API_KEY 与 MODEL_NAME，使用 RAG 或记忆功能时再补 PENSHOT_EMBED__DEFAULT__*。

变量组用途
PENSHOT_LLM__DEFAULT__*主模型的 BASE_URL、API_KEY、MODEL_NAME、TEMPERATURE、TIMEOUT
PENSHOT_LLM__FALLBACK__*主模型不可用或重试耗尽后的备用厂商
PENSHOT_EMBED__DEFAULT__*嵌入模型，模板默认 text-embedding-v4、1536 维
PENSHOT_REDIS_*多进程任务记录共享，单进程可省略

变量名使用双下划线表示层级：DEFAULT 是默认 profile，FALLBACK 是备用 profile。密钥也支持 ${ENV_VAR} 间接引用。接入本地 Ollama 时，BASE_URL 通常指向 http://localhost:11434/v1。

api 只做协议适配，SDK、REST 与 MCP 最终都调用同一套任务工厂；app 负责应用组装、生命周期与全局异常；neopen 承载业务，其中 agent/workflow 定义图结构与节点调度，task 定义任务记录、队列与工作线程。新增能力优先落在 neopen，避免在三个接口层分别实现同一段逻辑。

启动路径

三个入口最终都加载 penshot.app:app，启动后提供 /api/v1 路由与 /docs 交互文档。差别集中在参数来源与进程模型。

入口参数与行为
python main.py接受 --host、--port；reload 与 workers 从配置读取，reload 开启时强制 workers=1
python -m penshot.http_server额外接受 --max-concurrent、--queue-size、--reload，通过环境变量传给应用
story-shot-agent serve-restCLI 封装，接受 --host、--port，固定 reload=False
docker run … neotems/penshot容器入口执行 scripts.entrypoint start，再按 PENSHOT_API__HOST 与 PENSHOT_API__PORT 启动 main.py
 
flowchart LR
    A1["python main.py"] --> B["uvicorn / penshot.app:app"]
    A2["python -m penshot.http_server"] --> B
    A3["story-shot-agent serve-rest"] --> B
    A4["docker run / compose"] --> A5["scripts.entrypoint start"]
    A5 --> B
    B --> C["FastAPI lifespan<br/>startup_with_recovery"]
    C --> D["TaskFactory<br/>进程内队列"]
    D --> E["MultiAgentPipeline<br/>10 节点图"]
    E --> F["WorkflowOrchestrator<br/>LangGraph"]
    F --> G["SQLite / 内存检查点"]

任务队列、并发计数与回调都是进程内状态。使用多个 worker 且未配置 Redis 时，提交到进程 A 的任务在进程 B 查询会得到 not_found；启动日志会给出警告。需要横向扩展时配置 PENSHOT_REDIS_URL 或 PENSHOT_REDIS_HOST 等分键。容器同样是单进程模型，多副本部署需共享 Redis 与检查点，详见Docker 部署。

应用启动时，FastAPI lifespan 调用 startup_with_recovery，创建数据目录并尝试恢复未完成任务。检查点由 checkpoint_mode 选择：auto 按环境决定，memory 仅进程内有效，sqlite 与 postgres 支持跨进程恢复。多进程部署除了 Redis，还应固定使用可共享的检查点后端。

CLI 共 8 个子命令：breakdown、batch、status、result、cancel、queue-status、serve、serve-rest。其中 serve 启动 MCP stdio 服务，serve-rest 启动 REST 服务；其余命令直接创建 SDK 实例，适合本地验证单个任务。

两级状态机

任务生命周期由两层状态共同描述：TaskStatus 管理任务生死，共 8 个值；TaskStage 管理阶段进度，共 24 个带权重的中文阶段。任一处理环节失败都会进入 FAILED，不会把半成品当作成功结果返回。

TaskStatus值语义
PENDINGpending已创建，等待调度
PROCESSINGprocessing工作线程执行中
SUCCESSsuccess成功终态
FAILEDfailed失败终态
CANCELLEDcancelled取消终态
NOT_FOUNDnot_found任务不存在
TIMEOUTtimeout等待结果超时
UNKNOWNunknown未知状态
 
stateDiagram-v2
    [*] --> PENDING: 提交任务（TaskFactory.submit）
    PENDING --> PROCESSING: 队列调度到工作线程
    PENDING --> CANCELLED: 排队期间取消
    PROCESSING --> SUCCESS: 工作流执行完成
    PROCESSING --> FAILED: 节点失败或未捕获异常
    PROCESSING --> CANCELLED: 执行期间取消
    SUCCESS --> [*]
    FAILED --> [*]
    CANCELLED --> [*]

成功终态的字面量是 success，不存在 COMPLETED。completed 只出现在阶段明细 stages_progress[*].status 中，表示某个阶段完成，不能用于判断任务终态。

TaskStage 每个阶段包含 code、中文名与 0–100 的权重，权重用于估算总进度。init、processing、error_handling 的权重为 0，其余阶段按处理顺序递增。

阶段组阶段代码权重
剧本解析parsing_start / parsing_script / parsing_complete0 / 10 / 15
镜头拆分segment_start / segmenting / segment_complete15 / 25 / 30
视频分段split_start / splitting / split_complete30 / 45 / 50
提示词转换convert_start / converting / convert_complete50 / 65 / 70
质量审查audit_start / auditing / audit_complete70 / 80 / 85
连续性检查continuity_start / continuity_checking / continuity_complete85 / 92 / 95
输出output_start / output_generating / complete95 / 98 / 100

GET /api/v1/status/{task_id} 返回的 current_stage、stage_name、progress 与 stages_progress 来自这套阶段体系。单个阶段还有 pending、processing、completed、failed 四个子状态，用于驱动前端进度条。

提交任务时，TaskFactory.submit 先创建任务记录并置为 PENDING，再异步入队；工作线程取出后改为 PROCESSING，各节点在执行前后写入阶段明细。取消接口只对未进入终态的任务生效，对已结束任务返回 400。等待超时只影响调用方，不会自动终止后台工作流，因此 wait_for_result 可能返回 None，而任务仍在继续执行。

阶段权重是进度估算值，不是耗时比例。一个 10 权重单位的阶段可能很快完成，也可能长时间停在某个中间百分比；progress 只能用于展示，不能用作剩余时间预测。

工作流装配

核心流水线由 MultiAgentPipeline 构建，LangGraph 图中注册了 10 个节点：parse_script、segment_shot、split_video、convert_prompt、audit_quality、continuity_check、loop_check、human_intervention、error_handler、generate_output。

WorkflowOrchestrator 只负责结构定义：add_node(name, node) 注册接收并返回 WorkflowState 的 callable，add_edge 定义固定流转，add_conditional_edge(source, condition, mapping) 按决策函数返回值选择目标。装配顺序为 build(state_schema=WorkflowState)、validate()、compile(checkpointer=saver)；入口固定为 parse_script，终点为 END。

条件边使用 7 个决策状态：success、valid、needs_repair、needs_retry、needs_human、failed、abort。例如质量审查失败会回到 convert_prompt 修复，连续失败则转入 human_intervention 或 error_handler。

loop_check 是统一的重入闸门：拆分、分段、转换成功后先进入循环检查，再按决策结果跳回拆分、分段、转换、审查或继续输出。ShotConfig.max_total_loops 默认 20，按节点最大循环次数之和计算；超限后不再回退上游，转入错误处理或人工干预，避免无限重试。

检查点按 script_id 与 task_id 隔离，保存的是 LangGraph 状态而非最终结果。修改 WorkflowState 结构后，旧检查点可能无法反序列化；开发阶段可切换 checkpoint_mode="memory" 或清理对应检查点目录。多进程部署除 Redis 外，还应确认 checkpoint_mode 指向各进程都能访问的存储。

每个智能体采用“抽象基类 + LLM 实现 + 规则实现 + 工厂”的结构，对外包装类位于 neopen/agent/*_agent.py。当前运行期真正接线了两条降级路径：提示词转换在单片段粒度失败时回退模板转换器，视频分割异常时整镜头回退规则分割。剧本解析的规则校验路径已实现但调用被注释，use_local_rules 属于预留开关，不能当作现成能力。

新增智能体

推荐沿用现有结构，分三步接入。

建立子包。 在 neopen/agent/ 下新增 my_agent/，包含抽象基类、LLM 实现、规则实现、工厂与 Pydantic 模型。基类继承 BaseAgent（纯规则）或 BaseLLMAgent（带 LLM 重试与缓存接口）。

from penshot.neopen.agent.base_agent import BaseAgent

class MyBaseAgent(BaseAgent):
    def process(self, *args, **kwargs):
        raise NotImplementedError

声明状态与节点方法。 WorkflowState 由 InputState、DomainState、ExecutionState、ErrorState、ConfigState、OutputState 组合而成，新字段写入对应嵌套模型。节点方法放在 WorkflowNodes，签名统一为接收并返回 WorkflowState。

def my_node(self, state: WorkflowState) -> WorkflowState:
    state.domain.my_results = self.my_agent.process(state.domain.parsed_script)
    return state

注册到编排图。 在 _init_agents 中构造智能体并传入 WorkflowNodes，再在 _build_workflow 中挂节点与条件边。

orchestrator.add_node(
    "my_node",
    lambda graph_state: self.workflow_nodes.my_node(graph_state)
)
orchestrator.add_conditional_edge(
    "my_node",
    lambda graph_state: self.decision_funcs.decide_after_my_node(graph_state),
    {
        PipelineState.SUCCESS: PipelineNode.CONVERT_PROMPT.value,
        PipelineState.NEEDS_RETRY: "my_node",
        PipelineState.FAILED: PipelineNode.ERROR_HANDLER.value,
    }
)

节点方法不要吞掉异常：可恢复的问题写入 ExecutionState 的错误列表并返回修复状态，不可恢复的异常交给 error_handler。否则条件边拿到未知状态，图会在运行时中断。新增智能体后，至少补一个 tests/unit 用例，覆盖正常输入、空输入与 LLM 失败回退。

新增提示词模板

模板位于 neopen/prompts/v1.x/zh/，英文版本放在 v1.x/en/，每个智能体一个 YAML 文件。顶层固定 version 与 changelog，每个模板段落由 name、description、template 三个字段组成。

version: "1.3"
changelog: |
  - 2026-03-30: 添加 history_hint 参数
my_agent_system:
  name: "my_agent_prompt"
  description: "自定义智能体系统提示词"
  template: |
    输出 JSON，结构如下：
    {{ "items": [] }}
    输入剧本：{input}

模板渲染走 Python .format()：占位符使用单大括号，字面量大括号必须双写 {{ }}。读取入口是 PromptManager.get_prompt(name) 与 get_name_prompt(name)，内部按“版本 + 语言”定位文件，支持剥离 _prompt 后缀匹配，并带最多 1024 条的进程内缓存。全局管理器默认 version="v1.x"；v2.x 目录存在但为空，不能视为已启用的模板体系。

匹配顺序是：缓存键名、name 字段、去掉 _prompt 后缀后的名称。模板名不存在时抛出 KeyError，不会静默返回空字符串。模板按语言目录分别查找，不存在跨语言回退；新增模板后应同时补中文与英文两份，否则切换 ShotLanguage 时会因找不到模板而抛出 KeyError。

新增智能体时通常需要同步三处：智能体构造函数、WorkflowNodes 的依赖注入、以及 YAML 中对应的模板键。只加模板不加调用代码不会生效；只加代码不补模板，第一次 LLM 调用就会因找不到模板失败。

调试

日志级别与格式在 config/logging.yaml 中配置。业务代码直接导入模块级函数，不需要也不存在 set_level 这个模块函数。

from penshot.logger import debug, info, warning, error, log_with_context, log_performance

info("开始调试")
log_with_context("INFO", "带上下文的日志", {"task_id": "TSK001"})
log_performance("parse_script", 1234.5)

单跑流水线需要先准备 ShotConfig 与 TaskManager，再构造 MultiAgentPipeline。调试单个节点时，可直接构造 WorkflowState 并调用 WorkflowNodes 的方法，避免重复跑完整条链。

from penshot.neopen.agent.workflow.workflow_pipeline import MultiAgentPipeline

pipeline = MultiAgentPipeline(
    script_id="debug-001",
    task_id="TSK-DEBUG-001",
    config=shot_config,
    task_manager=task_manager,
)
result = await pipeline.run_process(raw_script, shot_config)
现象排查方向
任务长期停留在 pending并发已满导致排队；或提交与查询不在同一进程
多 worker 下查询 not_found未配置 Redis，任务记录没有跨进程共享
提示词被截断ShotConfig.max_prompt_length 默认 200；触发判断与截断动作的计数口径不一致
道具信息丢失检查 GlobalMetadata.key_props 及解析、拆分、转换各阶段的传递
模型切换无效同时核对 BASE_URL、API_KEY 与 MODEL_NAME 是否属于同一厂商

不依赖 LLM 的调试优先使用 tests/unit 下的单元测试与 mock；需要可运行场景时，从 examples/sdk/01 至 07 中选择最小示例。仓库没有 penshot.agent.mock_data 一类的模拟数据模块。
