## 2. P0（三条全做）

### 任务 1：资产“声明 + 回填”闭环（不做生成）

#### 1a. 默认路径边界收口（前置，风险最低）

**现状**：`workflow_nodes.py:177` 用无参 `AssetGeneratorAgent()`；`asset_generator_agent.py:245-263` 会惰性调用 `get_default_image_client()`。只要环境里配置了文生图供应商，默认工作流就会真实生图——违反边界 §8 规则 2（边界文档:178）。

**要做**：

- `AssetGeneratorAgent` 增加 `enable_execution: bool = False`：
  - 显式注入 `execution_adapter` / `image_client` 时照常启用（显式即 opt-in）；
  - 未显式注入且 `enable_execution=False` 时，`execution_adapter` 恒为 `None`，**不得调用** `get_default_image_client()`；
  - `_provider()` 不再通过会触发惰性解析的 `image_client` 属性取值。
- 工作流节点保持无参构造，不传 `enable_execution`。
- 新增测试：monkeypatch `get_default_image_client` 为抛错，跑默认 `generate_assets` 应正常返回 `mode="plan"`、全部 `pending`。

**边界说明**：这是把 0.5 M0.5.0.0 的“默认路径不实例化客户端”提前落到 0.4.5；`execution_adapter.py` 整体移除仍留给 0.5，避免 0.4.5 范围膨胀。

#### 1b. 回填模板与校验脚本

**现状**：回填机制已存在（`AssetManifest`、`_apply_manifest`、SDK/REST 入参、文档 §4），但没有“从 asset_plan 生成模板”“校验填好的清单”的工具，用户只能手写 JSON。

**要做**：新增 `scripts/asset_manifest_tool.py`，三个子命令：

- `template <asset_plan.json> [-o manifest.json]`：为每个 `asset_id` 生成空 `bindings` 骨架，带 `schema_version`、`task_id`、`asset_id_map: {}`；
- `validate <asset_plan.json> <manifest.json>`：校验 `asset_id` 必须存在于 plan、不得重复、`asset_ref` 非空（本地路径存在或 `http(s)://` 开头）、失败项必须带 `error`；有错误退出码非 0；
- `apply <asset_plan.json> <manifest.json> [-o asset_plan_filled.json]`：离线把 `asset_ref` 与 `status="generated"` 写回 plan 副本，供无 LLM 环境验证 AC（不替代工作流消费 manifest）。

脚本只读 plan、只写显式输出文件，默认不修改输入。

**注意**：代码状态枚举是 `AssetStatus.GENERATED = "generated"`（`asset_models.py:34-40`），**不是** v1 写的 `"ready"`。

**实现口径（2026-11-12 落盘）**：

- 空绑定（无 `asset_ref` 也无 `error`）默认视为“待回填”，记 warning 并计入 `missing`，不算错误；`validate`/`apply` 加 `--strict` 后要求计划内每个资产都有成功引用或失败原因。这样“只填 `char_001`、`scene_001`”可按验收通过，同时保留发布前全量核对手段。
- 仍属错误的：`asset_id` 不存在、重复绑定、`asset_ref` 本地文件不存在且非 `http(s)://`、`schema_version` 与 plan 不一致、空清单。
- `apply` 与工作流 `_apply_manifest` 同口径：跳过 `skipped`，成功写 `generated` + `asset_ref` + `metadata`（provider/model/checksum/seed/revision），失败项（有 error 无 ref）写 `failed`；输出路径与任一输入相同直接拒绝。
- 默认输出：`template` → 计划同目录 `asset_plan.manifest.template.json`；`apply` → `asset_plan_filled.json`。
- 离线回放（样本 9 资产）：模板 9 条；填 `char_001`/`scene_001` 后 `validate` 退出 0（已绑定 2、待回填 7）；`apply` 产物两项 `generated`、其余 `pending`；以同一 manifest 走 `generate_assets(plan=...)` 得 `mode=manifest`、`manifest_applied=2`、`generated=2`、`pending=7`。

**验收**：首跑产物生成模板；为 `char_001`、`scene_001` 填入合法 `asset_ref` 后，`validate` 通过；`apply` 产物中两者 `status="generated"` 且 `asset_ref` 非空；带同一 manifest 重跑工作流时 `report.mode="manifest"`、`manifest_applied>=2`。

### 任务 2：服装歧义消解与完整性校验

**现状修正**：0.4.4 已做到“结构化 `character_outfits` 优先”，本机样本的 `char_002/char_003` 提示词也确实来自 outfit；问题在于 outfit 文本本身含“A 或 B”，不是“没用上结构化数据”。因此“回退到 character_outfits”不是有效手段。

**要做**：

1. 新增歧义检测（作用于最终 `clothing` 锚点）：中文 `可能/也许/或/或者/之类/等/待定`、英文 `maybe/possibly/or/either/perhaps/unclear`、问号。
2. 歧义时按确定性顺序消解：
   - `style` 字段能唯一指向某个备选（如 style 含该服装名词）→ 取该备选；
   - 两个备选中只有一个命中 `GARMENT_NOUNS` 服装名词表 → 取命中的那个；
   - 仍无法区分 → **取阅读顺序第一个备选**，把其余备选写入 `metadata.outfit_alternatives`；
3. 任何消解结果都写 `metadata.outfit_resolution`（`style_match` / `garment_match` / `first_alternative` / `none`）；非 `style_match`/`garment_match` 时置 `requires_special_attention: true`，并在 `metadata.attention_reason` 写明。
4. 完整性兜底：最终 `clothing` 仍无服装名词时，用 `color + material + style` 组合出最小描述；仍为空则保留原文并标记待确认。
5. 人类可用既有 `asset_prompt_edits` 覆盖误判，不新增编辑通道。

**验收**：

- `char_002` 提示词变为“浅色连衣裙”（或套装，取决于消解结果），`char_003` 变为“运动背心配运动短裤”；两者均不含“或/可能/之类”；
- 两者 `metadata.requires_special_attention=true` 且 `outfit_alternatives` 非空；
- 李明（无歧义）不产生该标记；
- 新增单测覆盖：结构化 outfit 歧义、自由文本歧义、style 可判定、无歧义四种路径。

> **待确认（默认执行 A）**：当 style/名词表都无法判定时，是否接受“取第一个备选 + 标待确认”？选项 B 是“保留原文并标待确认，放宽‘不得含或’的 AC”。若无异议，按 A 执行。

### 任务 3：`asset_plan.style_anchor` 与片段风格同源

**根因**：`AssetGeneratorAgent.plan_assets` 直接 `dict(contract.style_anchor)`（`asset_generator_agent.py:295`），原样带出旧 `description`；而片段风格在渲染时由 `build_style_text(anchor, provenance)` 消解冲突（`style_anchors.py:730-789`），不会回写 anchor。

**要做**：

- 新增内部函数（如 `_resolve_plan_style_anchor(contract)`）：
  - 复制 `contract.style_anchor`；
  - 用 `build_style_text(anchor, provenance_copy)` 得到与片段同源的风格文本；
  - 用该文本覆盖 `description`；无风格文本时删除 `description`；
  - 不修改 `contract` 本身，不新增字段契约。
- `plan_assets` 改用该函数产出的字典。
- 保持其余键（`genre`、维度、`title`、`atmosphere`、`source_notes`）不变，避免无关行为变化。

**验收**：

- 样本重放后 `asset_plan.style_anchor.description` 不含 `muted colors`、`melancholic tone`；
- 该字段与 13 个片段的 `[Style: ...]` 内容完全一致；
- `asset_plan` 的 9 个 `image_prompt` 仍不含旧氛围短语（道具/场景已同源，回归即可）；
- 单测：旧 description 与维度冲突时被消解；无冲突时 description 保留。

## 3. P1（按顺序执行，不阻塞发布）

### 任务 4：`usage.fragments` 与引用同步精确化

**根因（两处）**：

1. `image_to_video.py:264-276` 把 scene 内 `appears_in` 的道具整体作为 `prop_names` 传入，`first_frame_builder.py:278-281` 只判断“在允许集合里”，不再看文本；
2. `backfill_usage` 对道具按 `appears_in` 场景全量回填（`asset_generator_agent.py:197-199`），再把 route refs 强制并入（:203-205）。

**要做**：

- 在 `first_frame_builder` 统一匹配谓词：`owner_name in text AND (allowed_props is None or owner_name in allowed_props)`；`text = fragment.description + prompt.prompt`（保留中文描述，现有样本靠中文命中“便利贴”）。
- `backfill_usage` 对道具使用同一谓词；`referenced` 并入前也过滤。
- 维持不变量：`route refs ⊆ usage.fragments`；若过滤后为空，不写该道具。
- 不改变角色/场景的既有口径（按主角色、按场景地点）。

**验收**：

- 样本中 `prop_001`、`prop_003` 的 `usage.fragments` 均不含 `frag_012`；
- `frag_012` 的 `references` 不含 `prop_001`、`prop_003`；
- `frag_013` 仍保留 `prop_001`（中文描述含“便利贴”）；
- 新单测覆盖：同场景未提及、英文同义词不误判、引用子集不变量。

**实现口径（2026-11-12 落盘）**：

- `build_package_references`：道具改为 `owner_name in text` **且**（`prop_names` 存在时）`owner_name in prop_names`；`text = fragment.description + prompt.prompt`。
- `backfill_usage` 新增可选 `instructions` 入参，从 `instructions.fragments[].prompt` 取提示词正文与描述合并为行文本；道具 usage 要求 `scene_id ∈ appears_in` 且 `owner_name ∈ text`；`route_plan` 引用并入前对道具套同一判定，过时引用丢弃（角色/场景口径不变）。
- 工作流节点 `_backfill_asset_plan` 传入 `state.domain.instructions`。
- 样本回放（13 片段）：`prop_001 usage=[frag_006..008, frag_013]`、`prop_003 usage=[frag_009, frag_010]`，均不含 `frag_012`；`frag_012 refs` 仅 `char_001, scene_003`；`frag_013 refs` 保留 `prop_001`；全片段 `refs ⊆ usage` 不变量成立。
- 新增单测：同场景未提及排除、提示词正文命中、英文同义词（movie ticket）不误判、过时道具引用丢弃、合法引用并入 + 不变量。

### 任务 5：`camera.motion` 与最终提示词一致

**现状修正**：v1 声称 frag_013 为 `static`，样本实际为 `zoom`；真实缺陷是“拉远/回拉”被归为 zoom，且 `_MOTION_KEYWORDS` 缺 `push-in/pull-back/tracking` 等常见表述（`camera_builder.py:125-133`）。

**要做**：

- 扩展运动词表：`DOLLY` 增加 `push in / push-in / pull back / pull-back / dolly in / dolly out / tracking`；保留既有中文映射，避免无关变更。
- 匹配顺序改为“多词具体短语优先于单词”，保证 `slow pull-back` 命中 DOLLY 而不是被 “zoom” 类词截胡。
- 当同一提示词命中多个运动族时，保留优先级最高者并 `warning` 记录冲突词。
- 在 `CameraControl` 构建后增加一致性自检：`motion=static` 但文本明显含运动动词时，记 warning（不静默）。

**验收**：

- 单测：`slow push-in` → DOLLY；`slow pull-back` → DOLLY；纯静态描述 → STATIC；
- 样本 `frag_013.camera.motion` 由 `zoom` 变为 `dolly`；
- 无新增误报（原 `pan/tilt/handheld/zoom` 用例保持不变）。

**实现口径（2026-11-12 落盘）**：

- `_MOTION_KEYWORDS[DOLLY]` 增 `dolly in/out`、`push in`、`push-in`、`pull back`、`pull-back`、`tracking shot`、`tracking`；中文映射保持原样。
- 匹配改为“收集全部命中 → 按（词数, 长度）取最具体者”，同分按词表顺序；命中多个运动族时 `warning` 记录冲突词。
- 新增 static 自检：文本含 `camera move/follow/push/pull/track`、`镜头移动/跟随`、`运镜` 等未入表动词时告警。
- 样本回放：仅 `frag_013` 由 `zoom` 变为 `dolly`，其余 12 个片段 motion 与 0.4.4 完全一致。
- 新增 8 条单测（push-in/pull-back/tracking/短语优先/中文映射不变/纯静态/冲突告警/static 自检）。
