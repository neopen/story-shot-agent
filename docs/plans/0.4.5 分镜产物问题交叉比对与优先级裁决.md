## 1. 三方交集问题（第一优先级，P0）

以下问题**至少两方提出，且经 0.4.5 产物核实仍然存在**。按“提出方数量 × 对成片影响”排序。

### P0-1 道具资产引用错配（纸条未关联、红围巾过度引用）

| 来源  | 表述                                                         |
| ----- | ------------------------------------------------------------ |
| **Y** | `prop_001`（纸条）`usage.fragments` 为空；`prop_002`（红围巾）关联 7 个片段，承担了纸条之外的道具引用职责 |
| **A** | 明确指出“`prop_001` 必须关联 frag_001/002/006/007/010；`prop_002` 只关联真正需要独立道具参考的镜头”；纸条在 frag_007 应从“皱”变“团”，需道具状态变化 |
| **B** | 未提出（只提“文字渲染风险”，未查 `usage.fragments`）         |

**0.4.5 核实**：仍存在。`prop_001.usage.fragments = []`，`prop_002.usage.fragments = [frag_001,002,005,006,007,008,010]`。

**裁决**：**P0，必须修**。纸条是核心叙事道具，未进资产体系意味着下游 I2V 无法绑定纸条参考图，frag_007 的“揉成团”状态变化也无从表达。

**修复建议**：
1. `prop_001` 关联 `frag_001/002/006/007/010`。
2. `prop_002` 收敛到真正需要独立围巾参考的镜头（建议仅 `frag_007` 的围巾飘动特写）。
3. 为 `prop_001` 增加 `state_variants: [{state: "crumpled", fragments: [001,002,006]}, {state: "balled", fragments: [007,010]}]`。

### P0-2 首帧提示词混入动作序列（非静态截面）

| 来源  | 表述                                                         |
| ----- | ------------------------------------------------------------ |
| **Y** | 上一轮已指出：`image_prompt` 应只保留视觉元素；0.4.5 的 T-009 清除了音频事件，但**未拆分动作序列** |
| **A** | P0 明确指出 frag_008、frag_010 的 `image_prompt` 包含“列车进站→开门→空车厢”“登车→回头→关门→驶离→渐黑”，建议拆分 `First Frame Prompt` / `Motion Prompt` / `End Frame` |
| **B** | 未直接指出，但其“先生成静态首帧再驱动”的建议**以首帧合格为前提**，而当前首帧不合格 |

**0.4.5 核实**：仍存在。frag_008 `image_prompt` = “列车头灯从隧道深处的黑暗中亮起, 光芒逐渐增强, 列车缓缓驶入站台, 车门打开, 车厢内空无一人…”。

**裁决**：**P0，必须修**。这是 A 和 Y 共同指向的结构性问题，且 B 的 I2V 工作流依赖它。

**修复建议**：
1. `image_prompt` 只保留**动作开始前**的静态画面（人物位置、姿态、场景、构图、光照）。
2. 新增 `motion_prompt` 字段承载动作序列。
3. 新增可选 `end_frame_prompt`（仅当目标模型支持首尾帧时下发）。
4. 验收：`image_prompt` 中不得出现“驶入、打开、回头、关门、渐黑”等时间序列动词。

### P0-3 资产全部 pending、`asset_ref` 为空（计划 ≠ 可执行）

| 来源  | 表述                                                         |
| ----- | ------------------------------------------------------------ |
| **Y** | 0.4.5 产物 `asset_ref` 全空、`status` 全 pending；但 0.4.5 Non-Goals 明确不接入生成 API，属范围外 |
| **A** | P0 明确指出“当前 JSON 只能证明生成了资产引用计划，不能证明实际使用了参考资产”；建议增加 `planned → generated → validated → bound → consumed` 生命周期 + 执行前硬检查 |
| **B** | 未检查，**默认资产可用**并直接建议 I2V 工作流——这是 B 的事实性遗漏 |

**0.4.5 核实**：仍存在。全部 `status: "pending"`，`asset_ref: ""`。

**裁决**：**P0，但归属 0.5 而非 0.4.x**。0.4.5 的 Non-Goals 已排除生成能力，这是**范围决策**而非缺陷。但 A 的“生命周期 + 执行前硬检查”建议应写入 0.5 spec。

**修复建议**：
1. 0.4.x 内：在 `asset_plan` 输出时增加 `executable: false` 与 `blocking_assets: [...]`，**如实告知下游不可直接执行**，避免 B 类使用者误用。
2. 0.5：引入 `Asset Resolver` + `validate_video_task()` 硬检查。

### P0-4 质量检查全部为空（无 warnings、无 attention）

| 来源  | 表述                                                         |
| ----- | ------------------------------------------------------------ |

## 3. 仅一方提出、但经核实成立的问题（P1/P2）

## 7. 一句话结论

**三方交集里真正需要立刻修的是 P0-1（道具错配）、P0-2（首帧动作序列）、P0-4（质检全空）三项**——它们同时被你和 A 指出、经 0.4.5 产物核实仍存在、且 0.4.x 范围内可修。P0-3（资产 pending）虽是 P0 但属 0.5 范围，0.4.x 只能如实标注 `executable: false`。**第三方 B 的乐观评价需以这三项 P0 的存在为前提做校正，其 I2V 工作流建议在 P0-2 修复前不可直接落地。**
