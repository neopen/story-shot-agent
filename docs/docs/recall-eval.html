评测概述：从评测报告到源码考证

为什么要评测召回系统

召回系统是 PenShot 智能增强层的核心组件，负责从历史成功案例和知识库中检索相关信息，以增强当前任务的处理质量。它的好坏直接决定了提示词增强与连续性验证的成效。本文围绕三个核心能力展开考察：向量检索的实现与效率边界、重排序对检索结果的优化效果、以及三层记忆系统在不同查询场景下的表现。

写在前面：本文的三条考察纪律

先说明本文的性质：这是一篇"源码考证 + 真机数据实测"文章，而非一份跑过完整基准的评测报告。项目当前没有积累任何真实的召回评测数据（原因见后文），因此本文坚持三条纪律：所有代码结论以源码为准、可回查；所有数据要么可复现、要么明确标注属性，真机证据与理论分析分开陈述；宁可指出项目当前实现的不足，也不为了"显得高级"而堆砌概念。

三个真实发现（先给结论，细节见下文）

  • 选型长期被误传：真机日志与 .env 显示，PenShot 的嵌入模型是阿里云 DashScope 的 text-embedding-v4（1536 维），备用链路为本地 Ollama 的 bge-large-zh-v1.5——并非配置模型类里那个从未生效的默认值；

  • 长期记忆真机空库：三个真实剧本的 Chroma 集合文档数均为 0——长期记忆的写入需要穿过"成功案例判定"门槛，现有样本尚未积累起可检索数据；

  • 评测脚本自带哑参数：项目内唯一的"重排序对照测试"传入的 use_rerank 参数从未被实现读取，无论怎么调都会输出"重排序无效"——直接照搬会得出完全错误的结论。

有两个被广泛误传的点需要纠正：

1）嵌入模型不是 bge-small-en。日志给出了直接证据——使用AI提供商: ClientType.QWEN, 嵌入模型: text-embedding-v4；"768 维"的说法同样无从谈起。而且这里还埋着一个更有意思的偏差：.env 中配置的维度是 1536，但真机向量存储里实测落盘的维度是 1024。对照阿里云官方文档可知，1024 恰好是 text-embedding-v4 的默认输出维度（该模型支持 2048/1536/1024 多档）——也就是说，配置里的 dimensions 参数并没有生效，模型按自己的默认值输出了 1024 维。这个偏差不会报任何错，却是一个真实隐患：任何按"1536 维"假设处理数据的代码都会错位，未来若按配置重建索引，新旧向量也无法混用。

2）重排序模型不是任何"base"版本。真机下载的是 BAAI/bge-reranker-large（data/models/bge-reranker-large/，权重文件约 2.1 GB），且它当前并未接入检索链路（详见《重排序》专题考证，此处不展开）。

三条事实要点：

  • 记忆链路是三套存储分工：短期走 Redis、中期走 JSON 摘要、长期走 Chroma——不是单一"文件系统"；

真机数据实况：data/embedding/ 下实际只有两份脚本知识库（12 条与 2 条记录），data/memory/ 下有三个剧本的记忆目录——其中长期记忆 Chroma 集合的文档数经 SQLite 核验全部为 0，中期摘要则有 2026-05-05 至 07-23 期间的多份按小时快照。"数千个向量文档"的评测口径在真机数据中并不存在，这也是本文无法给出真实召回率指标的根本原因。

关键要点拆解（一）：向量检索的实现与边界

相似度检索

先给出源码层面的结论：PenShot 里的"相似度检索"存在两条实现路径，理解它们的差异比任何跑分数字都重要。

生产路径一：search_similar（提示词模板检索）。走标准 LlamaIndex 检索：as_retriever(similarity_top_k=top_k, retriever_mode="similarity") 取回结果后，用 score < min_score 过滤低分项，再用 metadata.type == "prompt_template" 过滤类型。min_score 的默认值来自构造参数——workflow_nodes.py 实例化模板管理器时传入了 min_similarity_score=0.7, top_k=3，即生产环境的"及格线"是余弦相似度 0.7。

生产路径二：query()（场景相似检索）。这条路径没有走 LlamaIndex 的检索器，而是手动实现余弦相似度：查询文本嵌入后，遍历向量存储内的全部文档向量逐一计算、排序、截取 Top-K。源码摘录：

# llama_index_knowledge.py L517-522：手动遍历全量向量计算余弦相似度
for doc_id, embedding in vector_store._data.embedding_dict.items():
    dot = np.dot(query_embedding, embedding)
    norm_q = np.linalg.norm(query_embedding)
    norm_d = np.linalg.norm(embedding)
    similarity = dot / (norm_q * norm_d) if norm_q > 0 and norm_d > 0 else 0

这段实现有两个值得指出的细节：其一，每次查询都是 O(N) 全量线性扫描，没有 HNSW 等 ANN 索引加速，文档量增长到数万条时延迟将随文档数线性增长；其二，norm_q = np.linalg.norm(query_embedding)（查询向量模长）写在了循环体内——每次迭代都重复计算同一个恒定值。12 条记录时这些都无感，但它精确暴露了这段代码的定位：为单剧本小索引写的最简实现，而非可扩展的检索基础设施。

还有一处口径差异：search_similar 有 min_score 及格线过滤，而 query() 没有——只做 Top-K 截取，哪怕全库相似度都不高，也会照常返回最"像"的几条。search_similar_scene 的返回会直接被赋给连续性问题的 historical_solutions 字段（workflow_nodes.py 连续性检查节点），全程没有分数校验环节——这是接线上一个可改进点。

这里补充一条原理说明：余弦相似度衡量的是两个向量在高维空间中的夹角而非距离，取值范围在 -1 到 1 之间，越接近 1 表示方向越一致、语义越接近。相比关键词检索只能做字面命中，余弦相似度通过向量语义匹配，能够理解同义词与改写表达，这正是向量检索"语义召回"能力的基础。

延迟性能方面，本文只能给出基于代码结构的拆解（属性：理论分析，非实测）。一次检索的开销分两段：查询文本的嵌入编码——真机走 DashScope 云端 API，包含网络往返；向量比对计算——纯本地 numpy 运算，1024 维向量单次余弦计算仅数千次浮点乘加，即便数万条文档的线性扫描也在十毫秒量级。换句话说，当前链路真正的延迟大头大概率是嵌入 API 的网络往返，而非向量计算——这与"向量检索慢在计算"的直觉恰好相反，也解释了为什么这类在线嵌入架构需要本地模型缓存或批量嵌入优化。

原始版本中"检索延迟分布"“绝大多数查询在 100 毫秒内完成”"亚秒级响应"之类的描述，在项目日志与代码中找不到任何测量依据——真机索引只有 12 条记录，代码中也没有延迟埋点。这些数字在此撤回。

真机数据实况：脚本知识库的真实规模让"召回率"暂时失去比较意义——样本 A 全库 12 条（4 场景 + 8 角色），样本 B 仅 2 条。在这种规模下查询"角色"主题，返回结果里出现多个角色文档几乎是结构性必然，任何准确率百分比都会被样本量淹没。项目内也不存在标注数据集或评测产物，"角色查询准确率最高、动作序列最低"之类的分类型对比没有数据来源——这也是本文把重心放在机制考证而非指标罗列的根本原因。

MMR检索

MMR 检索在相似度基础上增加了多样性惩罚因子，避免返回语义冗余的结果。但必须先给出它在 PenShot 里的真实状态：已实现装配逻辑、未接线生效。create_retriever_for_script 中存在完整的分支：

# llama_index_knowledge.py L588-593：MMR 分支
if search_type == "mmr":
    retriever = index.as_retriever(
        similarity_top_k=similarity_top_k,
        vector_store_query_mode="mmr",
        mmr_threshold=0.6
    )

两层断裂让它无法生效：其一，create_retriever_for_script 的全部触达路径都没有生产调用方（详见前文接线图的"未接线区"）；其二，生产路径中的 query() 虽然签名带 search_type 参数，函数体却从未读取它——内部只有一条手动余弦相似度的代码路径。因此真机上从未有过一次 MMR 检索真正执行。下文保留原理与调参分析，是因为这个分支一旦接线就会用到；但请把"原理成立"与"已生效"分开看待。

关于 MMR 的公式：它实现在候选集 $D$ 中迭代选取文档，使目标函数

最大化，其中 $S$ 是已选集合。即每一步都在"更贴近查询"与"与已选内容更不重合"之间按 $\lambda$ 权衡，从而既保相关又添多样。

        F["MMR = argmax[ λ·Sim(Q,D) - (1-λ)·max Sim(D, D_j) ]"]
    end

代码中把 MMR 的权衡参数硬编码为 mmr_threshold=0.6——在 LlamaIndex 中该参数即 MMR 公式里的 $\lambda$（相似度与多样性的权衡系数），没有对外开放配置。也就是说，一旦接线启用，系统将固定以偏相关一侧的 0.6 运行。这个取值对提示词模板检索场景是否合适，项目尚无对照数据可依。

从设计意图看，这个能力对提示词模板检索确有价值：若 Top-K 结果全部集中在同一类情感场景（比如全是"愤怒"类模板），融合生成的提示词就容易风格固化；MMR 的多样性惩罚能把不同情绪类型的处理方式纳入候选。但必须再次标注属性：这是设计推演，不是实测结论——项目既没有 MMR 开/关的对照实验，也没有"多样性"指标的定义与测量代码。

排坑提示：MMR 的效果高度依赖 $\lambda$（本项目中即 mmr_threshold）。$\lambda$ 过大会退化成普通相似度检索，$\lambda$ 过小则会牺牲相关性、招回大量低质结果。若业务更看重"覆盖多种方案"，可将 $\lambda$ 适当调低；若追求"精准命中"，应保持较高的 $\lambda$。另外提醒：接线启用 MMR 时建议同步暴露参数配置——硬编码值迟早会遇到"某个场景想调却调不了"的困境。

关键要点拆解（二）：重排序原理与未接线真相

重排序使用专门的模型对初步检索结果进行精细排序：它基于交叉编码器架构，能捕捉查询与文档之间的深层语义交互——这是设计初衷。但在 PenShot 里，它当前并未接入生产链路。先看原理，再看真实状态。

补充架构说明：向量检索使用双编码器（BiEncoder）——查询与文档分别独立编码后再算余弦相似度，速度快但缺乏交互；重排序使用交叉编码器（CrossEncoder）——查询与文档拼接后联合编码，注意力机制让两者 token 相互"看见"对方，精度高但速度慢。因此业界普遍采用"先粗排后精排"的两阶段策略：

真实状态：装配完整，但未接线

create_retriever_for_script 中的重排序装配代码是完整的，三个关键事实逐一考证：

  • 模型路径解析：优先读配置项的 rerank_model_local_path（真机值为 data/models/bge-reranker-large 完整子目录），相对路径自动拼到项目根目录；路径不存在时输出警告并降级为模型名——这可能在不知不觉中触发从 HuggingFace 联网下载约 2.1 GB 权重，而日志里只有一行 warning；

  • 重排序器参数：SentenceTransformerRerank(model=model_to_use, top_n=min(3, similarity_top_k)) 挂入 node_postprocessors——重排序后最多保留 3 条结果，这是硬上限；

  • 日志埋点齐全：成功有 info("重排序已启用...")、失败有 warning("重排序初始化失败...")。

2026-05-21 的日志里确实出现过"重排序已启用"的记录，但复核全链路后发现，那是当天的调试脚本触发的——生产代码中没有任何路径会走到这段装配，RERANK_ENABLED=false 也一直是真机默认（完整考证见《重排序》专题）。

数据撤回：原文声称"重排序后 top-1 准确率由 68% 提升至 86%"，该数字没有任何来源——项目既无重排序实测（模型未接线），也无准确率埋点。同理，“单次重排序耗时是向量检索数倍”“重排序对查询长度敏感”"边界案例改进明显"等描述均无实测依据，一并撤回。

接线前值得审视的设计点

装配代码里还有几个细节，在接线启用前值得提前审视：

  1. 候选数扩大不等于输出数扩大：top_n=min(3, similarity_top_k) 把输出硬限制为 3 条。即便未来把召回候选扩到 10 条，最终仍只留 3 条——扩容只提升"选出好 3 条"的概率；

  2. 两级降级链是静默的：路径不存在→模型名→联网下载，每一级都在不报错的情况下悄悄改变行为；

  3. 模型构造在检索器创建函数内部：每次为该剧本重建检索器都会重新走一遍加载路径。单剧本场景无碍，多剧本高频重建时应考虑模型复用。

关键要点拆解（三）：三层记忆真实机制与失效边界

短期记忆

短期记忆的真实结构是"Redis 优先、内存降级"的双轨制。源码层面的关键事实：

  • 存储选择：初始化时尝试 Redis（RedisChatMessageHistory，key 为 penshot:memory:{session_id}，TTL 3600 秒）；Redis 不可用时降级为带文件持久化的进程内消息历史——2026-05-20 的提交"短期记忆文件持久化（Redis 不可用时）"为此新增了 short_term.json 落盘；

  • 窗口机制：deque(maxlen=20) 滑动窗口，超过 20 条自动淘汰最旧消息；

  • 会话隔离：session_id = f"short_term_{script_id[2:]}"（去掉剧本 ID 的 SN 前缀）。日志考古显示这个方案经历过一次演进：早期日志（5-05）还是 penshot_short_term_{md5} 的全局共享会话，5-15 之后变为"一个剧本一个会话"——隔离粒度从项目级细化到了剧本级；

  • 真机证据：Redis 6379 端口探测可达（db 1），日志有"Redis 连接成功"记录，且 data/memory/ 下不存在 short_term.json——说明真机一直走 Redis 主路径，文件降级通道备而未用。

从"评测"视角看短期记忆，有两个值得记录的工程细节：

其一，降级链的兑现条件：redis_utils.py 的 RedisClient 在建立连接时会 ping 一次，ping 失败直接抛异常。也就是说，"Redis 不可用时降级文件"并不是自动生效——它依赖调用方捕获初始化异常并切换到文件存储；同时 get_redis_url() 带了 lru_cache(maxsize=1)，运行期修改环境变量不会重新解析 URL（需清缓存或重启进程）。

其二，没有"任务完成即清空"：代码中不存在基于任务完成钩子的清理逻辑，短期窗口只靠两个机制自然滚动——deque 的 20 条上限与 Redis 的 1 小时 TTL。一小时内连续跑多个剧本时，会话残留属于设计内行为；隔离依赖 session_id 的剧本粒度，而不是"用完即清"。

中期记忆

中期记忆基于 LangChain 的摘要链（LLM 摘要 + 中文摘要提示词），把长对话浓缩为摘要后持久化为 JSON。源码层面有两个机制值得细看——一个是设计，一个是缺陷。

设计：滚动摘要的触发逻辑。积压的对话字符数超过阈值（max_token_limit * 4，默认 500 → 2000 字符）时，把新增对话交给 LLM 生成摘要，替换掉原始消息；摘要自身超过另一阈值（max_token_limit * 2 → 1000 字符）时截断。此外，工作流写入层还有一个独立的统计摘要（_calculate_medium_term_summary）：对数值字段计算 avg/min/max/count，并对 completeness_score 做 improving/declining/stable 趋势判定——这不是文本压缩，而是质量仪表盘。

缺陷：读写文件名不一致。这是本次考证中最值得记录的一处静默失效：_persist_to_file 写出的文件名是 medium_summary_{YYYYMMDDHH}.json（按小时分文件），而 _load_from_file 与 clear 操作的却是固定名 medium_summary.json——写入与读取指向两个不同的路径。后果是：中期摘要每次进程重启后都加载不回来，历史摘要永远在磁盘上"沉睡"。真机数据恰好两个面都印证了：data/memory/ 下堆积着 2026-05-05 至 07-23 期间多份按小时快照（写入一直在正常跑），但没有一份会被读取逻辑认领。

顺带记录一个精度问题：len(text) * 4 的"字符当 token"近似是英文经验的移植（约 4 字符 ≈ 1 token）。中文里 1 个汉字就能折合 1 个以上 token，这个近似会系统性低估中文的 token 数——配置里"500 token 上限"的语义在中文场景下是失真的。功能上无害（照样压缩），但参数的含义与文档声明不符。

排坑提示：两句话——其一，持久化的读路径和写路径必须使用同一个文件名约定。这类不一致不会报错、不会告警，只会在重启后表现为"记忆凭空消失"，排查成本极高；其二，中期记忆的 token 上限本质是信息取舍。若任务需要长时间保留细节（如跨幕伏笔），建议引入分层摘要或主题聚类，避免单一摘要"压过头"丢掉关键决策点。

此外，原文称"异步保存、不阻塞主流程"——源码中 save_json_result 是同步调用，没有异步包装。"阶段完成后即时触发写入"这句是准确的，但"异步"属于美化，一并纠正。

长期记忆

长期记忆基于 Chroma（langchain_chroma，每剧本一个 collection，SQLite + HNSW 落地）。但真机数据给出了本次考证最意外的一个事实：三个真实剧本的长期记忆集合，文档数全部为 0。

写入路径的机制是这样的：工作流每个阶段完成后，WorkflowMemory.after_stage_completion 会评估该阶段结果是否构成"成功案例"（_is_successful_case——如 parse_script 阶段要求 completeness_score >= 0.8），通过才生成长期记忆条目（格式为"[阶段] 执行完成 + 统计 + 场景/角色/镜头摘要"，限 2000 字符、保留最近 30 条成功模式），经增强文本后写入 Chroma。检索侧用 similarity_search_with_score 并按 score >= 0.7 过滤、long_term_k=3 取前 3 条。

也就是说，长期记忆是一个"全靠成功样本喂养"的冷启动系统：样本不够成功，它就一直是空的。空库状态下的检索不会报错——它安静地返回零条结果，任何依赖"历史经验"增强的逻辑都会静默退化为"没有经验可用"。这类失效没有任何告警，是记忆系统最需要监控的指标（本仓库中没有任何此类监控）。

原始版本中的两段"检索测试"描述——“成功召回相似角色的服装描述和位置轨迹”“镜头时长超限问题的多种分割策略”——在空库事实下全部不成立，予以撤回。这两个场景在机制上确实存在（长期记忆按 0.7 阈值检索后注入上下文），但真机数据里没有任何一条记录支撑"成功召回"。

真正值得记录的是空库的成因链条：写入需要穿过成功案例判定，而判定依赖 completeness_score 等质量指标；如果运行中的任务尚未积累出达标样本，或者达标阶段的写入链条存在断点，库就会长期为空。验证方法很简单——直接查 chroma.sqlite3 的 embeddings 计数（本文的核验就是这样做的），而不是看代码里"有没有写入逻辑"。

另外，"批量索引策略"的描述也与源码不符：长期记忆写入是阶段完成即触发的单条即时写入（add 逐条落库），没有任何批处理队列。真实存在的规模约束是两个裁剪上限——写入中期记忆时统计摘要最多 20 条、写入长期记忆时成功模式最多 30 条（patterns[-30:]）——它们约束的是写入内容的规模，而非写入时机。

排坑提示：长期记忆有两个"不报警的坑"。其一，查询与写入必须使用同一套嵌入模型与维度，否则召回静默失效——真机正是这个风险的活例：配置声明 1536 维、实际落盘 1024 维，任何按配置硬编码维度的处理代码都会错位；其二，空库不是错误：写入门槛未达标时系统一切"正常"，检索只是安静地返回零结果。给长期记忆加一个"集合文档数"监控，比任何检索日志都更能提前暴露问题。

关键要点拆解（四）：混合检索与缓存真相

混合检索策略

原始版本把混合检索描述成"加权合并"——源码里并非如此。真实的实现位于 llama_index_router.py 的 _hybrid_search：把向量检索、记忆检索、结构化查询三路结果直接合并，按各自的 score 排序，再用"前 100 字符"作去重键过滤，最后截取 top_k。全程没有任何权重系数——流传的 0.6/0.4/0.3 权重在代码里不存在。

三个来自源码的细节值得记录：

  • 去重键的颗粒度很粗：content[:100] 前 100 字符相同即视为重复——对结构相似的模板文本可能误判；

  • 结构化结果的分数是硬编码的 0.9（写死），在按分排序的合并里会恒定压制大多数真实分值的向量结果（余弦相似度通常落在 0.5-0.8 区间）；

  • 作者自己标注了简化：create_hybrid_retriever 的注释写着"目前简化实现……未来可以扩展支持真正的混合索引"。

更关键的是接线状态：整个 KnowledgeRouter 在生产代码里没有任何实例化点——它的全部引用都位于自己的文件内，"混合检索同时从多源获取信息、质量评分更高"之类的结论既无接线支撑、也无评测数据支撑，一并撤回。真正在生产链路上执行提示词增强的是 enhance_prompt → search_similar 这条链（见下一节的影响链考证）。

排坑提示：混合检索最容易被忽视的不是"权重调不好"，而是分数量纲不统一——本实现干脆放弃了加权，直接按原始分排序。当三路分数量纲差异大（余弦分数 0.5-0.8 vs 硬编码 0.9 vs 记忆侧分数）时，“排序"实际上是对结构化结果的无条件优先。若要真正启用这套混合检索，第一步应该是给三路分数做归一化或引入可配置权重，而不是照搬某个"经验权重表”。

原始版本关于"查询延迟是各来源最大值 + 融合开销"的描述属于推测性美化——融合逻辑本身就是内存里的列表合并与排序，开销可忽略；真正的成本大头仍是各路的嵌入/检索调用。但必须强调：这段逻辑当前没有任何生产流量，讨论其延迟没有实测意义。

缓存机制的真实形态

先把结论放前面：PenShot 没有任何检索结果缓存。真机代码里能找到的缓存只有两处，都与"加速检索"无关：

缓存 位置 默认状态 真实作用
模板列表缓存 PromptTemplateManager._caches 启用（上限 200） 服务模板去重（hash + 文本比对），不是检索加速
LLM 响应缓存 base_llm_agent 默认关闭 相同提示词的 LLM 调用复用（TTL 300 秒），需显式开启

原始版本中"缓存 TTL 设置为合理值"这类描述无从对应——唯一的 TTL 属于默认关闭的 LLM 缓存。

为什么没做检索缓存？从工程角度看，理由可能是充分且诚实的（作者分析，非项目声明）：当前真机索引只有 2-12 条文档、单剧本场景下每次检索的向量计算开销极小，缓存收益有限；而模板库每次 add_template 都在变化，缓存与写入的一致性成本远高于检索本身的成本。当规模小到不值得缓存时，"没有缓存"就是正确的工程决策——真正需要改变的是这个前提（规模），而不是先堆一个缓存。

反过来说，如果未来要给检索加缓存，最需要注意的不是 LRU 算法选择，而是缓存键的设计：检索依赖"查询文本 + 嵌入模型版本 + 索引内容版本"三者，漏掉任何一项都会产生"更新了数据却命中旧结果"的静默错误——这与前文的中期记忆文件名缺陷、维度偏差属于同一类问题：不报错的错误，才是最贵的错误。

检索缓存不存在，“命中率”"LRU 淘汰"等描述自然无从谈起，一并撤回。 值得校准的是对"缓存"的整体印象：PenShot 并非没有缓存，而是缓存全部集中在写入侧的成本规避（模板去重、LLM 复用），没有放在读取侧的延迟优化——这个取向与其"单剧本小索引"的规模前提是自洽的。技术讨论中常把"缓存命中率"当作系统先进性的指标，但这个案例展示了更朴素的判断标准：缓存收益必须大于一致性成本，否则"不做缓存"就是正确答案。

关键要点拆解（五）：召回对输出的真实影响链

先问一个比指标更重要的问题：召回结果究竟以什么路径影响最终输出？逐条复核调用链后，答案是"两通、一断"。

链路一：提示词增强（已接线）。convert_prompt 节点对每个片段调用 enhance_prompt(fragment.prompt, enhancement_mode="append")（workflow_nodes.py L574-582），内部走 get_best_match → search_similar（top_k=1、min_score=0.7、仅模板类型），命中就把匹配模板拼接进原提示词。这是"召回质量直接影响生成输入"的实链路——它只有一个质量闸门（0.7 分数阈值），过了闸门的内容直接进入提示词。

链路二：连续性检查（已接线）。search_similar_scene 为每个连续性问题检索历史场景方案（top_k=2），填充 historical_solutions。前文已指出这条链没有分数门槛——低质结果也可能被当作"历史方案"。

断点值得单独强调：MemoryManager.recall → MemoryContext.to_prompt（对外封装为 get_context_for_llm）与 WorkflowMemory.restore_context_for_stage 这两条"把记忆读回来注入上下文"的设计链路，全仓库没有生产调用方——记忆的语义检索能力完整实现、却从未接上消费端；真正执行的读取只有初始化时的 _load_common_patterns（把全局模式读出来只打了日志）。这意味着"三层记忆影响生成质量"在真机上尚未成立：写入侧持续运转，读取侧只有键值查询，语义读取是断的。

原始版本还声称"连续性问题的检出率显著提升"，同样没有数据支撑——检索返回的确被用于填充 historical_solutions，但"提升多少"从未被测量，撤回。

原始版本说"召回失败时系统回退到基于规则的默认处理"——源码里没有这样的显式降级分支。真实的"失败形态"是静默的：search_similar 查不到就返回空列表、增强环节原样保留提示词；query() 甚至不会返回空（无分数门槛，永远给出"最像的"几条）。换句话说，召回系统不会报错，它只会安静地少做事或做错事——这也解释了为什么"召回质量"在这类系统里最不容易被及时发现，最需要评测体系来兜底。

从零开始：一套可复现的召回评测方法论

本文反复指出"项目没有任何评测数据"。但发现缺失只是第一步，把评测做起来才是终点。基于本文考证出的真实架构，一套最小可行的评测流程如下——不需要新框架，用项目内现成能力即可：

第一步：构造最小评测集。按查询类型分层取样：角色查询（如"主角是谁"）、场景查询（如"雨夜街道"）、模板查询（如"愤怒情绪的提示词"），每类 10 条，人工标注期望命中的文档。真机索引只有 2-12 条文档，评测集的价值不在于统计显著性，而在于建立可重复的回归基线——更换嵌入模型或阈值后，同一套评测跑出的差异才是可解释的。

第二步：指标分为"健康度"与"效果"两层。健康度优先：空结果率、长期记忆集合文档数、嵌入维度一致性断言——这三项能第一时间暴露前文那类静默失效；效果层再跟上：命中率@K、MRR、首条命中分数分布。

第三步：先验证开关，再做对照。本文最大的教训是"哑参数"——use_rerank/search_type 传了等于没传。任何 A/B 实验开始前，先跑一次"开关有效性验证"：变更参数后打印最终生效的配置（或断言参数被读取），确认旋钮真的连着线。

第四步：从小索引的现实出发设计结论。2-12 条文档的召回实验只能回答"链路是否通"，回答不了"准确率多少"。要得到有价值的数字，需要先灌入几十上百条剧本构建有统计意义的索引——这是评测的前置工程量，无法绕过。

总结与建议

把全文考证压缩成一张"三口径"清单——这是本文最诚实的产出：

已接线（真实生产行为）

  • 相似度检索两条路径：search_similar（0.7 及格线 + 模板类型过滤，经 enhance_prompt 进入生成）与 query()（手写余弦、无分数门槛，用于连续性检查）；

  • 三层记忆写入：短期 Redis（20 条窗口 + 3600s TTL，剧本级 session）、中期 JSON 摘要（写入正常但重启读不回）、长期 Chroma（真机 0 文档）；

  • 提示词增强与连续性检查均在 convert_prompt / 连续性检查节点中真实执行。

已实现未接线（代码完整、无生产调用方）

  • 重排序装配（BGE-reranker-large）、MMR 分支、KnowledgeRouter 混合检索、记忆语义读取（get_context_for_llm / restore_context_for_stage）。

静默失效清单（不报错但行为偏离预期）

  • 长期记忆空库：检索安静返回零结果；

  • 中期摘要读写文件名不一致：重启即"失忆"；

  • 嵌入维度偏差：配置 1536、落盘 1024；

  • 哑参数与无分数门槛：传了不生效、查了不过滤。

三条来自实战的工程建议

  1. 先建测量，再谈指标。“毫秒级”"68%→86%"这类数字之所以能被轻易写下，是因为系统里没有任何测量体系。上召回系统前，先给延迟、空结果率、命中率留好埋点；

  2. 把静默失效当一等公民。空库、维度偏差、文件名不一致、哑参数——这四类问题都不抛异常。为它们建监控（哪怕只是文档计数日志），收益远超调参；

  3. 接一根线、验一根线。重排序、MMR、混合检索、记忆读取都是"看起来有、实际没有"的能力。每次声称"已支持"，用一条端到端调用链测试来证明它。
