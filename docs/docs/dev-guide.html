一、项目概览

1.1 什么是 PenShot？

PenShot（Pen & Shot）是一个基于大语言模型的多智能体协作系统，专门用于将自然语言剧本自动转换为适合AI视频生成的提示词序列。它通过多个专业化智能体的协同工作，完成剧本解析、镜头分割、视频分割、提示词转换和质量审查等全流程任务。

1.2 核心能力

  • 剧本智能解析：支持自然语言剧本、标准格式剧本、AI分镜脚本、纯对话等多种输入格式

  • 智能镜头拆分：基于剧本语义自动生成镜头序列，保持道具和角色一致性

  • 长镜头智能分割：对超过时长阈值的镜头进行智能分割，确保视觉连贯性

  • 双语提示词生成：同时生成英文和原始语言的高质量提示词

  • 音频提示词生成：基于剧本内容生成配套的音频提示词（台词、环境音、旁白）

  • 质量审查：自动审查提示词质量，检测截断、道具不一致等问题

价值定位：面向短剧/短视频/AI 影视创作者与自动化流水线，解决从写完剧本到手工拆镜、再到逐段写提示词这一串高重复度劳动，让创作者把精力放在内容本身。

1.3 技术栈

组件 技术选型 用途
LLM OpenAI 兼容多厂商（openai / qwen / deepseek / ollama） 剧本解析、镜头分割、提示词转换
Embedding text-embedding-v4（模板默认，可换 3-small 等） 语义检索与 RAG 知识库
工作流框架 LangGraph ≥ 1.1.4 多智能体流程编排
API 框架 FastAPI + uvicorn RESTful 服务
协议支持 MCP / A2A 接入 IDE 与跨 Agent 协作
任务与状态 进程内队列 + SQLite 检查点（Redis 可选） 任务调度、断点续传与跨进程共享

说明：.env.example 模板默认使用 OpenAI gpt-4o 与 text-embedding-v4，注释明确系统支持 openai、qwen、deepseek、ollama 四类厂商；LLM__FALLBACK__* 备用段可在主模型不可用时自动回退（模板里是 deepseek-chat）。模型切换方式详见常见问题 Q4。

2.3 任务状态机：任务级生死线与阶段级进度

任务的生命周期由两层状态体系共同刻画：任务级 TaskStatus 管生死，共 8 个值；阶段级 TaskStage 管进度，共 24 个带权重的中文阶段。先看任务级状态机——任一环节失败都会落入 FAILED 终止，杜绝半成品被当作成功结果返回：

stateDiagram-v2
    [*] --> PENDING: 提交任务（TaskFactory.submit）
    PENDING --> PROCESSING: 队列调度到工作线程
    PENDING --> CANCELLED: 排队期间取消
    PROCESSING --> SUCCESS: 工作流执行完成
    PROCESSING --> FAILED: 节点失败或未捕获异常
    PROCESSING --> CANCELLED: 执行期间取消
    SUCCESS --> [*]
    FAILED --> [*]
    CANCELLED --> [*]

源码里的枚举定义如下（节选自 src/penshot/neopen/task/task_models.py）：

class TaskStatus(str, Enum):
    PENDING = "pending"
    PROCESSING = "processing"
    SUCCESS = "success"      # 任务级成功终态是 success，不是 COMPLETED
    FAILED = "failed"
    CANCELLED = "cancelled"
    NOT_FOUND = "not_found"  # 查询不存在的任务时使用
    TIMEOUT = "timeout"      # 等待结果超时
    UNKNOWN = "unknown"

常见误读：终态 COMPLETED 在这套代码里并不存在。你在 REST 注释与部分示例里看到的 completed 有两个完全不同的来源：一是 list_tasks 接口 status_filter 里的枚举值（源码瑕疵，传它永远筛不到任务，见 4.4）；二是阶段明细 progress_details 中单个阶段的完成标记（complete_stage 写入 status: "completed"）。判断任务成功一律认 TaskStatus.SUCCESS。

阶段语义：细粒度进度由 TaskStage 提供——从 init、parsing_start、parsing_script 一路到 continuity_complete、output_generating、complete，每个阶段带 code、中文名与权重（0-100，用于加权估算总进度）。/api/v1/status/{task_id} 返回的 current_stage、stage_name 与 stages_progress 就来自这套体系。

三、核心模块详解

3.1 多智能体协作模型

五个智能体按流水线串联，每个智能体都配有 LLM 与规则/模板两套实现，由工厂（Factory）或配置开关在构造期选择，运行时再按需回退：

    subgraph "智能体协作图"
        A[剧本解析智能体<br/>ScriptParserAgent]
        B[镜头分割智能体<br/>ShotSegmenterAgent]
        C[视频分割智能体<br/>VideoSplitterAgent]
        D[提示词转换智能体<br/>PromptConverterAgent]
        E[质量审查智能体<br/>QualityAuditorAgent]
        
        A -->|结构化数据| B
        B -->|镜头序列| C
        C -->|片段序列| D
        D -->|提示词数据| E
        
        A -.->|降级| A1[规则解析器]
        B -.->|降级| B1[规则镜头分割器]
        C -.->|降级| C1[规则视频分割器]
        D -.->|降级| D1[模板转换器]
    end

降级接线现状（三口径考证）：运行期降级真实接线了两条——提示词转换在单片段粒度 try/except，LLM 转换失败即回退模板转换器（llm_prompt_converter.py）；视频分割的 LLM 实现内部持有 rule_splitter 实例，异常时整镜头回退规则分割（llm_video_splitter.py）。剧本解析的规则校验路径已实现但调用被注释（script_parser_agent.py），属于预留开关，二次开发时不要把 use_local_rules 当作现成功能。

3.2 智能体职责说明

智能体 输入 输出 核心功能
ScriptParserAgent 自然语言剧本 ParsedScript 解析剧本结构，提取角色、场景、对话、动作
ShotSegmenterAgent ParsedScript ShotSequence 将剧本元素拆分为镜头，估算时长，分配镜头类型
VideoSplitterAgent ShotSequence FragmentSequence 智能分割长镜头，生成片段序列
PromptConverterAgent FragmentSequence AIVideoInstructions 生成双语视频和音频提示词，保持道具一致性
QualityAuditorAgent AIVideoInstructions QualityAuditReport 审查提示词质量，检测截断、不一致问题

代码布局：每个智能体是一个子包，如 neopen/agent/script_parser/ 内含 base_script_parser.py、llm_script_parser.py、rule_script_parser.py 与 script_parser_models.py；对外暴露的 ScriptParserAgent 包装类位于 neopen/agent/script_parser_agent.py，负责注册两套实现、编排解析流程与质量评估。其余四个智能体同构。

模型文件映射：上述模型分散在各自子包的 models 文件中——ParsedScript 位于 script_parser_models.py、ShotSequence 位于 shot_segmenter_models.py、FragmentSequence 位于 video_splitter_models.py、AIVideoInstructions 位于 prompt_converter_models.py、QualityAuditReport 位于 quality_auditor_models.py，均基于 Pydantic 实现，跨阶段通过 LangGraph 状态传递。

四、快速开始（准备工作 → 步骤）

4.1 环境准备

git clone https://github.com/neopen/story-shot-agent.git
cd story-shot-agent
pip install -e .

前置环境要求：需要 Python 3.10+（pyproject 中 requires-python >= 3.10）与有效的 LLM API 密钥；Redis 7.0+ 可选，用于多进程部署时的任务记录共享。克隆后用 pip install -e . 以可编辑模式安装，便于修改源码即时生效；开发场景可装 pip install -e ".[dev]" 一次带上 pytest、black、flake8、mypy 等工具。安装后会注册 story-shot-agent、vs-agent 与 story-shot-agent-serve 三个命令入口。

cp .env.example .env

编辑 .env 文件，配置必要的 LLM 与 Embedding 参数：

4.3 启动服务

# 方式 1：主入口（走 penshot.app:app，支持 --host/--port，见下方说明）
python main.py

# 方式 2：独立 HTTP 启动器（额外支持并发与队列参数）
python -m penshot.http_server --host 127.0.0.1 --port 8000 --max-concurrent 5 --queue-size 500

# 方式 3：安装后使用 CLI（serve-rest 子命令，默认监听 0.0.0.0:8000）
story-shot-agent serve-rest --host 127.0.0.1 --port 8000

服务监听地址由配置决定：默认从 PENSHOT_API__HOST（模板 localhost）与 PENSHOT_API__PORT（8000）读取，命令行参数可覆盖；启动后提供完整 REST API 与 /docs 交互式文档。

多入口差异（源码考证）：main.py 与 http_server.py 最终都启动 penshot.app:app，但启动器各有侧重——main.py 支持 --reload 热重载与 workers 多进程（reload 与多进程互斥，reload=True 时强制 workers=1）；http_server.py 额外提供 --max-concurrent/--queue-size 参数（经环境变量传给应用）；CLI 的 serve-rest 是 cli.py 里 cmd_serve_rest 的封装。还需注意：多进程模式下任务队列与回调是进程内状态，任务记录需经 Redis 跨进程共享，未配置 Redis 时启动会打印警告且在进程间分裂（提交到进程 A 的任务在进程 B 查询为 not_found）。

4.4 API 调用示例

提交分镜任务（异步返回 task_id）：

curl -X POST 'http://localhost:8000/api/v1/storyboard' \
-H 'Content-Type: application/json' \
-d '{
  "script": "深夜11点，城市公寓客厅，窗外大雨滂沱。林然裹着旧羊毛毯蜷在沙发里，电视静音播放着黑白老电影..."
}'

查询任务状态：

curl 'http://localhost:8000/api/v1/status/{task_id}'

获取任务结果：

curl 'http://localhost:8000/api/v1/result/{task_id}'

调用流程：典型的三步——提交、轮询状态、取结果。提交后拿到 task_id，循环查询 GET /status/{task_id}，直到 status 变为 success（不是 COMPLETED），再调 GET /result/{task_id} 取提示词数据。请求量不大、想要低延迟的场景可以直接走同步接口 POST /storyboard/sync，一次请求阻塞到出结果；它的错误语义要注意——任务业务失败时抛 HTTP 400，错误文本在 FastAPI 标准的 detail 字段里（取自 result.error，兜底文案为 任务处理失败），成功时才返回完整的 ProcessResult 结构，两条路径的响应体不同，客户端要分开处理。

常用端点速览（rest_api.py 共 17 个路由，以下是集成时最常用的 9 个）：

方法 路径 说明
POST /api/v1/storyboard 异步提交，立即返回 task_id
POST /api/v1/storyboard/sync 同步提交，阻塞到出结果，业务失败返回 400
POST /api/v1/storyboard/batch 批量异步提交，单批上限 50 条
POST /api/v1/storyboard/batch/sync 批量同步提交，单批上限 20 条、超时 600 秒
GET /api/v1/status/{task_id} 查询状态，含 current_stage 与 stages_progress 阶段进度
GET /api/v1/result/{task_id} 获取结果，未完成时返回带 message 的任务结构
DELETE /api/v1/task/{task_id} 取消任务，对已结束的任务返回 400
GET /api/v1/queue/status 队列负载状态
GET /api/v1/health 健康检查

三处接口细节提醒（源码考证）：其一，取消任务的真实路由是 DELETE /api/v1/task/{task_id}，但 http_server.py 启动横幅里印的是 POST /api/v1/cancel/{id}，照横幅调用只会 404，以 rest_api.py 的路由表为准；其二，GET /tasks 的 docstring 声明了 status_filter 参数（枚举值里还出现了 completed），但函数签名里根本没有这个参数——传了会被静默忽略，且返回的 tasks 恒为空列表，它更像一个尚未接线的占位实现；其三，GET /result/{task_id} 在任务未完成时不返回 HTTP 202，而是正常 200 加上 message 字段提示处理中，客户端要靠 body 里的 status 判断进度，不要依赖 HTTP 状态码。

方式 1：Python SDK 调用

from penshot import ShotLanguage
from penshot.api import PenshotFunction
from penshot.neopen.agent.base_models import VideoStyle

# PenshotFunction 内部统一管理任务队列、并发与生命周期
agent = PenshotFunction(language=ShotLanguage.ZH, max_concurrent=5)

result = agent.breakdown_script(          # 同步：提交并等待完成（默认超时 300 秒）
    SAMPLE_SCRIPT,
    script_id="sdk-sync-001",             # 同属一个剧本的多次请求可传相同 ID，便于关联
    style=VideoStyle.CINEMATIC,
    wait_timeout=600.0,
)
print(result.task_id, result.success, result.status.value)
print(result.data["instructions"]["project_info"])

agent.shutdown()                          # 释放后台事件循环与线程

也可以异步提交、回调通知：

task_id = agent.breakdown_script_async(   # 异步：立即返回 task_id
    SAMPLE_SCRIPT,
    callback=lambda r: print(f"{r.task_id} 已完成"),
)
status = agent.get_task_status(task_id)   # 含 status、stage_name 等字段
# 之后同步等待结果；若在协程里可改用 await agent.wait_for_result_async(task_id)
result = agent.wait_for_result(task_id, timeout=600)

完整示例：examples/sdk/01_sync_breakdown.py（sdk/ 下共 7 个示例，覆盖同步、异步轮询、批量、队列管理、自定义配置、结果解析与文件剧本）

源码考证：breakdown_script 是同步封装——内部先调 breakdown_script_async 提交，再 wait_for_result 阻塞等待（默认超时 300 秒），所以两条调用路径背后是同一套机制。PenshotFunction(config, language, max_concurrent=10, queue_size=1000) 的并发与排队上限在构造时确定；create_penshot_agent() 只是它的一个便捷工厂函数。另外 wait_for_result_async 只能在事件循环里 await，普通脚本里用同步版 wait_for_result。

方式 2：嵌入 FastAPI Web 应用

可通过标准 HTTP 接口集成至现有业务系统（下面是真实示例的节选简化）：

from fastapi import FastAPI, HTTPException
from penshot import ShotLanguage
from penshot.api import create_penshot_agent

app = FastAPI(title="Penshot API", version="0.1.0")
penshot = create_penshot_agent(language=ShotLanguage.ZH, max_concurrent=5)

@app.post("/api/generate")
async def generate(req: WebScriptRequest):  # 请求模型：script_text / script_id / wait / timeout
    """wait=False 立即返回 task_id；wait=True 同步等待完成后再返回。"""
    if req.wait:
        result = penshot.breakdown_script(req.script_text, script_id=req.script_id,
                                          wait_timeout=req.timeout)
        return {"task_id": result.task_id, "status": result.status.value}
    task_id = penshot.breakdown_script_async(req.script_text, script_id=req.script_id)
    return {"task_id": task_id, "status": "pending", "message": "任务已提交"}

@app.get("/api/result/{task_id}")
async def get_result(task_id: str):
    r = penshot.get_task_result(task_id)
    if not r:
        raise HTTPException(status_code=404, detail="任务不存在或未完成")
    return {"task_id": r.task_id, "success": r.success, "data": r.data}

完整示例：examples/integrations/fastapi_web_app.py（313 行，含同步/异步/批量/取消/配置共 9 个端点；文件头部注释也提醒：状态比较一律取 .value，成功是 success，没有 completed）

方式 3：LangGraph 节点集成

支持把 SDK 封装成独立 Node 接入外部的 LangChain/LangGraph 工作流，实现端到端自动化流水线。 完整示例：examples/workflow/01_langgraph_integration.py

两套 LangGraph 的区别（源码考证）：这里容易混淆——PenShot 内部引擎本身就是 LangGraph 编排（MultiAgentPipeline 的 10 节点图，见 2.2），而这份示例演示的是把你的外层业务工作流（自定义 StateGraph + 状态模型）与 PenShot 对接：用 breakdown_script_async 提交、用返回的真实 task_id 轮询、按 result.data["instructions"] 契约取数。示例头部注释还特别提醒：breakdown_script_async 是普通函数不要 await，wait_for_result_async 是协程要直接 await，script_id 只是关联 ID、不能当轮询 ID 用。

方式 4：A2A 风格编排

支持与上游剧本创作 Agent、下游文生视频/剪辑 Agent 进行上下文传递与任务编排。 完整示例：examples/integrations/a2a_integration.py

A2A 说明（源码考证）：需要说清边界——仓库里的 a2a_integration.py 并不是 Google A2A 协议本身的实现（没有 Agent Card、没有协议端点），而是一个自包含的 A2A 风格编排示例：自定义代理层任务模型（A2ATask 与 A2ATaskStatus）、内部持有一个 PenshotFunction，演示怎样用一个稳定接口把分镜能力包成可被上游 Agent 调用、供下游视频 Agent 消费的代理。两个细节：A2A 层的任务 ID 由调用方指定（仅用于编排），真正轮询的 task_id 来自 breakdown_script_async 并存入 backend_task_id；A2A 层优先级（A2ATaskPriority）与 PenShot 内部的 TaskPriority 相互独立。

方式 5：MCP (Model Context Protocol) 支持

启动 MCP Server（stdio 模式，默认可直接运行）：

python -m penshot.mcp_server --max-concurrent 5 --queue-size 500

客户端可调用 4 个工具：breakdown_script（提交分镜任务）、get_task_status（查询状态）、get_task_result（取结果）、cancel_task（取消任务）。 完整示例：examples/mcp/mcp_client.py，HTTP 模式另有 mcp_http_server.py 与配套的 mcp_http_client.py。

MCP 说明：MCP 是 Anthropic 主导的开放协议，为 AI 应用与工具、数据源之间提供标准化接入方式，常被比作 AI 应用的 USB-C。PenShot 的 MCP Server 是手写 JSON-RPC 实现（未引入官方 MCP SDK），核心方法为 initialize、tools/list、tools/call；接入 Claude Desktop、Cursor 等 MCP 兼容客户端后，可直接在对话中用自然语言触发分镜。

七、开发指南（二次开发）

7.1 添加新的智能体

PenShot 的智能体是"双实现 + 工厂"结构（抽象基类 + LLM/规则两套实现 + factory + models），扩展时建议照抄这个模式。真实扩展路径分三步：

第 1 步：建智能体子包。 在 src/penshot/neopen/agent/ 下新建 my_agent/，包含 base_my_agent.py（抽象类）、llm_my_agent.py 与 rule_my_agent.py（两套实现）、my_agent_factory.py、my_agent_models.py。基类继承 BaseAgent（纯规则）或 BaseLLMAgent（带 LLM 重试与缓存接口）：

from penshot.neopen.agent.base_agent import BaseAgent

class MyBaseAgent(BaseAgent):
    def process(self, *args, **kwargs):
        raise NotImplementedError  # 子类实现具体逻辑

第 2 步：写节点方法。 工作流节点集中在 workflow/workflow_nodes.py 的 WorkflowNodes 类，签名统一为接收并返回 WorkflowState（新增字段要先在 workflow_state_types.py 的 WorkflowState 里声明）：

def my_node(self, state: WorkflowState) -> WorkflowState:
    state.my_results = self._do_something(state.raw_script)
    return state

第 3 步：注册进编排图。 在 workflow_pipeline.py 的 _build_workflow() 中按真实样式挂节点与条件边：

orchestrator = WorkflowOrchestrator()
orchestrator.add_node(
    "my_node",
    lambda graph_state: self.workflow_nodes.my_node(graph_state)
)
# 条件分支：按决策结果路由（成功/重试/失败各去不同节点）
orchestrator.add_conditional_edge(
    "my_node",
    lambda graph_state: self.decision_funcs.decide_after_my_node(graph_state),
    {
        PipelineState.SUCCESS: PipelineNode.CONVERT_PROMPT.value,
        PipelineState.NEEDS_RETRY: "my_node",
        PipelineState.FAILED: PipelineNode.ERROR_HANDLER.value,
    }
)

源码考证：add_node(name, node) 的 node 是接收 state 的 callable；add_edge 定义固定流转，add_conditional_edge(source, condition, mapping) 按 condition 返回值在 mapping 里选目标——这正是 10 节点图处理"成功/重试/人工介入/失败"分叉的机制（见 2.2）。图的装配由 MultiAgentPipeline 内部完成：build(state_schema=WorkflowState) → validate() → compile()（挂 SQLite 检查点）。

7.2 添加新的提示词模板

提示词模板放在 src/penshot/neopen/prompts/v1.x/zh/（英文在 v1.x/en/），每个智能体一个 yaml。真实文件结构如下（script_parser_prompt.yaml 节选）：

# 剧本解析相关提示词模板
version: "1.3"
changelog: |
  - 2026-03-18: 规范化提示词，细节性示例优化
  - 2026-03-27: 添加修复参数，通过修复建议和问题修复问题
  - 2026-03-30: 添加 history_hint 参数，支持记忆功能的历史上下文提示

script_parser_system:
  name: "base_script_parser_prompt"
  description: "系统提示词基础模板，适用于多种剧本格式的解析"
  template: |
    你是一个专业的剧本解析AI。请将输入的任意剧本文本内容解析为结构化的JSON结构。

    【输出格式】
      {{
        "title": "剧本标题",
        "characters": [...]
      }}

三个注意点：

  • 顶层固定 version 与 changelog 两段元信息，每个模板段落由 name、description、template 三个字段组成，新增时建议同步补 changelog 记录；

  • 模板里的字面量大括号要双写 {{ }}，占位符用单大括号（如 {input}）——渲染走 Python 的 .format()，双写是转义字面量大括号的标准写法，照抄现有文件的开头就不会踩坑；

  • 读取入口是 PromptManager.get_prompt(name) / get_name_prompt(name)（prompt_load_manager.py），内部按"版本 + 语言"定位文件，支持 _prompt 后缀剥离匹配，并带最多 1024 条的进程内缓存。

v2.x 的现状（源码考证）：prompts/v2.x/ 目录存在但为空占位，实际生效的模板全部在 v1.x/，全局 PromptManager 默认 version="v1.x"。v2.x 是预留的模板体系演进位，升级时别以为它已经是当前版本。

八、性能优化建议

  1. LLM 缓存（默认关闭，属预留能力）：BaseLLMAgent 提供了 _call_llm_with_cache（md5 缓存键含 prompt、system_prompt、temperature 与 task_id，带 TTL 与容量控制），但 AIConfig.enable_llm_cache 默认是 False，源码注释直言原因是 LLM 输出不稳定；而且缓存键包含 task_id，跨任务即使描述相同也不会命中——它的定位是任务内去重，不是跨任务复用。独立类 LLMCache（cache/llm_cache.py）的实例化在代码里被注释，属未接线状态；启用前建议先实测命中率与质量收益。

  2. 并发处理：max_concurrent 控制同时执行的任务数、queue_size 控制排队上限，两者在 PenshotFunction / create_penshot_agent 构造时确定；取值建议对齐 LLM 服务的速率限制，而不是越大越好。

  3. 多进程部署才需要 Redis：默认的进程内队列没有网络往返开销；只有横向扩展 worker 进程时，Redis 才作为跨进程的任务记录共享层登场（见 4.3 的多入口差异）。

  4. 降级策略分两层看：运行内已接线的有两条——提示词转换失败时按片段回退模板转换、视频拆分规则兜底（见 3.1）；script_parser_agent 里规则校验的接线目前处于注释状态，评估时不要把它算作已生效能力。

  5. 提示词长度控制：注意 max_prompt_length 的计数口径问题（触发按英文单词数、截断按字符数，见 Q2），过长提示词除了 token 成本，更直接的伤害是真实触发的截断会丢掉大量细节。

九、常见问题

Q1: 任务状态一直是 PENDING？

排坑（源码考证）：PENDING 说明任务已创建但还没被取走执行。先分清部署形态——默认是进程内队列，跟 Redis 无关，所以先查两件事：active_tasks 是否已达 max_concurrent 上限（并发打满时新任务排队等）；任务提交与查询是否落在同一进程（多 worker 且未配 Redis 时，提交到进程 A 的任务在进程 B 查询是 not_found）。确实启用了多进程 + Redis 的部署，再核对 .env 中 PENSHOT_REDIS_* 键与连接信息是否一致。

Q2: 提示词被截断？

排坑（源码考证 + 真实案例）：仓库自带的运行样例 examples/data/results/function_calls_data.json 里就留下了真实截断记录，repair_history 显示两条提示词从 989、881 被截到 200。对照源码注意三点：触发判断用 only_count_en 计英文单词数，截断动作却是字符切片 prompt[:阈值 - 20] + "..."，修复统计再用 len() 字符数，三种口径混用；所以看到 989 -> 200 别按单一单位去换算。调参入口是 ShotConfig.max_prompt_length（它的注释写"单词数"，与实现并不完全一致，建议自己实测确认）；不想被截的话，除了调大阈值，更稳的是在提示词模板里约束 LLM 的输出长度。

Q3: 道具信息丢失？

确保 GlobalMetadata 中正确配置了 key_props，并在解析、拆分、转换各阶段的传递链路中保持一致。

Q4: 如何自定义 LLM 模型？

修改 .env 中的 PENSHOT_LLM__DEFAULT__MODEL_NAME 配置。

排坑：改模型时需同时核对 BASE_URL 与 API_KEY 是否匹配目标厂商；若为本地 Ollama，BASE_URL 通常指向 http://localhost:11434/v1。gpt-4o 只是模板里的默认值，切换厂商属于配置行为，不涉及代码改动。

Q5: 生产环境要不要 Redis？

排坑（源码考证）：先纠正一个过度概括——Redis 在这套代码里并不是"任务队列 + 状态管理 + 结果缓存"的通吃角色。任务队列与并发控制在进程内（TaskManager），Redis 的定位只有一个：多进程/多实例部署时的任务记录共享层。判断标准很简单：单实例部署不必上 Redis；要跑 uvicorn 多 worker 或横向扩容多副本时才需要，并接受"未配 Redis 时任务在进程间分裂为 not_found"的约束（见 4.3）。
