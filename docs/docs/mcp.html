集成与接口

MCP 服务

七个工具、双传输与 Claude Desktop / Cursor 客户端配置。

更新 2026-10-31 约 17 分钟阅读 在 GitHub 编辑

MCP（Model Context Protocol）是连接大模型客户端与外部工具的开放协议。PenShot 提供 stdio 与 HTTP 两种 MCP 服务，把剧本分镜能力暴露为七个工具，客户端按“提交任务、轮询状态、获取结果”的顺序调用。

架构

两种服务共用 PenshotFunction 与任务池实现，七个工具的名称和用途一致；参数描述与部分返回字段存在差异，详见传输章节。stdio 服务由 mcp_server.py 手写 JSON-RPC 循环，HTTP 服务由 mcp_http_server.py 基于 FastAPI 暴露 /tools/* 路由。

flowchart LR
    C1["Claude Desktop / Cursor"] -->|"stdio JSON-RPC"| S1["mcp_server.py"]
    C2["HTTP 客户端"] -->|"POST /tools/*"| S2["mcp_http_server.py"]
    S1 --> A["PenshotFunction"]
    S2 --> A
    A --> T["TaskFactory 任务池"]
    T --> W["分镜工作流"]
    W --> R["data.instructions"]

一次完整调用包含握手、列工具、调用工具三个阶段。initialize 协商协议版本，tools/list 返回工具定义，tools/call 执行具体工具，执行结果统一序列化后放入 content[0].text。

sequenceDiagram
    participant C as MCP 客户端
    participant S as MCP Server
    participant A as PenshotFunction
    participant T as 任务池
    C->>S: initialize
    S-->>C: protocolVersion 0.1.0
    C->>S: tools/list
    S-->>C: 七个工具定义
    C->>S: tools/call breakdown_script
    S->>A: breakdown_script_async()
    A->>T: 提交任务
    T-->>A: task_id
    A-->>S: task_id
    S-->>C: content[0].text
    loop 轮询
        C->>S: tools/call get_task_status
        S-->>C: status / progress
    end
    C->>S: tools/call get_task_result
    S-->>C: data.instructions

stdio 模式下，每个客户端各自拉起一个 Python 进程，任务池、并发计数与结果都只存在于该进程；客户端退出后进程结束，未完成的任务随之消失。HTTP 模式在一个进程内维护全局 agent，多个客户端共享同一任务池。内存模式下任务随进程存活；启用 Redis 时默认保留 24 小时，超过后查询返回 not_found。需要重启后恢复或跨进程共享时，应配置 Redis 并改用 REST 服务。

七个工具

工具参数返回
breakdown_scriptscript 必填；language 默认 zh；wait 默认 false；timeout 默认 300 秒异步返回 task_id、status=pending 与提示信息；同步返回任务结果
get_task_statustask_idstatus、progress、current_stage、stage_name、stages_progress
get_task_resulttask_idtask_id、success、status、data、error、processing_time_ms
cancel_tasktask_id{task_id, cancelled}
list_taskslimit 默认 20；HTTP 版另支持 status_filtertotal、limit、tasks，任务项含状态、阶段与进度
get_queue_status无queue_length、queue_waiting、active_tasks、max_concurrent、queue_usage_percent
get_stats无提交、完成、失败、取消计数与队列快照

breakdown_script 只接受上述四个键，不支持 SDK 中的 script_id、style 与 priority；需要这些参数时改用 Python SDK 或 REST。异步调用立即返回任务号，同步调用在 timeout 内等待完整结果。

language 的解析在两种传输下不同：stdio 仅把字面量 zh 视为中文，其余值（包括 中文、cn）一律按英文处理；HTTP 使用 ShotLanguage.from_string，接受 zh、中文、en、英文 并忽略大小写，无法识别的值回退中文。跨传输复用时不要依赖同一个语言字符串。

list_tasks 的 total 是本次返回条数，不是任务总数。stdio 版只读取 limit，传入 status_filter 不会生效；HTTP 版才提供筛选。

调用示例

异步提交只需给出剧本与语言，返回的 task_id 用于后续查询。stdio 的响应文本是字符串化 JSON，需要再解析一次：

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "breakdown_script",
    "arguments": {
      "script": "第一场 日 内 办公室",
      "language": "zh",
      "wait": false
    }
  }
}

{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [{
      "type": "text",
      "text": "{\"task_id\": \"TSK202603282100504595\", \"status\": \"pending\", \"message\": \"任务已提交\"}"
    }]
  }
}

轮询时把工具名换成 get_task_status，参数只保留 task_id。响应中的 status 用于判断终态，stage_name 与 progress 用于展示，stages_progress 给出各阶段明细。

{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "get_task_status",
    "arguments": {"task_id": "TSK202603282100504595"}
  }
}

status 为 success 时调用 get_task_result，结果位于 data.instructions，与 SDK、REST 的结构一致。同步调用把 wait 设为 true 并给出 timeout，响应直接包含 data 与 error；超时返回 status=timeout，后台任务仍会继续，可保留 task_id 改用轮询。

data.instructions 通常包含项目信息与片段数组，片段数量随剧本长度变化。需要稳定字段时应以 SDK 的 PenshotResult.data 为准，不要把展示用文案当作契约。

任务生命周期

flowchart LR
    A["breakdown_script"] --> B["task_id"]
    B --> C["get_task_status"]
    C --> D{"status"}
    D -->|"pending / processing"| C
    D -->|"success"| E["get_task_result"]
    D -->|"failed / cancelled / not_found"| F["停止并读取 error"]

任务级终态为 success、failed、cancelled；completed 只出现在 stages_progress 的阶段状态里，不能用于判断任务结束。not_found 表示任务号不存在，常见于进程重启、跨进程未共享存储，或 Redis 模式下超过默认 24 小时保留期。成功结果位于 data.instructions，失败时读取 error；data 可能为空，不能只看 success。同步调用超时返回 status=timeout，后台任务不会因此终止，可继续用 task_id 轮询。轮询间隔建议 1 到 3 秒，过密只会增加空转。

stdio 传输

stdio 是桌面客户端的标准接入方式：客户端启动子进程，通过 stdin 逐行写入 JSON-RPC，通过 stdout 逐行读取响应。所有日志写入 stderr，stdout 只允许 JSON，任何多余的打印都会破坏协议流。

# 默认并发 10、队列 1000
python -m penshot.mcp_server

# 调整并发与队列
python -m penshot.mcp_server --max-concurrent 5 --queue-size 500
JSON-RPC 方法行为
initialize返回 protocolVersion 0.1.0、serverInfo（penshot-mcp-server / 1.0.0）与 capabilities.tools
tools/list返回七个工具，每个工具的 parameters 均为空对象
tools/call按 name 调用工具，结果写入 result.content[0].text

服务只实现这三个方法。notifications/initialized 等通知与其他方法一律返回 -32601；resources、prompts 与订阅能力不可用。由于 tools/list 的参数 schema 为空，客户端无法从协议层获知参数名，需要在系统提示词中约定，或改用 HTTP 版联调。

协议按行分帧：一行一个 JSON 对象，请求 id 原样回填，客户端按 id 匹配响应。服务不会强制先执行 initialize，直接发送 tools/call 也能得到结果，但标准客户端仍会先握手。stdin 关闭时循环退出，进程结束；需要常驻时应由客户端或进程管理器负责重启。

HTTP 传输

HTTP 服务用于本机联调，监听 127.0.0.1:8000，与 REST 服务默认端口相同，二者不要同时启动。它不是 MCP 标准的 SSE 或 Streamable HTTP 传输，而是 FastAPI 的 REST 封装，MCP 协议客户端无法直连，只可用普通 HTTP 请求调用。

python -m penshot.mcp_http_server
方法端点说明
GET/服务名称、版本与端点清单
GET/tools七个工具及参数说明
POST/tools/breakdown_script请求体为 script、language、wait、timeout
POST/tools/get_task_status查询状态，任务不存在返回 404
POST/tools/get_task_result获取结果，任务不存在返回 404
POST/tools/cancel_task取消任务，返回 cancelled
POST/tools/list_tasks支持 status_filter 与 limit
GET/tools/queue_status队列状态
GET/tools/stats统计信息

GET /tools 的参数说明是扁平的 name -> 描述 映射，并非标准 JSON Schema。任务不存在时，状态与结果接口返回 404；breakdown_script 内部异常统一转成 500。list_tasks 的 status_filter 枚举包含 completed，但任务状态中不存在该值，按成功筛选应使用 success。CORS 默认全放开，仅供本地使用。

curl -s http://127.0.0.1:8000/tools

curl -s -X POST http://127.0.0.1:8000/tools/breakdown_script \
  -H "Content-Type: application/json" \
  -d '{"script":"第一场 日 内 办公室","language":"zh","wait":false}'

HTTP 版返回普通 JSON，没有 content[0].text 包装；异步响应带有 success=true，它只表示请求被接受，不代表分镜已经完成，判断进度仍以 status 为准。

flowchart TB
    A["使用场景"] --> B{"桌面客户端?"}
    B -->|"是"| C["stdio<br/>python -m penshot.mcp_server"]
    B -->|"否"| D["本机 HTTP 联调<br/>python -m penshot.mcp_http_server"]
    C --> E["空参数 schema<br/>三个 JSON-RPC 方法"]
    D --> F["参数说明映射<br/>FastAPI /tools/*"]

服务配置

两个服务启动时都会创建 PenshotFunction。stdio 由 --max-concurrent 与 --queue-size 控制并发和队列，默认 10 与 1000；HTTP 使用 create_penshot_agent() 的默认值。模型配置从环境变量或 .env 读取，至少需要 LLM 与嵌入模型两组键。

PENSHOT_LLM__DEFAULT__BASE_URL=https://api.openai.com/v1
PENSHOT_LLM__DEFAULT__API_KEY=sk-xxxxxxxx
PENSHOT_LLM__DEFAULT__MODEL_NAME=gpt-4o

PENSHOT_EMBED__DEFAULT__BASE_URL=https://api.openai.com/v1
PENSHOT_EMBED__DEFAULT__API_KEY=sk-xxxxxxxx
PENSHOT_EMBED__DEFAULT__MODEL_NAME=text-embedding-v4
PENSHOT_EMBED__DEFAULT__DIMENSIONS=1536

多进程部署时需配置 Redis 共享任务状态，否则一个进程创建的任务在另一个进程中会返回 not_found；单进程可以省略。队列满时提交会被拒绝，任务可能停留在 pending，错误只写入日志；应监控 queue_usage_percent，或调大 --queue-size 后重启。

配置从系统环境变量与 .env 合并读取，.env 会在当前工作目录、上级目录与用户配置目录中查找。模型供应商、超时与重试等字段都可通过 PENSHOT_LLM__DEFAULT__*、PENSHOT_EMBED__DEFAULT__* 覆盖。Redis 可只设置 PENSHOT_REDIS_URL，也可拆成 PENSHOT_REDIS_HOST、PENSHOT_REDIS_PORT 与 PENSHOT_REDIS_DB。

客户端配置

Claude Desktop 的配置文件位于 macOS 的 ~/Library/Application Support/Claude/claude_desktop_config.json 或 Windows 的 %APPDATA%\Claude\claude_desktop_config.json；Cursor 使用 ~/.cursor/mcp.json 或项目内的 .cursor/mcp.json。两者都使用 mcpServers 结构。

{
  "mcpServers": {
    "penshot": {
      "command": "/path/to/venv/bin/python",
      "args": [
        "-m", "penshot.mcp_server",
        "--max-concurrent", "10",
        "--queue-size", "1000"
      ],
      "env": {
        "PENSHOT_LLM__DEFAULT__BASE_URL": "https://api.openai.com/v1",
        "PENSHOT_LLM__DEFAULT__API_KEY": "sk-xxxxxxxx",
        "PENSHOT_LLM__DEFAULT__MODEL_NAME": "gpt-4o"
      }
    }
  }
}

command 建议填写虚拟环境解释器的绝对路径，避免客户端启动时找不到 penshot。密钥放在 env 中可避开工作目录不确定的问题；若依赖 .env，需确保客户端启动目录就是仓库根目录。修改配置后重启客户端。

Cursor 的项目级配置会随仓库分发，写入密钥前应确认该文件已被版本控制忽略；团队共享时更适合使用用户级配置或系统环境变量。Windows 下把示例中的解释器路径换成 C:\\path\\to\\venv\\Scripts\\python.exe，JSON 中的反斜杠需写成两个。

在 bash 或 Git Bash 中可先用一行请求验证握手：

echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' | python -m penshot.mcp_server

返回 protocolVersion 为 0.1.0、serverInfo.name 为 penshot-mcp-server 即表示进程与依赖正常。

错误与排查

flowchart LR
    A["读取一行输入"] --> B{"JSON 可解析?"}
    B -->|"否"| C["写入 stderr<br/>stdout 不返回"]
    B -->|"是"| D{"方法或工具存在?"}
    D -->|"否"| E["-32601"]
    D -->|"是"| F{"handler 抛异常?"}
    F -->|"是"| G["-32000 + 异常消息"]
    F -->|"否"| H["result.content[0].text"]
错误码或状态含义处理
-32000工具 handler 抛出异常，如缺少 script 或 task_id读取 stderr 日志与异常消息
-32601方法或工具不存在，通知类消息也归入此类核对三个方法与七个工具名
无响应输入不是合法 JSON，或 stdout 被日志污染检查 stderr 与第三方打印
HTTP 404任务号不存在确认任务由同一进程创建且未过期
HTTP 422请求体字段缺失或类型错误对照请求模型修正
HTTP 500工具执行异常，HTTP 版统一包装为 500查看响应 detail 与服务日志

排查顺序：先确认进程能启动，再确认 initialize 有响应，然后检查 tools/list 是否返回七个工具，最后单独调用 get_queue_status。只有某个工具失败时，通常是参数缺失或后台任务失败；所有工具都失败时，优先检查 stdout 污染与解释器环境。

现象可能原因处理
客户端看不到工具解释器路径错误，或依赖未安装用同一解释器执行 python -m penshot.mcp_server 验证
参数不被识别stdio 版 schema 为空在提示词中约定参数，或改用 HTTP 版
任务长时间 pending队列积压或工作器未消费查看 get_queue_status 与服务日志
同步调用超时剧本较长或模型较慢设置 wait=false 后轮询
状态判断不命中把 completed 当作任务终态使用 success、failed、cancelled
跨进程查不到任务任务状态未共享配置 Redis，或固定单进程运行

安全与部署边界

stdio 服务以启动它的用户权限运行，能够读取该用户的环境变量与文件，只应接入可信客户端。HTTP 服务不提供鉴权、TLS 与限流，CORS 默认允许所有来源，只适合绑定 127.0.0.1 做本机联调；需要远程访问时，应放在反向代理之后并补充身份校验。

默认配置下，两种服务都把任务与结果保存在进程内，进程退出即丢失；启用 Redis 后任务状态跨进程共享，但仍不承担结果归档。生产环境若要求审计、重试或结果归档，应在 REST 层实现，而不是依赖 MCP 服务。

延伸阅读

官方镜像默认启动 REST 服务；需要在容器内运行 stdio MCP 时，可覆盖入口：docker run --rm -i --env-file .env --entrypoint python neotems/penshot:latest -m penshot.mcp_server。端口、数据卷与 Compose 配置见Docker 部署。

SDK 与 REST 的完整参数见集成指南；服务端任务池与状态机见开发者指南与架构说明；实现与示例代码见GitHub 仓库。
