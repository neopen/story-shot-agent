核心价值与需求背景

为什么剧本分镜需要"召回"

剧本分镜智能体的核心任务是把原始剧本拆解并增强为可供 AI 视频模型使用的提示词序列。面对动辄数万字的剧本，模型单独推理既无法精确定位"某句台词"“某个人物的设定”，也无法复用自己的历史成功经验。召回（Retrieval）就是解决这个问题的关键环节——它决定了系统能否在正确的时间取出正确的上下文。

在文档与规划层面，PenShot 的召回体系被描述为多路召回 + 融合重排的组合拳。但把源码摊开逐项核对之后，结论要克制得多：真正进入工作流调用链的召回链路其实只有两段——已接线的三层记忆系统（MemoryManager 被注入提示词模板管理、工作流记忆与输出写入三处消费），以及形态朴素的剧本知识库检索（手动余弦相似度全量扫描）。而 GraphRAG、BM25、RRF 融合、学习排序（LTR）这些名字，在整个仓库里检索不到对应实现。

本文按三个口径逐章核对：已接线（真正进入调用链）、已实现未接线（代码存在但无调用方）、规划中（仅存在于文档与路线图）。每一项判断都给出源码位置或"零命中"的检索结论。

  • 逻辑关系缺失：剧本中主角与助手前三集建立的信任，在第五集"助手背叛"时才产生戏剧张力。仅靠语义相似度检索不到这种深层的因果与人物关系——这是 GraphRAG 试图解决的问题，也是 PenShot 目前尚未落地的规划项。

  • 一致性维护：跨集创作时角色性格、外貌、世界观的一致性极易"崩塌"，需要长短时记忆系统在生成时强制参考既有设定——这一部分真实存在，且已接线。

下文先纵览各类召回方案与平滑演进思路，再逐章拆解每一项机制在源码中的真实状态。

关键要点拆解（一）：常用召回方案对比

以下是剧本分镜场景中几类主流的召回方案及各自的适用场景与技术挑战。先说明性质：本节的方案与详解综合了行业公开资料（阿里云 AnalyticDB、爱奇艺"纳逗 Pro"等），属于行业方案综述——每一种方案在 PenShot 中的落地状态各不相同，后文第三章起会逐项核对，不建议把本节内容当作"PenShot 已实现功能"来读。

方案名称 核心原理 适合场景 技术挑战
GraphRAG 构建知识图谱，通过实体和关系进行检索 人物关系复杂、逻辑因果强的剧本（如悬疑、宫斗）。 图谱构建成本高，数据稀疏时效果不佳。
长记忆模块 隔离存储长期（角色设定）和短期（当前剧情）信息 需要保证跨集数角色性格、说话风格一致性的长剧创作。 需设计有效的记忆总结与压缩机制。
自迭代优化 通过"生成-质检-修复"闭环持续优化 解决生成内容的硬伤（如逻辑矛盾、人设崩塌）导致的"伪召回"。 依赖高质量、多维度的自动化质检标准。
混合检索策略 结合关键词（BM25）、向量、结构化标签的多路召回 需要高精度、高召回率，且兼容模糊语义和精确匹配的通用场景。 多路结果的融合与重排序算法设计复杂。
多智能体协作 不同Agent负责不同维度的检索（如分镜、台词） 分工明确的专业影视制作流水线，各环节对素材需求差异大。 智能体间的通信与任务编排开销大。

方案详解

GraphRAG：让AI真正"读懂"剧本逻辑

传统RAG基于向量相似度，容易忽略剧情中复杂的逻辑关系。阿里云AnalyticDB的方案引入了GraphRAG，它在向量检索的基础上，构建了包含"角色-事件-场景"的知识图谱。

  • 用法：当用户要求"写一段男主发现助手背叛后的对峙戏"时，系统不仅找"背叛"相关语义，还能图谱中定位"男主"和"助手"的关系及历史。
  • 价值：确保后续情节发展与前面埋下的伏笔和人物关系逻辑自洽。

长记忆模块：确保人设"不崩塌"

剧本创作的最大痛点是角色或场景的"不一致"。AnalyticDB for PostgreSQL内置的Long-term Memory技术就是为此设计。

  • 分层存储：将长期记忆（如角色性格、外貌、核心世界观）与短期记忆（如当前场景对话、情绪）分开管理。
  • 效果：在生成新对话时，AI会强制参考长期记忆库中的角色设定，有效防止角色"精分"。

框架仿写与结构化提取：迁移"神"而非"形"

爱奇艺"纳逗Pro"智能体及阿里云方案均强调了结构化提取的重要性。

  • 做法：从参考剧本中提取出叙事框架（如起承转合的结构、冲突模式、情感线），将其剥离具体台词后存入向量库。
  • 应用：当用户想写一个"现代版罗密欧与朱丽叶"时，系统能召回的是两个家族世仇下的爱情冲突框架，而非直接给古代台词，实现了高层次的创意复用。

自迭代优化：用"质检"倒逼"召回"

有时召回失败不是因为没找到，而是因为生成的内容质量不过关（如角色做出了不符合人设的动作）。这就引入了质检闭环：

  • 流程：生成 → 自动质检（检查角色、逻辑、格式等多个维度） → 发现缺陷（如"逻辑一致性"低分） → 触发定向召回（专门去找前文中相关的逻辑设定） → 修复。
  • 意义：通过反馈机制，让系统知道自己"漏掉了什么"，实现自我进化。

单次交互模式（短剧）

短剧（单集2-5分钟，总时长20-60分钟）的核心需求是快速响应和成本可控。

记忆管理 单次会话上下文(同场景内) 无需长期记忆，降低复杂度
智能体架构 单智能体或双智能体(剧本+分镜) 简化调度，端到端效率优先

超长剧本支持（电影）

电影/电视剧/动漫（单集40分钟以上，总时长数小时）的核心挑战是长上下文管理和跨集一致性。

万字级剧本 → 语义索引系统 → 事件图谱构建 → 分层检索

  • 采用语义索引管道：将长篇内容分割为5-15分钟的重叠窗口，提取层次化摘要

  • 章节事件图谱：用RAG技术分析长文本结构，提取事件、动作和情感点

关键数据流

  1. 主创作流：用户输入 → 导演拆解 → 各 Agent 创作 → 质检 → 输出
  2. 记忆流：创作过程中持续读写记忆库，保持一致性
  3. 反馈流：质检发现缺陷 → 触发导演重新调度或定向召回
  4. 仲裁流：导演 Agent 随时干预风格冲突或资源分配问题

（注：以上是规划蓝图的数据流定义——当前实现中没有导演 Agent，编排由固定的工作流承担，详见第八章。）

关键要点拆解（四）：混合检索策略详解

核心解决的问题

剧本分镜场景中，用户查询呈现多样化的特点：有时需要精确的角色名称匹配（如"林小雨的所有台词"），有时需要语义相似的内容（如"雨天的氛围场景"），有时需要结构化的筛选（如"第三幕的对话"）。单一检索方式无法同时覆盖这些需求，"混合检索"因此成为文档中的重点设计。

但需要先把两件事分开：需求是真实的，混合检索的"文档描述"与"源码实现"却差距很大。逐项对照：

需求类型 示例查询 文档方案 源码现状
精确匹配 “查找陈阳的所有台词” 关键词 BM25 零命中；接近的替代是 query_character 精确字段比对
语义相似 “类似雨中相遇的浪漫场景” 向量检索 ✅ 手动余弦全量扫描（已接线）
关系推理 “男主发现真相后的反应镜头” GraphRAG 零命中，规划项
结构筛选 “第二幕中时长>3秒的特写” 标签过滤 部分支持：query_scene 按场景编号精确查询，无时长等复合条件

检索的真实形态：一次全量扫描

ScriptKnowledgeBase.query 的实际流程远比"多路召回融合"朴素——它就是一次嵌入 + 全量扫描 + 排序截断：

    D --> S[按 similarity 降序排序]

没有倒排索引、没有 HNSW 图、没有 RRF 融合——优点是完全可解释、零额外依赖；代价是 O(N) 复杂度，每次查询都要把向量库里的每个文档过一遍。文档规模小的时候这完全够用，但它是"正确的简单"，而不是"高性能的复杂"。

融合算法：文档说法与真实实现的距离

倒数排序融合（RRF）：多路召回的标准融合算法，只依赖排序位置（rank）而非原始分值，天然回避"向量相似度 0.9 vs BM25 8.5"这类量纲不可比问题，公式为 RRF_score = Σ 1/(k + rank_i)，k 常取 60。但 PenShot 仓库中检索不到 RRF 的实现——这个算法目前只存在于设计文档和文章演示代码里。

加权求和：各源分数归一化后按权重合并。同样未实现——所谓"经验调优权重"没有对应的配置项或代码。

学习排序（LTR）：需要标注数据训练排序模型。未实现，且在"融合策略"本身都还没上线的阶段，讨论 LTR 属于超纲。

那么已实现的融合在哪里？在 KnowledgeRouter._hybrid_search 里——注意，这条链路整体未接线。它的真实逻辑只有三步：

  1. 串行调用三路检索（向量 + 记忆 + 结构化）。源码注释自己写明了：“简化版，实际可用 asyncio.gather”——作者清楚这里本该并行；

  2. 合并后按 score 降序排序。而记忆与结构化结果的 score 是硬编码常量：短期记忆 0.9、中期记忆 0.7、长期记忆 0.6、结构化场景 1.0、结构化角色 0.9——它们反映的是"来源权重"的直觉，而不是与查询的真实相关性；

  3. 用内容前 100 字符作 key 做前缀去重，截断 top_k 返回。

评估这段实现时不宜套用"多路融合算法"的滤镜。更准确的说法是：它是一个把三路结果拼在一起的基础聚合器，排序靠硬编码分数、去重靠字符串前缀。它离 RRF 这类算法只差"排名位置"这一个转化，但这一步还没迈出去。

核心解决的问题

传统RAG（检索增强生成）基于向量相似度进行检索，这种方式难以理解剧情中的复杂逻辑关系。例如：

场景一：剧本中"男主"和"助手"在前三集建立了深厚的信任关系，第五集"助手背叛"。当用户要求生成"男主发现助手背叛后的对峙戏"时，传统RAG只能检索到"背叛"相关的片段，但无法理解"为什么背叛会带来强烈的情绪冲击"——这需要理解前文中建立的信任关系。

场景二：用户要求"延续上一场的氛围"，传统RAG无法理解"上一场"指的是哪个场景，更无法理解该场景的氛围特征是什么。

GraphRAG 的思路，是在向量检索的基础上构建"角色-事件-场景"实体与互动、因果、时序关系的知识图谱，把"检索"升级为"推理"。但需要先明确：PenShot 仓库中检索不到图谱实体抽取、图存储、图遍历的任何实现——以下是设计蓝图与落地评估，不是"已实现功能详解"。想先看结论的读者可以直接跳到本章末的落地评估部分。

排坑说明：GraphRAG 的实现成本明显高于纯向量检索——图谱构建需要额外的实体识别与关系抽取，数据稀疏时（样本不足）关系边稀少，效果甚至可能不如向量检索。因此 GraphRAG 更适合关系密集、逻辑因果强的长剧场景，短剧可先用已接线的链路打底，再评估是否叠加图谱。

概念示例：图谱构建与检索 Demo

⚠️ 代码性质说明：以下代码是概念示例，并非 PenShot 项目源码。它演示"实体识别 → 图遍历 → 路径打分"的通用思路（广度优先遍历、深度限制 3 层、路径越短分越高等），与项目代码无关——项目里没有这段实现的对应物。

# graph_rag_demo.py
"""
GraphRAG演示 - 知识图谱构建与推理检索（概念示例）
"""

class GraphRAGDemo:
    """GraphRAG核心逻辑演示"""
    
    def __init__(self):
        # 实体存储
        self.entities = {}
        # 关系存储（邻接表）
        self.relations = {}
        # 实体类型索引
        self.type_index = {}
    
    def build_from_script(self, script_data):
        """
        从剧本构建知识图谱
        
        构建步骤：
        1. 添加角色实体 - 每个角色成为图中的一个节点
        2. 添加场景实体 - 每个场景成为图中的一个节点
        3. 添加事件实体 - 每个动作/对话成为事件节点
        4. 建立关系边 - 根据剧本内容建立实体间的连接
        """
        print("构建知识图谱...")
        
        # 1. 添加角色实体
        for char in script_data.get("characters", []):
            self._add_entity(
                entity_id=f"char_{char['name']}",
                name=char["name"],
                entity_type="character",
                properties={
                    "gender": char.get("gender"),
                    "role": char.get("role"),
                    "description": char.get("description")
                }
            )
        
        # 2. 添加场景实体
        for scene in script_data.get("scenes", []):
            self._add_entity(
                entity_id=f"scene_{scene['id']}",
                name=scene.get("location", ""),
                entity_type="scene",
                properties={
                    "time": scene.get("time_of_day"),
                    "weather": scene.get("weather")
                }
            )
        
        # 3. 添加事件实体和关系
        for scene in script_data.get("scenes", []):
            scene_id = f"scene_{scene['id']}"
            for elem in scene.get("elements", []):
                event_id = f"event_{elem['id']}"
                self._add_entity(
                    entity_id=event_id,
                    name=elem.get("content", "")[:30],
                    entity_type=elem.get("type", "action"),
                    properties={
                        "emotion": elem.get("emotion"),
                        "intensity": elem.get("intensity", 0.5)
                    }
                )
                # 事件发生在场景中
                self._add_relation(event_id, scene_id, "occurs_in")
                
                # 如果事件涉及角色，建立关系
                if elem.get("character"):
                    char_id = f"char_{elem['character']}"
                    self._add_relation(char_id, event_id, "performs")
        
        print(f"图谱构建完成: {len(self.entities)}个实体, {self._count_relations()}条关系")
    
    def retrieve(self, query, context=None):
        """
        图谱检索 - 结合实体识别和关系推理
        
        检索流程：
        1. 从查询中识别实体
        2. 在图中定位这些实体节点
        3. 进行广度优先遍历，收集关联实体
        4. 对路径进行相关性排序
        """
        # 1. 实体识别
        entities = self._extract_entities(query)
        if context:
            entities.update(self._extract_context_entities(context))
        
        if not entities:
            return []
        
        print(f"识别实体: {entities}")
        
        # 2. 广度优先遍历
        results = []
        visited = set(entities)
        queue = [(e, 0, [e]) for e in entities]
        
        while queue:
            current, depth, path = queue.pop(0)
            
            if depth > 3:  # 限制遍历深度
                continue
            
            # 获取邻居节点
            neighbors = self.relations.get(current, [])
            
            for neighbor in neighbors:
                if neighbor not in visited:
                    visited.add(neighbor)
                    new_path = path + [neighbor]
                    
                    results.append({
                        "entity_id": neighbor,
                        "entity": self.entities.get(neighbor),
                        "path": new_path,
                        "depth": depth + 1
                    })
                    
                    queue.append((neighbor, depth + 1, new_path))
        
        # 3. 排序
        results.sort(key=lambda x: (x["depth"], self._path_score(x["path"])))
        
        return results
    
    def _extract_entities(self, text):
        """从文本中提取实体"""
        entities = set()
        for entity_id, entity in self.entities.items():
            if entity["name"] and entity["name"] in text:
                entities.add(entity_id)
            # 检查属性匹配
            if entity["entity_type"] == "character":
                if entity["name"] in text:
                    entities.add(entity_id)
        return entities
    
    def _extract_context_entities(self, context):
        """从上下文中提取实体（当前角色、当前场景等）"""
        entities = set()
        if "current_character" in context:
            char_id = f"char_{context['current_character']}"
            if char_id in self.entities:
                entities.add(char_id)
        if "current_scene" in context:
            scene_id = f"scene_{context['current_scene']}"
            if scene_id in self.entities:
                entities.add(scene_id)
        return entities
    
    def _path_score(self, path):
        """计算路径相关性分数"""
        # 路径越短分数越高
        return 1.0 / (len(path) + 1)
    
    def _add_entity(self, entity_id, name, entity_type, properties=None):
        """添加实体"""
        self.entities[entity_id] = {
            "id": entity_id,
            "name": name,
            "entity_type": entity_type,
            "properties": properties or {}
        }
        
        if entity_type not in self.type_index:
            self.type_index[entity_type] = []
        self.type_index[entity_type].append(entity_id)
        
        if entity_id not in self.relations:
            self.relations[entity_id] = []
    
    def _add_relation(self, from_id, to_id, rel_type):
        """添加关系"""
        if from_id not in self.relations:
            self.relations[from_id] = []
        self.relations[from_id].append(to_id)
    
    def _count_relations(self):
        """统计关系数量"""
        return sum(len(v) for v in self.relations.values())

关键要点拆解（六）：长短时记忆系统

核心解决的问题

剧本创作中最大的痛点是角色或场景的"不一致"。具体表现为：

不一致类型 示例 后果
角色性格突变 内向角色突然变得外向 观众出戏，人物可信度下降
外貌描述矛盾 前文说"黑色外套"，后文写"灰色大衣" 视觉一致性被破坏
能力设定冲突 前文不会游泳，后文跳河救人 逻辑漏洞
关系定位混乱 前文是同学，后文变成陌生人 叙事断裂

这些问题的根源在于：生成新内容时，系统"忘记"了之前已经建立的设定。长短时记忆系统通过分层存储来解决这个问题。

三层记忆的职责划分（按源码实现核订）

记忆层 存储内容 容量 / 窗口 生命周期 实际机制

两处易混淆的数字：MemoryManager 的"窗口 20 条"是 deque 长度；WorkflowMemory 类文档里还定义了自己的归档策略（短期保留最近 5 条、中期最多 20 条、长期最多 30 条）。两套数字分属不同层，不冲突。

短期记忆详解

短期记忆基于 LangChain 的 ChatMessageHistory 构建，存两类内容：会话消息对（用户输入 + AI 输出），以及手工维护的 deque 滑动窗口（maxlen 由 short_term_size 决定，工作流里取 20）。

常见说法"短期记忆用 LRU + TTL"需要修正：源码里的窗口是 deque(maxlen=20)（short_term_memory.py）——满了自动从队首丢弃，这是固定长度滑动窗口（FIFO），不是按访问时间淘汰的 LRU。TTL 只在 Redis 模式下生效（RedisChatMessageHistory 的 ttl=3600）；纯内存模式下没有自动过期，退场靠窗口滚动。系统还准备了一条兜底通道：Redis 不可用且配置了 term_persist_path 时，会话落到 {path}/{script_id}/short_term.json 文件。

启动时的可用性探测值得单独一提：ShortTermMemory 会先 redis.from_url(...).ping() 试探，成功才用 Redis，失败仅打一条 warning 就切换到内存存储——静默降级，调用方无感知。

中期记忆详解

中期记忆的写入时机与工作流阶段绑定：每个节点完成后，WorkflowMemory.after_stage_completion() 提取该阶段统计（场景数、角色数、问题数、修复参数等），作为一条带时间戳的摘要存入中期层。读取侧则相反——每个阶段开工前先取 stats_parse_script（解析统计）、stats_segment_shot（分镜统计）等历史摘要，注入智能体作为参照。

"压缩存储（max_tokens=500）"与代码一致，这个限制挂在 MemoryConfig.medium_term_max_tokens 上。需要说明的是：实际压缩发生在写入路径，读出来的就是已压缩的统计字典；"任务完成时归档到长期或清理"属于规划描述，当前代码没有自动归档/清理逻辑，需要显式调用。

长期记忆详解

长期记忆的底层是 Chroma 向量库（langchain_chroma），collection 按剧本隔离：script_{script_id}_memory，持久化目录为 {term_persist_path}/{script_id}。检索时用 similarity_search_with_score 取回 Top-K（k=3）并按 long_term_score_threshold 过滤低分结果。写入的内容包括：

  • 各阶段提炼的"成功模式"与可复用结论

  • 长期层维护的常见问题模式（_load_common_patterns() 在工作流启动时就把它们读回来）

  • 经过质检的片段与修复经验

文章早期版本写过"已存储 78 条文档、768 维 BGE 嵌入"——这两个具体数字没有可在仓库中追溯的来源，勘正为：集合中文档数可随时通过 get_stats() 查询（返回 Chroma collection 的实际 count），嵌入维度取决于运行时配置的嵌入模型，都不应写成固定值。

记忆生命周期：一次事件，三层分发

真实代码里没有"短期提升为中期、中期提升为长期"的自动升华机制——after_stage_completion() 是在同一次事件里把不同粒度的结果分别写进三层：

"""
记忆系统演示 - 三层记忆的存储与检索（概念示例）

from datetime import datetime, timedelta
from collections import OrderedDict

class ShortTermMemory:
    """短期记忆 - LRU缓存 + TTL过期"""
    
    def __init__(self, max_size=20, ttl_seconds=3600):
        self.max_size = max_size
        self.ttl = ttl_seconds
        self._store = OrderedDict()  # key -> (value, timestamp)
    
    def set(self, key, value):
        """存储短期记忆"""
        # 容量控制
        if len(self._store) >= self.max_size:
            self._store.popitem(last=False)
        self._store[key] = (value, datetime.now())
    
    def get(self, key):
        """获取短期记忆（自动检查过期）"""
        if key not in self._store:
            return None
        
        value, timestamp = self._store[key]
        if datetime.now() - timestamp > timedelta(seconds=self.ttl):
            del self._store[key]
            return None
        
        # LRU: 移到末尾
        self._store.move_to_end(key)
        return value
    
    def get_all(self):
        """获取所有未过期的记忆"""
        result = {}
        for key, (value, timestamp) in list(self._store.items()):
            if datetime.now() - timestamp <= timedelta(seconds=self.ttl):
                result[key] = value
            else:
                del self._store[key]
        return result


class MediumTermMemory:
    """中期记忆 - 阶段摘要存储"""
    
    def __init__(self, max_tokens=500):
        self.max_tokens = max_tokens
        self.summaries = {}  # stage -> summary
        self._current_tokens = 0
    
    def add_summary(self, stage, summary):
        """添加阶段摘要"""
        # 估算token数（简单按字符数/2估算）
        estimated_tokens = len(summary) // 2
        
        if self._current_tokens + estimated_tokens > self.max_tokens:
            # 触发压缩：保留最重要的信息
            summary = self._compress(summary)
            estimated_tokens = len(summary) // 2
        
        self.summaries[stage] = summary
        self._current_tokens += estimated_tokens
    
    def get_summary(self, stage=None):
        """获取摘要"""
        if stage:
            return self.summaries.get(stage)
        return self.summaries
    
    def _compress(self, text):
        """压缩文本（保留关键信息）"""
        # 简化实现：取前200字符 + "..."
        if len(text) > 200:
            return text[:200] + "..."
        return text


class LongTermMemory:
    """长期记忆 - 向量存储 + 语义检索"""
    
    def __init__(self):
        # 模拟向量存储
        self.documents = []  # 实际使用向量数据库
        self.id_counter = 0
    
    def store(self, content, metadata):
        """存储长期记忆"""
        doc_id = f"doc_{self.id_counter}"
        self.id_counter += 1
        
        self.documents.append({
            "id": doc_id,
            "content": content,
            "metadata": metadata,
            "timestamp": datetime.now()
        })
        
        print(f"存储长期记忆: {doc_id} - {content[:50]}...")
    
    def search(self, query, top_k=3):
        """语义检索（模拟）"""
        # 实际实现使用向量相似度计算
        results = []
        query_lower = query.lower()
        
        for doc in self.documents:
            # 简单的关键词匹配（实际应用使用向量检索）
            content_lower = doc["content"].lower()
            score = 0
            for word in query_lower.split():
                if word in content_lower:
                    score += 1
            
            if score > 0:
                results.append({
                    "id": doc["id"],
                    "content": doc["content"],
                    "metadata": doc["metadata"],
                    "score": score / len(query_lower.split())
                })
        
        results.sort(key=lambda x: -x["score"])
        return results[:top_k]


class MemorySystemDemo:
    """记忆系统完整演示"""
    
    def __init__(self):
        self.short_term = ShortTermMemory()
        self.medium_term = MediumTermMemory()
        self.long_term = LongTermMemory()
    
    def process_interaction(self, user_input, response):

            "input": user_input,
            "response": response,
            "timestamp": datetime.now()
        })

        if "通过" in response or "成功" in response:

            )
    
    def get_context(self, query):

            for key, value in list(recent.items())[-3:]:

            for doc in similar:
                context_parts.append(f"  - {doc['content'][:80]}... (相关度: {doc['score']:.2f})")

关键要点拆解（七）：自迭代优化闭环

核心解决的问题

传统的召回系统是静态的——检索策略一旦确定就不会改变。剧本分镜场景需要的是"生成-质检-修复"闭环：生成结果被审计，不合格的打回重做，成功的经验沉淀下来。

但需要先区分两种"自迭代"：

  1. 策略自调整：系统自动分析问题根源，然后修改检索策略（例如"增加角色情绪历史作为检索维度"）。这种机制在 PenShot 中不存在——仓库里没有任何"根据审计结果调整召回参数"的代码；

  2. 参数化返工 + 经验沉淀：审计不合格 → 生成修复参数 → 节点带参重跑；成功的结果与修复记录写入记忆层与模板库。这是真实实现的形态，细节如下文。

真实质检：两层审计，五个规则维度

文章早期版本写"覆盖 10+ 个检查维度"，并按角色一致性、道具状态机等叙事维度描述"检查方式"——这些检查方式在源码中不存在。真实的质检由两个审计器组成：

RuleQualityAuditor（规则审计，5 项）：

检查项 源码方法 检查内容
片段时长 _check_fragment_duration 每个片段的时长是否在允许区间
提示词内容 _check_prompt_content 提示词是否为空、是否含占位符残留
提示词长度 _check_prompt_length 长度是否超出模型可接受范围
片段数量 _check_fragment_count 片段总数是否符合预期
模型支持 _check_model_support 目标视频模型是否支持该配置

LLMQualityAuditor（语义审计）：用 LLM 对生成结果做连贯性与质量审查，输出评分与问题描述。

两层审计共同产出 QualityAuditReport（分数 + 问题清单）。值得注意的恰是规则审计的口径：五项全是"工程格式"维度（时长/长度/数量），而不是"叙事"维度（角色一致性/道具状态）——后者由 LLM 审计与连续性守护（另一套组件）承担。文章的叙事化描述属于对职责的误记。

修复回流流程详解（真实口径）

步骤一：问题发现——节点产出（如 AIVideoInstructions）被两层审计器检查，生成 QualityAuditReport，包含总体评分与问题列表。不是文章早期版本所说的"输出问题位置到片段的哪个属性"这类细粒度定位。

步骤二：修复参数生成——审计未通过时，系统生成修复参数 repair_params（issue_types 表明问题类型、suggestions 给出修复建议），写入工作流状态。

步骤三：节点带参重跑——下一次进入该节点时，节点先读取 repair_params（apply_repair_params），把它注入提示词作为额外修正指令，然后重新执行。没有"定向召回角色情绪历史"之类的定向检索增强——真实的重跑是"同一个节点、带更多上下文、再试一次"。

步骤四：循环保护——重跑次数受节点级循环限制保护（workflow_decision 中的 _check_node_loop_limit），达到上限后不再盲目重试。

步骤五：经验沉淀——成功的阶段结果经 after_stage_completion 写入三层记忆；成功提示词经 WorkflowMemory 调用 knowledge_manager.save_successful_prompt 进入模板库（嵌入相似度阈值 0.7 去重后保存）。下一次任务开工时，这些沉淀会作为历史上下文被重新读出——闭环由此合上。

"""
自迭代优化演示 - 生成-质检-修复-学习闭环（概念示例）
"""

class SelfHealingDemo:
    """自迭代优化闭环演示"""
    
    def __init__(self):
        self.repair_history = []
        self.success_patterns = []
    
    def generate_with_quality_loop(self, query, context, max_attempts=3):
        """
        带质检闭环的生成
        
        流程：生成 -> 质检 -> 有问题则修复 -> 重试 -> 记录学习
        """
        attempt = 0
        last_result = None
        repair_strategy = None
        
        while attempt < max_attempts:
            attempt += 1
            
            # 1. 执行召回
            recall_results = self._multi_recall(query, context, repair_strategy)
            
            # 2. 生成内容
            result = self._generate(query, recall_results)
            
            # 3. 质量审计
            issues = self._audit(result, context)
            
            if not issues:
                # 通过质检
                print(f" 第{attempt}次尝试通过质检")
                self._record_success(query, result, repair_strategy)
                return result
            
            # 4. 分析问题根源
            root_cause = self._analyze_root_cause(issues, result, context)
            print(f" 第{attempt}次尝试发现问题: {root_cause['description']}")
            
            # 5. 生成修复策略
            repair_strategy = self._generate_repair_strategy(root_cause, issues)
            print(f" 修复策略: {repair_strategy['description']}")
            
            last_result = result
        
        print(f" {max_attempts}次尝试后仍未通过质检")
        return last_result
    
    def _multi_recall(self, query, context, repair_strategy=None):
        """多路召回（可根据修复策略调整）"""
        results = {
            "exact": [],
            "vector": [],
            "graph": [],
            "memory": []
        }
        
        # 基础召回
        results["exact"] = self._exact_recall(query)
        results["vector"] = self._vector_recall(query)
        
        # 根据修复策略增强召回
        if repair_strategy:
            if repair_strategy["type"] == "character":
                # 增强角色相关召回
                char_name = repair_strategy["target"]
                results["memory"] = self._character_memory_recall(char_name)
            elif repair_strategy["type"] == "scene":
                # 增强场景相关召回
                scene_name = repair_strategy["target"]
                results["memory"] = self._scene_context_recall(scene_name)
        
        return results
    
    def _audit(self, result, context):
        """
        质量审计 - 检测多个维度的问题
        
        返回问题列表，空列表表示通过
        """
        issues = []
        
        # 检查角色一致性
        character_issue = self._check_character_consistency(result, context)
        if character_issue:
            issues.append(character_issue)
        
        # 检查场景连续性
        scene_issue = self._check_scene_continuity(result, context)
        if scene_issue:
            issues.append(scene_issue)
        
        # 检查动作逻辑
        action_issue = self._check_action_logic(result, context)
        if action_issue:
            issues.append(action_issue)
        
        return issues
    
    def _analyze_root_cause(self, issues, result, context):
        """分析问题根源"""
        # 根据问题类型判断根源
        for issue in issues:
            if issue["type"] == "character_inconsistent":
                return {
                    "type": "character",
                    "description": f"角色{issue['character']}的描述不一致",
                    "target": issue["character"],
                    "missing_info": "角色的完整设定或情绪历史"
                }
            elif issue["type"] == "scene_jump":
                return {
                    "type": "scene",
                    "description": f"场景切换不连贯: {issue['from']} -> {issue['to']}",
                    "target": issue["to"],
                    "missing_info": "过渡描述或场景氛围"
                }
        
        return {"type": "unknown", "description": "未知问题", "target": None}
    
    def _generate_repair_strategy(self, root_cause, issues):
        """生成修复策略"""
        if root_cause["type"] == "character":
            return {
                "type": "character",
                "description": f"增强召回角色'{root_cause['target']}'的设定和历史",
                "target": root_cause["target"],
                "enhanced_recall": True
            }
        elif root_cause["type"] == "scene":
            return {
                "type": "scene",
                "description": f"增强召回场景'{root_cause['target']}'的氛围和上下文",
                "target": root_cause["target"],
                "enhanced_recall": True

关键要点拆解（八）：多智能体协作召回的真实形态

在影视制作流程中，不同环节对素材的需求差异很大：

智能体 职责 素材需求 数据特征
脚本解析器 理解剧本结构 角色、场景、对话、动作 结构化数据
分镜生成器 将文字转为视觉描述 镜头类型、构图、运镜 视觉元素
视频分割器 将长镜头切分为片段 动作断点、对话停顿 时序数据
提示词转换器 生成 AI 视频提示词 风格、光线、色彩 描述性文本

理想中的"协作召回"是这样的：每个智能体维护自己的向量索引，智能体间互相调用检索结果。这套描述在 PenShot 中没有实现——真实形态要朴素得多，也更符合工程直觉：

  • 不是"每个智能体一套索引"，而是共用一套资源、按 script_id 隔离：所有节点共享同一个 PromptTemplateManager / ScriptKnowledgeBase / MemoryManager（均由 WorkflowNodes 在初始化时创建）；

  • 不是"智能体间互相调用"，而是工作流顺序编排 + 状态传递：上游节点把结果写进 WorkflowState，下游节点从中读取；

  • "上下文保持连贯"的真实机制是 WorkflowMemory：每个阶段开工读历史、完工写归档，这是跨节点共享上下文的枢纽。

排坑提示

综合本次源码核对，给召回体系的工程落地提炼五条更有针对性的提示：

  • 先确认"哪个模块真的在跑"：PenShot 的教训是文档与代码的差距可以很大——GraphRAG 零命中、混合检索未接线、记忆系统真在跑。集成前先做一次"调用方检索"，比读文档可靠。

  • "已实现未接线"是隐蔽陷阱：KnowledgeRouter 有完整的四源检索与重排序接线，但无调用方。这类代码在重构时最容易被误删，也最容易让人误以为功能已上线——建议在文件头标注接线状态。

  • 静默降级要能被观测：短期记忆的 Redis 探测失败时只打 warning，降级本身是合理设计，但缺少"当前处于哪档降级"的可观测指标，线上排查会很被动。

  • 手写相似度扫描要知道它的边界：ScriptKnowledgeBase.query 是 O(N) 全量扫描，文档量小时简单可靠，规模上来后需换索引结构（HNSW 等）——届时注意迁移路径与分数口径的变化。

  • 质检闭环的重试必须有界：节点级循环限制（_check_node_loop_limit）是现有保护；修复参数虽会记录（repair_applied），但"哪种修复建议最有效"缺乏回访统计——这是自迭代闭环下一步最有价值的增强点。

总结与建议

把全文的核对结论收拢成一张清单——PenShot 召回体系的真实面貌是"两段已接线的朴素链路 + 一套已实现未接线的混合检索 + 一批规划中的概念"：

机制 文档口径 源码口径 性质
三层记忆 分层存储、跨任务复用 MemoryManager + WorkflowMemory，四阶段读写 ✅ 已接线
模板召回 历史成功案例复用 PromptTemplateManager（阈值 0.7、top_k=3） ✅ 已接线
向量检索 BGE + HNSW 手动余弦全量扫描 ✅ 已接线（形态朴素）
混合检索 RRF 融合多路召回 串行聚合 + 硬编码分数 + 前缀去重 ⚠️ 未接线
重排序 CrossEncoder 精排 bge-reranker-large 挂在未接线路径 ⚠️ 未接线
GraphRAG 知识图谱推理 无 ❌ 零命中
策略自迭代 自动调整检索维度 无（真实的是修复参数重跑 + 经验沉淀） ❌ 概念混淆

给同类"带记忆创作智能体"的三条建议，来自这次核对的直接观察：

  1. 记忆的价值在"读"而不在"写"：PenShot 的记忆系统之所以是全系列少见的"真在跑"模块，关键在于每阶段开工前的读取动作（历史统计、常见问题注入）——只写不读的记忆是最常见的过度设计；

  2. 融合算法的前置条件是统一分数口径：在"手动余弦 + 硬编码分数"的混合分数体系升级到 RRF 之前，先做归一化或排名化改造，否则融合只会放大分数口径的混乱；

  3. 把"接线状态"当成一等公民：未接线的完整实现（KnowledgeRouter）、零命中的规划（GraphRAG）与已接线的链路混在一起，最直接的治理手段是让每种状态都有可核查的标记——这也是本系列文章的立意。
