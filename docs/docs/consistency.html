PenShot 一致性策略：多片段生成如何压制角色与场景漂移

相关链接：GitHub | 官网 | 文档 （架构设计 · 集成指南 · MCP Server · RAG 增强） | 多智能体如何保证 AI 视频分镜一致性

文档定位：这是一篇设计/机制文档。文中会把已经实现的能力与设计推演分开，避免把路线图、示例代码或理论方案误认为当前版本功能。
事实边界：实现文档：功能、接口和代码行为以文中标注版本对应的源码为准；仓库后续版本可能发生变化。
权威来源：PenShot 源码仓库；涉及版本历史时，以仓库 Release / CHANGELOG 为准。
代码标记：如果正文出现“源码/实现”字样，表示对应代码路径可在仓库中核对；示例代码仅用于演示调用方式，不应理解为项目源码原样。

一、概述：一致性保障核心价值

PenShot 围绕"多片段生成的片段间漂移"建立了一套从数据传递到检查修复的策略体系，但各部分的落地程度并不相同。本文按"源码考证"的口径逐层核实：哪些链路已在工作流中真实接线（全局元数据传递、统一提示词约束、规则检查、RAG 检索），哪些是已实现但尚未接入运行时的预留机制（连续性锚点、状态时间线、风格守护、固定种子），哪些属于规划中的增强策略。文中代码均取自真实源码，刻意简化的演示会单独标注。

问题背景：多片段 AI 视频生成最大的痛点在于"片段间漂移"——同一个角色在不同片段里长得不一样、道具时有时无、色彩光影跳变。PenShot 的一致性策略正是为系统性压制这种漂移而设计。

阅读口径："已接线"指该机制在工作流图中被真实调用且有消费方（本文逐项给出源码依据）；"已实现但未接线"指数据结构与算法已落地，但运行时无调用点或调用方缺失（如快照、锚点、风格守护、固定种子）；"修复参数"的生成与消费代码两侧齐备，但连续性修复的回流存在缺口——这是全文唯一的"半接线"状态，细节见 3.3。

三、已实现的核心策略

3.1 锚点信息传递：全局元数据、连续性注释与预留的契约

核心目标：把故事中必须"稳定不变"的事实（谁、在哪、拿什么）抽成结构化数据，从剧本解析一路带到提示词，让每个片段都参考同一份"事实基线"。当前真正在跑的是两条通道——全局元数据（整剧级）与连续性注释（片段级）；为此设计的契约体系尚未接入。

flowchart LR
    subgraph Parse[剧本解析]
        A[global_metadata<br/>key_props / character_outfits<br/>key_locations]
    end

    subgraph Segment[分镜生成]
        B[ShotInfo.main_character]
    end

    subgraph Split[视频分段]
        C[VideoFragment.continuity_notes<br/>main_character / location<br/>main_action / split_type]
    end

    subgraph Convert[指令转换]
        D[_format_global_context<br/>拼装全剧上下文]
        E[提示词模板引用<br/>角色服装/道具/地点]
    end

    A --> D
    B --> C
    A --> C
    C --> E

通道一：全局元数据（整剧级基线）。解析器把贯穿全文的一致性要素提取到 ParsedScript.global_metadata——真实字段为：key_props（关键道具）、character_outfits（角色服装）、key_locations（关键地点）、continuity_notes（字符串形式的连续性要点）、audio_atmosphere（全局音频氛围）、recurring_sounds（重复出现的声音）。转换节点用 _format_global_context 把它格式化为四段提示词上下文：【本场景关键道具】（按 appears_in 过滤 + importance 标记 ⭐）、【角色服装要求】（颜色 + 描述 + 风格 + 材质）、【本场景地点】（视觉线索）、【特别注意，连续性要求】——只有出现在当前场景的条目才会注入，避免无关信息稀释提示词。

通道二：连续性注释（片段级接力）。视频分段节点把镜头级信息写入 VideoFragment.continuity_notes，供下游读取。这里有一个容易被忽略的细节——字段集因切分路径而异：

写入方 字段集
规则切分（rule_video_splitter） main_character、location（固定为 场景{scene_id}）、main_action、split_type（none / split），拆分时另有 part
LLM 切分（llm_video_splitter） main_character、location、continuity_id、prev_fragment、split_reason、segment_part、character_consistency、scene_consistency、transition_suggestions、continuity_hints

工程提示：转换器读取 main_character / location 时（多为直接索引、个别路径用 .get 兜底）——两条切分路径都保证写入了这两个键，所以不会因缺键而崩；但如果你写的下游代码依赖 main_action 或 split_type，务必注意 LLM 切分路径不产生这两个字段。

预留未接线：ContinuityAnchor 与契约体系。代码库中另有专为"锚点约束生成"设计的模型 ContinuityAnchor（位于 continuity_guardian/continuity_guardian_models.py），字段为 anchor_id / anchor_type（character、scene、prop、style）/ name / value / start_time / end_time / fragment_range / priority / metadata，并带 is_active_at(time) 判定"某时刻是否生效"；StateTimeline.continuity_anchors 与工作流状态也在等它的写入方。但全仓库检索：ContinuityAnchor 除定义处外没有任何引用——它和配套的 GlobalConsistencyContract 契约体系（script_parser 的 process_with_contract、检查器的 check_with_contract、CrossChunkValidator）都处于"实现完成、接线未完成"状态。换句话说：当前的角色/道具/地点一致性靠"文本字段传递 + 提示词引用"实现，而非结构化的锚点约束。

要点：锚点信息的现状是"两条已通电的通道 + 一套未通电的体系"——global_metadata（整剧）和 continuity_notes（片段）负责今天的稳定性；ContinuityAnchor / 契约体系是为此设计的下一步，接入后锚点才能带生效区间与优先级参与生成约束。

3.2 状态快照：一条"搭好未通电"的时间线

状态快照机制的设计意图是"以时间线保存每一刻的连续状态"，让任意片段都能回放到其前驱状态。如实说明：这套机制的数据结构与算法已完整落地在连续性守护模块中，但在当前工作流里没有任何调用点——属于"预留未接线"。 本节按其真实实现展开，并给出接入时需要留意的语义细节。

flowchart LR
    subgraph 已实现模型[已实现的模型与算法]
        A[StateSnapshot<br/>快照模型] --> B[StateTimeline<br/>时间线管理]
        B --> C[add_snapshot<br/>按时间排序]
        B --> D[get_snapshot_at_time<br/>按时间查询]
        B --> E[get_latest_snapshot<br/>最新状态]
    end

    subgraph 缺口[未接线]
        F[take_snapshot<br/>检查器提供入口]
        G[工作流调用方]
    end

    F -.->|缺调用方| G

真实实现（continuity_guardian_models.py）。StateSnapshot 的关键字段：timestamp、snapshot_id（必填）、character_states（人名 → CharacterState）、scene_state、global_state（默认含 current_scene / time_elapsed / narrative_phase / emotional_tone）、references（fragment_id / shot_id / element_ids 来源引用）。StateTimeline 提供 add_snapshot（追加后按时间排序）、get_snapshot_at_time、get_latest_snapshot、get_character_evolution 与 record_evolution（状态演化历史），另有 tolerance_settings 容差设置（位置中等 / 外观低 / 时间高 / 颜色中等）。

检查器里提供了快照创建入口，实现如下（真实源码，ContinuityGuardianChecker.take_snapshot）：

def take_snapshot(self, context: Dict[str, Any]) -> StateSnapshot:
    """创建状态快照"""
    self.snapshot_counter += 1

    snapshot = StateSnapshot(
        timestamp=time.time(),
        snapshot_id=f"snapshot_{self.snapshot_counter:04d}",
        character_states={},
        scene_state=None
    )

    parsed_script = context.get("parsed_script")
    if parsed_script:
        for char in parsed_script.characters:
            snapshot.character_states[char.name] = CharacterState(
                character_name=char.name,
                appearance={"description": char.description or ""},
                emotion={"type": "neutral", "intensity": 0.5}
            )

    self.timeline.add_snapshot(snapshot)
    return snapshot

未接线考证：全仓库检索 take_snapshot，除定义处外没有任何调用点；工作流状态中的 continuity_anchors、快照列表也没有写入方。也就是说，当前工作流在视频分段后不会创建快照，提示词转换也不会加载历史快照——片段间的接力仍靠 continuity_notes 与 global_metadata 的文本传递（3.1）。

接入前需要厘清的语义：get_snapshot_at_time(t) 的真实行为是返回第一个 timestamp ≥ t 的快照（从头线性遍历），全部快照都早于 t 时返回最后一个——这与"按时间回溯最近状态"的直觉不同（源码注释写的是"二分查找最接近的快照"，实现却是线性遍历且方向朝前）。若未来要支持"回放某时刻状态"，这里需要先统一定义：是要"≥ t 的最近快照"还是"≤ t 的最近快照"；此外快照的 references（片段引用）目前也未被填充，无法定位快照与具体片段的对应关系。

要点：状态快照是一条完整设计但尚未接入的时间线。它的价值场景很明确——双向约束、运动插值、跨片段回放（见第四、五节规划）都依赖"任意时间点的状态查询"；但接入前要先解决查询语义与引用信息两个前置问题。

3.3 修复参数反馈：生成链路与未接通的回流

修复参数反馈是"自我纠错"的载体：检查节点不直接改数据，而是生成一份 QualityRepairParams，告诉上游"下次怎么做"。它由 Pydantic 模型承载，生成与消费两侧的代码都已落地，唯独连续性修复的"回流"存在一处缺口——本节先讲真实链路，再指出缺口。

flowchart LR
    subgraph Detect[检测与生成]
        A[质量审查 / 连续性守护<br/>发现违规或问题] --> B[QualityRepairParams<br/>按问题分组生成]
        B --> C[写入 state.domain.repair_params<br/>键为 PipelineNode 枚举]
    end

    subgraph Consume[消费与回流]
        D[四个上游节点开头<br/>读本阶段修复参数] --> E[apply_repair_params<br/>记录修复历史]
        E --> F[_on_repair_params_applied 钩子<br/>子类调整执行策略]
    end

    C -->|质量审查侧：已接通| D
    C -.->|连续性侧：回流未接通| D

真实数据结构（quality_auditor_models.py）：

class QualityRepairParams(BaseModel):
    fix_needed: bool = Field(default=False, description="是否需要修复")
    issue_count: int = Field(default=0, description="问题数量")
    issue_types: List[str] = Field(default_factory=list, description="修复类型")
    issues: List[Any] = Field(default_factory=list, description="完整问题列表（可以是 BasicViolation 或 ContinuityIssue）")
    fragments: List[str] = Field(default_factory=list, description="对应的片段ID集合")
    suggestions: Dict[str, List[str]] = Field(default=None, description="修复建议")
    severity_summary: Dict[str, int] = Field(default=None, description="严重程度摘要")

值得注意：它没有 source_stage 字段——"该回退到哪个阶段"不由参数自己声明，而是由写入 repair_params 字典时的键（PipelineNode 枚举）表达；issues 用 List[Any] 同时容纳 BasicViolation（审查）与 ContinuityIssue（守护）两种来源。问题类型、路由目标、策略修正三层在数据结构层面是解耦的。

两条生成链路：

  • 质量审查：审计节点把违规聚合成修复参数写入状态；决策返回 NEEDS_REPAIR 时图映射把流程送回对应阶段——审查侧的修复回流是真实接通的。

  • 连续性守护：ContinuityRepairGenerator.generate_repair_params() 按 8 种问题类型生成建议文案（character_missing →"为角色添加镜头…"、scene_jump →"添加过渡镜头…"等），建议按 fragment_id 或 global 分组；_route_to_fix_stage 再按"解析 → 拆分 → 分段 → 转换"优先级挑选最早命中的阶段，改写 current_node。

消费端真实实现（base_repairable_agent.py）：

def apply_repair_params(self, node: PipelineNode, repair_params: QualityRepairParams) -> None:
    """应用修复参数（在下次执行时生效）"""
    self.current_repair_params = repair_params

    info(f"{node.value}节点收到修复参数，问题类型: {repair_params.issue_types}")
    if repair_params.suggestions:
        info(f"修复建议: {repair_params.suggestions}")

    # 记录修复历史
    self.repair_history.append({
        "timestamp": time.time(),
        "repair_params": {
            "issue_types": repair_params.issue_types,
            "suggestions": repair_params.suggestions
        }
    })

    # 子类可以重写此方法，根据修复参数调整内部状态
    self._on_repair_params_applied()

四个上游节点（解析 / 分镜 / 分段 / 转换）在节点函数开头统一执行"读 repair_params[自己节点] → 非空则调用 apply_repair_params"，再由各 Agent 子类重写 _on_repair_params_applied() 落地具体调整。这种"参数驱动重试 + 钩子式策略修正"的取舍：新增一类修复只需定义问题类型与建议文案，不必改动路由骨架；代价是实际修正效果分散在各子类钩子里，排查时要顺着钩子逐个看。

未接通缺口（源码考证）：连续性检查节点发现问题后会完成"生成修复参数 + 计数 + 改写路由目标"全套动作，但图边决策函数 decide_after_continuity 读取的是 state.continuity_issues——组合状态重构后该字段已移入 state.domain.continuity_issues，顶层属性不存在，getattr(..., []) 静默取空，决策恒为 SUCCESS，流程直接进入结果生成。因此本次运行中连续性修复参数不会被上游消费；即便修正读取路径，决策返回的 NEEDS_RETRY 也不在图映射的键集合里（只声明了 NEEDS_REPAIR 等键）。要让回流真正通电，需同时做这两处小改动。质量审查侧的修复回流不受影响。

闭环语义：检测 → 生成参数 → 按节点枚举写入 → 重试时消费 → 钩子调整策略。现状：审查侧闭环可用，连续性侧回流未通电；issue_types / suggestions / severity_summary 在两侧生成链路中都已被真实填充，消费端代码也齐备——缺的只是"把流程送回去"的那一跳。

3.4 统一提示词约束：从 global_metadata 到四段注入

统一提示词约束把"每段都要遵守的共性要求"抽出来，在生成每个片段的提示词时重复注入，避免各写各的导致风格漂移。真实实现与常见想象不同：没有一份全局约束模板字符串，而是由 _format_global_context 在运行时按场景过滤 global_metadata、拼出四段上下文，再通过提示词模板进入 LLM 生成指令。

flowchart LR
    subgraph Source[数据来源]
        A[ParsedScript.global_metadata<br/>key_props / character_outfits<br/>key_locations / continuity_notes]
    end

    subgraph Format[运行时格式化]
        B[_format_global_context<br/>按场景过滤]
        C[【本场景关键道具】<br/>无命中降级为全量]
        D[【角色服装要求】<br/>全量输出]
        E[【本场景地点】<br/>无命中降级为全量]
        F[【特别注意，连续性要求】]
    end

    subgraph Inject[模板注入]
        G[提示词模板<br/>【全剧上下文】区块]
        H[【重要约束】生成指令<br/>与全局上下文保持一致]
    end

    A --> B
    B --> C & D & E & F
    C & D & E & F --> G --> H

真实实现（base_llm_agent.py 的 _format_global_context），四段文本的触发与内容：

段落 触发与内容
【本场景关键道具】 key_props 按 appears_in 过滤当前场景，命中输出 名称（颜色）：描述；无命中但存在关键道具时降级为【关键道具】全量输出——importance == "high" 前缀 ⭐，其余 📌
【角色服装要求】 character_outfits 全量输出：角色：{颜色}色{描述}、{风格}、{材质}（服装一致性不分场景，故不过滤）
【本场景地点】 key_locations 按 appears_in 过滤，命中输出 名称：描述，视觉线索；无命中降级为【主要场景】全量
【特别注意，连续性要求】 continuity_notes 原文注入；另有 _format_global_metadata 统一格式化函数，按 prompt / split / shot 三档给不同阶段输出简洁到详细的版本，简化档带超长截断保护

约束如何进入生成：提示词模板（prompts/v1.x/zh/）用"【全剧上下文】“区块引用这段文本，并把一致性要求写进生成指令——例如转换器模板规定"如果参数矛盾，优先采用【全剧上下文】中的设定”；分段模板的【重要约束】要求"本场景涉及【全剧上下文】中的道具，必须在分割后的片段中完整保留"“角色服装必须严格遵循【全剧上下文】中的描述，不可将某个角色的服装特征错误地分配给其他角色”。约束作用在 LLM 的生成指令层，而不是靠字符串硬拼进最终提示词——这比机械拼接更灵活（模型会理解语义），代价是执行程度取决于模型遵从性，需要在质量审查环节兜底验证。

要点：这份设计的巧妙处是"按场景裁剪"——只注入与当前场景相关的道具与地点，而不是把整份全局元数据全量重复 N 遍；既控制 Token 也降低无关信息干扰，而真正要求全局稳定的部分（服装、连续性要点）则始终全量。要复刻这层约束，关注三个词即可：global_metadata → _format_global_context → 模板中的"【全剧上下文】"区块。

3.5 规则检查器：六项词表规则、通过判定与风格守护

连续性守护节点里的真实检查组件是 ContinuityGuardianChecker——它由关键词与数值规则实现，不是 LLM 语义审查，也没有"规则引擎 + 向量相似度"多路校验架构（那是规划设想）。本节按真实实现重写，并补上代码库中另一套独立的风格守护组件。

flowchart LR
    subgraph Check[六项检查（关键词/数值规则）]
        V1[角色：出现在场对照<br/>外观三类词表]
        V2[场景：相邻 scene_id 跳变<br/>跳变占比阈值]
        V3[动作：动作词表按镜头描述追踪]
        V4[风格：style 去重种类数]
        V5[时间：起止时间差]
        V6[道具：道具动词表]
    end

    subgraph After[后处理]
        R1[签名去重] --> R2[通过判定<br/>critical>0 或 major>3] --> R3[分级与修复建议]
    end

    Check --> After

核心检查循环：check_all_continuity(context) 依次执行六项检查——角色（check_character_continuity）、场景、动作、风格、时间、道具，每项先从上下文里提取可用数据（解析结果 / 镜头序列 / 片段序列 / 提示词指令），问题经 _create_issue() 去重后汇入 ContinuityCheckResult。

通过判定是理解这套机制的关键——ContinuityCheckResult.add_issue() 里的真实规则：

if self.critical_count > 0 or self.major_count > 3:
    self.passed = False

即：任何一个 CRITICAL 问题，或超过 3 个 MAJOR 问题，即判定不通过；WARNING / MODERATE / MINOR 再多也不改变 passed。但如前文考证，这个标记目前只影响日志与状态记录，不会真正阻断流程（回流缺口）。

六项检查的判定细节（词表与阈值均取自源码）：

检查 判定方式 触发与严重度
角色 角色出现在场对照 + 外观三类词表（服装 / 发型 / 配饰） 有对话无镜头 → CHARACTER_MISSING（MAJOR）；同类外观词变化 → APPEARANCE_CHANGE（WARNING）
场景 相邻镜头 scene_id 变化；跳变计数 > 镜头数 × 30% 单次跳变 → SCENE_JUMP（WARNING）；占比超限 → SCENE_TOO_FREQUENT（MODERATE）
动作 动作词表（走/跑/跳/转身/坐下/站起/拿起/放下）在镜头描述中追踪 同角色相邻动作词变化 → ACTION_BREAK（MODERATE）
风格 AIVideoPrompt.style 去重种类数 种类数 > 2 → STYLE_INCONSISTENT（MODERATE）
时间 片段 start_time 与"前段起始 + 时长"差值 差值 > 0.1s：正差 → TIME_GAP（MAJOR）；负差 → TIME_OVERLAP（ERROR）
道具 道具动词表（拿/举/抱/提/端/持/握）按角色统计相邻变化 同角色动词变化 → PROP_CHANGE（WARNING）

另一套组件：PromptStyleGuardian（未接线）。代码库还有一份专做风格一致性守护的 PromptStyleGuardian：用 StyleProfile（视觉风格 / 色彩 / 光照 / 镜头运动 / 氛围 / 关键词）描述基线风格，enhance_prompt_with_style() 把风格前缀拼进提示词（带重复检测），detect_style_drift() 用关键词重叠度判定漂移——重叠 < 0.3 判为 style_drift，0.3–0.6 判为 warning（分词靠 re.findall，不做词干归一）。但体检结果同样是"未接线"：全仓库没有实例化点，且它的 initialize_style() 调用了一个当前不存在的方法 search_similar_style——一旦接线会直接 AttributeError。典型的 WIP 组件，如实指出。

要点：规则检查器的务实之处在于零模型成本、可解释、毫秒级完成；边界同样明确——词表匹配的误报/漏报必然存在（"转头"不在词表、"拿手机→握手机"会被判道具变化）。需要真正的语义级判定时，应等风格守护修复接线或引入 LLM 审查补位。

3.6 固定种子：目前只是"执行建议"，尚未真实下发

固定种子（seed）是所有片段共用同一随机数种子，从源头降低文生视频模型的随机差异。如实说明：global_settings 里没有 fixed_seed 字段，生成链路也不传递种子参数——这个策略目前只以"建议文案"的形式存在。

真实结构：AIVideoInstructions.global_settings 的默认值只有两项全局开关：

global_settings = {
    "style_consistency": True,
    "use_common_negative_prompt": True
}

execution_suggestions = [
    "按顺序生成片段",
    "保持相同种子值以获得一致性",
    "生成后检查片段衔接"
]

每个片段的 AIVideoPrompt 携带 duration、model（默认 runway_gen2）与统一的 negative_prompt，但没有任何字段承载种子值。值得玩味的是 execution_suggestions 的第二条——“保持相同种子值以获得一致性”：文案在建议种子，而代码既不生成也不下发任何种子。这是"策略先行、实现未到"的典型切面，也是本文坚持"数据与能力都要区分标注"的原因。

为什么可能是有意为之：PenShot 的定位是"生成指令（提示词包）“而非"调用模型的执行器”——它产出 AIVideoInstructions 交给下游或人工执行，是否能用种子取决于执行方与模型的 API。这带来两个事实边界：

  1. 部分 AI 视频平台（如 Runway Gen-2 的 API）支持显式 seed；这类环境下，执行方完全可以在消费 AIVideoInstructions 时自行注入固定种子——但本仓库中还没有这段代码。

  2. 消费级 AI 视频产品多数不暴露 seed 参数；这类场景下一致性的抓手就落到"统一负面提示词 + 风格约束 + 每段提示词中的角色/场景描述复用"上（3.1、3.4 所述的机制）。

要点：若你的部署环境模型支持 seed，建议在执行层（消费 AIVideoInstructions 的环节）自行注入，而不是改 PenShot 内核；若需要 PenShot 端支持，应先给 AIVideoPrompt 增加种子字段并把"建议"变为数据，再沿生成链路传递。

3.7 向量检索（RAG）：模板库与剧本知识库

PenShot 的 RAG 并不是"把角色/场景/道具/动作分成四类向量库"——那是设计想象。真实实现基于 LlamaIndex + SimpleVectorStore（JSON 持久化），由 KnowledgeManager 统一组织两个知识库：提示词模板库（PromptTemplateKB）与剧本知识库（ScriptKnowledgeBase），且都按 script_id 隔离。

flowchart LR
    subgraph KM[KnowledgeManager 内部]
        A[PromptTemplateKB<br/>成功提示词模板] 
        B[ScriptKnowledgeBase<br/>剧本级知识检索]
    end

    subgraph Store[存储机制]
        C[SentenceSplitter<br/>chunk 512 / overlap 20]
        D[SimpleVectorStore<br/>prompt_vector_store.json]
        E[data/embedding/prompt_templates/<br/>按 script_id 隔离]
    end

    subgraph Query[检索入口]
        F[search_similar_prompts<br/>top_k=3，min_score=0.6]
        G[query 手动余弦检索<br/>search_similar_scene 等入口]
        H[query_character / query_scene<br/>解析结果字典直查]
    end

    A --> C --> D --> E
    B --> G
    F & G & H --> I[检索结果注入生成或问题增强]

提示词模板库（prompt_template_knowledge.py）的真实机制：

  • 存储：提示词以 Document 入库（metadata 带 type=prompt_template、fragment_id、scene、style、quality_score），经 SentenceSplitter(chunk_size=512, chunk_overlap=20) 切分，写入 SimpleVectorStore 并持久化到 data/embedding/prompt_templates/{script_id}/prompt_vector_store.json。

  • 检索：search_similar(query, top_k=3, min_score=0.6)——相似度低于 0.6 的结果直接丢弃，且只返回 type == "prompt_template" 的节点；另提供 get_best_match(min_score=0.7) 的单条入口。

  • 降级：索引未初始化返回空列表、异常返回空列表——不抛错、不让 RAG 故障阻断主流程。

剧本知识库（llama_index_knowledge.py）：工作流实际触发的 query()（search_similar_scene 走它）采用手动余弦相似度全量扫描——遍历向量库逐个算相似度后排序取 Top-K。这里有一个值得注意的细节：方法签名接收 use_rerank 参数，但方法体内并未消费它——调用方传 use_rerank=True 并不会真正重排。真正的 rerank 重排序（BAAI/bge-reranker-large）实现在另一条检索器路径 create_retriever_for_script（支持 similarity / mmr），但该路径目前只被尚未接线到工作流的 KnowledgeRouter 使用；query_character / query_scene 则是解析结果的字典直查，不走向量检索。同样是"失败即降级"：检索不可用时返回空结果，不阻断工作流（工作流侧另有 is_script_kb_available() 前置判断）。

RAG 在一致性链路里的三个真实用法：

场景 入口 作用
提示词生成 search_similar_prompts 检索历史高分模板作为生成参考
连续性问题增强 search_similar_scene（问题描述→历史解决方案，top_k=2） 为 ContinuityIssue 附加 historical_solutions 字段
剧本背景检索 query_character / query_scene 按剧本检索角色与场景背景信息

与"四类向量库"说法的差异：真实实现不存在"角色向量 / 场景向量 / 道具向量 / 动作向量"四个独立集合，也没有固定 1536 / 768 / 1024 维度分工——嵌入模型由外部注入（KnowledgeManager(embeddings, script_id)），维度取决于所选模型。按 script_id 隔离的设计在多剧本场景下能防止跨剧污染，但也意味着跨剧本的经验复用目前无法直接实现——这是"隔离优先"的合理取舍，也是后续可讨论的增强点。

四、各维度规划策略

以下策略均为规划内容，尚未在当前代码中实现，按优先级分为高中低三档。其中"双向约束"“运动插值”"关键帧锁定"等方向所依赖的状态快照与锚点机制已预留了数据结构（见 3.1、3.2），但均未接线；"固定种子"目前仅有建议文案（见 3.6）。本节保留原始规划设想，供路线参考。

4.1 高优先级策略

策略名称 集成位置 预期效果 实现复杂度
色彩管理策略 剧本解析后、提示词生成时 确保场景色调统一 中
光照锚点策略 剧本解析后、提示词生成时 确保光影方向一致 中
关键帧锁定策略 分镜规划时、质量审计后 确保重要帧不偏差 中
双向约束策略 提示词生成时 确保前后片段衔接 中
情绪曲线策略 剧本解析后、提示词生成时 确保情感表达连贯 高
渐进式生成策略 片段生成顺序 优先保证关键片段 高

色彩管理策略实现步骤

  1. 第一步，扩展场景元数据模型。在 SceneInfo 中添加 color_palette 字段，包含主色调、辅助色、色温和饱和度。

  2. 第二步，在剧本解析后分析场景色彩。调用色彩分析服务，从场景描述中提取合理的色彩配置。

  3. 第三步，在提示词生成时嵌入色彩参数。将色彩配置转换为自然语言描述写入提示词。

  4. 第四步，在连续性检查中验证色彩一致性。比较相邻片段的色彩直方图，偏差过大时触发修复。

要点：色彩策略"先定义后校验"——解析后定义调色板并写入提示词（如"暖黄色主色调，色温 3200K，饱和度 0.6"），最后用色彩直方图比对相邻片段，形成闭环。

光照锚点策略实现步骤

  1. 第一步，扩展场景元数据模型。添加 light_anchor 字段，包含主光源方向、辅光源位置、光源类型和强度。

  2. 第二步，从场景描述中推断光照设定。根据场景类型和时间信息自动生成合理的光照配置。

  3. 第三步，在提示词生成时嵌入光照参数。将光照配置写入提示词，如"主光源从左侧45度照射"。

  4. 第四步，在连续性检查中验证阴影方向。确保相邻片段中角色和物体的阴影方向一致。

关键帧锁定策略实现步骤

  1. 第一步，定义关键帧识别规则。基于剧本情感强度、动作重要性识别关键帧。

  2. 第二步，在分镜规划阶段标记关键帧。为识别出的关键帧添加 is_keyframe 标记。

  3. 第三步，优先生成关键帧。修改片段生成调度器，将关键帧排在队列前面优先处理。

  4. 第四步，验证关键帧质量。关键帧生成后，验证关键特征与预期的相似度，低于阈值则重新生成。

双向约束策略实现步骤

  1. 第一步，修改提示词生成逻辑。在生成片段 N 时，同时查询片段 N-1 和片段 N+1 的状态。

  2. 第二步，加载前后片段约束。从片段 N-1 的结束状态获取开始约束，从片段 N+1 的开始状态获取结束约束。

  3. 第三步，生成双向约束描述。将前后约束转换为自然语言写入提示词。

  4. 第四步，验证生成结果满足双向约束。生成后检查片段是否同时满足开始和结束约束。

要点：双向约束突破"只看前驱"的局限——片段 N 开头要匹配 N-1 的结尾、结尾要过渡到 N+1 的开头，从而强化镜头间的衔接。

情绪曲线策略实现步骤

  1. 第一步，扩展角色模型。在 CharacterInfo 中添加 emotion_timeline 字段存储情绪曲线。

  2. 第二步，从剧本中提取情绪标注。识别每个场景中角色的情绪状态，量化为 0-10 的强度值。

  3. 第三步，构建情绪曲线。按时间顺序连接情绪点，形成连续的情绪变化轨迹。

  4. 第四步，在提示词中嵌入情绪参数。当前片段对应的情绪强度值写入提示词，附带典型表现描述。

  5. 第五步，验证情绪变化合理性。连续性检查时评估情绪变化是否平滑，是否符合曲线预期。

渐进式生成策略实现步骤

  1. 第一步，修改片段生成调度器。从顺序生成改为优先级队列调度。

  2. 第二步，识别关键帧优先级。根据关键帧标记和剧本重要性计算每个片段的优先级分数。

  3. 第三步，按优先级顺序生成。高分片段优先生成，低分片段延后生成。

  4. 第四步，以关键帧为锚点扩展。关键帧生成后，向前后方向逐步生成过渡片段。

要点：渐进式生成"先关键帧、后过渡"——核心画面优先获得高质量生成机会，再以关键帧为锚点向前后补齐过渡片段，避免"关键信息被低优先级片段拖累"。

4.2 中优先级策略

策略名称 集成位置 预期效果 实现复杂度
构图模板策略 分镜规划时 确保镜头语言统一 中
镜头语法策略 分镜规划时 确保专业剪辑规范 中
因果链追踪策略 剧本解析后 确保逻辑完整性 高
运动插值策略 连续性守护时 解决动作不连续 中

构图模板策略实现步骤

  1. 第一步，定义构图模板库。预定义过肩镜头、正反打、全景、中景、特写等模板的参数。

  2. 第二步，在分镜规划时选择模板。根据剧本类型和镜头用途匹配最合适的构图模板。

  3. 第三步，将模板参数写入分镜数据。记录模板类型和关键参数作为后续生成的参考。

  4. 第四步，在提示词中应用构图约束。将构图要求转换为自然语言写入提示词。

镜头语法策略实现步骤

  1. 第一步，在分镜规划中实现 180 度轴线规则。记录每个对话场景的轴线方向，后续镜头检查是否越轴。

  2. 第二步，实现视线匹配规则。根据角色位置自动计算视线方向，确保角色看向正确的方向。

  3. 第三步，实现动作连贯规则。检查动作的起势和收势是否完整。

  4. 第四步，在质量审计中验证语法规则。违反规则时生成修复参数触发重试。

要点：镜头语法把专业剪辑的硬规则（180 度轴线不越轴、视线匹配、动作起收完整）编码进系统，让分镜"符合行业规范"而不仅是"语义正确"。

因果链追踪策略实现步骤

  1. 第一步，在剧本解析阶段构建因果图。识别事件之间的因果关系，构建有向图结构。

  2. 第二步，存储因果关系到全局元数据。记录每个事件的前置原因和后置结果。

  3. 第三步，在连续性检查阶段验证因果链。检查片段序列是否完整体现了因果关系。

  4. 第四步，检测到逻辑断裂时生成补全片段。如检测到敲门后没有开门，生成开门片段。

运动插值策略实现步骤

  1. 第一步，在连续性检查中检测动作不连续。比较相邻片段结束和开始的位置、姿态差异。

  2. 第二步，计算需要插值的中间状态。根据位移距离和动作类型生成合理的中间步骤描述。

  3. 第三步，生成过渡片段描述。将中间状态转换为提示词，触发重新生成过渡片段。

  4. 第四步，验证插值效果。检查新生成的过渡片段是否平滑连接前后片段。

要点：运动插值解决"片段一结束在门口、片段二开始在沙发上"这类空间跳变——计算位移并生成"从门口走向沙发，坐下"的中间片段，补齐运动逻辑。

4.3 低优先级策略

策略名称 理由
景别序列策略 可由构图模板部分覆盖
节奏图谱策略 对文生视频模型约束力有限
提示词向后兼容 现有锚点机制已部分覆盖
对抗生成策略 资源消耗过大
时间线对齐策略 可由双向约束替代

取舍逻辑：低优先级策略或因"已被其他策略覆盖"（景别≈构图、时间线≈双向约束），或因"性价比低"（对抗生成资源消耗过大、节奏图谱对模型约束力有限），故暂缓实现。

4.4 规划策略集成说明

  • 色彩管理策略

    在剧本解析完成后，系统为每个场景定义主色调、辅助色、色温和饱和度范围。这些色彩参数存储在场景元数据中。在提示词转换阶段，色彩参数被写入提示词。例如：“场景采用暖黄色主色调，色温 3200K，饱和度 0.6”。在连续性守护阶段，系统会检查相邻片段的色彩直方图是否匹配，不匹配则触发修复。

  • 光照锚点策略

    为每个场景定义主光源方向、辅光源位置、光源类型和光照强度。例如：“主光源从左侧 45 度照射，辅光源从右侧补光，柔光类型，强度 0.7”。光照参数同样在提示词中编码，并在连续性检查中验证阴影方向的一致性。

  • 关键帧锁定策略

    在分镜规划阶段，系统识别剧情的关键转折点、角色的首次出场、重要道具的特写等关键帧。这些关键帧被标记为"锁定"，在生成时优先处理，并且生成后需要验证关键特征与预期的相似度。相似度低于阈值则重新生成，直到满足要求。

  • 双向约束策略

    在生成片段 N 时，系统同时加载片段 N-1 的结束状态和片段 N+1 的开始状态作为约束。片段 N 的开始必须匹配片段 N-1 的结束，结束必须能够自然过渡到片段 N+1 的开始。这种双向约束通过提示词中的明确描述实现，例如：“片段开始时，林然站在窗前，面向窗外；片段结束时，林然转身面向门口，准备开门”。

  • 情绪曲线策略

    从剧本中提取每个场景中角色的情绪状态，量化为 0-10 的强度值，构建情绪曲线。在提示词生成时，情绪强度被写入，例如：“林然的焦虑程度为 7，表现为眉头紧锁、呼吸急促”。连续性守护会检查角色情绪的变化是否平滑，是否符合情绪曲线。

  • 渐进式生成策略

    改变片段的生成顺序。不再是按时间顺序从第一个片段生成到最后一个片段，而是先识别所有关键帧优先生成。关键帧生成完成后，再以关键帧为锚点，向前后两个方向逐步生成过渡片段。这种策略确保最重要的片段有更多机会获得高质量结果，过渡片段围绕关键帧进行调整。

  • 构图模板策略

    预定义对话场景的过肩镜头模板、动作场景的中景镜头模板、情绪场景的特写镜头模板。在分镜规划时，根据剧本内容选择合适的模板，模板参数写入分镜数据，作为提示词生成的参考。

  • 镜头语法策略

    在分镜规划阶段应用 180 度轴线规则和视线匹配规则。系统记录每个对话场景的轴线方向，确保后续所有镜头不越轴。视线方向根据角色位置自动计算，确保角色看向正确的方向。

  • 因果链追踪策略

    在剧本解析阶段，构建事件之间的因果关系链。在连续性守护阶段，验证这些因果关系是否在片段序列中得到完整体现。如果发现逻辑断裂，例如有敲门但没有开门，系统会生成缺失的过渡片段。

  • 运动插值策略

    在连续性守护阶段，检测到动作不连续时（如片段一结束在门口，片段二开始在沙发上），系统计算位移距离和动作轨迹，生成中间状态的描述（如"林然从门口走向沙发，坐下"），然后触发重新生成。

五、一致性策略工作流

把前述内容按"现状 + 规划"两条线串起来：真实在跑的一致性流水线是"全局元数据与连续性注释传递 → 统一提示词约束注入 → 质量审查五项规则检查 → 连续性守护六项词表检查"，修复侧有一个已接通的回流（审查 → 指令转换）与一个未接通的回流（连续性侧）；规划中的策略环绕在这条主链周围，等依赖的数据机制（快照、锚点）接入后逐步生效：

flowchart TB
    subgraph Real[真实主链（已接线）]
        Start([输入原始剧本]) --> Parse[剧本解析<br/>提取 global_metadata]
        Parse --> Segment[分镜生成]
        Segment --> Split[视频分段<br/>写入 continuity_notes]
        Split --> Convert[指令转换<br/>全剧上下文 + 模板参考]
        Convert --> Audit[质量审查<br/>五项检查→加权评分→修复参数]
        Audit -->|通过| Continuity[连续性守护<br/>六项词表检查→修复参数]
        Audit -.->|NEEDS_REPAIR：已接通| Convert
        Continuity -.->|四阶段修复路由：未接通| Parse
        Continuity --> FinalOutput[最终输出<br/>AIVideoInstructions]
    end

    subgraph Planned[规划中（未实现）]
        P1[色彩管理 / 光照锚点 / 情绪曲线]
        P2[构图模板 / 镜头语法 / 关键帧锁定]
        P3[双向约束 / 运动插值 / 渐进式生成]
    end

评分与分发闸门（真实阈值）：质量审查用 calculate_weighted_score() 按违规严重度从 100 分扣减（warning 5 / moderate 10 / major 25 / critical 40 / error 60），determine_status_from_score() 把分数映射为状态（≥90 PASSED、≥75 MINOR_ISSUES、≥60 MODERATE_ISSUES、≥40 MAJOR_ISSUES、≥20 CRITICAL_ISSUES、否则 FAILED），再由 decide_after_audit() 按状态路由——PASSED 放行、MINOR_ISSUES 默认继续（违规超过 3 个才转修复）、MODERATE / MAJOR 回到指令转换修复、CRITICAL 重试或转人工；另有一处务实后门：FAILED 但分数 ≥ 80 仍放行。并不存在"≥80 / 60–80 / <60"两档闸门——那是旧版本的想象，真实分档是六档。

六、总结与建议

策略选择原则

PenShot 的一致性体系处于"主链已跑通、增强在建设中"的阶段——已接线：全局元数据/连续性注释传递、统一提示词约束、审查五项与守护六项规则检查、审查侧修复回流、RAG 检索；已实现未接线：状态快照、锚点/契约体系、风格守护、固定种子；规划中：色彩、光照、情绪曲线等增强策略。做技术选型时建议沿用同一口径，先分清"现在能用什么"与"将来会有什么"。

落地顺序建议：鉴于现状，接入工作的优先级应该是——① 先接通连续性修复回流（两处小改动，价值最高）；② 修复并接入 PromptStyleGuardian（含 search_similar_style 缺失）；③ 让状态快照接入分段/转换节点（同时统一 get_snapshot_at_time 语义与 references 填充）；④ 扩展 AIVideoPrompt 支持固定种子；⑤ 最后再按投入产出比引入色彩/光照/情绪曲线等规划项。"快照 + 锚点 + 契约"体系是多项规划的共同前置，值得优先拉通。

性能优化建议

向量检索建议使用增量索引，避免每次添加都重建全量索引（当前 SimpleVectorStore 的持久化是全量 JSON，数据量大时成本明显）。一致性检查当前是纯本地词表/数值规则、毫秒级完成，无需采样；若未来引入 LLM 语义校验（风格守护接线后），建议用轻量模型或异步调用避免阻塞主流程。词表本身可以按剧本语料扩充——这是零成本收益。

调试与监控

建议为每个策略添加独立的日志标记，便于追踪策略的执行情况和效果。关键的一致性检查点建议记录检查结果和修复动作，形成可追溯的审计日志。定期分析修复参数的类型分布，识别系统性的薄弱环节并针对性优化。

监控指标示例：可关注"修复参数类型分布"——若 appearance_change（外观变化）或 scene_jump 占比居高不下，说明角色描述定义或 global_metadata 传递仍有短板，应回到解析/转换阶段优化；"审查评分均值"与"人工介入频率"也是衡量策略有效性的直观指标。

版本与验证说明

本文属于项目文档而不是永久不变的 API 契约。以下情况发生时，应重新核对源码或发布说明：

  1. 项目版本升级，尤其是公开 API、配置模型、存储实现和工作流发生变化；

  2. 本文中的默认值、性能数据或示例依赖外部服务版本；

  3. 运行环境与本文案例不同，例如 Python 版本、Redis/数据库版本、模型供应商或操作系统不同。

如果你要把本文内容用于生产环境，请优先使用仓库当前版本的 README、源码、测试和 Release 记录进行最终确认。
