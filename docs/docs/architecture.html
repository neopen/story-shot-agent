一、概述：系统核心价值

PenShot（Pen & Shot）是一个基于 LangGraph 的多智能体协作系统，目标是把"自然语言剧本"端到端转化为"可直接投喂给 AI 视频模型（Runway Gen-2 / Sora / Veo / Pika 等，对应源码中的 VideoModelType 枚举）的指令序列"。它将"分镜"这一复杂任务拆解为解析、拆分、分段、转换、审查、守护六个相互衔接的专业节点，每个节点只专注一项职责，再由 WorkflowOrchestrator 统一装配成图、由 MultiAgentPipeline 调度执行。

这种架构带来的核心收益有三点：

  • 职责清晰：单一 Agent 的 prompt 与数据结构可各自优化，避免"一个 LLM 干所有事"导致的指令冲突与质量漂移。

  • 可控可重试：每个节点都能独立判定成功/失败，配合修复参数实现精准的局部重试，而非整条链路推倒重来。

  • 错误兜底：内置重试、错误处理与人工干预三重机制，保证长链路任务的鲁棒性。

概念澄清：LangGraph 是 LangChain 官方推出的图状态机框架，通过 StateGraph 描述节点（Node）与边（Edge）、条件分支（Conditional Edge），天然支持循环、路由与状态持久化，是多智能体流程编排的主流选择。

二、关键要点拆解

2.1 整体架构

智能体框架：LangGraph（专为多智能体状态机设计）

整个系统可分为 输入层 → LangGraph 多智能体核心工作流 → 记忆层 → 输出层 四个区块。核心工作流包含六个业务智能体（剧本解析 / 镜头拆分 / 视频分段 / 指令转换 / 质量审查 / 连续性守护）与四个控制节点（循环检查 LOOP_CHECK / 错误处理 ERROR_HANDLER / 人工干预 HUMAN_INTERVENTION / 结果生成 GENERATE_OUTPUT）：前者负责内容生产，后者负责计数、路由与兜底。记忆层由 ScriptMemory 门面统一管理短期 / 中期 / 长期三层记忆（Chroma 是长期记忆的底层向量存储，并非独立的第四层）。输出端经 WorkflowOutputFixer 修复片段序列后以 JSON 返回；对外接口有 Python API（PenshotFunction）、REST API、MCP Server 与 CLI 四种形态。

边界说明：video_model 参数（runway_gen2 / sora / veo / pika 等）只影响提示词的风格适配——PenShot 输出的是指令序列，系统本身不调用这些视频模型生成视频，也不内置 FFmpeg 合成环节；下游渲染需要使用者自行接驳工具链。

智能体职责

智能体 职责 输入 → 输出
1. 剧本解析智能体 将任意格式剧本统一解析为结构化叙事单元，提取场景、角色、动作、对话、道具、情绪等 原始文本 → 结构化序列（场景、角色、对话等）
2. 镜头拆分智能体 基于情感强度、节奏变化等，将剧本划分为最小可独立表达的镜头单元，并分配合理时长 结构化对象 → 带时间戳的镜头序列
3. 视频分段智能体 将超长镜头按片段时长上限（默认 5 秒）切分，分割点对齐关键帧与动作自然停顿处，输出符合AI视频模型要求的片段序列 镜头序列 → 符合AI视频长度限制的片段序列
4. 指令转换智能体 为每个AI片段生成模型适配的文生视频提示词（Prompt），包含构图、光线、运动等 片段内容 + 连续性锚点 → 可直接用于AI视频生成指令
5. 质量审查智能体 对全序列进行连贯性、时长合规性、角色漂移等检查，输出修正建议 AI片段序列 → 审查报告 （通过 / 修正建议列表）
6. 连续性守护节点 跨阶段连续性检查，识别角色、场景、动作、风格等连续性问题 所有阶段输出 → 连续性检查结果

设计说明：这六个节点呈"细化 → 拆分 → 合规化 → 转译 → 校验 → 兜底"的流水线逻辑。"按 5 秒切分"适配主流文生视频模型的单段时长硬上限（max_fragment_duration 默认 5.0 秒）；"在动作自然停顿处切割"写在分段提示词的分割规则里（动作完成瞬间 / 转身前 / 视线转移时），可避免动作半途被截断造成的视觉跳变。

2.2 工作流编排

采用 LangGraph 实现多智能体协作流程，支持状态管理、循环控制和错误恢复。每个业务节点后都有决策判断（PipelineDecision 决策函数），根据执行结果返回七种决策状态之一并路由到不同后续路径。特别地：拆分 / 分段 / 转换三个阶段成功后并不直接进入下一节点，而是先经过循环检查节点（LOOP_CHECK）——它同时承担"计数器递增、上限检查、阶段推进"三项职责（详见后文决策路由映射）：

决策状态

每个节点的执行结果统一收敛为一组判定状态，由决策函数解释并路由，这是 LangGraph 条件分支的落地形态：

状态 含义 后续动作
SUCCESS 完全成功 进入下一节点
VALID 验证通过（有小问题） 带病继续执行
NEEDS_RETRY 需要重试 重新执行当前节点
NEEDS_REPAIR 需要修复 应用修复参数后重试
NEEDS_HUMAN 需要人工干预 进入人工干预节点
FAILED 一般失败 进入错误处理
ABORT 中止流程 直接结束（END）

源码注：PipelineState 枚举的注释显示 NEEDS_REPAIR 合并了早期的 NEEDS_ADJUSTMENT 与 NEEDS_FIX 两个状态——语义收敛后，所有"修改后重试"的场景统一走一条修复链路，减少了路由分支。

状态机设计要点：SUCCESS 与 VALID 都"放行"，但语义不同——VALID 表示有轻微瑕疵、可带病继续；只有 NEEDS_REPAIR 才携带修复参数回退。这样既保证质量，又避免因轻微问题反复重试拖垮吞吐。

决策路由映射表（源码提取）

下表直接从 workflow_pipeline.py 的条件边定义与 workflow_decision.py 的决策函数提取，是"每个节点执行完之后，LangGraph 实际会去哪里"的完整答案：

节点 SUCCESS / VALID NEEDS_RETRY / NEEDS_REPAIR NEEDS_HUMAN FAILED / ABORT
PARSE_SCRIPT → SEGMENT_SHOT NEEDS_RETRY → 自身 → HUMAN_INTERVENTION → ERROR_HANDLER
SEGMENT_SHOT → LOOP_CHECK 两者 → 自身 → HUMAN_INTERVENTION → ERROR_HANDLER
SPLIT_VIDEO → LOOP_CHECK 两者 → 自身 → HUMAN_INTERVENTION → ERROR_HANDLER
CONVERT_PROMPT 两者 → LOOP_CHECK 两者 → 自身 → HUMAN_INTERVENTION → ERROR_HANDLER
LOOP_CHECK 按阶段推进到 SPLIT_VIDEO / CONVERT_PROMPT / AUDIT_QUALITY - → HUMAN_INTERVENTION → ERROR_HANDLER
AUDIT_QUALITY 两者 → CONTINUITY_CHECK 两者 → CONVERT_PROMPT → HUMAN_INTERVENTION FAILED → ERROR_HANDLER；ABORT → END
CONTINUITY_CHECK 两者 → GENERATE_OUTPUT NEEDS_REPAIR → CONVERT_PROMPT → HUMAN_INTERVENTION → ERROR_HANDLER
HUMAN_INTERVENTION 两者 → GENERATE_OUTPUT RETRY → PARSE_SCRIPT；REPAIR → CONVERT_PROMPT 自身（继续等待） FAILED → ERROR_HANDLER；ABORT → END
ERROR_HANDLER 按错误来源节点回退 - → HUMAN_INTERVENTION ABORT → END

三个值得注意的路由细节：

  1. 质量审查失败不是"重试审查"，而是"回炉重生成提示词"——AUDIT_QUALITY 的 NEEDS_RETRY / NEEDS_REPAIR 都路由到 CONVERT_PROMPT。因为审查本身是"读"操作，问题出在被审查的提示词上，重跑审查没有意义。
  2. 连续性检查的修复目标同样收敛到 CONVERT_PROMPT——连续性问题大多体现为"提示词描述不一致"，系统采取的是"回炉重写"而非"就地打补丁"的策略。
  3. 疑似路由缺口：decide_after_continuity 在问题严重且可重试时会返回 NEEDS_RETRY，但 CONTINUITY_CHECK 的条件边映射中只有 SUCCESS / VALID / NEEDS_REPAIR / NEEDS_HUMAN / FAILED 五个键，没有 NEEDS_RETRY——这是一个建议读者在自己使用的版本上验证的疑点：若命中该路径，LangGraph 可能因找不到目标节点而报错，而非优雅降级。

循环与重试上限（两级配置）

很多资料会把"重试次数"简化为一张表，但源码里其实是两个独立维度：node_max_loops（节点被循环检查计数的上限）与 stage_max_retries（该阶段的质量重试上限）：

节点 node_max_loops stage_max_retries 超限后果
PARSE_SCRIPT 3 3 节点超限 → FAILED
SEGMENT_SHOT 5 3 节点超限 → NEEDS_HUMAN（等待人工）
SPLIT_VIDEO 5 3 节点超限 → NEEDS_HUMAN
CONVERT_PROMPT 5 3 节点超限 → FAILED
AUDIT_QUALITY 3 2 审查类操作重试成本高，上限更低
CONTINUITY_CHECK 5 2 另有 max_continuity_retries=3 控制修复循环
ERROR_HANDLER 5 - 错误处理自身也有循环上限
HUMAN_INTERVENTION 1 - 人工干预不参与计数循环

重试语义：两个维度的区别在于"谁在计数"——node_max_loops 由 LOOP_CHECK 节点每次经过时递增，防止流程在图里"打转"；stage_max_retries 只在该阶段产出质量不达标、需要带着修复参数重来时才递增，是质量视角的预算。两者任一超限，都会把流程导向人工干预或错误处理。

状态持久化流程

PenShot 的"状态"其实分成两套独立存储，分别解决不同问题：

存储 实现 存什么 降级策略
任务记录 TaskRepository：Redis key penshot:tasks:data:{task_id} + 索引集合 penshot:tasks:ids，TTL 默认 86400 秒 任务状态 / 阶段 / 进度 / 结果元信息 Redis 不可用 → 进程内存字典（重启即丢失）
工作流检查点 WorkflowCheckpointer：LangGraph SqliteSaver，data/checkpoints/{script_id}/task_{task_id}.db 图执行到哪一步、各阶段中间状态 目录不可写 → 内存模式；langgraph-checkpoint-sqlite 未安装 → 内存模式

降级要点与边界：

  • Redis 不可用时任务仍可"仅内存"运行，服务不至于完全不可用——代价是进程重启即失忆，恢复能力归零。
  • "2 小时窗口"的实现是过滤而非标记：超龄任务不会被改写状态或主动清理，只是不再被恢复，最终静静等待 TTL（默认 86400 秒）自然过期。
  • 恢复时优先级信息会丢失——recover_pending_tasks 重建 QueuedTask 时统一使用 TaskPriority.NORMAL，原本的 CRITICAL / HIGH 任务降级为普通优先级，且直接 append 到队列尾部（不走有序插入）。这是一个可以改进的点（队列快照里保存原始优先级即可解决）。
  • 另有 recover_task(task_id) 方法用于把单个任务软重置：status → PENDING、stage → “recovered”、progress → 0、清除完成时间。

三级循环防护：长任务为何不会"打转到死"

为避免 LLM 反复失败导致无限循环拖垮系统（token 与时间的双重消耗），架构设置了三组互相独立、任一触顶即熔断的计数器：

层级 计数器 上限来源 递增时机 触顶后果
节点级 node_current_loops node_max_loops（3~5，见前表） LOOP_CHECK 每次经过当前节点 拆分/分段 → 人工；其他 → FAILED
阶段级 stage_current_retries stage_max_retries（2~3，见前表） 该阶段质量不达标、需带修复参数重来 不可再重试 → 人工/修复
全局级 global_current_loops max_total_loops × 2（默认 40） 每次经过 LOOP_CHECK 直接 FAILED

防护原理：三个计数器分别对应"微观节点自旋、中观质量重试、宏观全局预算"三种失控形态。任一超限都强制把流程导向错误处理或人工干预，保证工作流在最坏情况下也有确定的终止。

两个值得注意的实现细节：

  1. 80% 预警共用标记：loop_check_node 在节点循环达到上限 80% 时打 Warning 日志，decide_after_loop_check 也会在全局循环达到 80% 时预警——但两者共用同一个 loop_warning_issued 布尔标记，先触发者会"吃掉"标记，另一处不再报警。如果想让两级预警都生效，应拆成两个独立标记位。

  2. 判定符号不一致：loop_check_node 用 > 判断节点超限（第 max+1 次才标记），而决策函数 decide_after_loop_check 用 >=（第 max 次即判超限）。同一语义两处口径不同，实际生效的是决策函数的 >=（路由总是发生在 LOOP_CHECK 之后），这属于可以统一清理的代码坏味道。

全局上限的推导：global_max_loops 的推导注释写"所有节点最大循环次数之和"，但实际赋值是 ShotConfig.max_total_loops × 2（默认 20 × 2 = 40）；而八个节点上限之和为 32，与 20 并不相等——若严格按注释取值应为 64。使用时以运行日志里打印的实际值为准。

记忆组合策略：按层组装，而非加权融合

# 源码节选（script_memory.py）：recall 按层直接组装 MemoryContext
def recall(self, query: str, level: Optional[MemoryLevel] = None, k: int = 3) -> MemoryContext:
    context = MemoryContext()
    if level is None or level == MemoryLevel.SHORT_TERM:
        context.short_term = self.short_term.get_recent(k)
    if level is None or level == MemoryLevel.MEDIUM_TERM:
        context.medium_term = self.medium_term.get_summary()
    if (level is None or level == MemoryLevel.LONG_TERM) and self.long_term:
        context.long_term = self.long_term.search(query, k)
    return context

为什么不加权？ 很多记忆系统会给不同层级分配权重（如 0.6/0.3/0.1）做分数融合，但 PenShot 选择分层拼装：短期/中期/长期各自是一段独立的提示词文本（由 MemoryContext.to_prompt() 格式化，总预算 2000 token），层与层之间不参与同一排序。原因是三层的语义完全不同——“最近说了什么”“阶段摘要”“语义相关历史”——强行加权反而会把不同性质的信息混进同一分数空间；分层拼装则让模型自行根据段落标题判断信息可信度。

三、故障实战：四个典型异常场景

理论上的容错设计，只有在真实故障下才见真章。以下四个场景全部来自 v0.3.x 源码中的真实处理路径或真实缺口。

场景 1：工作流超时——"定时器"为何可能掐不断工作流？

发生什么：任务卡在某个 LLM 调用上长时间不返回，超过默认 1800 秒超时。

系统设计：_enhanced_workflow_execution 用 asyncio.wait_for(output_fixer.enhanced_workflow_invoke(...), timeout) 包裹执行，超时后返回 workflow_status: "timeout"。

为什么可能失效：enhanced_workflow_invoke 内部调用的是同步 workflow.invoke()——源码注释里写着"注意：这里需要await workflow.ainvoke"但仍使用同步调用。同步调用会阻塞事件循环，asyncio.wait_for 的超时回调没有机会执行；工作流不主动让出控制权，超时定时器就形同虚设。

如何应对：真正兜底的是节点内部的 LLM 超时（LLMBaseConfig.timeout=60）与循环上限；生产环境建议额外配合进程级看门狗。这是当前实现的一个已知边界，不应当作完备的超时保护依赖。

场景 2：Redis 宕机——两套存储、两种命运

发生什么：运行期间 Redis 突然不可用。

任务层：TaskRepository.write_task 捕获异常后返回 False 并打 error 日志，任务主流程不中断，但状态更新开始丢失；若 Redis 一直不可用，崩溃恢复能力随之丧失（内存字典随进程消失）。

记忆层：短期记忆的降级决策发生在构造时（3 秒超时 + ping）——构造时 Redis 可用、运行中途挂掉的情况下，缓冲追加与 Redis 写入在同一个 try 块里，异常被吞掉，本次交互静默丢失，且没有重连补偿机制。

如何恢复：重启进程后任务层会尝试重新连接 Redis；但中途丢失的记忆无法找回（短期记忆的文件降级同样是构造时决定的）。

场景 3：Worker 崩溃——恢复窗口的三种静默降级

发生什么：进程崩溃或被重启，队列里的 PENDING / PROCESSING 任务悬空。

系统处理：启动时调用 recover_pending_tasks(max_age_hours=2)，把 2 小时内的未完成任务重新入队。

三种静默降级：

  1. 超过 2 小时的任务不做标记、不清理，只是不再恢复（等待 Redis TTL 86400 秒自然过期）——没有告警；

  2. 恢复的任务优先级统一降为 NORMAL——紧急任务复活后与普通任务同权；

  3. 恢复是 append 到队列尾部而非按优先级有序插入。

如何恢复：任务会从头执行（任务级"重新入队"语义，而非从 SQLite 检查点续跑——检查点与恢复路径没有直接衔接）；要接受"进度可能回退到上一次状态写入点"。

场景 4：循环失控——预警、熔断与一个路由缺口

发生什么：某节点反复失败，循环计数不断增长。

系统处理：三级计数器（节点 / 阶段 / 全局）任一触顶即熔断——拆分、分段两类节点超限转人工，其余节点超限直接 FAILED；80% 水位会打 Warning 日志。

两个真实缺口：

  1. 节点级与全局级的 80% 预警共用 loop_warning_issued 标记，只有先触发的那一级会报警；

  2. decide_after_continuity 可能返回 NEEDS_RETRY，但 CONTINUITY_CHECK 的条件边没有这个键——命中该路径时不是"优雅降级"，而可能是框架级路由错误。建议部署前用单元测试覆盖这条路径，确认所用 LangGraph 版本的实际行为。

四、总结与建议

PenShot 的技术架构体现了多智能体系统设计的几个通行范式：

  1. 以 LangGraph 为骨架：用图状态机承载"分支、循环、重试、路由"，让复杂的创作流程可编排、可观测、可恢复。

  2. 六业务节点 + 四控制节点：业务节点各司其职；LOOP_CHECK 兼任计数与阶段推进，ERROR_HANDLER / HUMAN_INTERVENTION / GENERATE_OUTPUT 负责兜底与收口。

  3. 多级容错：七态决策路由 + 三级循环防护（节点/阶段/全局）+ 两套持久化（Redis 任务记录 + SQLite 检查点）+ 分层降级（内存/规则引擎），构成完整的鲁棒性体系。

  4. "轻前置 + 重最终"质检：节点内基础检测随做随修，深度检测集中于收尾，兼顾成本与质量。

  5. 工程边界透明：超时保护对同步阻塞的局限、连续性路由缺口、恢复优先级丢失——这些已知不足同样是架构认知的一部分。

落地建议：接入时先从最小的"两到三个阶段"流水线起步验证效果，再逐步扩展节点与修复参数机制；配置好三级循环阈值与人工干预触发条件，并为同步阻塞路径补上进程级看门狗，避免长任务在无监督环境下"打转"或"白跑"。
