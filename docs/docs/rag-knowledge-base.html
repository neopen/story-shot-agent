核心价值与整体架构

什么是 RAG 知识库，为什么需要它

剧本分镜智能体是一个基于多智能体协作的视频分镜生成系统。它将原始剧本作为输入，通过一系列智能体协作，输出可供 AI 视频生成模型使用的提示词序列。在这个过程中，LLM 单独推理往往无法"记住"历史成功经验、相似场景与既有设定，导致输出不稳定、前后不一致。

RAG（检索增强生成，Retrieval-Augmented Generation）知识库正是为此而生——它在模型生成前先从外部存储中检索相关上下文，再注入提示词参与生成。它扮演着系统的核心记忆与检索角色，为各个智能体提供历史经验、相似场景和成功模板的参考，从而把"一次性生成"升级为"经验驱动的生成"。

需要说明的是，RAG 与单纯的关键词检索有本质区别：关键词检索依赖字面命中，无法处理同义词、改写与语义相近但文字不同的表达；而 RAG 通过将文本映射为高维向量，在"语义空间"中计算相似度，因此能够理解"林然裹着旧羊毛毯"与"年轻女性裹着羊毛毯"这类语义等价的关系。这也是后续所有检索环节得以成立的基础。

下文将以"三口径"逐层考证 PenShot 中 RAG 知识库的真实形态：已接线的提示词模板增强与三层记忆、以简化实现落地的剧本向量库、以及已实现但未接线的知识路由器。

核订说明：本文所称"已接线"，指组件确实被工作流节点或其他生产代码调用；"已实现未接线"指代码完整存在、但全仓库找不到调用方；"规划中"指只存在于设计文档或概念描述中。所有类名、方法签名与参数取值均取自仓库当前源码，读者可对照复验。

工作流节点层是知识的使用者，也是判断"接线状态"的关键——只有被这一层真实调用的组件才算"已接线"。剧本解析节点把解析结果写入知识库（add_parsed_script），提示词转换节点检索成功模板增强提示词（enhance_prompt），质量审计节点在审查通过后沉淀成功模板（save_successful_prompt），连续性守护节点用问题描述检索相似场景（search_similar_scene）。这四个调用点都能在 workflow_nodes.py 中找到对应代码。

知识中枢层的真实入口是 PromptTemplateManager（位于 prompts/prompt_template_manager.py），它同时持有两套向量索引——按剧本隔离的模板索引，以及内嵌的 ScriptKnowledgeBase 剧本内容索引——并挂接统一的三层记忆管理器。工作流节点并不直接接触向量库，所有知识读写都经由这个中枢转发。

知识存储层包含两套 LlamaIndex 向量索引与三层记忆：模板索引与剧本索引都由 SimpleVectorStore 承载；记忆则分别由滑动窗口（短期）、LLM 摘要链（中期）、Chroma 向量库（长期）实现。需要注意的是，设计图上常见的"结构化存储"并不是独立组件，它的实体是 ScriptKnowledgeBase 内部的 parsed_results 缓存与磁盘 JSON 文件。

持久化层的真实文件包括：模板缓存与索引目录（templates_cache.json + index_store/）、剧本向量存储（default__vector_store.json 与 docstore.json）、剧本解析结果（parsed_results/ 下的 JSON），以及长期记忆的 Chroma 集合。

图底部还有一个已实现未接线的组件：KnowledgeRouter（知识路由器）。它支持四种检索源与混合检索融合，代码完整、可独立实例化，但全仓库找不到任何调用方——它与存储层之间是"悬空引用"。这个组件的真实形态会在拆解三中单独考证。

关键要点拆解（一）：LlamaIndex 向量知识库

LlamaIndex 是什么

LlamaIndex 是一个专为 LLM 应用设计的索引框架，它提供了文档加载、索引构建、检索查询等一系列工具。在 PenShot 中，LlamaIndex 主要用于构建剧本的向量索引，实现语义级别的相似度检索。

ScriptKnowledgeBase 类是剧本向量知识库的核心实现（knowledge/llamaIndex/llama_index_knowledge.py，约 960 行）。它的构造参数为 (embeddings, script_id, storage_dir=None, chunk_size=512, chunk_overlap=20)——第二个参数 script_id 是必需的，类内部用四组字典（_indices / _vector_stores / _storage_contexts / _retrievers）按剧本 ID 隔离全部数据。调用 add_parsed_script / add_script_text 入库时，系统先把剧本转成场景、角色文档，再按分块参数切分、向量化，写入 SimpleVectorStore，并立即持久化到磁盘。

分块解析器的选择有一个真实的条件分支：chunk_size > 1000 时使用 SentenceWindowNodeParser（窗口大小 3），否则使用 SentenceSplitter。默认 chunk_size=512，因此默认路径走的是 SentenceSplitter；窗口解析器只在显式调大分块时才启用，而不是两个解析器二选一由调用方随意指定。

这里有两个值得注意的工程细节：

  • 文本分块（chunking）：chunk_size 与 chunk_overlap 直接影响检索质量。分块过小会丢失上下文语义，分块过大又会引入噪声、稀释相似度。重叠区（overlap）用于缓解切分把一句话从中间截断的问题，是 RAG 中常见的调参重点。本项目的默认取值（512/20）属"块偏小、重叠保守"的配置。

  • 嵌入维度与模型：嵌入模型将文本映射为固定维度的向量（业界常见取值有 768/1024/1536 维等），维度越高编码信息越丰富，但索引体积与检索耗时也随之上升，需要按精度与成本权衡。本项目具体加载哪种嵌入模型由外部配置注入，代码本身不绑定某一维度。

这里必须区分两条检索路径，它们的成熟度完全不同：

  • query() 方法（真实主线）：方法体注释直言"使用手动余弦相似度计算"——它直接遍历向量存储中的全部向量，逐个计算余弦相似度后排序取前 top_k（默认 5）。签名中的 search_type、use_rerank、rerank_model 三个参数接收后从不使用，是典型的"占位参数"。

  • create_retriever_for_script() 方法（候选路径）：这里才有完整装配——支持 similarity/mmr 两种模式（MMR 的 mmr_threshold=0.6）、可选 SentenceTransformerRerank 重排序（模型选择链为本地路径 → 配置名 → 默认 BAAI/bge-reranker-large，top_n=min(3, similarity_top_k)）。值得注意的实现细节：rerank 生效时会用 index.as_retriever 重建检索器，mmr 模式因此被覆盖——两者不能叠加使用。这条路径当前仅被未接线的 KnowledgeRouter 引用。

关于 MMR：当多个候选在语义上高度相似（如同属同一情感场景）时，仅按相似度排序会得到一堆"雷同"结果。MMR 在排序目标中加入了一项目标集合内部多样性的惩罚项，用 $\lambda$ 在"与查询更相关"和"与已选集合更多样"之间做权衡，适合需要一份覆盖多种类型的候选清单的场景。

文档解析与索引流程

检索查询流程

真实主线（query() 方法）的检索流程如下——没有检索器对象、没有阈值过滤、也没有重排序环节：

flowchart TD
    Q[查询文本] --> E[embeddings.embed_query<br/>转查询向量]

关键要点拆解（二）：多层级记忆管理器

记忆层是这个知识体系里真实接线深度最高的部分——它是工作流四个阶段节点共同的读写枢纽。需要先理清一个结构事实：MemoryManager 本身是多剧本容器（内部是 _script_memories: Dict[str, ScriptMemory]），真正持有三层记忆的是每个剧本对应的 ScriptMemory；MemoryManager 的职责是按 script_id 路由到对应容器，并统一做序列化与反序列化。

配置值来自 WorkflowNodes 构造时的注入（MemoryConfig）：短期 20 条 / TTL 3600 秒、中期 500 tokens 上限、长期启用且召回 k=3。三个层级的真实机制各有不同：

短期记忆的底层是 LangChain 的 ChatMessageHistory，容量控制用 deque(maxlen=20) 实现——是滑动窗口（FIFO），超出容量的最旧消息被自动挤出，而不是按访问频率淘汰的 LRU。TTL 由 Redis 会话历史继承（RedisChatMessageHistory 的 ttl 参数），键为 penshot:memory:{session_id}；Redis 不可用时降级为内存存储，若配置了持久化目录还会把消息归档到 short_term.json。

中期记忆常被误读为"统计仓库"，真实实现是基于 LLM 的摘要链：每次写入（add(stage_name, content)）都会调用一次 LLM，把新内容"逐步总结"融合进旧摘要；超出 500*4 字符的输入先截断，生成后超过 500*2 字符的摘要也会被截断——容量限制实际体现在字符截断上。

长期记忆的底层是 Chroma 向量库（langchain_chroma），集合命名为 script_{script_id}_memory，写入时拼接标签等信息增强文本，检索走 similarity_search_with_score 并按分数阈值过滤。它是三层中唯一具备语义检索能力的层级。

三层之间存在有条件的自动流转：写入时若条目标记 important，会从短期提升到中期；短期使用量达到容量 80% 时，系统取最近 5 条生成摘要自动压缩进中期；add_stage 写入的重要阶段内容还会同步写入长期。不过这是"阈值触发"而非"持续学习式的自动升华"——写什么、何时写，主要仍由调用方显式决定，行为可预测、可调试。

关键要点拆解（三）：知识路由器

先说结论：KnowledgeRouter（knowledge/llama_index_router.py，约 550 行）是一个已实现但未接线的组件。它确实封装了四类检索源的统一入口、带有完整的查询对象与结果对象定义，但全仓库找不到任何实例化它的生产代码——工作流节点用的一直是 PromptTemplateManager 这条线。因此下文描述的是"设计与实现"，而不是"线上行为"。

向量检索（VECTOR_INDEX）转发到 ScriptKnowledgeBase.query 或经过缓存的检索器；记忆检索（SEMANTIC_MEMORY）按短期/中期/长期分别从 MemoryManager 取数据；结构化检索（STRUCTURED）走 query_scene / query_character 的精确字段匹配；混合检索（HYBRID）则是把上面几路的结果合并排序。

关于混合检索的"并行执行、分数归一化"这类说法，需要按源码纠偏：_hybrid_search 的真实实现是串行依次调用三路（代码注释自认"简化版，实际可用 asyncio.gather 并行"）；融合时没有分数归一化，而是给不同来源硬编码固定分数——短期记忆 0.9、中期记忆 0.7、长期记忆 0.6、结构化场景 1.0、结构化角色 0.9；去重用的是"内容前 100 字符作前缀 key"的朴素策略。这套分数设计保证了结构化结果优先、记忆越"近"越优先的排序直觉，但不同来源的分数不可比，融合结果并不能反映真实相关性。

路由器的设计意图是：调用方只构造一个 KnowledgeQuery 对象（指定查询文本与期望来源），路由器自动完成检索并返回格式化结果。接口设计本身是合理的——问题在于它从未被接入工作流。

关键要点拆解（四）：提示词模板管理器

PromptTemplateManager（prompts/prompt_template_manager.py，约 1000 行）是专门管理成功提示词模板的组件，也是工作流节点接触知识系统的真实中枢：它同时持有按剧本隔离的模板向量索引与内嵌的 ScriptKnowledgeBase 剧本内容索引（拆解一），并可挂接三层记忆管理器（拆解二）。先澄清一个常见误解：模板库并不是全局共享的——_indices、_caches 等结构都以 script_id 为键隔离，模板只在所属剧本内可见；真正全局的只有长期记忆层。

写入链路是真实接线的：当质量审计节点判定某个片段的提示词通过审查后，workflow_nodes.py 会调用 save_successful_prompt(fragment_id, prompt_text, quality_score, script_id, additional_metadata)。内部组装元数据（source 标记为 quality_audit_passed，叠加片段 ID、质量分数、场景、风格等外部字段），转交 add_template 入库：超过 2000 字符的模板会被截断为 1997 字符加省略号；入库前做 hash 与全文双重去重，并用 _processing_stack 防止递归重入；随后更新索引与 templates_cache.json 缓存，并以默认的 save_to_memory=True 把模板写入长期记忆。

读取链路同样真实：提示词转换节点生成新提示词后调用 enhance_prompt(fragment.prompt, enhancement_mode="append")。内部先走 get_best_match（本质是 search_similar 传 top_k=1），检索经 index.as_retriever 的相似度模式取候选，再做后置过滤——低于 min_similarity_score 的丢弃，且只保留 metadata.type 为 prompt_template 的节点；命中后按模式拼装增强文本（精确格式见后文流程图）。

这里必须纠偏一处编造："模板管理器在启动时会从长期记忆层加载历史成功模板构建向量索引"并不存在。真实实现中 _save_to_memory 是只写不读的单向沉淀（写入长期记忆的 successful_prompt_patterns 键），全类没有任何回读方法。进程重启后，模板库的恢复完全依赖磁盘上的 templates_cache.json 与 index_store/，长期记忆中的模板不会自动回流——这是当前实现的真实缺口，而非特性。

在这个前提下，"正向循环"是有限成立的：同一剧本内沉淀的成功模板越多，enhance_prompt 可参考的样本越好；但循环半径受限于剧本隔离与单向沉淀，跨剧本的经验复用尚未形成闭环。

连续性检查的知识增强

连续性守护节点的职责是检查片段序列中是否存在视觉、角色、场景或动作上的不一致。这个节点的知识库增强是真实接线的，也是知识系统中少数真正落地的高级功能之一。

当检查发现问题后，workflow_nodes.py 先判断 is_script_kb_available()，再逐条遍历问题：以 getattr(issue, 'description', str(issue)) 取出问题描述作为查询文本，调用 search_similar_scene(issue_desc, script_id=..., top_k=2) 检索相似场景，命中后写入问题对象的 historical_solutions 属性，供后续修复流程参考：

# workflow_nodes.py 连续性检查中的检索调用（源码摘录）
if self.knowledge_manager and self.knowledge_manager.is_script_kb_available():
    enhanced_issues = []
    for issue in continuity_issues:
        issue_desc = getattr(issue, 'description', str(issue))
        similar_scenes = self.knowledge_manager.search_similar_scene(issue_desc,script_id=state.input.script_id, top_k=2)
        if similar_scenes:
            if hasattr(issue, 'historical_solutions'):
                issue.historical_solutions = similar_scenes
        enhanced_issues.append(issue)
    state.domain.continuity_issues = enhanced_issues

例如：若检查发现某角色服装在相邻片段不一致，检索会命中该角色在其他场景中的服装描述或类似问题的历史场景记录，作为修复生成的参考素材。

三个实现细节值得注意：其一，调用方 self.knowledge_manager 的真实类型是 PromptTemplateManager（历史命名遗留，下一节展开）；其二，search_similar_scene 内部调用 script_kb.query(..., search_type="similarity", similarity_top_k=top_k, use_rerank=True)——表面开启了重排序，但拆解一已考证 query() 的三个模式参数是哑参数，use_rerank=True 实际不产生任何重排序行为；其三，hasattr(issue, 'historical_solutions') 的守卫意味着：只有问题对象本身定义了该属性时，检索结果才会被真正挂载。

持久化与恢复

知识库的持久化分三层，真实文件名与加载时机如下：

剧本向量存储：SimpleVectorStore 持久化为 default__vector_store.json（兼容读取旧名 vector_store.json），配套 docstore.json 与 index_store.json。加载时优先读新文件名，空文件或异常只记 warning 并返回 None；恢复主索引走 StorageContext.from_defaults(persist_dir=...)——源码注释特别标注"关键修复：使用 VectorStoreIndex 构造函数，而不是 from_vector_store"。遇到损坏文件，_recreate_vector_store 会先把损坏文件备份为 *_corrupted_{时间戳}，同时清掉可能损坏的 docstore.json / index_store.json，再重建空存储——自愈而非报错退出。

解析结果：每个剧本单独存放在 {storage_dir}/{script_id}/parsed_results/{script_id}.json，与向量文件分离；ScriptKnowledgeBase 构造时通过 _load_all_scripts 扫描全部剧本目录、把这些 JSON 读入内存，而向量索引不在此时加载——源码注释明确写着"延迟加载向量存储（在需要时加载）"。

模板库：按剧本存放在 {base_storage_dir}/prompt_templates/{script_id}/ 下的 templates_cache.json 与 index_store/ 目录；模板管理器对两者采用懒加载（首次访问该剧本时读盘），而不是启动时全量扫描。

"重启可恢复"的边界也要说清：恢复的是磁盘上的解析结果、剧本索引与模板缓存三类文件；拆解四已述，长期记忆中的模板不会自动回流模板索引——三者各自独立恢复。

扩展性设计

按照"三口径"重新审视原稿列出的四个扩展点，真实成色差异很大：

嵌入模型替换（真实扩展点）：通过构造函数注入 embedding_model，索引与查询共用同一实例即可替换——代价是替换后必须重建全部索引。

向量存储替换（可改造点）：ScriptKnowledgeBase 内部实例化 SimpleVectorStore，替换为 Chroma、Pinecone 需要修改源码中的实例化与持久化逻辑，原文"只需修改实例化方式"的说法本身就说明了它是一条改写路径，而非配置项切换。

检索器自定义（纸面扩展）：KnowledgeRouter 支持注册新检索源，但该组件本身未接线，扩展它不会影响任何线上行为。

记忆层级扩展（纸面扩展）：MemoryLevel 枚举可以加值，但 ScriptMemory 的读写分发基于 short_term / medium_term / long_term 三个硬编码属性与 if/elif 分支——新增层级需要同步改造组合结构与所有分发逻辑。

尤其需要强调嵌入模型一致性：索引建立与查询必须使用相同的嵌入模型，否则查询向量与文档向量落在不同向量空间，相似度计算将完全失去意义。这个约束对剧本索引与模板索引同时成立，还存在一个隐蔽的运维陷阱：更换嵌入模型配置后若不清空磁盘索引文件，旧向量与新查询向量会静默失配——检索不报错，只是结果不可信。

排坑提示

在落地此类 RAG 知识库时，通常需要在以下几个方面重点排查（每条都对应本文考证中的真实实现）：

  • 嵌入模型一致性：索引与查询必须使用同一套嵌入模型与同一维度，混用会导致相似度失配——注意这种失配通常不报错，只是检索结果变得不可信，排查时优先核对磁盘索引文件的生成时间与当前模型配置。

  • 分块参数调优：chunk_size 与 chunk_overlap 需结合剧本文本长度反复调试；本项目默认 512/20，且 chunk_size > 1000 会自动切换到 SentenceWindowNodeParser（窗口 3）——调参时要意识到解析器也会跟着变。

  • 相似度阈值的真实语义：过滤是检索后的后置过滤（search_similar 先取回候选再按 min_similarity_score 丢弃），阈值调高会直接改变"有没有结果"，而不是改变"结果的质量排序"；连续性检查链路则完全没有阈值过滤，结果质量完全依赖 top_k 控制。

  • 存储文件完整性：剧本索引同时依赖 default__vector_store.json 与 docstore.json（模板索引为 templates_cache.json + index_store/），缺失任一都可能导致加载失败或检索为空；项目内置了 *_corrupted_* 备份自愈机制，遇到检索突然为空时先去目录里找这类备份文件。

  • 多剧本隔离：所有索引、缓存、模板库都以 script_id 为键隔离——漏传 script_id 时会静默降级（如 search_similar 直接返回空列表并记 debug 日志），而不是抛错，排查"检索没结果"时先确认剧本 ID 传了没有。

总结与建议

按"三口径"回收全文考证，PenShot 的 RAG 知识库真实成色如下：

已接线的两条主线。其一，三层记忆：短期 deque 滑动窗口（Redis TTL 1 小时）、中期 LLM 摘要链、长期 Chroma 向量库，经 WorkflowMemory 在每个处理节点做"两段式"读写（加载历史上下文 + after_stage_completion 三段写入）；其二，提示词模板增强：质量审计通过后 save_successful_prompt 落库（模板索引 + 长期记忆），后续任务经 enhance_prompt 检索本剧本模板拼接增强——这是全系统最完整的"积累-复用"闭环。另有一处已接线的点状增强：连续性检查用 search_similar_scene(top_k=2) 检索相似场景并附加到问题的 historical_solutions 上。

已接线但以简化实现落地的部分。剧本向量库 ScriptKnowledgeBase 的 query() 走手动余弦全量扫描（O(N)），search_type / use_rerank / rerank_model 三个接收参数从不使用；search_similar_scene 内部的 use_rerank=True 因此也从不生效——"重排序"在这条链路上只存在于图纸。

已实现未接线。KnowledgeRouter（四源路由 + 串行混合检索 + 硬编码分数融合）代码完整但无调用方；create_retriever_for_script 的 MMR 与重排序装配只服务这个未接线的组件；PromptStyleGuardian 与 save_contract 是悬空引用。评估这套系统时，不应把未接线的能力算入"现有能力"。

三个值得注意的边界。其一，模板库按剧本隔离，长期记忆的 successful_prompt_patterns 不会回读进模板索引（但仍会被提示词转换节点读作上下文）——跨剧本经验复用尚未闭环；其二，审计失败分支没有任何知识沉淀——失败样本没有被利用；其三，中期记忆是摘要而非台账——不适合需要精确回放的数据。

对于要构建类似"带记忆的创作智能体"的开发者，建议从可验证的最小闭环起步：先做单剧本的"成功样本沉淀 → 检索增强"循环（这是当前代码里唯一真正跑通的循环），再考虑记忆分层与多路路由；调试时把"嵌入模型一致性、script_id 传递、磁盘索引文件状态"作为首要检查项——不要把"检索阈值归一化"列入检查清单，本项目的融合链路上并不存在归一化。
