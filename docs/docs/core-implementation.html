一、LLM 客户端：多厂商可插拔封装

背景：PenShot 需要调用大语言模型做解析、拆分、转换，而不同厂商（OpenAI、本地 Ollama、通义千问）的 API 与 Embedding 接口差异较大，需要统一的封装层。配置分两级：配置文件/环境变量提供默认值，代码参数实时覆盖（优先级更高），厂商类型由 base_url 自动探测。

OpenAI

# 真实源码（openai_client.py）
class OpenAIClient(BaseClient):
    """OpenAI 客户端实现"""

    def __init__(self, config: AIConfig):
        super().__init__(config)
        self.base_url = self.llm_config.base_url or "https://api.openai.com/v1"
        os.environ["OPENAI_API_KEY"] = self.llm_config.api_key.get_secret_value()

    def llm_model(self) -> BaseLanguageModel:
        return ChatOpenAI(
            model=self.llm_config.model_name,
            temperature=self.llm_config.temperature,
            api_key=self.llm_config.api_key,
            base_url=self.base_url,
            timeout=self.llm_config.timeout,          # 默认 60 秒
            max_retries=self.llm_config.max_retries,  # 默认 3
            max_tokens=self.llm_config.max_tokens,
        )

    def llm_embed(self) -> Embeddings:
        return OpenAIEmbeddings(
            model=self.embed_config.model_name,       # 默认 text-embedding-3-small
            api_key=self.embed_config.api_key,
            base_url=self.embed_config.base_url or self.base_url,
            dimensions=self.embed_config.dimensions,  # 默认 1536 维
            timeout=self.embed_config.timeout,
            max_retries=self.embed_config.max_retries,
        )

class OllamaClient(BaseClient):
    """Ollama 客户端实现"""

    def __init__(self, config: AIConfig):
        super().__init__(config)
        self.base_url = self.llm_config.base_url or "http://localhost:11434"

            num_predict=self.llm_config.max_tokens * 4,  # 生成上限，按 token 计

            seed=self.llm_config.seed,                   # 显式传随机种子
            num_thread=8,
            client_kwargs=self._get_model_kwargs(),
        )

# 真实源码（qwen_client.py）
class QwenClient(BaseClient):
    """Qwen LLM 客户端实现"""

    def __init__(self, config: AIConfig):
        super().__init__(config)
        self.base_url = "https://dashscope.aliyuncs.com/compatible-mode/v1"
        os.environ["DASHSCOPE_API_KEY"] = self.llm_config.api_key.get_secret_value()

    def llm_model(self) -> BaseLanguageModel:
        return ChatTongyi(
            model=self.llm_config.model_name,
            model_kwargs=self._get_model_kwargs(),
            api_key=self.llm_config.api_key,
            max_retries=self.llm_config.max_retries,
            streaming=False,  # 结构化输出场景关闭流式
        )

    def _get_model_kwargs(self):
        """ChatTongyi 未直接暴露的采样参数经 model_kwargs 透传"""
        return {
            "temperature": self.llm_config.temperature,
            "timeout": self.llm_config.timeout,
            "max_tokens": self.llm_config.max_tokens,
        }

核心逻辑解释（为什么这么设计）：

  • 统一抽象，差异下沉：所有客户端继承 BaseClient 并只实现 llm_model() 与 llm_embed() 两个方法，上层智能体只依赖 LangChain 的 BaseLanguageModel / Embeddings 抽象，不感知厂商差异；新增厂商只需注册到 CLIENT_REGISTRY。
  • 厂商自动探测：工厂函数 detect_ai_provider_by_url() 根据 base_url 域名路由客户端（openai.com → OpenAI、aliyuncs.com → Qwen、deepseek.com → DeepSeek，其余兜底 Ollama）。配置里只需填 base_url，减少一个必填字段、少一处出错点。
  • 参数语义对齐是真实坑点：同样叫"max tokens"，Ollama 的 num_predict 按生成 token 计数，代码显式乘 4 留出余量；Qwen 的 temperature/timeout 只能经 model_kwargs 透传。切换厂商时这些隐性差异必须逐项确认，否则会出现"配置没变、行为变了"的排查难题。
  • 环境变量是已知副作用：OpenAI/Qwen 客户端在构造时写入 os.environ（部分 LangChain 组件依赖环境变量读取密钥）。这是实现便利与副作用之间的取舍——同进程多客户端实例共存时环境变量会互相覆盖，属于当前实现的边界。

客户端工厂与降级链

配置初始化之外，真正决定"AI 服务挂了系统还能不能跑"的是工厂层的降级设计：

# 真实源码（client_factory.py，节选）
def get_default_llm(**kwargs) -> Optional[BaseLanguageModel]:
    try:
        return _get_default_llm(settings.get_llm_config())                # ① 默认配置
    except Exception:
        warning("默认LLM模型初始化失败，尝试使用备用配置")
        try:
            return _get_default_llm(settings.get_llm_config("fallback"))  # ② 备用配置
        except Exception as e:
            error(f"LLM模型初始化失败（错误: {str(e)}），系统将自动使用规则引擎模式继续工作")
            return None                                                   # ③ 降级标记

核心逻辑解释：LLM 在 PenShot 中是"增强项"而非"必需项"。初始化链路为 默认配置 → fallback 备用配置 → 返回 None 并打日志，共三级。上层拿到 None 后转入纯规则路径（例如视频切分自动降级为规则切分），任务不会因 AI 服务不可用而整体失败——这是"AI 辅助 + 规则兜底"架构在客户端层的落点。代价是降级后的输出质量只能靠规则保证，且降级发生时只有一条日志，调用方需要自行监控。

shot_segmenter_system:
  name: "shot_segmenter_system"
  description: "系统提示：将结构化剧本拆分为多个镜头序列节点"
  template: |
    你是一个专业的影视分镜师，负责将剧本场景转换为具体的镜头序列。
    
    你的任务是根据提供的场景信息，生成合适的镜头序列，包括镜头类型、时长、构图和情感表达。
    
    【规则约束】
      1. 生动描述: 画面描述要具体、生动，包含视觉细节、光影、氛围、角色状态和情感变化
      2. 连续性保证: 严格遵循连续性约束，确保角色外观、位置和状态的一致性
      3. 时长估算: 根据元素内容和类型合理估算每个镜头的时长，确保节奏感
      4. 镜头描述: 每个镜头的描述要简洁明了，突出视觉元素和情感氛围
      5. 角色聚焦: 镜头应突出主要角色，确保角色在镜头中的位置和状态一致
      6. 场景一致性: 确保同一场景内的镜头保持相同的视觉风格和环境元素
      7. 转场建议: 根据内容和节奏提供合理的转场建议，如切换、淡入淡出等
      8. 避免过度分割，保持镜头的视觉和叙事连贯性
      9. 片段时长控制: 根据内容类型和情感重量调整镜头时长，遵循以下建议：
         - 快节奏动作/突发事件：1.5-2.5秒（如急刹、奔跑、意外发生）
         - 对话/表情反应：2.5-4秒（根据台词长度和情感深度调整）
         - 风景/环境建立：3-5秒（让观众有时间沉浸）
         - 情感高潮/重要台词：4-6秒（给足情感发酵空间）
         - 特写细节/道具揭示：2-3秒（确保观众看清关键信息）
    
    【拆分规则】
      1. 对话元素通常用特写镜头（close_up）或中景（medium_shot），时长根据台词长度和情感重量估算：
         - 简短台词（2-3秒）：2.5-3.5秒
         - 中等长度台词（4-6秒）：3.5-5秒
         - 长段情感台词（6-8秒）：5-7秒
      2. 重要：对话元素必须在镜头描述中完整逐字呈现，不可省略、概括或使用"他说……"代替。必须确保台词原文完整出现在描述中
      3. 动作元素通常用中景镜头（medium_shot），时长根据动作复杂度：
         - 简单单一动作：1.5-2.5秒
         - 复合动作序列：2.5-4秒
      4. 场景描述用全景镜头（wide_shot），时长3-5秒
      5. 连续相关元素可以合并到一个镜头，避免过度分割
      6. 道具一致性：必须严格遵循【全剧上下文】中列出的关键道具描述，同一物品在不同镜头中的名称、外观、颜色、文字必须完全相同。
      7. 角色服装分配：必须严格遵循【全剧上下文】中列出的角色服装要求，不可混淆不同角色的服装特征
      8. 台词必须在相应镜头中完整出现
      9. 避免将单一元素/台词分割到多个镜头中，除非原始时长确实过长（超过7-8秒）
      10. 如果元素时长较短（<3秒），通常用一个镜头完整呈现，不要分割
      11. 如果元素时长中等（3-6秒），评估内部是否有自然的视觉停顿点，否则保持单一镜头
      12. 如果元素确实需要分割（>7秒），确保分割后的每个片段都有独立的视觉焦点或情感递进
    
    【镜头衔接规则】
      - wide_shot → medium_shot：空间定位
      - medium_shot → close_up：情感聚焦
      - close_up → close_up：视线匹配
      - 避免同一镜头类型连续超过3次
    
    【转场建议规则】
      - 场景变化：淡入淡出
      - 情感高潮：直接切换
      - 时间跳跃：叠化
      - 视角转换：跟拍/摇移
    
    【镜头选择规则】
      - wide_shot: 远景/广角镜头，展现场景全貌和环境氛围
      - long_shot: 长焦镜头，压缩空间感，突出人物与背景关系
      - medium_shot: 中景镜头，展现人物上半身和动作，最常用的镜头类型
      - close_up: 特写镜头，聚焦面部表情或重要细节
      - extreme_close_up: 极特写，强调极端情绪或关键细节
    
    
    【元素分配规则】
      - elem_001（开场）→ shot_001
      - elem_002（发展）→ shot_002-003
      - elem_003（高潮）→ shot_004
      
    【关键要求】
      - 台词完整性：所有对话元素必须在相应镜头描述中完整逐字呈现，不可省略、概括或仅用"说台词"代替
      - 道具一致性：同一物品在所有镜头中的名称、外观、颜色、文字内容必须完全一致
      - 文字准确性：任何出现在物品上的文字必须在所有相关镜头中保持完全相同的表述
      - 角色视觉标识：每个角色的服装颜色、配饰等视觉特征必须严格遵循剧本设定，在所有镜头中保持一致
      - 角色服装分配：严格区分每个角色的专属服装特征，不可将A角色的服装特征错误分配给B角色
      - 元素追踪：每个镜头的描述必须明确包含其对应的元素ID所代表的所有关键信息

    【错误处理】
      - 如果无法解析，返回空数组
      - 如果置信度过低，标记为NEEDS_REVIEW
      - 如果有矛盾信息，优先采用高置信度
        
    【性能优化】
      - 缓存常用结果
      - 并行处理独立片段
      - 增量更新（只处理变化部分）

提示词管理器

与 YAML 模板配套的是加载器 PromptManager（源码文件 prompt_load_manager.py，注意与做"向量化模板复用"的 PromptTemplateManager 是两个不同的类）。以下为真实源码节选：

class PromptManager:
    def __init__(self, version: str = "v1.x", language: Language = Language.ZH):
        # 默认使用当前文件的父目录
        self.prompt_dir = Path(__file__).parent / version / language.value
        # 缓存已加载的提示词模板 - 最大缓存1024个提示词
        self._prompt_cache: Dict[str, Dict[str, Any]] = {}
        self._all_prompts_loaded = False

    def get_version(self, name: str) -> str:
        """获取指定名称提示词的版本

        Args:
            name: 提示词名称或标识符

        Returns:
            提示词版本字符串
        """
        # 检查缓存
        if name in self._prompt_cache:
            return self._prompt_cache[name].get("version", "unknown")

        # 如果不在缓存中，先加载提示词
        try:
            self.get_prompt(name)  # 这会更新缓存
            return self._prompt_cache[name].get("version", "unknown")
        except KeyError:
            return "unknown"

    def get_all_prompts(self) -> Dict[str, Dict[str, Any]]:
        """获取所有可用的提示词模板

        Returns:
            所有提示词模板的字典，键为提示词名称，值为提示词配置
        """
        # 使用标志位避免重复加载所有提示词
        if not self._all_prompts_loaded:
            for yaml_file in self.prompt_dir.glob("*.yaml"):
                try:
                    with open(yaml_file, "r", encoding="utf-8") as f:
                        data = yaml.safe_load(f)

                        # 处理嵌套结构
                        if isinstance(data, dict):
                            for prompt_key, prompt_data in data.items():
                                if isinstance(prompt_data, dict):
                                    # 使用name字段或键名作为缓存键
                                    # cache_key = prompt_data.get("name", prompt_key)
                                    self._prompt_cache[prompt_key] = prompt_data
                        # 处理旧格式（注：此分支不可达——
                        # 上面的 if isinstance(data, dict) 已捕获所有 dict 情况）
                        elif isinstance(data, dict) and "name" in data:
                            self._prompt_cache[data["name"]] = data
                except Exception as e:
                    error(f"加载提示词文件 {yaml_file} 时出错: {str(e)}")
                    print_log_exception()
                    continue

            # 标记所有提示词已加载
            self._all_prompts_loaded = True

            # 限制缓存大小为1024个提示词
            if len(self._prompt_cache) > 1024:
                # 只保留最新的1024个提示词
                self._prompt_cache = dict(list(self._prompt_cache.items())[-1024:])

        return self._prompt_cache.copy()

    def get_prompt(self, name: str, file_name: str = None) -> str:
        """获取指定名称的提示词模板
        
        Args:
            name: 提示词名称或标识符
            
        Returns:
            提示词模板字符串
        
        匹配策略（按优先级）：
        1. 首先检查缓存
        2. 对于嵌套格式，优先通过键名(prompt_key)匹配
        3. 对于嵌套格式，其次通过name字段匹配
        4. 对于简单格式，通过name字段匹配
        5. 尝试移除_prompt后缀进行匹配（兼容重命名后的文件）
        """
        # 检查缓存
        if name in self._prompt_cache:
            return self._prompt_cache[name].get("template", "")

        # 尝试多种匹配方式
        match_methods = [
            # 原始名称匹配
            name,
            # 尝试移除_prompt后缀匹配（兼容文件重命名）
            name.replace("_prompt", "") if name.endswith("_prompt") else None
        ]

        # 移除None值
        match_methods = [m for m in match_methods if m]

        data = self.get_all_prompts()  # 确保所有提示词已加载

        # 查找所有YAML文件
        try:
            for prompt_key, prompt_data in data.items():
                # 对每种匹配方式尝试键名和name字段匹配
                for match_name in match_methods:
                    # 优先通过键名匹配
                    if prompt_key == match_name:
                        return prompt_data.get("template", "")
                    # 其次通过name字段匹配
                    if prompt_data.get("name") == match_name:
                        return prompt_data.get("template", "")
        except Exception as e:
            # 记录错误但继续尝试其他文件
            error(f"加载提示词文件 {match_methods} 时出错: {str(e)}")

        # 如果找不到指定名称的提示词，抛出异常
        raise KeyError(f"提示词模板 '{name}' 不存在")

    def get_name_prompt(self, name) -> str:
        """获取剧本解析提示词模板"""
        return self.get_prompt(name)


prompt_manager = PromptManager(version=prompts.__version__, language=get_language())

核心逻辑解释：

  • 懒加载 + 标志位：用 _all_prompts_loaded 保证所有 YAML 只全量加载一次，避免反复 IO。
  • 多策略匹配 & 容量上限：get_prompt() 按"缓存 → 键名 → name 字段 → 去 _prompt 后缀"逐级匹配；缓存超过 1024 条时只保留最新 1024 条，防内存膨胀。
  • 注意事项：模板以 version + language 目录隔离，切换语言/版本即切换目录，便于 A/B 调试。
  • 已知代码缺陷（如实记录）：get_all_prompts() 中"处理旧格式"的 elif isinstance(data, dict) and "name" in data 分支永远不可达——上面的 if isinstance(data, dict) 已捕获全部 dict 情形，这是历史重构的残留；另外 get_prompt() 的 docstring 列出了 5 条匹配策略，实现层实际只落地了其中 2 条。这类"文档与实现漂移"不影响主流程，但会误导二次开发者，属于可以顺手清理的技术债。

def _call_llm_chat_with_retry(self, system_prompt: str, user_prompt, max_retries: int = 2) -> Optional[str]:
    """
        调用LLM，直接返回json字符串（支持重试）
    """
    messages = [
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": user_prompt}
    ]

    for attempt in range(max_retries):
        try:
            return llm_chat_complete(self.llm, messages)  # 直接使用实例持有的 self.llm

        except Exception as e:
            if attempt == max_retries - 1:
                raise Exception(f"LLM调用失败: {e}")
            time.sleep(1)

# 真实源码（client_factory.py）
def llm_chat_complete(llm: BaseLanguageModel, messages: List[Dict[str, str]], **kwargs) -> str:
    """ LLM 聊天接口封装 """
    response = llm.invoke(_convert_messages(messages), **kwargs)
    return response.content

核心逻辑解释：超时/网络抖动导致调用异常时，先 sleep(1) 再重试（默认 max_retries=2）；最后一次仍失败则显式上抛，交由工作流节点层的异常处理与三级循环控制接管（见第四节）。

注意事项（如实记录）：重试间隔是写死的 time.sleep(1)，并未使用 LLMBaseConfig.retry_delay 配置项；也没有区分"可重试错误/不可重试错误"——参数类的 4xx 错误同样会重试 2 次再上抛。这是用增加延迟换取实现简单，属于当前版本可优化的边界。

机制 计数器 触发条件 重置条件 作用
硬限制 node_current_loops 每次进入节点 永不重置 防止死循环
软限制 stage_current_retries 决策返回 NEEDS_RETRY 成功时重置为0 控制质量重试
全局后备 global_current_loops 每次进入节点 永不重置 最后防线

关键设计原则：

  1. 软限制失败后降级为 NEEDS_REPAIR，不是直接失败
  2. 修复参数会随 NEEDS_REPAIR 传递，指导节点如何修复
  3. 全局限制作为兜底，防止极端情况下的无限循环

全局 80% 预警（真实源码 workflow_decision.py）：全局循环用到 80% 时发出一次 warning 日志——条件为 global_current_loops >= global_max_loops * 0.8 and not loop_warning_issued，由 loop_warning_issued 标志位保证只发一次。这是典型的"软着陆"设计：等到 100% 直接 FAILED 时往往来不及排查，80% 预警给了运维介入的窗口。

默认参数参考（真实源码 workflow_state_types.py）：节点硬限制按节点差异化配置（PARSE_SCRIPT: 3、SEGMENT_SHOT: 5、SPLIT_VIDEO: 5、AUDIT_QUALITY: 3、HUMAN_INTERVENTION: 1）；阶段软限制多为 3（AUDIT_QUALITY、CONTINUITY_CHECK 为 2）；全局上限默认 global_max_loops = 30，工作流启动时按"所有节点最大循环次数之和 × 2"推导（workflow_pipeline.py 的 2 倍安全系数）。

for i, existing in enumerate(self._queue):
    if self._priority_order[queued_task.priority] < self._priority_order[existing.priority]:
        self._queue.insert(i, queued_task)
        break

核心逻辑解释（为什么不用 heapq）：heapq 能做到 O(log n) 入队，但 PenShot 选择 list.insert 有序插入（最坏 O(n)）。原因在于队列还要支持按 task_id 遍历与移除——cancel_task() 的实现就是 for i, queued in enumerate(self._queue) 找到后 del；用堆实现这种操作反而更绕且需要延迟删除。队列上限 1000 的量级也不构成性能瓶颈。这是"数据结构选型服从业务操作集合"的典型例子；若队列规模升到数万级，才值得考虑堆 + 懒删除方案。

1. 短期记忆：滑动窗口 + Redis 双通道

真实实现不是 ConversationBufferMemory，而是"自维护 deque 滑动窗口 + LangChain 会话历史"的双通道结构：

# 真实源码（short_term_memory.py，节选）
class ShortTermMemory:
    """
    数据隔离策略：
    - 每个剧本有独立的 session_id
    - Redis key 格式: penshot:memory:{session_type}_{script_hash}
    """

    def __init__(self, config: MemoryConfig, script_id: str):
        self.max_size = config.short_term_size          # 默认 20 条

        # 为当前剧本生成唯一 session_id
        self._session_id = f"short_term_{script_id[2:]}"

        self._message_buffer = deque(maxlen=config.short_term_size)

        self._redis_available = False
        self._check_redis_availability()                # socket_connect_timeout=3 + ping()

        if not self._redis_available and config.term_persist_path:

                session_id=redis_key,
                url=self.config.short_term_redis_url,

核心逻辑解释（三条通道各司其职）：

  • deque 滑动窗口：deque(maxlen=20) 在添加时自动丢弃最旧条目，O(1) 且不可能溢出——比"判断超限再裁剪 list"的写法更难出错。get_recent(n) 优先读内存 deque（快），为空时回查 Redis（进程重启后的恢复路径）。
  • Redis 会话历史：跨请求可见，ttl=3600 让单次任务周期内的记忆自动过期，不需要额外清理任务。
  • 文件降级：Redis 不可用时每次 add() 同步写 short_term.json，重启后 _load_from_file() 恢复窗口。

故障实战（Redis 挂掉会发生什么）：降级决策发生在实例构造时——_check_redis_availability() 用 3 秒超时连接并 ping()，失败则整体切换到"内存 + 文件"模式并打 warning 日志，这是设计好的路径。运行中途 Redis 才挂的情况更微妙：add() 会走异常分支（error 日志），且由于缓冲区追加与 Redis 写入在同一 try 块内，本次交互既写不进 Redis 也不会进入内存窗口；后续 add() 持续失败，直到 Redis 恢复。也就是说，当前版本没有运行期重连与补偿机制，中途故障不会自动切通道。影响面可控的原因在于：单次记忆丢失不会中断主流程，且工作流有质量审计与检查点兜底；想彻底解决需引入重连探活与本地补偿队列，属于 Roadmap 级别的工作。

2. 中期记忆：LLM 摘要融合 + 双重截断保护

真实实现用 RunnableWithMessageHistory 包装自定义摘要函数（也不是 ConversationSummaryMemory），默认摘要是"逐步融合式"的滚动摘要（rolling summary）：

# 真实源码（medium_term_memory.py，节选）
class MediumTermMemory:
    """中期记忆 - 基于LangChain的摘要记忆，支持文件持久化"""

    DEFAULT_SUMMARY_PROMPT = PromptTemplate(
        input_variables=["summary", "new_lines"],
        template="""逐步总结对话内容，将之前的总结与新的对话内容融合。

            当前总结:
            {summary}

            新的对话内容:
            {new_lines}

            请生成更新后的总结（保持简洁，突出重点）:"""
    )

    def _create_summary_chain(self):
        def summarize(input_dict):
            summary = input_dict.get("summary", "")
            new_lines = input_dict.get("new_lines", "")

            # 截断保护：新内容不超过 max_token_limit*4 字符
            if len(new_lines) > self.max_token_limit * 4:
                new_lines = new_lines[:self.max_token_limit * 4]

            prompt = self.config.medium_term_summary_prompt or self.DEFAULT_SUMMARY_PROMPT.template
            response = self.llm.invoke(prompt.format(summary=summary, new_lines=new_lines))
            new_summary = response.content

            # 输出保护：摘要本身不超过 max_token_limit*2 字符
            if len(new_summary) > self.max_token_limit * 2:
                new_summary = new_summary[:self.max_token_limit * 2] + "..."
            return new_summary

        return RunnableLambda(summarize)

核心逻辑解释（为什么是"融合式"而不是"重新总结"）：每次摘要把"已有摘要 + 新内容"一起交给 LLM 做增量融合，而不是把全部历史重读一遍——摘要成本与内容总量呈线性关系，而不是随历史长度平方级增长。两处硬截断（输入 ≤ max_token_limit*4 字符、输出 ≤ max_token_limit*2 字符）是防"摘要越滚越大"的保险丝；代价是超长内容会被静默砍掉尾部（没有告警日志），排查"摘要信息缺失"类问题时要意识到这一点。

持久化与恢复：中期记忆写入 data/memory/{script_id}/ 下的 JSON（按小时归档），实例化时 _load_from_file() 恢复 _stage_summaries（阶段摘要字典）。注意滚动摘要本体不在恢复范围内，进程重启后需要从新的交互重新积累——这是当前实现的边界之一。

class LongTermMemory:
    """长期记忆 - 基于向量检索的记忆"""

    def __init__(self, config: MemoryConfig, script_id: str):
        self.store_path = f"{config.term_persist_path}/{script_id}"

        # 每个剧本一个独立 collection
        self.vectorstore = Chroma(
            collection_name=f"script_{script_id}_memory",
            embedding_function=config.embeddings,
            persist_directory=self.store_path
        )

    def add(self, text: str, metadata: Optional[Dict] = None):
        """tags/category 拼进文本后再入库，让元数据参与语义召回"""
        enhanced_text = text
        if metadata:
            enhanced_text = f"{text}\n"
            if metadata.get("tags"):
                enhanced_text += f"标签: {', '.join(metadata['tags'])}\n"
            if metadata.get("category"):
                enhanced_text += f"类别: {metadata['category']}\n"
        self.vectorstore.add_texts(texts=[enhanced_text], metadatas=[{...}])

    def search(self, query: str, k: int = None) -> List[Dict]:
        results = self.vectorstore.similarity_search_with_score(query, k=k)
        return [
            {"content": doc.page_content, "score": score, "metadata": doc.metadata}
            for doc, score in results
            if score >= self.config.long_term_score_threshold   # 默认 0.7
        ]

核心逻辑解释：每个剧本一个 collection（script_{id}_memory）落盘到 data/memory/{script_id}/；add() 时把 tags/category 拼进正文再入库，让元数据也参与语义召回——这是轻量的"信息增强检索"手法，代价是命中的文本里混有元数据行。ScriptMemory.__init__ 里还有一个细节：即使配置 long_term_enabled=False，也会探测一次已有数据，若发现历史条目则自动启用长期记忆并回写配置——避免"配置改错导致历史记忆静默失效"。

需要验证的疑点（如实记录）：similarity_search_with_score() 在 Chroma 默认 L2 距离度量下返回的是距离（越小越相似），而过滤条件是 score >= threshold（0.7）——方向与"保留更相似结果"的直觉相反，疑似"按余弦相似度习惯写过滤条件"的遗留。这里不下结论，建议使用方打印分数分布验证：如果命中的都是距离偏大的条目，应改为 score <= threshold。

三层记忆解决的是运行时交互记忆；PenShot 还有另一条与工作流深度耦合的记忆链路——workflow_memory.py 按阶段（stage）持久化质量数据，并在下一轮执行时反向注入提示词：

# 真实源码（base_repairable_agent.py，节选）：历史上下文 → 提示词片段
def build_history_hint(self) -> str:
    hints = []
    # 常见问题提示（按出现次数排序的高频问题）
    high_freq_issues = self._historical_insights.get("high_freq_issues", {})
    if high_freq_issues:
        issue_desc = ", ".join([f"{t}({c}次)" for t, c in high_freq_issues.items()])
        hints.append(f"历史常见问题: {issue_desc}，请特别注意避免这些问题。")

    # 质量等级提示（由历史 completeness_score 分档）
    quality_level = self.get_quality_level()      # poor / medium / good
    if quality_level == "poor":
        hints.append("历史解析质量较低，请提高解析质量，确保输出结构的完整性和准确性。")

    if not hints:
        return ""
    return "\n".join(["", "【历史参考信息】", *[f"  - {h}" for h in hints], ""])

核心逻辑解释（记忆如何真正影响输出）：闭环为"阶段统计 → 高频问题提取 → 提示词注入 → 输出改善"。节点执行前的调用顺序（workflow_nodes.py）是先 apply_historical_context() 再 apply_repair_params()：历史上下文负责"长期经验"，修复参数负责"上一轮的具体问题"，两者共同渲染进用户提示词。历史问题类型（如 prompt_truncated、style_inconsistent）还会触发智能体内部的增强开关（如 _focus_on_style_consistency）。

故障实战（历史上下文没清干净会怎样）：clear_historical_context() 约定在"节点成功完成后"调用。若某条成功路径忘记调用（或新增节点未接入），历史问题会持续影响后续提示词——表现为"已经修好的问题，LLM 仍在小心翼翼地规避"，输出越来越保守。排查方法是看提示词日志里【历史参考信息】是否含过时条目；这也是为什么基类把它设计成显式的一对方法（apply / clear），而不是隐式状态。

统一门面：ScriptMemory 的"自动流转"与按层组装

三层记忆不是并列被调用的，而是由 ScriptMemory 统一组合。它有一个值得注意的设计——add 时的自动流转规则：

# 真实源码（script_memory.py，节选）
def add(self, input_text: str, output_text: str, level: MemoryLevel = MemoryLevel.SHORT_TERM,
        metadata: Optional[Dict] = None):
    """添加记忆"""

    # 1. 始终写入短期记忆
    self.short_term.add(input_text, output_text, metadata)

    # 2. 根据级别或重要性决定是否流转到中期/长期
    if level == MemoryLevel.MEDIUM_TERM:
        self.medium_term.add(input_text, output_text, metadata)
    elif level == MemoryLevel.LONG_TERM and self.long_term:
        combined = f"问题: {input_text}\n回答: {output_text}"
        self.long_term.add(combined, metadata)
    else:
        # 自动流转：标记 important 的短期记忆提升到中期
        if metadata and metadata.get("important", False):
            self.medium_term.add(input_text, output_text, metadata)

        # 短期用到 80% 容量时，把最近 5 条打成摘要注给中期
        short_term_stats = self.short_term.get_stats()
        if short_term_stats.get("message_count", 0) >= self.short_term.max_size * 0.8:
            recent = self.short_term.get_recent(5)
            summary_content = "\n".join([f"Q: {m['content']}\nA: {m.get('output', '')}" for m in recent])
            self.medium_term.add("short_term_summary", summary_content, {"auto_summary": True})

def recall(self, query: str, level: Optional[MemoryLevel] = None,
           k: int = 3) -> MemoryContext:
    """回忆记忆，返回融合上下文"""
    context = MemoryContext()
    if level is None or level == MemoryLevel.SHORT_TERM:
        context.short_term = self.short_term.get_recent(k)
    if level is None or level == MemoryLevel.MEDIUM_TERM:
        context.medium_term = self.medium_term.get_summary()
    if (level is None or level == MemoryLevel.LONG_TERM) and self.long_term:
        context.long_term = self.long_term.search(query, k)
    return context

核心逻辑解释（这里的"融合"是组装，不是加权）：recall() 的真实语义是"按层查询、原样组装进 MemoryContext"，没有 0.6/0.3/0.1 之类的加权融合，也不存在 MemoryFusion 类——网上把"设计意图"当成了实现。三层信息的取舍发生在两个地方：MemoryContext.to_prompt() 的格式化（短期最多 10 条、长期最多 5 条、逐条截断）和调用方传入的 level 参数（指定只查某一层）。

一个值得讨论的设计点：触发"短期→中期"流转的人数阈值判断发生在每次 add() 末尾，且没有水位线/已压缩标记——窗口达到 80% 后每次 add 都会再触发一次摘要融合（多一次 LLM 调用），直到窗口被清空才会停。由于 deque maxlen=20、阈值为 16，窗口饱满后这条路径几乎每轮都执行；且在近满载时每次摘取的"最近 5 条"高度重叠。要修的话加一个 last_summarized_count 水位线即可——这属于读源码才能发现的优化点。

记忆生命周期（真实语义）

stateDiagram-v2
    [*] --> 短期: add() 默认写入 deque + Redis
    短期 --> 中期: metadata.important 标记
    短期 --> 中期: 窗口用量 ≥ 80% 自动压缩最近5条
    短期 --> 过期: deque 超出 maxlen=20 自动丢弃
    短期 --> 过期: Redis TTL 3600 秒到期
    中期 --> 长期: 显式 level=LONG_TERM（ScriptMemory.add）
    长期 --> 过期: 手动 delete_by_filter / clear

核心逻辑解释：真实生命周期以"自动流转 + 时间/容量兜底"为特征——短期靠 TTL 与 deque 容量自然衰减；中期靠重要标记与 80% 水位触发晋升；长期永不自动过期（Chroma 持久化落盘），只能显式清理。

注意事项（如实记录）：当前代码没有"中期→长期"的自动晋升——那一步必须调用方显式指定 level=LONG_TERM；也没有基于重要度评分的自动分层。把"重要度评估自动进长期"当成本项目现成能力是过度解读。

七、文本压缩：真实机制与边界

针对长剧本场景，PenShot 的"压缩"分散在三个层次，而不是一个独立的摘要模块。这里如实拆解每一层实际做了什么、没做什么。

# 真实源码（memory_context.py，节选）：提示词组装与截断
def to_prompt(self, max_tokens: int = 2000) -> str:
    parts = []
    if self.short_term:
        parts.append("=== 最近对话 ===\n" + self._format_short_term())
    if self.medium_term:
        parts.append("=== 历史摘要 ===\n" + self.medium_term)
    if self.long_term:
        parts.append("=== 相关经验 ===\n" + self._format_long_term())

    context = "\n\n".join(parts)
    return self._truncate(context, max_tokens)

def _format_short_term(self) -> str:
    formatted = []
    for msg in self.short_term[-10:]:           # 限制最多10条
        content = msg.get("content", "")
        if len(content) > 500:                  # 单条超长也截断
            content = content[:497] + "..."
        formatted.append(f"{role}: {content}")
    return "\n".join(formatted)

def _truncate(self, text: str, max_tokens: int) -> str:
    """截断文本：1 token ≈ 2 字符（保守估算）"""
    estimated_tokens = len(text) // 2
    if estimated_tokens <= max_tokens:
        return text

    max_chars = max_tokens * 2
    truncated = text[:max_chars]

    # 尝试在完整句子处截断
    last_period = truncated.rfind('。')
    last_newline = truncated.rfind('\n')
    cut_pos = max(last_period, last_newline)

    if cut_pos > max_chars * 0.7:               # 截断点落在后70%才采用
        truncated = truncated[:cut_pos + 1]

    return truncated + "\n[上下文已截断]"

核心逻辑解释（为什么用"字符估算"而不是精确分词）：_truncate 用"1 token ≈ 2 字符"的保守估算。为什么不上 tiktoken 等精确分词器？因为这里只需要一个"不超窗"的安全上界，而非精确计费——引入分词器会给每次提示词组装增加计算与依赖成本，而截断点本身已有冗余。这是一次典型的"精度换简洁"取舍；未来若做精确 token 计费或硬限流，才需要替换。

边界与不足（重要）：当前版本没有一个独立的"长剧本分块摘要器"类。网上流传的 ScriptSummarizer、按场景/对话/动作三级摘要以及 70%/80%/60%/50% 压缩比在源码中均不存在，属拟造内容。实际的长文本处理是"分而治之"：shot_segmenter 按场景（scene）逐个处理、video_splitter 按镜头（shot）逐个处理，每个单元的提示词只携带本场景信息 + 元素列表 + global_context（角色服装/关键道具等跨场景一致性汇总）。也就是说，长剧本的"分块"发生在场景/镜头拆分阶段，而非文本摘要阶段；真正的"全剧摘要压缩"属于 Roadmap 方向。

九、实现要点小结

  • 多 LLM 可插拔 + 三级降级：OpenAI / Ollama / Qwen 统一封装与厂商自动探测；默认配置失败退备用配置，再失败返回 None 走规则引擎模式。

  • 提示词工程是质量瓶颈：规则化约束 + one-shot 示例 + 版本化 YAML + {repair_hint}/{history_hint} 占位回传；加载器中存在不可达分支与文档漂移（已在第二节标注）。

  • 一致性保障：连续性锚点（带生效范围的结构化约束）、修复参数反馈（审计 → 注入 → 定向重试）、全局风格开关（style_consistency / use_common_negative_prompt）——而非"固定种子"这类被误传的说法。

  • 防御性循环控制：硬限制 / 软限制 / 全局后备三级计数器 + 80% 预警，节点级参数差异化配置，2 倍安全系数推导全局上限。

  • 三层记忆 + 分层存储：deque/Redis（短期）、LLM 滚动摘要/文件（中期）、Chroma（长期），recall() 按层组装而非加权融合；workflow_memory 的"历史参考信息"闭环让记忆真正影响下一轮输出。

  • 工程边界（如实记录）：无独立长剧本摘要器、无运行期 Redis 重连、长期记忆阈值过滤方向存疑、LLMBaseConfig.seed 仅 Ollama 透传——这些都在正文标注，供读者评估与向社区反馈。
