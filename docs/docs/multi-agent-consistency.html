一、概述：问题背景与整体架构

问题背景

AI 视频生成模型在单片段生成上已经表现出色，但当需要生成一个完整的、包含多个连续片段的视频时，一致性问题就成为了最大的挑战。角色外貌在不同片段中发生变化、场景细节前后矛盾、道具位置突然改变——这些不一致性会严重破坏观众的沉浸感。

PenShot 给出的答案是"六节点流水线 + 知识支撑"的多智能体协作：剧本解析提取事实基线，分镜与分段把基线写进结构化字段，指令转换把约束拼进提示词，质量审查与连续性守护负责发现问题。但这套体系里各机制的真实落地程度并不相同——本文按"已接线 / 已实现但未接线 / 规划中"三分组逐项核查，每个结论都给出源码依据。

二、一致性的定义与维度

在视频分镜中，一致性可以从多个维度来定义和度量。这五个维度是 PenShot 的设计口径，也是后文七个策略的"服务对象"。

角色一致性要求同一个角色在全部片段中外貌、服装、体型保持一致。角色的面部特征不能出现突然变化，服装不能在不同场景中随意更换，除非剧情明确要求换装。

场景一致性要求同一个场景的空间布局、陈设道具、色彩基调在各个片段中保持一致。如果某个场景的沙发是红色的，那么所有该场景的片段中沙发都应该是红色的。

道具一致性要求关键道具的位置和状态需要连续追踪。角色手中的水杯不能突然消失，桌上的书籍不能改变位置。

动作一致性要求角色的动作在片段之间保持连贯。角色从站立到坐下的过程需要合理的中间状态。

风格一致性要求整体的视觉风格、镜头语言和剪辑节奏保持统一。不能一个片段是写实风格，下一个片段突然变成卡通风格。

这些维度如何落地？连续性守护模块给出了当前实现的答案——不是视觉模型比对，而是六项词表级规则检查（比设计口径多出"时间"一项）：

设计维度 检查器对应方法 当前实现方式
角色一致性 check_character_continuity 外观关键词分类对比（服装 / 发型 / 配饰三类词表）+ 有台词角色无镜头检测
场景一致性 check_scene_continuity 相邻镜头场景跳变检测 + 跳变频率阈值（超 30% 镜头数告警）
道具一致性 check_prop_continuity "拿 / 举 / 抱 / 提 / 端 / 持 / 握"七动词变化检测
动作一致性 check_action_continuity 动作关键词（走 / 跑 / 跳 / 转身 / 坐下 / 站起 / 拿起 / 放下）变化检测
风格一致性 check_style_continuity 片段 style 字段的去重统计（>2 种风格即告警）
（时间维度） check_time_continuity 片段首尾时间的间隙 / 重叠检测（容差 0.1 秒）

补充说明：五维并非并列——风格一致性处于最上层，是角色、场景、道具、动作四者"视觉收敛"后的总体观感，后面所有策略本质上都在为这些维度服务。但也要直说：词表级检查只能发现"同类关键词切换"这类显性漂移（例如"穿衬衫"变成"穿裙子"），对语义级的微妙变化（同义改述、方位错误）无能为力——这是当前实现的边界，也是后文规划章节中视觉级校验要补的课。

三、核心策略一：角色基线——三视图没有进入代码

如果只看设计讨论，"角色三视图"一定会排进一致性方案的前三名：为每个角色生成正面、侧面、背面三张标准参考图，任何片段、任何角度都拿这三张图做视觉锚点。

但先给结论：在当前代码库中，三视图机制的三个关键环节——三视图生成、三视图库、参考图注入——都不存在。检索 三视图 / tri_view / turnaround / reference_image 等关键词，在所有源码与提示词模板中零命中。这条常被讲述的"核心策略"，目前停留在设计稿阶段。

那么角色一致性靠什么兜底？当前实现打的是"文本基线 + 模板强约束"两张牌：

为什么没做三视图？ 这不是能力问题，而是依赖边界的取舍：三视图需要一条"生成参考图 → 存储 → 在视频生成时作为条件图引用"的外部图像链，而当前仓库的边界是"提示词与指令编排"——它不直接调用图像生成模型，自然也无法假定下游模型支持参考图条件输入。相比之下，文本基线零外部依赖、可程序化校验（六项检查器正是基于这些文本做词表比对）、实现成本低。

代价也要说清楚：文本描述承载不了精确视觉外观。“黑色长发、白色衬衫"这类描述在不同片段反复生成时仍会有像素级漂移，模板约束只能降低概率，无法锁死。真正要"锁形”，得靠参考图 / 首尾帧条件生成这类能力——那是下游模型集成层的课题，超出本仓库范围。

四、核心策略二：连续性锚点——实现了，但没有接线

连续性锚点的设计意图是：在剧本层面定义关键一致性参照点（某角色在某段时间内必须保持什么状态），并带上生效区间与优先级，让"约束"第一次具备结构化语义，而不是散落的文本字段。

这套设计的模型类是真实存在的——ContinuityAnchor（continuity_guardian/continuity_guardian_models.py，完整真实源码）：

# continuity_guardian_models.py L499-527（真实源码）
class ContinuityAnchor(BaseModel):
    """连续性锚点 - 用于约束生成"""

    anchor_id: str = Field(..., description="锚点唯一标识")
    anchor_type: str = Field(..., description="锚点类型: character, scene, prop, style")

    # 锚点内容
    name: str = Field(..., description="锚点名称")
    value: Any = Field(..., description="锚点值")

    # 约束范围
    start_time: float = Field(default=0.0, description="生效开始时间")
    end_time: Optional[float] = Field(default=None, description="生效结束时间")
    fragment_range: Optional[List[int]] = Field(default=None, description="生效片段范围")

    # 优先级
    priority: int = Field(default=1, description="优先级（越高越重要）")

    # 元数据
    metadata: Dict[str, Any] = Field(default_factory=dict, description="扩展元数据")

    def is_active_at(self, time: float) -> bool:
        """检查锚点是否在指定时间生效"""
        if time < self.start_time:
            return False
        if self.end_time is not None and time > self.end_time:
            return False
        return True

字段本身就说明了设计意图：

设计要素 字段 设计意图
锚点类型 anchor_type 角色 / 场景 / 道具 / 风格四类统一建模
生效区间 start_time / end_time / is_active_at() 解决"约束从第几秒到第几秒有效"——剧情合理的状态变化不会误报
范围限定 fragment_range 限定只在某些片段内生效（如某道具只出现在某几场戏）
冲突裁决 priority 多个锚点矛盾时按优先级取舍

但现实是：这套锚点体系没有通电。ContinuityAnchor 除定义处外全仓库无任何引用；StateTimeline.continuity_anchors 在等一个不存在的写入方；配套的 GlobalConsistencyContract 契约体系（process_with_contract / check_with_contract / CrossChunkValidator）同样没有调用方。

为什么要有"降级为全量"的设计？这是防御性取舍：如果解析器没能为某场景标注道具关联，宁可给模型全量道具信息（略带噪音），也不要漏掉关键约束（信息缺口）——宁冗余、勿缺失。代价是提示词变长，但在一致性场景下这个 token 成本的权衡是划算的。

模板侧的强制约束：四段上下文并非"参考信息"，三档模板都把它定义为必须遵循的硬约束：

  • video_splitter_prompt.yaml：【重要约束】“如果本场景涉及【全剧上下文】中的道具，必须在分割后的片段中完整保留”

  • shot_segmenter_prompt.yaml：“道具一致性：必须严格遵循【全剧上下文】中列出的关键道具描述，同一物品在不同镜头中的名称、外观、颜色、文字必须完全相同”

  • prompt_converter_prompt.yaml：“参数矛盾优先采用【全剧上下文】设定”——当镜头描述与全局基线冲突时，以基线为准

为什么用固定段落而不是自由文本？ 三个工程理由：① 程序可以逐字段拼装，不依赖 LLM 自由发挥（确定性）；② 检查器可以按段落读取文本做词表比对（可验证）；③ 按场景裁剪减少了无关信息对提示词的稀释（信噪比）。这套设计的边界同样明确：段落是"文本级强约束"，约束力取决于下游模型对提示词的服从程度——它降低了漂移概率，但无法给出图像级的保证。

七、核心策略五：状态快照——一条未通电的时间线

多智能体协作有一个天然的薄弱点：每个节点只看得到自己那一段输入。分段阶段不知道转换阶段干了什么，转换阶段也不知道前面片段的最终状态。状态快照就是为这个断点设计的——用时间线保存"每一刻的连续状态"，让任意片段的生成都能回放到它的前驱状态。

数据结构与算法已经完整落地（continuity_guardian_models.py），核心是两个模型：

class StateSnapshot(BaseModel):
    timestamp: float
    snapshot_id: str            # 必填
    character_states: Dict[str, CharacterState]
    scene_state: Optional[SceneState]
    global_state: Dict[str, Any]   # 默认含 current_scene / time_elapsed / narrative_phase / emotional_tone
    references: Dict[str, Any]     # 默认含 fragment_id / shot_id / element_ids

class StateTimeline(BaseModel):
    snapshots: List[StateSnapshot]

    # get_snapshot_at_time：按时间查询（语义见下文）
    # get_latest_snapshot / get_character_evolution / record_evolution
    # tolerance_settings：位置 medium / 外观 low / 时间 high / 颜色 medium

检查器还提供了创建入口 take_snapshot——从 parsed_script.characters 构建 CharacterState（外观取角色描述、情绪初始化为 neutral），并挂到时间线上。设计上它应该由工作流在片段完成后调用。

但这条时间线没有通电：take_snapshot 没有任何调用点，StateTimeline 实例只活在检查器内部，没有工作流节点读取它，StateSnapshot 也不会出现在任何提示词里。当前片段间的"状态接力"，实际靠的是前文提到的文本通道（continuity_notes + 四段上下文）——它传递的是"设定量"（角色穿什么、道具是什么），而不是"瞬时状态"（角色的姿态、位置、情绪强度）。

接线时要注意的一个语义细节：get_snapshot_at_time(t) 的返回语义不是"t 时刻之前最近的历史状态"，而是"首个时间戳 ≥ t 的快照"（找不到则兜底返回最后一个）——真实代码如下，注释声称的"二分查找"实为线性扫描：

# continuity_guardian_models.py L345-354（真实源码）
def get_snapshot_at_time(self, timestamp: float) -> Optional[StateSnapshot]:
    """获取指定时间的快照"""
    if not self.snapshots:
        return None

    # 二分查找最接近的快照
    for i, snapshot in enumerate(self.snapshots):
        if snapshot.timestamp >= timestamp:
            return snapshot
    return self.snapshots[-1]

这类细节在快照真正参与生成前需要先澄清，否则"回放前驱状态"可能取到未来状态。

为什么值得补课：快照是三件事的共同前提——锚点的生效区间判定、连续性检查的时间对齐、以及"片段 N 承接片段 N-1 结束状态"的提示词注入。没有它，多智能体的"共享状态"始终缺一块黑板。

十、规划蓝图：渐进式生成与双向约束——为什么它们进不了当前代码

渐进式生成：一个被成本否决的优化

渐进式生成的设计意图是：先锁定关键帧（情绪高潮、动作转折、出场/退场），再以关键帧为锚点向时间轴两侧扩展生成过渡片段，让最重要的片段优先定型，次要片段围绕它们调整。

flowchart LR
    subgraph Keyframe[关键帧生成]
        K1[情绪高潮帧]
        K2[动作转折帧]
        K3[出场/退场帧]
    end

    subgraph Expand[向两侧扩展]
        E1[从前一关键帧生成过渡]
        E2[向后一关键帧生成过渡]
        E3[填补中间空白]
    end

    Keyframe --> Expand

这个思路本身是成熟的（视频编码、动画分镜都这么干），但把它搬到 LLM 分镜流水线上有硬性障碍：

  1. 关键帧识别没有可靠信号源。要判断哪一帧是"情绪高潮"，需要情绪曲线或叙事张力评分——代码里两者都不存在，剧本解析产出的是结构化事实（角色、场景、道具、对白），不含任何量化情绪信号。

  2. 多处生成会放大 token 成本。渐进式生成意味着同一批片段要经历"先关键帧、再过渡、再回填"的多轮 LLM 调用，而当前设计是一次分镜 + 一次分段 + 一次转换的线性管线，成本可控性优先于生成顺序优化。

  3. 收益兑现依赖下游能力。即便生成了顺序更优的片段，最终成片一致性仍取决于视频生成模型本身——而工具侧能做的是把约束写清楚，顺序优化的边际收益不明确。

当前代码的真实做法是：分镜阶段由 LLM 一次性产出完整镜头列表，时长分配在 llm_video_splitter 中按规则计算（见《核心实现》中分段逻辑），没有关键帧优先级的概念。这不是偷懒，而是在"线性成本 + 可预测性"与"顺序优化 + 成本翻倍"之间选了前者。

双向约束的设计意图是：生成片段 N 时同时加载 N-1 与 N+1 的约束，要求片段 N 始于前一状态、止于可衔接后一状态，消除"往返不一致"。

为什么向前看这么难？因为它要求管线从"逐片段流式处理"改为"全片协同规划"——每个片段的生成都要等待邻接片段的约束就绪，这会让管线从线性变成图状调度，复杂度和重试成本都上一个台阶。而修复手段（连续性守护 + 回流）本质上是在为"单向约束"兜底：允许先把片段生成出来，再用规则检查发现断裂并回流修复。“事后检查 + 回流"替代"事前双向约束”，是当前架构最核心的工程妥协。

结构组管的是"电影语言"层面的规范：180 度轴线、视线匹配、动作连贯（镜头语法），片段间的转场方式（转场规范），景别的变化规律（景别序列）。

优化组：提示词向后兼容、对抗生成（与第十章的两个机制）

优化组在原规划全景图里列了三项：对抗生成、渐进式生成、双向约束。后两项已在第十章分析过（成本否决与管线拓扑约束），这里补充另外两项。

提示词向后兼容策略：设计意图是"导演决定让角色换装，系统自动把变更传播到之后的所有片段，并在提示词中生效"。这个方向是原蓝图里唯一不需要新硬件、不需要新模型的候选机制——片段之间的依赖关系理论上可以从数据结构恢复（片段属于镜头、镜头属于场景、场景共享角色）。但真实的缺口不在传播，而在失效重算：当前对某个片段 prompt 的人工修改，不会自动刷新后续片段的提示词；修改后重跑修复，靠的是节点重试与回流，而不是依赖图驱动的精准失效。知识库侧同理：现有接口只有"新增与检索"，库中已入库的历史模板不会随上游修改退出检索，也没有失效标记机制。

对抗生成策略：设计意图是同一片段用多个模型或参数版本生成，取一致性最高的结果。以当前成本结构（一集短剧十几个片段、每片段多次调用），多模型投票会把生成成本翻倍，而项目连"单模型生成结果的质量评估"都还停留在提示词层面（没有画面级评估），投票所需的特征相似度计算无从谈起。这条机制的搁置原因最直白：收益无法度量，成本却可即时计量。

规划章节的诚实总结

把两章的规划内容合起来看，可以给出一个"落地成本分级"（另有一个可核对的细节：原规划图列出 15 项机制，但正文只展开了 12 项——“时间线对齐”"转场规范"有图无文，而"提示词向后兼容"有文无图；本文按 16 项口径合并整理）：

分级 机制 判断依据
改造成本低（值得优先） 景别序列检查、提示词失效重算 数据与检查框架已存在，只需扩展判据/增加依赖追踪
等基础设施 时间线对齐、快照驱动类机制 前置依赖：快照机制先接线
等模型能力 关键帧锁定、对抗生成、视觉级校验 前置依赖：视觉特征提取/多模型接入
等数据/信号源 情绪曲线、因果链追踪、运动插值 前置依赖：叙事分析信号或帧级处理能力
纯蓝图 色彩/光照/构图的参数化、镜头语法、转场规范 需要重构提示词管线的表示层，当前无此规划

这份分级本身也是本文的一个立场：规划不是问题，"把规划当现状"才是问题。一份可信的技术方案，应该能让读者一眼分清哪些在跑、哪些在等什么条件——而不是笼统地宣称"层层设防、高可靠性保证体系"。

十二、故障实战：七个真实断点与降级场景

前文的考证如果只落成一句"有些机制没接线"，就浪费了。本节把七个最有代表性的场景按"发生什么 → 为什么 → 系统如何处理 → 如何恢复"展开。它们分为三类：断链型（零件齐了、电线错位）、降级型（设计上主动选择放行或失败）、口径型（同一职责存在多套实现）。所有场景均来自源码级考证，非设想。

故障一：连续性检查报了问题，修复却没有发生

发生什么：某次运行中，连续性守护在分段阶段检出 MAJOR 级问题（如"角色在片段 3 消失"），日志里问题记录完整，但最终输出仍带着这些问题——没有修复，也没有失败，悄无声息。

为什么：守护节点的修复准备动作其实全都做了——把修复参数写进 state.domain.repair_params、置位 needs_continuity_repair、把 current_node 改写为上游修复节点，四个上游节点也有对应的 apply_repair_params 消费逻辑。断点在图的条件边上：decide_after_continuity 读取的是顶层 state.continuity_issues，而数据实际挂在 state.domain.continuity_issues 下，取出来恒为空列表，永远判 SUCCESS 直达输出；即便字段读对，该决策返回的 NEEDS_RETRY 在图的边映射里也没有对应键（双重缺口）。

系统如何处理：当前表现是"静默跳过"——检查结果仍在状态与日志中，但路由不触发修复。

如何恢复：临时方案是人工核对日志、手动重跑受影响阶段；代码修复需两处：条件边改读 state.domain.continuity_issues，并补齐 NEEDS_RETRY 的图边映射。这也说明"已实现"的验收标准应包含"接线验证"，否则零件越全，越容易误判可用。

故障二：知识库悄悄降级

发生什么：RAG 增强整体失效——生成提示词里不再出现"参考优秀模板"段，但整个工作流照常成功，没有任何报错。

为什么：当检索无命中（知识库为空、索引未建、相似度低于 min_similarity_score=0.7 阈值）时，查询返回空结果，调用方对空模板直接跳过拼接。这意味着"增强链路坏掉"与"增强链路正常但恰好无命中"，在流程输出上几乎无法区分。

系统如何处理：静默继续。这是有意的 fail-open 选择：知识库是可选增强，不能因为增强失效阻断主流程。

如何恢复：排查靠检索相关日志；恢复靠重建/重灌索引。注意：验证 RAG 是否工作，只看流程成功与否是无效的——必须核对提示词里是否真的出现了参考模板段。

故障三：参考模板错配——append 拼接没有归属校验

发生什么：某片段的提示词尾部被拼接了一段"参考优秀模板"，但模板描述的是另一部剧本的场景与服装，与当前片段直接矛盾。

为什么：enhance_prompt 在转换节点以 append 模式直接把检索到的模板拼到提示词尾部（真实格式是 f"{original_prompt}\n\n参考优秀模板:\n{template}"），且调用时不传 script_id——检索范围是全库，跨剧本命中是允许的。而 append 只是文本拼接：模板里若包含具体角色、服装、地点特征，没有任何机制校验它属于当前片段。有意思的是，提示词转换模板里明确写着"不可将 A 角色的服装特征错误分配给 B 角色"——说明团队意识到了这类风险，但那条约束管的是 LLM 生成过程，管不到知识库拼接这一步。

系统如何处理：get_best_match(top_k=1) 先找最相似的一条成功模板，低于相似度阈值就不拼接；但"高于阈值的错配"没有防线。

如何恢复：人工审查被 append 的模板段，错配就删除或重生成片段；根治方向是给 enhance_prompt 传入 script_id 收窄检索范围，并在模板入库时打上来源与角色标签。

故障四：“分数很高，状态却要修复”——审计口径的分裂

发生什么：审计报告显示 90 分，状态却是 MODERATE_ISSUES 并被送进修复流程——使用者第一反应是"90 分都不及格？"

为什么：实际生效的判定是"存在性判定"：只要有一个 MODERATE 违规，状态就是 MODERATE_ISSUES，与分数无关；而分数是 100 减去严重度权重（{WARNING:5, MODERATE:10, MAJOR:25, CRITICAL:40, ERROR:60}）的连续扣分值。一个 MODERATE 违规扣 10 分，于是"90 分 + MODERATE_ISSUES"完全可能。更绕的是项目里同一职责存在三套实现（内部审计器的 pass_rate 制、模型层未接线的六档阈值、agent 生效的扣分制+存在性判定），新人读代码极易混淆。

系统如何处理：决策只看状态（decision_map），分数只记录、不参与路由。

如何恢复：排查时以"状态的来源违规列表"为准，不要只看分数；长期应把三套口径收敛为单一真源。另一个值得注意的数据口径差异：知识库回写成功案例时的 quality_score 取自 stats.completeness_score（缺省 85.0），与审计报告分数根本不是同一来源——做数据分析时不能把两者当成一个指标。

故障五：审计器自己挂了——fail-closed 的保守失败

发生什么：LLM 审查器调用失败（超时、限流）时，整个审计不是"跳过检查"，而是直接 FAILED。

为什么：qa_process 捕获异常后返回兜底报告：状态 FAILED、分数 0.0、结论"质量审查失败，请检查系统状态后重试"。

系统如何处理：保守失败——宁可让工作流走失败/重试路径，也不放行未经审查的结果。这与故障二的静默降级形成有意对照：知识库是可选增强，可以 fail-open；质量闸门是最后防线，必须 fail-closed。

如何恢复：临时性故障直接重试工作流；持续性故障检查模型配置。auto 模式下反复失败会走重试上限逻辑，最终转入人工或失败退出。

故障六：传了 use_rerank=True，什么都没发生

发生什么：调用方按签名传 use_rerank=True，期望检索结果被重排序，实际返回顺序就是余弦相似度排序。

为什么：ScriptKnowledgeBase.query() 的签名接收 use_rerank，但方法体未消费该参数（检索实现是手动余弦相似度全量扫描）；真正的 rerank（BAAI/bge-reranker-large）在另一条 create_retriever_for_script 路径上，而那条路径只被未接线的 KnowledgeRouter 使用。

系统如何处理：无感知——参数被静默忽略，检索照常返回（质量略低但没有报错）。这是最难排查的一类故障：没有错误日志，没有异常路径。

如何恢复：短期不要指望该参数；要真 rerank 需走 retriever 路径。根治是二选一：真正接线，或删除哑参数并修正文档——“参数存在 ≠ 功能存在”，配置与文档必须以调用链为准。

故障七：180 秒没人理，系统"默认继续"

发生什么：交互模式下系统弹出人工决策请求；夜间批量运行时机器前没有人，180 秒后系统自动以"默认继续决策"放行。

为什么：HumanInputHandler(timeout_seconds=180) 的超时行为被设计为"使用默认继续决策"——不卡死是首要目标。

系统如何处理：超时放行。这在无人值守场景意味着"需要人工把关的片段被默认放行"。

如何恢复：无人值守场景建议改用 auto 模式（NEEDS_HUMAN 自动转 NEEDS_RETRY），或调大超时并接告警。另外系统有兜底保证"一定会终止"：修复/审计重试有上限，超限后转人工或失败退出，不会无限循环。

总结与建议

回到开头的问题：PenShot 的多智能体一致性体系，究竟哪些在跑？

真实在跑的（有调用链证据）：结构化提示词管线——global_metadata 的四段上下文注入（道具/服装/地点/连续性要求）+ 三档模板的强制约束文案；连续性守护的六项词表检查（角色/场景/动作/风格/时间/道具）与签名去重；质量审计的双审查器合并、扣分制评分、存在性判定与闸门映射（含故障五的 fail-closed 兜底）；RAG 的三条检索链路（解析入库、审计通过后回写、转换时检索增强，其中 rerank 参数为哑参数）。这套组合的实质，是把一致性从"祈祷模型发挥稳定"变成"结构化约束 + 规则检查 + 回流修复"的工程流程。

已实现但未接线的（有代码、无通电）：ContinuityAnchor 锚点体系与 CrossChunkValidator、StateTimeline 状态快照（take_snapshot 零调用）、知识路由 KnowledgeRouter（含真 rerank 路径）、修复回流的条件边（双重缺口，见故障一）、KnowledgeManager 工厂。这批代码的共同特征是"契约完整、调用方缺位"。

规划中的（零命中）：三视图等价物（当前只有 character_outfits 字段与模板文字约束）、渐进式生成、双向约束，以及第十一章的十五项补充机制。

如果只记三件工程经验：

  1. fail-open 与 fail-closed 按组件定位选择：可选增强（知识库）故障时降级让路，质量闸门（审计）故障时保守失败。PenShot 在这一点上方向正确，可以直接借鉴。

  2. "已实现"与"已接线"是两回事：本项目最贵的教训是"零件齐、没通电"（锚点、快照、回流边、哑参数）。评审时把"调用方是否存在、消费方是否读取"作为独立验收项；本文的考证方法（从定义出发检索调用点）可以直接复用。

  3. 词表级检查值得做，但要认清边界：它能低成本抓住"显性漂移"（服装/发型/配饰词切换、镜型重复、时间重叠），抓不住语义级变化。知道边界比堆机制重要——这也是本文对两章规划机制给出"落地成本分级"的原因。

如果你的团队要接手或二开这个项目，建议的动作顺序：先修断链（decide_after_continuity 读对字段、补 NEEDS_RETRY 图边）→ 让快照时间线通电（时间轴类机制的前置）→ 收敛审计三套口径为单一真源 → 处理哑参数（接线或删除）→ 再评估规划章候选机制。共同原则只有一条：先把已有资产用起来，再扩张版图。
