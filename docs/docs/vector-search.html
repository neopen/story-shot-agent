背景问题：向量检索为什么返回空结果

向量检索是 PenShot 剧本分镜智能体的核心能力之一，它使系统能够"记住"过去处理过的剧本片段，通过将文本内容转换为高维向量空间中的点，以语义相似度而非字面匹配找到与当前查询最接近的历史记录。在源码中，它的真实服务场景有三个：提示词转换节点通过 enhance_prompt 检索同剧本内的成功模板用于增强生成；连续性守护节点通过 search_similar_scene 检索相似场景充实问题的 historical_solutions；剧本解析结果通过 add_parsed_script 入库，形成场景与角色两类可检索文档。

这里先纠偏一个常见误解：质量审查阶段并不检索"历史问题及其修复方案"——审计失败时没有任何知识落点，而审计通过时它的动作反倒是写入（save_successful_prompt 把成功提示词沉淀为模板，供后续查询使用）。在这条链路上，知识是先沉淀、后被检索的。

然而在基于 LlamaIndex 构建知识库的过程中，我们遇到了一个非常典型的问题：向量检索始终返回 0 条结果，尽管向量存储文件与文档存储文件都存在且完整、手动计算的余弦相似度也完全正常。本文将完整复盘这一问题的根因、排查过程与解决方案，并顺带考证"手写余弦相似度替代检索器"背后的真实取舍，以及重排序在源码中的接线现状。

向量检索原理：从文本到向量

向量检索的核心思想是将非结构化的文本数据转换为结构化的数学向量。这个过程由嵌入模型完成——一个经过大规模语料训练的深度学习模型，能够将任意长度的文本映射为固定维度的浮点数向量。

    subgraph Input["输入层"]
        T1["剧本文本"]
        T2["提示词模板"]
        T3["角色描述"]
    end
    
    subgraph Embedding["嵌入模型"]
        E["Embedding Model\n(768/1024/1536维)"]
    end
    
    subgraph Vector["向量空间"]
        V1["v1: [0.12, -0.34, 0.56, ...]"]
        V2["v2: [0.45, -0.12, 0.78, ...]"]
        V3["v3: [-0.23, 0.67, -0.45, ...]"]
    end
    
    T1 --> E
    T2 --> E
    T3 --> E
    E --> V1
    E --> V2
    E --> V3

在这个高维向量空间中，语义相似的文本会被映射到彼此接近的位置。例如，"林然裹着旧羊毛毯"和"年轻女性裹着羊毛毯"这两个描述虽然文字不完全相同，但它们的向量在空间中是相近的。这种性质使得向量检索能够理解同义词、近义词和上下文语义。

关于 embedding 维度的经验：常见的嵌入维度为 768 / 1024 / 1536，维度越高编码信息越丰富，但索引体积与查询耗时也随之上升。PenShot 中嵌入模型由外部注入（构造参数），代码本身不绑定维度——仓库当前真实使用的嵌入维度为 1024（见后文存储结构一节的数据快照）。

余弦相似度计算

检索时，系统将用户的查询文本也转换为向量，然后计算查询向量与库中每个文档向量的余弦相似度。余弦相似度的取值范围在 -1 到 1 之间，值越接近 1 表示两个向量方向越一致，语义越相似。

flowchart TD
    Q["用户查询文本\n'林然的羊毛毯'"]
    E1["embed_query()"]
    QV["查询向量\n[q1, q2, q3, ...]"]
    
    subgraph Documents["文档库"]
        D1["文档1向量"]
        D2["文档2向量"]
        D3["文档N向量"]
    end
    
    subgraph Calculation["相似度计算"]
        C1["cos θ = (A·B) / (|A|×|B|)"]
    end
    
    subgraph Results["结果排序"]
        R1["1. 林然角色 (0.64)"]
        R2["2. 场景描述 (0.44)"]
        R3["3. 其他角色 (0.39)"]
    end
    
    Q --> E1 --> QV
    QV --> Calculation
    D1 --> Calculation
    D2 --> Calculation
    D3 --> Calculation
    Calculation --> Results

图中第二行的数字为示意——真实检索的分数区间可参考后文验证结果（调试实测集中在 0.49-0.64），低分并不意味着异常，只是语义空间中的常见分布。

余弦相似度的计算公式为：

similarity = cos(θ) = (A · B) / (||A|| × ||B||)

其中 A 和 B 分别代表查询向量和文档向量，分子是向量的点积，分母是向量模长的乘积。这个公式的本质是计算两个向量之间的夹角余弦值，不受向量长度的影响。

需要意识到一个关键点：向量检索衡量的是语义相似度，而非字面匹配。这正是它与关键词检索的分水岭——关键词检索依赖字符命中，对同义词束手无策；向量检索则天然兼容"意思接近但写法不同"的文本。但反过来，它的排序也未必等于用户真正关心的相关性——这正是交叉编码器重排序要解决的问题，不过它在 PenShot 中的真实接线状态，后文会专门考证。

检索流程架构

PenShot 的向量检索采用分层架构，但真实的链路与教科书画法有差距：写入侧完整，检索侧则并存两套实现——模板库走 LlamaIndex 检索器加后置过滤，剧本内容库走手写余弦全量扫描；重排序代码完整却停在未接线状态。下图已标注每个环节的真实形态。

flowchart TB
    subgraph DataLayer [数据层]
        D1[剧本解析结果<br/>场景/角色两类文档]
        D2[成功提示词模板<br/>质量审计通过后写入]
    end

    subgraph IndexLayer [索引层]
        I1[文本分块<br/>SentenceSplitter<br/>chunk_size 大于 1000 时切换窗口解析器]
        I2[向量化<br/>外部注入的嵌入模型]
        I3[SimpleVectorStore<br/>按 script_id 隔离 + 三文件持久化]
    end

    subgraph RetrievalLayer [检索层 - 两套实现并存]
        P1[模板库路径<br/>as_retriever + 后置过滤]
        P2[内容库路径<br/>手写余弦全量扫描 + Top-K]
    end

    subgraph Application [应用层 - 已接线]
        A1[提示词增强<br/>enhance_prompt]
        A2[连续性检查<br/>search_similar_scene]
    end

    subgraph IdleLayer [未接线]
        X1[重排序 BGE-reranker<br/>配置默认关闭]
    end

    D1 --> I1
    D2 --> I1
    I1 --> I2 --> I3
    I3 --> P1 --> A1
    I3 --> P2 --> A2
    X1 -.-> P1
    X1 -.-> P2

关于这张图，有三处与"标准 RAG 流水线"的差异需要点明：其一，检索层并存两套实现——PromptTemplateManager.search_similar 走 LlamaIndex 的 as_retriever 并附加分数与类型双重后置过滤，而剧本内容库的 query() 干脆绕开检索器，用 embed_query 加 np.dot 手写全量余弦；两者的分数口径与过滤语义并不一致。其二，应用层只有两个真实消费方：提示词增强与连续性检查——质量审查在链路上是"写入方"而非"检索方"。其三，重排序（BGE-reranker）的初始化代码完整（见后文重排序一节），但配置默认关闭，且引用它的 KnowledgeRouter 全仓库无人调用，因此在主链路上呈虚线状态。

代码与实现

初始化知识库

在使用向量检索功能之前，需要先初始化剧本知识库实例。知识库会为每个剧本创建独立的存储目录，实现数据隔离。

from penshot.neopen.knowledge.llamaIndex.llama_index_knowledge import ScriptKnowledgeBase
from penshot.neopen.shot_config import ShotConfig

# 初始化配置和嵌入模型（ShotConfig 继承 AIConfig，get_embed_by_config 是真实方法）
config = ShotConfig()
embeddings = config.get_embed_by_config()

# 创建知识库实例（指定剧本ID）
kb = ScriptKnowledgeBase(
    embeddings=embeddings,
    script_id="my_script_001"
)

初始化时有两个容易被误读的行为：其一，storage_dir 不传时默认为 data/embedding/script_kb，并在构造时用 os.makedirs 惰性建目录；其二，构造函数会调用 _load_all_scripts()，但它只加载各剧本的解析结果 JSON（遍历 parsed_results/ 目录），向量索引此时并不加载——真正的索引恢复发生在首次查询时由 _ensure_script_index 完成（这正是后文排坑叙事的主角）。此外 chunk_size（默认 512）与 chunk_overlap（默认 20）也是构造参数，直接决定入库时的分块形态。

添加剧本到知识库

知识库支持三种真实存在的添加入口：添加已解析的剧本对象、添加剧本文本、添加剧本文件。

# 方式一：添加已解析的剧本对象
kb.add_parsed_script(parsed_script, script_id="my_script_001")

# 方式二：直接添加剧本文本
kb.add_script_text(script_text, script_id="my_script_001")

# 方式三：添加剧本文件（按 UTF-8 文本读取，实际适用于 .txt/.md 等纯文本）
kb.add_script_file("path/to/script.txt", script_id="my_script_001")

这里需要对"方式三"做一处纠偏：该方法的真实实现是 open(file_path, 'r', encoding='utf-8') 读取全量文本再交给解析器——它只支持纯文本格式，并不具备 .pdf/.docx 的二进制解析能力。三种入口的后续流程完全一致：脚本解析为 ParsedScript → create_documents 生成文档（每个场景一个 type: scene 文档 + 每个角色一个 type: character 文档，并注入 script_id 元数据）→ 分块为节点 → 写入向量索引 → 通过 _save_storage 将向量、文档与索引元数据三件套落盘。

执行向量检索

query() 的真实实现是"手写余弦 + 全量扫描"：将查询文本用 embed_query 转成向量后，遍历向量存储中的每个向量逐个计算余弦相似度，排序后截断取 Top-K。方法签名保留的三个参数 search_type / use_rerank / rerank_model 在方法体中从未被读取——传了不会报错，也不会产生任何行为。

# 执行查询（三个检索行为参数实为哑参数，建议省略以免误读）
result = kb.query(
    query_text="林然的羊毛毯",
    script_id="my_script_001",
    similarity_top_k=5
)

# 处理结果：formatted_results 含 id/score/text/metadata/rank 五个字段
for item in result.get("results", []):
    print(f"相似度: {item['score']:.4f}")
    print(f"内容: {item['text'][:100]}...")
    print(f"类型: {item['metadata'].get('type')}")

查询结果按相似度从高到低排序，且不做任何阈值过滤——低于任何分数线的结果同样会占满 Top-K 名额（这与模板库路径的"后置过滤"完全不同，使用时需要自行判断分数）。若未指定且未设置任何剧本 ID，query() 会记录 debug 日志并返回带 error 字段的空结果字典，不会跨剧本检索。

结构化查询

除了语义检索，知识库还有两个不经向量链路的精确查询入口：query_scene 与 query_character。它们直接在构造时加载的 parsed_results 内存字典中遍历比对——按 id/number 找场景、按 name 找角色，命中即返回原始字典，既不计算相似度，也不做模糊匹配。

# 按场景ID查询（先匹配 scene["id"]，再兼容字符串化的 scene["number"]）
scene = kb.query_scene("scene_001", script_id="my_script_001")

# 按角色名查询（精确匹配 character["name"]）
character = kb.query_character("林然", script_id="my_script_001")

这两个方法的实际查询对象是磁盘 parsed_results/ 目录 JSON 的内存副本，而不是向量库——把它们与语义检索混为一谈，是理解该模块时最常见的偏差之一。

应用场景

向量检索在实际工作流中主要服务于两个已接线场景（提示词增强与连续性检查），以及一个容易被误解为"检索"的写入场景（质量审计）。逐一来看。

提示词生成增强

提示词转换节点生成原始提示词后，会调用 enhance_prompt(fragment.prompt, enhancement_mode="append")，走模板库路径：get_best_match（实为 search_similar 传 top_k=1）→ LlamaIndex as_retriever 相似度检索 → 分数与类型双重后置过滤（不达 min_similarity_score 或类型不是 prompt_template 的候选直接丢弃）。命中后按 append 模式拼接，未命中则原样返回。

flowchart LR
    F[转换节点生成<br/>原始提示词] --> E[enhance_prompt<br/>append 模式]
    E --> S[get_best_match<br/>search_similar top_k=1]
    S --> G{分数与类型<br/>后置过滤}
    G -->|命中| P[原始提示词在前<br/>追加参考优秀模板块]
    G -->|未命中或 none 模式| O[原样返回]

一个容易被"融合"二字带偏的细节：append 模式的真实拼接只是一个 f-string——原始提示词 + "参考优秀模板:\n" + 模板文本；replace 与 hybrid 模式同样只是模板在前的另一种拼接（_merge_prompts），所谓"融合"并不存在额外算法，真正消化参考模板的是下游 LLM 自己。

质量审计的知识落点：写入而非检索

原稿此处描述为"质量审查检索历史问题及修复方案，自动应用修复策略"——这在源码中不存在。真实的质量审计节点是模板库的写入方：当审计状态为 PASSED 且存在修饰指令时，对每个片段调用 save_successful_prompt，把通过的提示词连同质量分、场景、风格等元数据沉淀进模板索引；审计失败时没有任何知识落点。

flowchart TD
    A[质量审计通过 PASSED] --> B[save_successful_prompt<br/>逐片段写入]
    B --> C[add_template<br/>2000 字符截断 + hash/全文去重]
    C --> D[模板向量索引<br/>同剧本隔离]
    C --> E[templates_cache.json<br/>磁盘缓存]
    C --> F[长期记忆<br/>successful_prompt_patterns]

    G[质量审计失败] -.->|当前实现无沉淀| H[无知识落点]

这个方向值得强调：在这条链路上知识是先沉淀、后被检索——审计的成功样本成为未来 enhance_prompt 的参考；而审计失败留下的只有错误记录，不会进入任何知识库。失败案例的知识化，是当前实现尚未覆盖的边界。

连续性一致性检查

连续性守护节点发现片段间的不一致后，会对每个问题执行一次检索：以问题描述为查询文本，调用 search_similar_scene(issue_desc, script_id=..., top_k=2)，在剧本内容索引（场景/角色文档）中找出相似的历史场景，写回问题对象的 historical_solutions 属性，为后续修复生成提供素材。

flowchart TB
    subgraph Issues [连续性守护发现的问题]
        I1[问题1: 服装不一致<br/>description 作查询文本]
        I2[问题2: 场景光线跳跃]
    end

    subgraph Query [逐条检索]
        Q[search_similar_scene<br/>top_k=2]
    end

    subgraph Store [剧本内容索引]
        S1[场景文档<br/>type: scene]
        S2[角色文档<br/>type: character]
    end

    I1 --> Q
    I2 --> Q
    Q --> Store
    Store -->|命中结果| H[写回 issue.historical_solutions<br/>供修复生成参考]

这里需要澄清两个常见误解：其一，检索的是剧本内容索引（入库的场景/角色文档），不是什么"角色状态向量库"——一致的判定由守护节点自身的检查逻辑完成，向量检索只负责为修复补素材；其二，search_similar_scene 内部调用 script_kb.query(..., use_rerank=True)，而 query() 的 use_rerank 是哑参数（拆解见前文），所以这条链路同样没有真实的重排序行为。此外，检索结果只有在问题对象定义了 historical_solutions 属性时才会被真正挂载（源码中有 hasattr 守卫），否则检索白做但不报错。

PenShot 的向量数据按剧本隔离，每个剧本拥有独立目录；同一 storage_dir 下，剧本知识库与提示词模板库分立两个子目录。以下结构直接对照仓库 data/embedding/ 下的真实运行目录绘制：

核心逻辑解释与重排序

基础向量检索的排序只依赖整体语义接近度，可能把"语义相关但实际不合适"的结果排在前面。交叉编码器重排序（BGE-reranker 是典型代表）能把这类误差压下去——但 PenShot 的现状需要如实说明：重排序的初始化代码完整存在，但配置默认关闭，且唯一引用它的路由组件未接线，在主链路上并未真实生效。先看它设计中的工作形态：

flowchart LR
    Q[用户查询] --> V[as_retriever 初筛<br/>similarity_top_k 条候选]
    V --> R[SentenceTransformerRerank<br/>交叉编码器逐对打分]
    R --> F[最终结果<br/>top_n 取 3 与 k 的最小值]

向量检索（双编码器）和重排序（交叉编码器）的区别在于：

  • 双编码器将查询和文档分别编码，速度快但精度相对较低；
  • 交叉编码器将查询和文档拼接后一起编码，精度高但速度慢。

两者结合可以兼顾效率和精度。

把这段链路拉回源码，可以完整看到它的"接线实况"：其一，装配逻辑位于 create_retriever_for_script——支持 similarity/mmr 两种模式（MMR 的 mmr_threshold=0.6），重排序模型选择链为"本地路径（配置默认 data/models）→ 配置名 → 兜底 BAAI/bge-reranker-large"；仓库 data/models/ 下确实存放着下载好的 bge-reranker-large，说明这套能力曾被真实部署过。其二，触发条件是 use_rerank or retriever_config.rerank_enabled，而 RetrieverConfig.rerank_enabled 的默认值是 False——不显式开启就不会加载重排序模型。其三，重排序生效时会用 index.as_retriever(similarity_top_k=..., node_postprocessors=[rerank]) 重建检索器，重建调用不携带 vector_store_query_mode——因此 mmr 模式会被覆盖，两者无法叠加使用（一个静默的配置陷阱）。其四，也是决定性的：这三个检索器方法只被 llama_index_router.py 的 KnowledgeRouter 引用，而 KnowledgeRouter 全仓库没有生产调用方——重排序因此在"已实现未接线"之列。

问题排查与解决：返回 0 条结果的完整复盘

问题现象

项目早期，基于 LlamaIndex 搭建的剧本知识库出现了一个棘手现象：检索始终返回 0 条结果，尽管：

  • 向量存储文件存在且完整（当时的调试快照为 3 个向量，768/1024 维）

  • 文档存储文件存在且完整（同一快照下 3 个文档节点）

  • 手动计算的余弦相似度正常（0.44-0.64），排序也符合直觉

根本原因

排查后确认，这不是单点故障，而是三个问题叠加的结果。其中第一条需要先纠正一个流传甚广的归因：

  • 原因一（纠偏）：问题不在"检索器默认阈值"

    很多资料声称"index.as_retriever() 默认内置约 0.7 的相似度阈值"——这与 LlamaIndex 的实际行为不符：默认的向量检索器不做任何分数过滤，similarity_top_k 只控制返回数量，只有显式配置 similarity_cutoff 之类的参数才会出现阈值行为。

    真正让 retrieve() 返回空的原因更隐蔽：从 vector_store.json 单独恢复的索引没有文本。向量存储里只有节点 id 与向量，节点文本与元数据全部在 docstore 中；当索引的存储上下文不完整时，检索器找不到可返回的文本节点，表现就是"有向量、有文件、却返回 0 条"。

    # 问题代码：从向量存储恢复的索引缺少 docstore 文本
retriever = index.as_retriever(similarity_top_k=5)
nodes = retriever.retrieve(query)  # 返回 0 条结果

    那"0.7 阈值"的传说从何而来？在本项目里它确实存在——但位置是应用层：PromptTemplateManager.search_similar 的后置过滤，min_similarity_score 类默认为 0.5、WorkflowNodes 注入 0.7。把应用层的阈值设计误记成框架默认行为，正是这次排查中绕过的最大弯路。

  • 原因二：vector_store.query() 查询模式不匹配

    直接调用 vector_store.query(VectorStoreQuery(...)) 时，返回的节点仍需依赖 text_id_to_ref_doc_id 映射回查 docstore 才能取出文本；查询模式（VectorStoreQueryMode）与写入时的配置不一致时，还可能得到空候选。一句话：这条路能走通，但需要把存储上下文配齐，收益不如后文的方案二。

    # 问题代码
vector_query = VectorStoreQuery(query_embedding=query_embedding, similarity_top_k=5)
query_result = vector_store.query(vector_query)  # nodes 为空

  • 原因三：索引加载方式错误

    使用 VectorStoreIndex.from_vector_store() 加载已有存储时，该方法无法恢复已持久化的存储上下文（文档文本不在向量存储里），报错堪称直白：

    # 问题代码
index = VectorStoreIndex.from_vector_store(vector_store, embed_model=embeddings)
# ValueError: Cannot initialize from a vector store that does not store text.

    源码中至今保留着这次修复的注释——_ensure_script_index 里的"关键修复：使用 VectorStoreIndex 构造函数，而不是 from_vector_store"，就是这段排查留下的路标。

解决方案

  • 方案一：正确加载索引（修复加载错误）

    # 正确方式：从目录加载完整的存储上下文
storage_context = StorageContext.from_defaults(persist_dir=script_dir)
index = VectorStoreIndex(
    nodes=[],
    storage_context=storage_context,
    embed_model=embeddings
)

    这正是 _ensure_script_index 采用的修复（源码注释"关键修复：使用 VectorStoreIndex 构造函数，而不是 from_vector_store"即指此处）：nodes=[] 表示不传入新文档、完全从 storage_context 恢复；存储上下文由 persist_dir 一次性加载 vector / docstore / index 三件套，文本与向量同时就位。

  • 方案二：手动计算余弦相似度（本项目最终选择）

    import numpy as np

query_embedding = embeddings.embed_query(query_text)
results = []
for doc_id, embedding in vector_store._data.embedding_dict.items():
    dot = np.dot(query_embedding, embedding)
    norm_q = np.linalg.norm(query_embedding)
    norm_d = np.linalg.norm(embedding)
    similarity = dot / (norm_q * norm_d) if norm_q > 0 and norm_d > 0 else 0

    doc = storage_context.docstore.get_document(doc_id)
    results.append({
        "doc_id": doc_id,
        "similarity": similarity,
        "text": doc.text if hasattr(doc, 'text') else str(doc),
        "metadata": doc.metadata if hasattr(doc, 'metadata') else {}
    })

results.sort(key=lambda x: x["similarity"], reverse=True)
return results[:top_k]

    注意它和方案一的关系：手动余弦并不是"绕开存储上下文"——它同样从 storage_context 取 docstore 与向量，只是把检索这一步从框架管线换成了 20 行显式计算。直接收益是分数完全透明：每个候选的相似度可见、可日志、可单测，过滤策略完全由调用方掌握，也不再依赖检索器对存储完整性的隐式假设。这就是本项目最终选择手写余弦的真实原因。

  • 方案三：真实源码中的完整实现

    上述思路落地后的成品即 ScriptKnowledgeBase.query()。与示意代码相比，真实实现（llama_index_knowledge.py，精简摘录如下）多了几层防护：

    def query(self, query_text: str, script_id: str, similarity_top_k: int = None):
    target_id = script_id or self._current_script_id
    if not target_id:
        return {"query": query_text, "results": [], "total_results": 0, "error": "未指定剧本ID"}

    self._ensure_script_index(target_id)
    index = self._indices.get(target_id)
    if not index:
        return {"query": query_text, "results": [], "total_results": 0, "error": "索引未创建"}

    if similarity_top_k is None:
        similarity_top_k = 5
    vector_store = self._vector_stores.get(target_id)
    if not vector_store or not hasattr(vector_store, '_data'):
        return {"query": query_text, "results": [], "total_results": 0, "error": "向量存储未就绪"}

    query_embedding = self.embeddings.embed_query(query_text)
    import numpy as np
    results = []
    for doc_id, embedding in vector_store._data.embedding_dict.items():
        dot = np.dot(query_embedding, embedding)
        norm_q = np.linalg.norm(query_embedding)
        norm_d = np.linalg.norm(embedding)
        similarity = dot / (norm_q * norm_d) if norm_q > 0 and norm_d > 0 else 0

        doc = None
        storage_context = self._storage_contexts.get(target_id)
        if storage_context and hasattr(storage_context, 'docstore'):
            doc = storage_context.docstore.get_document(doc_id)

        text = ""
        metadata = {}
        if doc:
            text = doc.text if hasattr(doc, 'text') else str(doc)
            metadata = doc.metadata if hasattr(doc, 'metadata') else {}

        results.append({
            "doc_id": doc_id, "similarity": similarity,
            "text": text, "metadata": metadata
        })

    results.sort(key=lambda x: x["similarity"], reverse=True)
    results = results[:similarity_top_k]
    # 其余部分为格式化输出：每项补齐 id / score / text / metadata / rank 五个字段

    这些防护分别是：剧本 ID 缺省与索引未创建时的早退（返回带 error 字段的结构化结果而不是抛异常）、向量存储尚未就绪时的可读错误、零向量除法保护（模长为 0 时返回 0 而非 NaN）、以及 docstore 缺失时的文本空串兜底。整个函数体还被 try/except 包裹——查询失败不会拖垮上游工作流，只会留下错误信息。

关键经验总结

问题 错误做法 正确做法
索引加载 VectorStoreIndex.from_vector_store() StorageContext.from_defaults() + VectorStoreIndex()

验证结果

修复后，查询测试正常返回结果（以下数字为项目调试期实测记录，非通用基准）：

查询词 最佳匹配 相似度
“林然” 角色"林然" 0.6363
“羊毛毯” 角色"林然" 0.4883
“场景” 场景文档 0.5088

结果本身值得玩味：三条查询的最佳匹配都落在 0.49-0.64 区间。这类"中低分"结果正是阈值设计的经典困境——模板库路径用 min_similarity_score=0.7 做后置过滤（宁缺毋滥），而剧本内容库的手写余弦不做任何过滤（召回优先）。同一个系统里两种分数口径与过滤策略并存，是理解 PenShot 检索行为时必须记住的对照。

注意事项与排坑提示

  • 嵌入模型一致性：创建索引时使用的嵌入模型必须与查询时使用的模型完全相同，否则向量空间不一致，相似度计算将失去意义。需要特别强调：PenShot 不会自动校验这一点——换模型后查询既不报错也不警告，只会静默给出失真的分数或空结果。手动管理存储文件时，换模型应立即重建索引。

  • 相似度阈值归属：LlamaIndex 检索器默认没有分数阈值；真正带阈值的是应用层的后置过滤（模板库路径的 min_similarity_score）。在手写余弦的实现里，过滤与否完全由调用方决定：

    # 手写余弦的返回值不过滤，调用方可按需自行筛选
results = [r for r in result["results"] if r["score"] > 0.3]  # 按业务需要调整

  • 存储文件完整性：一次完整的持久化产出 default__vector_store.json（向量）、docstore.json（文本与元数据）、index_store.json（索引元数据）三件套，缺任一个都可能导致索引恢复不完整。使用 StorageContext.from_defaults(persist_dir=...) 可以整体恢复；若向量文件损坏，_recreate_vector_store 会自动备份为 *_corrupted_{时间戳} 后重建。

  • 内存与性能考虑：手写余弦需要把全部向量载入内存并逐个计算——以真实数据为例，单剧本 12 条 1024 维向量是小菜一碟，但规模上到数万文档时 O(N) 扫描会成为瓶颈。按剧本隔离存储天然限制了单次加载的数据量；若未来需要更大规模，项目的长期记忆层已经给出了迁移样板（Chroma 向量库，见 RAG 知识库一文）。

  • 多剧本隔离：始终在查询时指定 script_id 参数——但与你可能预期的相反，忘记指定不会检索到其他剧本的内容：query() 会记录 debug 日志并返回带 error 字段的空结果，search_similar 同样静默返回空列表。这个"静默降级"设计保证了隔离性，代价是调用方不检查 error 字段时就难以察觉。

三条高频排坑提示

  1. 检索为空的头号原因：不是"检索器默认阈值"，而是索引恢复不完整（docstore 文本缺失）或 vector_store._data 未就绪。先确认存储上下文三件套是否齐全，再打印手写余弦的实际分数排查。

  2. 索引加载报 ValueError: Cannot initialize from a vector store that does not store text：这是 from_vector_store 的典型报错。改用 StorageContext.from_defaults(persist_dir=...) 从目录整体加载，并以 VectorStoreIndex(nodes=[], storage_context=...) 构造。

  3. 嵌入模型不一致导致结果失真：写入索引与查询务必使用同一嵌入模型与维度；系统不会报错，只会静默给出错误分数——换模型应立即重建索引。

总结

向量检索是 PenShot 记忆系统与知识增强能力的地基。按"三口径"收束全文：已接线的是两条真实检索路径——模板库路径（search_similar：as_retriever + 分数/类型双重后置过滤）与剧本内容库路径（query()：手写余弦全量扫描，分数透明但不过滤）；它们分别支撑提示词增强与连续性检查两个下游场景，写入侧由质量审计的成功模板沉淀与剧本解析入库构成完整闭环。已实现未接线的是重排序（BGE-reranker 默认关闭、检索器方法无生产调用方）与 MMR 检索器。需要记住的边界同样有三个：审计失败的样本没有任何知识落点；漏传 script_id 与嵌入模型失配都只会静默降级、不报错；手写余弦的 O(N) 扫描在小剧本下无感，但规模上去后需要迁移专业向量库。

理解"文本→向量→余弦排序"这条链路只是起点；知道自己系统里哪些环节真正接线、哪些还在图纸上，才是排坑时最可靠的地图。
