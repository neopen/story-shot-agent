核心设计

检查点与恢复

状态如何落盘、任务如何恢复，以及当前版本的能力边界。

更新 2026-11-14 约 15 分钟阅读

PenShot 用 LangGraph 检查点持久化工作流状态：每个 super-step 结束后把完整状态快照写入 saver，理论上可凭同一 thread_id 从最近快照恢复。当前版本只接通写入侧，断点续传尚未生效。

事实边界：本页描述 WorkflowCheckpointer（workflow_checkpointer.py）与 MultiAgentPipeline 的实际接线，对应 v0.4.4 源码。检查点文件只用于状态回溯，不能替代业务结果存档。

能力边界

能力 当前状态 说明
状态写入 已实现 saver 已接入 compile(checkpointer=saver)，逐 super-step 落盘
状态查询 无入口 没有 get_state 调用；只能离线打开 .db 复盘
断点续传 未实现 执行时 thread_id 不稳定，历史快照无法命中
任务迁移 未实现 单机 SQLite，无分布式存储后端
旧检查点清理 未接线 cleanup_old_checkpoints() 无调用方
连接释放 部分失效 close() 为异步方法，__exit__ 调用时未 await

写入机制

LangGraph 的 BaseCheckpointSaver 定义保存与读取接口。工作流在每个 super-step 边界写入一条快照：同步执行走 put / get_tuple，异步执行走 aput / aget_tuple。快照保存的是过程态而非结果态，因此可支撑回溯与续跑。

sequenceDiagram
    participant User as 用户
    participant Workflow as LangGraph工作流
    participant Saver as CheckpointSaver
    participant Storage as 存储后端
    
    User->>Workflow: 启动任务 (thread_id)
    Workflow->>Saver: 检查是否存在历史检查点
    Saver->>Storage: 查询 thread_id 对应的状态
    
    alt 存在检查点
        Storage-->>Saver: 返回保存的状态
        Saver-->>Workflow: 恢复状态
        Workflow-->>User: 从断点继续执行
    else 不存在检查点
        Workflow->>Workflow: 从头执行
    end
    
    loop 每个节点执行后
        Workflow->>Saver: 保存状态快照
        Saver->>Storage: 持久化存储
    end
    
    Workflow-->>User: 任务完成

上图是 LangGraph 的完整读写路径。PenShot 只执行其中的写入循环；“查询历史 → 恢复状态”这一段在代码中没有调用入口。

检查点记录以 (thread_id, checkpoint_ns, checkpoint_id) 为联合主键。checkpoint_ns 是子图命名空间，顶层图默认为空字符串；checkpoint_id 按执行顺序递增。同一 thread_id 对应一条完整时间线，更换 thread_id 即产生新时间线。

存储模式与降级

模式 后端 持久性 适用场景
memory MemorySaver（进程内存） 进程退出即丢失 本地开发、单元测试
sqlite SqliteSaver（单文件） 跨进程保留 单机部署、顺序任务

auto 模式（默认）通过“在目标目录创建 .write_test 文件再删除”判断可写性，可写则选 SQLite，否则落回内存。降级共有两条链：导入期缺少 langgraph-checkpoint-sqlite，或运行期目录不可写。两条链都只写 warning 日志，任务照常成功。

SQLite 连接建立后执行 PRAGMA journal_mode=WAL 与 PRAGMA synchronous=NORMAL。WAL 改善单文件读写并发，但不改变 SqliteSaver 的定位：轻量、同步、面向小规模场景，不以多线程扩展为目标。

文件与表结构

每个任务一个数据库文件，目录按剧本隔离；隔离依赖路径拼装，而不是数据库字段。

data/checkpoints/
├── script_001/
│   ├── task_001.db
│   └── task_002.db
└── script_002/
    └── task_003.db

SqliteSaver.setup() 只建两张表：checkpoints 存状态快照，writes 存通道中间数据（pending writes）。状态与元数据序列化为 BLOB，表中没有 script_id / task_id 等业务列。

CREATE TABLE IF NOT EXISTS checkpoints (
    thread_id TEXT NOT NULL,
    checkpoint_ns TEXT NOT NULL DEFAULT '',
    checkpoint_id TEXT NOT NULL,
    parent_checkpoint_id TEXT,
    type TEXT,
    checkpoint BLOB,
    metadata BLOB,
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id)
);
CREATE TABLE IF NOT EXISTS writes (
    thread_id TEXT NOT NULL,
    checkpoint_ns TEXT NOT NULL DEFAULT '',
    checkpoint_id TEXT NOT NULL,
    task_id TEXT NOT NULL,
    idx INTEGER NOT NULL,
    channel TEXT NOT NULL,
    type TEXT,
    value BLOB,
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id, task_id, idx)
);

快照内容与观测

一条 checkpoints 记录包含执行后的通道值、父检查点 ID、序列化类型与元数据；writes 保存尚未合并进通道的 pending writes，用于重放同一 super-step 内已完成的节点输出。两者都由 LangGraph 序列化，业务代码不应直接解析 BLOB。

观测以数据库为准。执行 SELECT thread_id, COUNT(*) FROM checkpoints GROUP BY thread_id; 可判断同一任务是否产生多条时间线；执行 SELECT COUNT(*) FROM checkpoints; 可确认写入是否真的发生。若 thread_id 种类随运行次数增长，说明标识不稳定，续传不可能命中。

检查点不保存 LLM 请求与响应原文。需要复现提示词时，应结合业务日志、模板版本与输入剧本；磁盘占用随任务数与 super-step 数线性增长，长剧本单任务会产生较多快照。

WorkflowCheckpointer

门面类封装模式选择、存储路径与连接管理，对外提供 saver 和运行配置。

        subgraph StorageModes["支持的存储模式"]
            memory[MemorySaver<br/>开发测试/降级兜底]
            sqlite[SqliteSaver<br/>单机持久化]
        end
        
        PublicAPI --> Internal
        Internal --> StorageModes

接口 行为
get_saver() 返回 SqliteSaver 或 MemorySaver 实例，用于 graph.compile()
get_config() 返回稳定配置 {"configurable": {"thread_id": "{script_id}_{task_id}"}}
get_stats() 返回模式、路径与文件大小等信息
cleanup_old_checkpoints(keep_count=10) 按修改时间保留最近 N 个 task_*.db，跳过当前实例文件
close() async def，关闭 SQLite 连接并置空 saver

CheckpointerFactory 以 {script_id}_{task_id} 为键、threading.RLock 加锁复用实例，避免重复创建 SQLite 连接。工厂的 close_all() 与实例的 close() 都没有调用方；__exit__ 直接调用异步 close() 只会创建协程，连接不会真正关闭，并留下 coroutine 'close' was never awaited 警告。

调用链与 thread_id 缺口

# workflow_pipeline.py —— 初始化时创建管理器
self.checkpointer = create_checkpointer(self.script_id, self.task_id, config)

# workflow_pipeline.py —— 构建图时把 saver 交给 LangGraph
saver = self.checkpointer.get_saver()
compiled_graph = orchestrator.graph.compile(checkpointer=saver)

# workflow_output_fixer.py —— 执行时传入 thread_id 配置
final_state = workflow.invoke(
    initial_state,
    config={"configurable": {"thread_id": f"process_{id(initial_state)}"}}
)

前两处接线正确。第三处没有使用 get_config() 的稳定标识，而是使用 f"process_{id(initial_state)}"。id() 是 CPython 对象的内存地址，同一任务每次运行都会得到新值，因此每次执行都写入一条全新时间线。

环节 设计意图 当前实现
写入 每个 super-step 落盘快照 真实执行
标识 同一任务固定 thread_id 每次运行使用对象内存地址
读取 按 thread_id 查历史并恢复 无读取入口
清理 定期删除旧检查点 方法存在，无调用方
释放 任务结束关闭连接 无调用方，且异步关闭失效

    subgraph WritePath["已接线的写入路径"]
        W1[任务执行] --> W2[compile 时注入 saver]
        W2 --> W3[每个 super-step 写入快照]
        W3 --> W4[(任务 .db 文件)]
    end

    subgraph ReadPath["未接线的恢复路径"]
        R1[任务启动] -.->|无 get_state 调用| R2[查询历史检查点]
        R2 -.-> R3[复用 thread_id 续跑]
        R3 -.-> R4[跳过已完成阶段]
    end

    W4 -.->|thread_id 每次变化| X[历史时间线不可命中]
    X -.-> R2

结果是一本“只进不出”的账：数据真实、完整、可离线回溯，但任务失败后仍从头执行，已落盘的快照不会被读取。检查点当前的价值集中在事后分析，而不是恢复执行。

异步执行边界

ainvoke 会调用 saver 的 aput / aget_tuple / alist，同步版 SqliteSaver 对这三个方法一律抛出 NotImplementedError。项目因此把执行链路整体切回同步 invoke，并在回退路径中保留了被注释的 await workflow.ainvoke(...)。

flowchart LR
    direction LR %% 强制主画布从左到右
    subgraph SyncSaver["同步 Saver 问题"]
        direction LR %% 强制子图1内部从左到右
        A[async def run] -->|ainvoke| W[异步工作流]
        W -->|调用| S[SqliteSaver]
        S -.->|不支持异步方法| E[NotImplementedError]
    end

    subgraph AsyncSaver["异步 Saver 方案"]
        direction LR %% 强制子图2内部从左到右
        A2[async def run] -->|ainvoke| W2[异步工作流]
        W2 -->|调用| AS[AsyncSqliteSaver]
        AS -->|await| DB2[(SQLite)]
    end
方案 依赖 代价
invoke + SqliteSaver langgraph-checkpoint-sqlite 调用方线程内顺序执行，放弃协程调度
ainvoke + AsyncSqliteSaver 额外安装 aiosqlite 异步链路全改造，连接需用 async with 管理

两条链路不能交叉：异步工作流配同步 saver 会在首次写入时直接失败；同步工作流配异步 saver 则拿不到协程结果。选择哪条取决于调用方是否已经在事件循环内。

配置项

字段 默认值 是否生效
checkpoint_mode auto 是
checkpoint_dir data/checkpoints（取自 settings.get_data_paths()） 是
postgres_uri None 否，无消费方
max_checkpoints_per_script 10 否，无消费方
checkpoint_max_connections 5 否，无消费方
checkpoint_idle_timeout 600 否，无消费方

checkpoint_mode 的注释仍列出 postgres，但枚举只有 MEMORY 与 SQLITE。传入其他值时 _determine_mode 会落入 auto 分支，按 SQLite 逻辑处理，不会报错。

常见失效

现象 原因 处理
重启后没有新 .db 依赖缺失或目录不可写，静默降级到内存 检查启动 warning；生产环境显式设置 checkpoint_mode=sqlite
任务失败后从头重跑 thread_id 使用对象地址 改用 checkpointer.get_config()，并补续跑入口
目录持续增长 清理方法未接线，时间线只增不减 任务收尾显式调用清理；多进程下先确认无活跃写入
ainvoke 抛出 NotImplementedError 同步 SqliteSaver 不支持异步方法 改用 AsyncSqliteSaver 并安装 aiosqlite，不要混搭
coroutine was never awaited 同步 __exit__ 调用异步 close() 改为同步 close()，或在关闭钩子中 await close()

最小修复路径

  1. 把执行路径的 config 换成 self.checkpointer.get_config()，让同一任务跨运行命中同一时间线。
  2. 任务启动时以 None 为输入、复用同一 thread_id 续跑，把“从头执行”改为“从最近快照继续”。
  3. 把 cleanup_old_checkpoints() 接入任务收尾，把 CheckpointerFactory.close_all() 接入服务关闭钩子，并修正 close() 的异步调用。

更远的方向是切换 AsyncSqliteSaver 以支持异步链路，或引入 Postgres / Redis 后端实现多机共享；这些属于后续版本范围，不是当前能力。

上线核对

  • 启动日志中不存在“依赖未安装”或“SQLite 不可用”的 warning。
  • data/checkpoints 存在且可写；容器部署时挂载持久卷，避免随镜像重建丢失。
  • 任务结束后 .db 可打开，checkpoints 记录数大于 0。
  • 显式设置 checkpoint_mode，避免 auto 在只读环境中静默退化为内存模式。

修复顺序有依赖：先稳定标识，续跑才有意义；清理与释放可以独立接入，但应在确认无并发任务后执行。在续跑入口补齐之前，应把检查点视为审计日志，而不是恢复机制。
