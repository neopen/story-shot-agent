在基于 LangGraph 的多智能体工作流系统里，检查点（Checkpoint）往往被当作"配好就万事大吉"的基础设施：compile(checkpointer=saver) 一挂，状态似乎就会自动落盘。本文对 PenShot 的检查点实现做一次完整的源码考证：双模式设计与自动降级链、SQLite 中真实的库表结构、一个留下了注释痕迹的 ainvoke 排坑现场；以及一个更值得正视的缺口——检查点写入已经通电，但用于续传的稳定 thread_id 从未真正被使用。

  • 哪些内容属于当前版本的实现，哪些内容需要以仓库最新代码重新核对。

一、背景问题：长剧本处理为什么离不开检查点

工作流检查点（Checkpoint）的核心作用是在工作流执行的特定时刻保存完整的运行状态，以便在系统故障、任务中断或需要回溯时能够精确恢复。对于 PenShot 这样的剧本分镜系统，一个任务通常需要处理数万字的剧本，经过剧本解析、镜头拆分、视频分割、提示词转换、质量审查等多个阶段，整个流程可能耗时数十秒甚至数分钟。

    direction LR %% 强制全局从左到右
    subgraph Without["无检查点的工作流"]
        direction LR %% 强制子图内部从左到右
        A1[开始] --> B1[阶段1] --> C1[阶段2] --> D1[阶段3] --> E1[阶段4] --> F1[完成]

在没有检查点机制的情况下，任何阶段的失败都意味着整个任务需要从头执行，这对于长剧本处理场景是不可接受的。检查点机制的价值体现在三个维度：

  • 断点续传：当工作流执行到某个阶段时发生异常，可以从最近保存的检查点恢复，避免重复计算。这对于依赖外部 LLM API 的场景尤为重要，因为网络波动或 API 限流是常见问题。

  • 状态调试：开发人员可以保存工作流在不同阶段的快照，用于问题复现和调试。当某个片段生成质量不佳时，可以回溯到该片段生成前的状态进行分析。

  • 任务迁移：在分布式部署场景下，检查点理论上允许任务在不同节点间迁移，实现负载均衡和故障转移。不过 PenShot 当前采用的是单机 SQLite 方案（见第四章），这一条属于能力方向而非现状描述。

补充原理：检查点的本质是"状态可重放"。LangGraph 会在每个 super-step（一或数个节点构成的执行步）边界，把完整状态快照（state snapshot）写入 saver，配合稳定的 thread_id 即可实现"从最近的检查点继续执行"，而无需重跑此前已稳定的阶段。这也意味着检查点保存的是过程态而非仅结果态，这正是它能支撑断点续传与回溯调试的根本原因。注意其中两个前提——快照要真的写得进去，续传要能用同一个 thread_id 读得出来。本文后半程的考证将表明：PenShot 做到了前者，卡在了后者。

状态快照机制

LangGraph 的检查点核心是 BaseCheckpointSaver 抽象类，它定义了保存与恢复工作流状态的标准接口。工作流在每个 super-step 结束后，LangGraph 会自动调用 saver 写入检查点：同步 API（invoke）走 put / get_tuple，异步 API（ainvoke）走对应的 aput / aget_tuple——这一对同步/异步接口的分野，正是第三章"排坑现场"的直接起因。

sequenceDiagram
    participant User as 用户
    participant Workflow as LangGraph工作流
    participant Saver as CheckpointSaver
    participant Storage as 存储后端
    
    User->>Workflow: 启动任务 (thread_id)
    Workflow->>Saver: 检查是否存在历史检查点
    Saver->>Storage: 查询 thread_id 对应的状态
    
    alt 存在检查点
        Storage-->>Saver: 返回保存的状态
        Saver-->>Workflow: 恢复状态
        Workflow-->>User: 从断点继续执行
    else 不存在检查点
        Workflow->>Workflow: 从头执行
    end
    
    loop 每个节点执行后
        Workflow->>Saver: 保存状态快照
        Saver->>Storage: 持久化存储
    end
    
    Workflow-->>User: 任务完成

Thread ID 隔离机制

前面这张时序图描述的是 LangGraph 的完整读写路径：查历史、恢复、逐节点保存。PenShot 当前只走了其中的"写"一半——"查历史检查点→恢复状态"这段流程在代码中没有任何调用入口，第五章会展开考证。

LangGraph 使用 thread_id 作为不同任务状态的隔离标识：每个独立任务拥有自己的 thread_id，检查点按此维度隔离，不同任务的状态互不覆盖。SqliteSaver 的类文档同时给出了一个重要的边界警告——它面向轻量、同步的使用场景（demos and small projects），并不以多线程扩展为目标；这一点在第四章结合 PenShot 的连接配置再展开。

补充原理：thread_id 相当于检查点记录的主键第一维。LangGraph 的检查点记录以 (thread_id, checkpoint_ns, checkpoint_id) 作为联合主键写库：checkpoint_ns 是子图命名空间（顶层图默认为空字符串），checkpoint_id 按执行顺序递增。因此同一 thread_id 下天然保留一份完整的历史轨迹，查询时可精确回放到任意节点——而这也解释了下文的关键缺口：换了 thread_id，就等于换了一条全新的时间线。

SQLite 落盘后的真实表结构

很多介绍文章会把检查点表画成"业务字段表"（比如带 script_id / task_id 列），但真实数据库中长什么样，应以 langgraph-checkpoint-sqlite 的 SqliteSaver.setup() 为准——它只会建两张表：

CREATE TABLE IF NOT EXISTS checkpoints (
    thread_id TEXT NOT NULL,
    checkpoint_ns TEXT NOT NULL DEFAULT '',
    checkpoint_id TEXT NOT NULL,
    parent_checkpoint_id TEXT,
    type TEXT,
    checkpoint BLOB,
    metadata BLOB,
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id)
);
CREATE TABLE IF NOT EXISTS writes (
    thread_id TEXT NOT NULL,
    checkpoint_ns TEXT NOT NULL DEFAULT '',
    checkpoint_id TEXT NOT NULL,
    task_id TEXT NOT NULL,
    idx INTEGER NOT NULL,
    channel TEXT NOT NULL,
    type TEXT,
    value BLOB,
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id, task_id, idx)
);

两个细节值得注意：

  • 没有业务字段：script_id / task_id 从未进入表结构，它们只存在于文件系统路径与 thread_id 的拼装里（详见第四章）。状态数据本身被序列化进 checkpoint / metadata 两个 BLOB 列，这是 LangGraph 让 saver 与业务解耦的设计。

  • 两张表分工：checkpoints 存状态快照（每个 super-step 一条），writes 存待写入通道的中间数据（pending writes，用于崩溃恢复与任务重放）。setup() 里还会顺带执行 PRAGMA journal_mode=WAL——与 PenShot 连接时主动设置的配置互为双保险。

三、排坑现场：从 ainvoke 报错到同步执行

先说一个需要纠正的流行说法：不少介绍会把 PenShot 的检查点描述为"MemorySaver → SqliteSaver → 同步版"的三版本演进。但翻遍 workflow_checkpointer.py，找不到任何版本演进的技术证据——文件头注释写的是"简化版（仅同步）"，代码里保留的是两个并存的模式（内存 / SQLite），而不是递进的三代实现。更接近事实的表述是：这是一套"双模式 + 一次排坑"的最终形态，而演进痕迹只能从配置字段的残留物里推断（见第四章）。

真正值得复盘的技术现场是下面这个：项目一度以异步方式执行工作流，并在 SqliteSaver 上撞出了一个经典错误。

双模式一：MemorySaver，零依赖的验证路径

WorkflowCheckpointer 的第一种模式是 LangGraph 内置的 MemorySaver：所有状态保存在进程内存中。在这个实现里它身兼两职——既可以由 checkpoint_mode='memory' 显式启用，又会在两条降级链里自动接管（SQLite 目录不可写、SQLite 依赖未安装，详见第四章）。

flowchart LR
    subgraph MemoryMode["MemorySaver 模式"]
        Worker[PenShot Worker] --> RAM[进程内存]
        RAM -->|存储| CP1[检查点1]
        RAM -->|存储| CP2[检查点2]
        RAM -->|存储| CP3[检查点3]
        
        Worker -.->|进程重启| X[所有检查点丢失]
    end

这种方式的优点是零配置、零依赖、性能最高，但致命缺陷是进程重启后所有检查点丢失，无法实现真正的断点续传。仅适合本地开发和单元测试场景。

双模式二：SqliteSaver，单文件持久化

第二种模式使用 LangGraph 官方提供的同步版 SQLite 检查点实现，把状态写入每个任务独立的 .db 文件：

flowchart TB
    subgraph SQLiteMode["SqliteSaver 模式"]
        direction TB
        
        Worker[PenShot Worker] --> Conn[SQLite连接<br/>check_same_thread=False]
        Conn --> DB[(task_xxx.db)]
        
        subgraph Storage["表结构（LangGraph 内建）"]
            T1[(checkpoints表<br/>thread_id, checkpoint_ns, checkpoint_id<br/>状态快照与元数据BLOB)]
            T2[(writes表<br/>thread_id, checkpoint_id, task_id<br/>中间数据value BLOB)]
        end
        
        DB --> Storage
    end

每个任务独立的数据库文件实现了任务级数据隔离；连接建立时还会执行 PRAGMA journal_mode=WAL 与 PRAGMA synchronous=NORMAL，用写前日志换取更好的读写并发与吞吐。不过要认清两层边界：其一，SqliteSaver 官方定位是轻量同步场景，不面向多线程扩展；其二，WAL 优化的是单文件内的读写并发，解决不了"检查点能否被读回来"的问题——后者取决于 thread_id 是否稳定（第五章）。

排坑现场：ainvoke 与同步 Saver 的正面冲突

代码里留下了两处"考古证据"：

  • workflow_pipeline.py 的回退执行路径中，一行 # raw_state = await self.workflow.ainvoke( 被注释掉，紧接着是同步的 self.workflow.invoke(...)；

  • workflow_output_fixer.py 中更直白：# 注意：这里需要await workflow.ainvoke 的注释下面，同样换成了 workflow.invoke(...)。

这两处注释说明：项目一度以 ainvoke 异步方式执行工作流，随后撞上了 SqliteSaver 的异步接口缺失，最终整体切回同步执行。用 ainvoke 时 LangGraph 会调用 saver 的 aput / aget_tuple / alist，而同步版 SqliteSaver 对这几个异步方法一律直接抛错，报错原文（摘自 langgraph-checkpoint-sqlite 源码的 _AIO_ERROR_MSG）：

The SqliteSaver does not support async methods. Consider using AsyncSqliteSaver instead.
from langgraph.checkpoint.sqlite.aio import AsyncSqliteSaver
Note: AsyncSqliteSaver requires the aiosqlite package to use.

    direction LR %% 强制主画布从左到右
    subgraph SyncSaver["同步 Saver 问题"]

当时的解决方案有两个方向：把 saver 换成 AsyncSqliteSaver（引入 aiosqlite 依赖，异步链路全改造），或者把工作流切回同步 graph.invoke。PenShot 选择了后者——以稳定性优先、改动面最小，代价是放弃了原生协程调度的并发能力。

为什么选择同步而非异步？

考量因素 同步模式 异步模式
代码复杂度 低 高（需要 aiosqlite）
依赖数量 langgraph-checkpoint-sqlite 另需 aiosqlite
调试难度 简单 复杂（事件循环问题）
并发处理 调用方线程内执行 原生协程调度
适用场景 单机顺序处理 高并发 Web 服务

对于 PenShot 的剧本分镜场景，任务以顺序执行为主，同步模式完全够用，代码也更简洁易维护。这个选择与 SqliteSaver 的官方定位（轻量、同步、小项目）刚好匹配；但代价会在任务量增长时显现——SQLite 的单写者模型、以及下一章将看到的连接与线程配置，都会成为后续优化的发力点。

四、实现剖析：WorkflowCheckpointer 与它的降级链

模式选择：两种模式，与一个"注释里的第三种"

一个必须澄清的点：运行时的存储模式只有两种。CheckpointMode 枚举里只有 MEMORY 和 SQLITE 两个成员，postgres 从未进入实现。但在配置层能看到它的三处"残留物"：

  • ShotConfig.checkpoint_mode 的注释写着 “auto, memory, sqlite, postgres”；

  • ShotConfig.postgres_uri: str = None 字段保留，但全仓库无任何消费方；

  • _determine_mode 的 else 分支注释只有 “auto 或其他”——意味着即便传入 checkpoint_mode='postgres'，也会静默落入 auto 分支、按 SQLite 逻辑处理，而不会报错。

这些残留物暗示：早期规划中可能包含 Postgres 模式（面向分布式部署），后来简化为同步双模式（与文件头"简化版（仅同步）"的注释吻合）。这是"规划未落地"的又一个典型样本：配置字段存在，不代表能力存在。

def _determine_mode(self) -> CheckpointMode:
    mode = getattr(self.config, 'checkpoint_mode', 'auto')
    
    if mode == 'memory':
        return CheckpointMode.MEMORY
    elif mode == 'sqlite':
        return CheckpointMode.SQLITE
    else:  # auto 模式
        try:
            # 检查 SQLite 是否可写
            checkpoint_dir = getattr(self.config, 'checkpoint_dir', 'data/checkpoints')
            os.makedirs(checkpoint_dir, exist_ok=True)
            test_path = os.path.join(checkpoint_dir, '.write_test')
            with open(test_path, 'w') as f:
                f.write('test')
            os.remove(test_path)
            return CheckpointMode.SQLITE
        except Exception:
            warning("SQLite 不可用，降级到内存模式")
            return CheckpointMode.MEMORY

auto 模式的探测方式很"土"但有效：直接在目标目录写一个 .write_test 文件再删掉，用"能不能写"代替"猜环境"。配合模块导入层的 try/except ImportError（langgraph-checkpoint-sqlite 未安装时 SqliteSaver = None），这个类实际上布下了两条降级链：

  1. 导入期降级：依赖缺失 → get_saver() 时打 warning 并回退 MemorySaver；
  2. 运行期降级：目录不可写 → _determine_mode 阶段直接落回 MEMORY。

换句话说，“任何环境下都能把图跑起来"是被优先保证的；被牺牲的是持久性——所有降级路径的共同终点都是"进程重启即丢失”。两处都只打了 warning 级别日志，属于静默降级：流程照常成功，没有人会被叫醒。

任务数据隔离

每个剧本处理任务拥有独立的数据存储路径：

  • 按 script_id 创建子目录

  • 按 task_id 创建独立的数据库文件

  • 支持按剧本维度清理历史检查点

data/checkpoints/
├── script_001/           # 按剧本ID隔离
│   ├── task_001.db       # 按任务ID隔离
│   └── task_002.db
└── script_002/
    └── task_003.db

这种设计确保了多任务并发执行时数据不会相互干扰，同时也便于按剧本维度进行数据管理。有一个容易误解的点值得指出：隔离靠的是文件路径字符串拼装（os.path.join(checkpoint_dir, script_id) 加 f"task_{task_id}.db"），而不是数据库 schema——script_id / task_id 从未写进表字段（见第二章的真实表结构）。

补充说明：之所以用 script_id 与 task_id 双层目录隔离，是因为一个剧本可能对应多个任务（如多版本重跑）。这样既能在"剧本维度"统一清理旧数据，又能在"任务维度"避免同剧本并发任务的检查点互相覆盖。

工厂模式管理实例

通过 CheckpointerFactory 避免重复创建相同任务的检查点实例：

class CheckpointerFactory:
    _instances: Dict[str, WorkflowCheckpointer] = {}
    _lock = threading.RLock()
    
    @classmethod
    def get_or_create(cls, script_id: str, task_id: str, config: ShotConfig):
        key = f"{script_id}_{task_id}"
        with cls._lock:
            if key not in cls._instances:
                cls._instances[key] = WorkflowCheckpointer(script_id, task_id, config)
            return cls._instances[key]

补充说明：工厂模式的引入是为了避免为同一任务重复创建 Sqlite 连接。SqliteSaver 本质上是对一个 sqlite3 连接加锁封装，重复 new 会造成连接泄漏与锁竞争。用 script_id_task_id 作为缓存键，在并发场景下借助 threading.RLock 保证线程安全。

但这里有一处需要注意的接线缺口：工厂提供了 close_all() / get_stats()，WorkflowCheckpointer 也提供了 close()，但全仓库找不到它们的调用方——_instances 缓存里的实例在整个进程生命周期内不会被主动释放。配合下一小节将看到的 close() 的 async 细节，资源回收链实际上只画了一半。

旧检查点自动清理：实现了，但没有接线

cleanup_old_checkpoints(keep_count=10) 是类里最"重"的一个方法，真实逻辑分四步：glob 出同剧本目录下所有 task_*.db → 按修改时间降序 → 保留前 keep_count 个 → 逐个 os.remove（跳过当前实例正在使用的 db_path，删除失败仅 warning）。

需要澄清原描述的几处偏差：

  • 没有"检测文件是否被占用"：代码只判断"是不是当前实例自己的 db_path"，不检测其他进程是否正在写入该文件；

  • 没有异步清理：方法是同步的，删除是串行 os.remove；

  • 最关键的是：它从未被调用。全仓库没有 cleanup_old_checkpoints 的调用方，ShotConfig.max_checkpoints_per_script（默认 10）也从未被读取——保留策略的旋钮和清理的执行器都在，但中间那根线没接。

真实后果是：同一 script_id 下的 .db 文件只增不减，长跑场景下磁盘占用会随任务次数线性增长（配置里预留的 checkpoint_max_connections、checkpoint_idle_timeout 同样无消费方——六个检查点配置字段里，真正被读取的只有 checkpoint_mode 和 checkpoint_dir 两个）。

资源释放的两个坑：async close 与逃逸的 close_all

翻看类的收尾部分，有两处与资源释放相关的细节值得记录。先看 close() 与上下文管理器的矛盾组合：

async def close(self):
    """关闭检查点，释放资源"""
    if self._conn:
        try:
            self._conn.close()
        except Exception:
            pass
        self._conn = None
    self._saver = None

def __exit__(self, exc_type, exc_val, exc_tb):
    """上下文管理器出口"""
    self.close()   # 这里没有 await

  • 坑一：close() 是 async def，而类又同时提供了同步的 with 支持。__exit__ 里直接调用 self.close() 只会创建一个协程对象，连接不会被真正关闭，日志里还会留下 coroutine 'close' was never awaited 的 RuntimeWarning。同步模式的场景下，最自然的两种释放形式（with 退出、直接调用）都拿不到预期的资源释放行为；

  • 坑二：CheckpointerFactory.close_all() 没有任何调用方，配合工厂的全局缓存 _instances，单个进程中累积的 saver 与 SQLite 连接会一直存活到进程退出。

这两处都属于"不影响功能、但影响长跑稳定性"的问题：在短生命周期的测试里几乎无感，在长期运行的服务进程里则会转化为文件句柄与内存的缓慢滞留。

五、集成考证：真实调用链与从未生效的 thread_id

基础配置

ShotConfig 中与检查点相关的字段共六个（以下为源码实际定义）：

class ShotConfig():
    checkpoint_mode: str = "auto"   # 检查点模式: auto, memory, sqlite, postgres
    checkpoint_dir: str = settings.get_data_paths().get('data_checkpoint')
    postgres_uri: str = None    # PostgreSQL URI
    max_checkpoints_per_script: int = 10    # 每脚本最多保存的检查点数量
    checkpoint_max_connections: int = 5     # 检查点最大连接数
    checkpoint_idle_timeout: int = 600      # 检查点空闲超时时间（秒）

checkpoint_dir 的默认值并非硬编码字符串，而是从项目的 settings.get_data_paths() 读取（配置模型侧的默认值为 data/checkpoints）。另需如实说明：除 checkpoint_mode 与 checkpoint_dir 外，其余四个字段（含 postgres_uri）在源码中没有任何读取方，属于预留字段——它们描述的是理想中的能力（保留份数、连接池、空闲回收、Postgres 支持），而不是当前实际具备的行为。

真实调用链：三处接线，与一个断点

PenShot 在 MultiAgentPipeline 中的真实接线路径如下（摘自源码，而非示例）：

# workflow_pipeline.py —— 初始化时创建管理器
self.checkpointer = create_checkpointer(self.script_id, self.task_id, config)

# workflow_pipeline.py —— 构建图时把 saver 交给 LangGraph
saver = self.checkpointer.get_saver()
compiled_graph = orchestrator.graph.compile(checkpointer=saver)

# workflow_output_fixer.py —— 执行时传入 thread_id 配置
final_state = workflow.invoke(
    initial_state,
    config={"configurable": {"thread_id": f"process_{id(initial_state)}"}}
)

前两处接线都正确：管理器接入管道、saver 接入编译。问题出在第三处：thread_id 不是 WorkflowCheckpointer.get_config() 返回的 f"{script_id}_{task_id}"，而是 f"process_{id(initial_state)}"——id() 是 CPython 对象的内存地址标识，同一个任务每次运行都会得到全新的值。

这意味着两件事同时发生：

  1. get_config() / get_thread_id() 这两个专门为"稳定标识"准备的方法，全仓库没有任何调用方；

  2. 每次执行都等于向 SQLite 写入一条全新 thread 的时间线——上一轮运行存的检查点永远不可能被下一轮命中。

缺口的影响：检查点"只写不读"

结合第二章的机制原理，这个缺口的后果可以做一次完整推演：

环节 设计意图 当前实现
写入 每个 super-step 落盘状态快照 真实执行（saver 已接入编译）
标识 同一任务固定 thread_id，可跨进程命中 每次运行随机新 ID（对象内存地址）
读取 复用 thread_id 查询历史、恢复执行 无任何读取入口（无 get_state 调用）
清理 定期删除旧检查点 cleanup_old_checkpoints 无调用方
释放 任务结束关闭连接 close() / close_all() 无调用方，且 close() 自身有 async 陷阱

也就是说：当前检查点是一本只进不出的账。它写入的数据是真实、完整、可回溯的（开发者可以手动打开 .db 文件复盘状态），但"断点续传"这条产品级能力并没有被接通——它在版本演进路线图里归属于 v1.5"分布式调度"阶段的规划项。所以现状可以准确概括为：状态每次都在落盘，任务失败后依然从头再跑。根因就藏在这一处 thread_id 的生成方式里。

六、效果与收益：写入侧的确定性，续传侧的空缺

对"效果"部分做一次口径校准：凡依赖"从检查点恢复"的收益，在当前实现下都还不能兑现；能确认的收益，都在"写入侧"。

已真实获得（写入侧）：

  • 过程态可回溯：每个 super-step 的状态快照都会完整落盘，.db 文件自带一条完整时间线。出现异常片段时，可以离线打开数据库逐条复盘哪些阶段已经完成——这是当前确定的调试价值；

  • 故障不丢现场：在没有持久化检查点的场景里，任务失败意味着现场随进程一起消失；现在即使服务崩溃，SQLite 里的历史记录依然可用于事后分析（尽管不能自动续跑）。

设计目标中、但当前尚未兑现（续传侧）：

  • 断点续传 / 任务恢复：受第五章考证的 thread_id 缺口影响，任务失败后依然从头执行，这部分收益目前为零；

  • 避免重复 LLM 调用：同上——没有恢复入口，就没有"跳过已稳定阶段"的能力；

  • 任务迁移：属于分布式方案的规划能力，当前单机 SQLite 未涉及。

需要坦诚说明的是：检查点机制当前没有公开的性能基准。"恢复能节省多少时间/成本"取决于剧本规模、LLM 调用分布与故障点位置，在没有可复现基准的情况下，任何具体数字都不应被当作结论——本文也据此不提供估算值。

七、故障实战：五个运行期场景与恢复路径

以下场景均能在当前源码中找到确切依据，按"发生什么→为什么→系统如何处理→如何恢复"四段式整理。

故障一：服务重启后，检查点"全丢"

发生什么：重启服务后，部署目录下的 data_checkpoint/ 里没有任何新写入，甚至目录本身都没被创建。

为什么：两条降级链之一被触发——①运行环境未安装 langgraph-checkpoint-sqlite（导入期降级）；②部署目录只读或权限不足（运行期降级）。两者都会静默切换到 MemorySaver：工作流照常成功，但状态只活在本进程内存里。

系统如何处理：静默降级——不中断、不重试、不告警，只留下一条 warning 级日志。

如何恢复与避免：

  • 排查顺序：先查启动日志中有无"langgraph-checkpoint-sqlite 未安装"或"SQLite 不可用，降级到内存模式"两条 warning；

  • 部署检查清单里加入"data_checkpoint 目录存在且可写"，并把这两条 warning 接入告警；

  • 需要强持久化保证的场景，把 checkpoint_mode 显式设为 sqlite——显式模式下目录不可写会在初始化 os.makedirs 时直接报错（更吵，但更早暴露）。

故障二：任务失败重跑，"恢复"从未发生

发生什么：长剧本任务在质量审查阶段崩溃，重启任务后从头重新调用 LLM——所有已落盘的检查点数据视而不见。

为什么：第五章考证的 thread_id 缺口——主执行路径使用 f"process_{id(initial_state)}"（对象内存地址），每轮运行都是新时间线，历史检查点永不可命中。

系统如何处理：无感知——旧检查点继续留库，新时间线照写一份。

如何恢复：

  • 第一步修复只需要一行：把执行路径的 config 换成 self.checkpointer.get_config()（返回稳定的 {script_id}_{task_id}）；

  • 真正的续跑还需要补恢复入口：LangGraph 支持以 None 为输入、复用同一 thread_id 从最近检查点继续执行——这是 v1.5 的完整工作量，修标识只是第一步；

  • 验证方法：打开任意任务 .db 执行 SELECT thread_id, COUNT(*) FROM checkpoints GROUP BY thread_id;——若同一任务下 thread_id 种类随运行次数增长，即证明本故障存在。

故障三：磁盘只增不减

发生什么：定时任务连续运行一周后，data_checkpoint/ 目录占用从几 MB 涨到数百 MB 甚至 GB 级。

为什么：两个因素叠加——①cleanup_old_checkpoints 没有任何调用方；②thread_id 漂移让同一个 .db 只增不减（每次运行写入新时间线，而写入本身是每个 super-step 一条记录）。

系统如何处理：无任何自动清理。

如何恢复：

  • 短期：手动调用 cleanup_old_checkpoints(keep_count=N)，或在运维层按目录维度归档/清理旧 task_*.db；

  • 中期：把清理接入任务收尾流程（finally 块或定时任务），并让 max_checkpoints_per_script 配置真正生效；

  • 注意：当前实现只跳过"当前实例自己的 db_path"，不检测其他进程是否正在写入——多进程部署下直接调用可能误删活跃文件，建议先确认无并发任务再执行清理。

故障四：切回异步后，检查点写入集体报错

发生什么：团队把执行链路改回 ainvoke（期待更好的并发），运行后每个任务都在 saver 处抛出 NotImplementedError: The SqliteSaver does not support async methods...。

为什么：同步版 SqliteSaver 的 aput / aget_tuple / alist 三个异步方法一律直接报错（第三章的排坑现场就是这个问题的第一次发生）。

系统如何处理：异常向上抛出——图执行失败，任务显式报错（这个故障反而属于"吵得早"的类型）。

如何恢复：安装 aiosqlite 并切换为 AsyncSqliteSaver（from langgraph.checkpoint.sqlite.aio import AsyncSqliteSaver），连接生命周期用 async with 管理。不要尝试"异步工作流 + 同步 Saver"的混搭，这是本故障的唯一正确姿势。

故障五：日志反复出现 coroutine was never awaited

发生什么：任务收尾阶段日志出现 RuntimeWarning: coroutine 'WorkflowCheckpointer.close' was never awaited，SQLite 文件句柄缓慢累积。

为什么：close() 是 async def，但 __exit__ 按同步方式调用它（第四章"资源释放的两个坑"）——协程对象被创建后直接丢弃，连接从未真正关闭。

系统如何处理：静默——除了 RuntimeWarning，没有任何报错；功能不受影响，但资源持续滞留。

如何恢复：

  • 方向一：把 close() 改成同步方法——它内部只是 conn.close() 加置空，本就不需要 async；

  • 方向二：保留异步签名，但补齐调用链（await checkpointer.close()），并在服务关闭钩子里调用 CheckpointerFactory.close_all()；

  • 验证：修复后确认日志中 RuntimeWarning 消失，进程正常退出后 .db 文件不再被句柄占用（如 lsof / 资源监视器确认）。

五个故障的共性

除故障四外，其余四个的共同特征是：系统都不会大声报错。降级是静默的、缺口是静默的、资源滞留也是静默的——它们全部属于"看起来一切正常、但能力没生效"的类别。对这类问题的防御，不能靠盯盘，而应把"接了什么线、验证过哪条路径"写进发布检查清单。

八、最佳实践总结

基于全文考证，工作流检查点落地的关键经验可以收敛为七条：

  • 开发测试用 MemorySaver，单机部署用 SqliteSaver：这是项目当前双模式的定位；注意 SqliteSaver 的官方级别是"轻量同步"，不要按高并发数据库去期待它；

  • thread_id 必须稳定且可复现：用 {script_id}_{task_id} 这类业务标识，绝不要用对象内存地址或随机数——否则检查点只写不读（本文最重要的教训）；

  • saver 接入编译、config 接入执行：compile(checkpointer=saver) 与 invoke(..., config=...) 缺一不可；

  • 验证写入真的发生：部署后打开 .db 执行 SELECT COUNT(*) FROM checkpoints;——比相信日志更可靠；

  • 清理与释放都要显式接线：保留策略、连接关闭、工厂清理不会自己生效（见第四章的两个资源坑）；

  • 异步链路用异步 Saver：ainvoke 必须搭配 AsyncSqliteSaver（另装 aiosqlite）；同步链路用 invoke + SqliteSaver，不要混搭；

  • 降级必须可见：auto 模式的两条降级链只打 warning，生产环境务必接入监控，否则"持久化"会静默退化为"内存态"。

九、扩展方向与最小修复路径

如果要把当前实现推进到"真正的断点续传"，最小修复路径大致是三步：

  1. 修 thread_id：执行路径改用 checkpointer.get_config()（一行改动），让同一任务的检查点跨运行可命中；

  2. 补恢复入口：任务启动时复用同一 thread_id、以 None 为输入续跑，把"从头跑"改成"从断点续跑"；

  3. 接清理与释放：把 cleanup_old_checkpoints 接入任务收尾，把 close_all 接入服务关闭钩子（顺手修掉 close() 的 async 问题）。

在此之上，更远的方向是：分布式部署时切换 AsyncSqliteSaver（异步链路），或引入 Postgres / Redis 存储（对应 postgres_uri 这个预留字段的初衷）；同步探索检查点压缩与增量落盘，控制单文件体积的增长速度。这些都属于 v1.5"分布式调度 / 断点续传"阶段的工作量。
