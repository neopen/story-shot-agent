PenShot 源码级测评：分镜 Agent 的架构成色、工程短板与演进路线

项目：PenShot / Story Shot Agent
仓库：neopen/story-shot-agent
版本参考：0.3.x（pyproject.toml 当前为 0.3.8）
许可证：MIT
定位：剧本分镜智能体 / AI Story Intelligence / 视频生成中间层
测评类型：架构、工程、Agent、RAG/Memory、API、生态、安全与商业化综合评估
测评方法：本文结论基于对公开源码（src/、tests/、examples/）、pyproject.toml、docker-compose.yml 与 Dockerfile 的逐项核验；评分为工程维度评估，不构成统一硬件与数据集下的实测 Benchmark。

1. 评测结论

PenShot 是一个面向剧本、小说到 AI 视频分镜与视频提示词生成的 Agent 项目。

它并不是一个简单的 Prompt Generator，而是试图建立一套从：

文本理解 → 剧情拆解 → 分镜生成 → 视频切分 → Prompt 转换 → 质量审核 → 连贯性检查 → 记忆检索 → 人工干预 → API/Agent 输出

的完整智能工作流。

从架构方向来看，项目选择 LangChain + LangGraph + RAG + 多级 Memory + Chroma + MCP（内置支持）与 A2A（示例级集成） + FastAPI 的组合，已经具备比较完整的 Agent Engineering 雏形。

综合代码结构、技术选型、产品定位和扩展能力：

综合评分：8.5 / 10（分维度评分与依据见第 29 章；评分基于源码结构与工程方案评估，非统一硬件与数据集下的实测 Benchmark）

如果目标是做一个开源的 AI 分镜 Agent，它已经具有较强的工程完整度；如果目标进一步升级为生产级 AI 视频制作平台，当前最需要补齐的是自动化评测、可观测性、安全、多租户、成本控制，以及更加结构化的 Story State / Story Graph——具体不足清单与建议见第 24 章与第 28 章。

2. 项目定位

2.1 解决的问题

传统文本到视频流程通常需要人工完成：

  1. 阅读剧本

  2. 理解人物关系

  3. 拆分剧情

  4. 设计镜头

  5. 确定景别和机位

  6. 描述人物动作

  7. 描述环境

  8. 设计镜头运动

  9. 生成视频 Prompt

  10. 检查人物和场景连续性

  11. 交给视频模型生成

PenShot 的核心目标，就是将上述过程 Agent 化。

可以抽象为：

剧本 / 小说
    ↓
文本解析
    ↓
剧情结构理解
    ↓
分镜生成
    ↓
镜头拆分
    ↓
Prompt 转换
    ↓
质量审核
    ↓
连续性检查
    ↓
记忆 / RAG
    ↓
人工干预（可选）
    ↓
结构化结果
    ↓
Sora / Runway / Veo / Pika 等视频模型

这意味着 PenShot 的价值并不局限于"生成一句 Prompt"，而在于：

把复杂的视频前期制作流程封装成可编排、可检查、可扩展的 AI 工作流。

3. 核心能力分析

3.1 Script → Storyboard

这是项目最核心的能力。

输入可以是：

  • 剧本

  • 小说

  • 故事梗概

  • 长文本

  • 分章节内容

输出进一步拆解为：

  • 场景

  • 镜头

  • 人物

  • 动作

  • 环境

  • 镜头语言

  • 视频 Prompt

这一层决定了项目的实际产品价值。

评价

9.0 / 10

优点：

  • 从文本直接进入结构化分镜

  • 适合 AI 视频生成场景

  • Agent 工作流比单次 LLM 调用更适合长文本

  • 可以通过后续节点进行质量控制

不足：

  • 目前仍然高度依赖 LLM 推理质量

  • 缺少公开、标准化 Benchmark

  • 缺少统一的 Story State 数据模型作为全局事实源

4. Agent 架构分析

4.1 LangGraph 是正确选择

项目采用 LangGraph 构建核心 Workflow，这是整个项目比较重要的技术决策。

典型工作流可以抽象为：

                ┌──────────────┐
                │ Script Parser│
                └──────┬───────┘
                       ↓
                ┌──────────────┐
                │ Storyboard   │
                │ Generator    │
                └──────┬───────┘
                       ↓
                ┌──────────────┐
                │ Video Split  │
                └──────┬───────┘
                       ↓
                ┌──────────────┐
                │ Prompt       │
                │ Conversion   │
                └──────┬───────┘
                       ↓
                ┌──────────────┐
                │ Quality      │
                │ Audit        │
                └──────┬───────┘
                       ↓
                ┌──────────────┐
                │ Continuity   │
                │ Guard        │
                └──────┬───────┘
                       ↓
                 Result / Human

同时包含：

  • Loop Check

  • Error Handling

  • Human Intervention

  • Result Generation

这种结构明显优于：

result = llm.invoke(prompt)

式的单 Agent 架构。

评分

9.0 / 10

优点

  • 工作流显式化

  • 节点职责明确

  • 支持条件分支

  • 支持循环

  • 支持状态管理

  • 更适合长任务

  • 更容易加入人工审核

风险

随着节点数量增加，Graph 很容易演变为：

“复杂但难以理解的 Agent Workflow”

因此后续需要进一步加强：

  • State Schema

  • Node Contract

  • Error Contract

  • Retry Policy

  • Timeout

  • Budget Control

  • Workflow Versioning

5. RAG 与 Memory

项目在记忆体系方面是比较值得关注的一部分。

整体设计包含三层记忆，由 src/penshot/neopen/knowledge/memory/ 下的 MemoryManager 统一调度：

Short-Term Memory（滑动窗口缓冲，Redis 会话历史）
        ↓
Medium-Term Memory（LLM 摘要压缩，文件持久化）
        ↓
Long-Term Memory（Chroma 向量检索，按剧本隔离 collection）
        ↓
Vector Retrieval
        ↓
Chroma

源码对应关系：short_term_memory.py 基于 LangChain 缓冲记忆与 deque(maxlen=...) 滑动窗口，Redis key 按 penshot:memory:{script_id} 隔离，且带 Redis 可用性探测与降级；medium_term_memory.py 用 LLM 逐步融合摘要并落盘；long_term_memory.py 以 langchain_chroma.Chroma 建立 script_{id}_memory collection，检索器带 k 与 score_threshold 参数。

并结合：

  • Embedding

  • Vector Retrieval

  • Reranking

  • Snapshot

  • 多维度检索

来解决长剧本场景中的上下文问题。

5.1 为什么需要 Memory？

例如：

第 1 章：

张三穿着黑色风衣。

第 35 章：

张三进入咖啡馆。

第 80 章：

张三站在雨夜街头。

如果每次生成镜头都只读取当前上下文：

当前章节 → LLM

很容易出现：

黑色风衣
↓
突然变成白色西装

Memory 的价值就是让 Agent 能够获得：

人物历史
场景历史
物品历史
剧情历史
镜头历史

Story

 │    ├── Personality
 │    ├── Costume
 │    └── Relationship
 │
 ├── Scene
 │    ├── Location
 │    ├── Time
 │    ├── Weather

 ├── Object
 │    ├── Weapon

 │    └── Important Item

这样可以把：

LLM Memory

进一步升级为：

Structured Story Knowledge
+

这会明显提升长剧本一致性。

7. RAG 架构建议

当前 Vector RAG 是合理的，但对于故事类任务，仅使用向量检索并不理想。

推荐升级成：

                    Story Knowledge
                          │
              ┌───────────┴───────────┐
              ↓                       ↓
         Vector RAG               Graph RAG
              │                       │
              ↓                       ↓
       Semantic Search        Relationship Search
              │                       │
              └───────────┬───────────┘
                          ↓
                       Rerank
                          ↓
                     LLM Context

Vector RAG

适合：

  • 相似剧情

  • 相似描述

  • 历史 Prompt

  • 场景语义搜索

Graph RAG

适合：

  • 谁和谁是什么关系

  • 谁在哪个场景

  • 某个物品属于谁

  • 某角色经历过什么事件

  • 某事件发生之后发生了什么

这两者结合后，更适合 Story Intelligence。

13. Docker 部署

项目提供 Docker Compose：

PenShot
   │
   ├── Application
   │
   └── Redis

并配置：

  • Health Check：应用每 30s 探测 /health，Redis 每 10s 执行 redis-cli ping，应用通过 condition: service_healthy 等待 Redis 就绪

  • CPU Limit：cpus: '2.0'

  • Memory Limit：memory: 2G（另设 512M 预留）

  • Redis AOF：--appendonly yes + redis_data 数据卷持久化

  • 日志轮转：json-file 驱动，单文件 10m、保留 3 份

对于开源项目而言，这已经比较实用。

13.1 安全问题

当前 Compose 配置中可以看到固定的 Redis 密码配置，例如：

123456

这在本地开发环境可以接受，但：

绝对不建议直接用于生产环境。

生产环境应该使用：

REDIS_PASSWORD=${REDIS_PASSWORD}

并通过：

  • Secret

  • Environment Variable

  • Docker Secret

  • Kubernetes Secret

管理。

14. 测试体系

项目已经具备比较完整的测试目录：tests/ 下共有 38 个测试文件，覆盖六个领域——api/（function_calls、MCP）、knowledge/（索引重建、向量查询、rerank 质量、知识库诊断等 9 个）、planner/（时长估算、规则/混合估计器、镜头生成共 10 个）、task/（记忆、任务工厂、生命周期、工作流注册）、unit/（客户端、工具与解析函数）与 workflow/（orchestrator），根目录另有 6 个针对配置、解析器、分段器与连续性守护的用例；pyproject.toml 中启用了 pytest-asyncio 的 auto 模式与 strict 标记。

但从项目定位来看，传统 Unit Test 并不足够。

AI Agent 项目更需要：

Unit Test
+
Integration Test
+
Workflow Test
+
LLM Evaluation
+
Regression Test
+
Benchmark

尤其是：

LLM 输出正确 ≠ HTTP 返回 200

真正需要测试的是：

剧本
 ↓
Storyboard
 ↓
Prompt

是否正确。

然后定义指标。

Story Fidelity

剧情还原度。

人物一致性。

场景一致性。

时间线一致性。

Prompt Quality

Prompt 质量。

JSON Validity

 ├── Retry Budget
 ├── Time Budget
 └── Video Generation Budget

19. 安全评估

AI Agent 项目需要重点考虑 Prompt Injection。

例如剧本内容中可能出现：

Ignore previous instructions.

如果直接交给 Agent，可能影响系统 Prompt。

建议将：

System Instruction
+
User Story
+
Retrieved Memory
+
Tool Output

严格分层。

推荐：

Trusted Context
      │
      ├── System
      └── Policy

Untrusted Context
      │
      ├── Story
      ├── Retrieved Text
      └── External Data

不要让外部文本直接拥有工具调用权限。

30. 最终结论

PenShot 是一个方向正确、架构完整、Agent 化程度较高的开源项目。

它最值得肯定的地方不是"能够生成分镜"，而是尝试解决：

复杂故事内容如何被 AI 长期理解、拆解、记忆、检查并最终转换成可执行的视频生产任务。

其技术路线：

LangGraph
+
RAG
+
Memory
+
MCP
+
A2A
+
FastAPI
+
Multi-Model

已经构成了一套比较完整的 Agent 基础设施。

但是，如果希望进一步从：

开源 AI 分镜工具

升级为：

生产级 AI Story Intelligence Platform

那么下一阶段不应该继续单纯堆叠 Agent。

真正值得投入的方向应该是：

                    Story Intelligence
                           │
             ┌─────────────┼─────────────┐
             ↓             ↓             ↓
        Story State     Story Graph    Evaluation
             │             │             │
             └─────────────┼─────────────┘
                           ↓
                        Memory
                           ↓
                       LangGraph
                           ↓
                     Agent Workflow
                           ↓
                    Video Generation

换句话说：

下一阶段的核心不是"让 Agent 更聪明"，而是让 Agent 拥有一套可靠、可验证、可追踪的 Story World Model。

如果这一层能够建立起来，PenShot 的定位将从：

Storyboard Generator

进一步升级为：

AI Story Intelligence Engine

并最终具备成为：

AI Film Production Agent Platform
